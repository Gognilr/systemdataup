01
阻断级缺陷
3 项 · 上线前必须修
这三项的共同点是：它们让某个安全或数据防线看起来存在，实际不存在。文档、注释、迁移脚本都写了，唯独执行路径上没有。

P0-1
强制改密只在浏览器里生效，服务端零校验
安全
位置
AuthService.cs:131 · app.js:462 · views/auth.js:25
现象
登录成功后服务端把 mustChangePassword 放进响应体，前端将其存入 localStorage 并在路由里拦截。但 MustChangePassword 没有写进 JWT，也没有任何中间件、过滤器或权限策略读取它——我全仓搜索该字段，只有实体、迁移、赋值三处，没有一处校验。
影响
拿着 V005 注入的初始口令登录，那一次登录返回的就已经是全权限访问令牌。用 curl 直接打任意管理接口，或者在浏览器控制台执行 localStorage.removeItem('bm_mustChange') 刷新，就能一直用初始口令操作整个系统。BATCH2 报告里"注入式管理员口令与强制改密"这条验收，实际只完成了前半句。
建议
在 CreateAccessToken 里加 must_change_password claim，并加一个 IAuthorizationFilter：该 claim 为 true 时，除 /auth/change-password、/auth/me、/auth/logout 外一律 403。这是本报告里投入产出比最高的一处修改。
P0-2
LAN Turnkey 直连 mTLS 大概率握手失败
可用性
位置
Program.cs:109 · CertificateAuthority.cs
现象
Kestrel 只设了 ClientCertificateMode.AllowCertificate，没有设置 ClientCertificateValidation 回调。该回调为 null 时，Kestrel 的默认行为是：只要 SslPolicyErrors != None 就拒绝。而 Agent 持有的是本系统自签 CA 签发的叶子证书，这张 CA 全仓找不到任何安装进 Windows 信任存储的代码（我搜索了 X509Store、StoreName.Root，零命中）。链验证必然报 RemoteCertificateChainErrors。
影响
Turnkey 形态下 Agent 一旦带上客户端证书，TLS 握手直接失败，连接被重置——不是 401，是根本连不上。整个"局域网一键交付"的主链路断在这里。之所以至今没被发现，是因为验收文档记录的测试只有"无客户端证书时返回 401"这个反向用例，而 AllowCertificate 模式下无证书本来就能握手成功，所以那个用例恒过。正向用例从未跑过。
验证
启动 Turnkey 服务端，用一张已签发的 Agent 证书发一次请求即可确认。若如判断，一行修复：https.ClientCertificateValidation = (cert, chain, errors) => true;——本设计的真正信任源是数据库指纹查表（AuthenticateByThumbprintAsync），把链验证交还给它是符合架构意图的。
P0-3
保留策略物理删除没有仓库根目录围栏
数据安全
位置
RetentionCleanupWorker.cs:436
现象
DeleteRepositoryDirectory 在执行 Directory.Delete(full, recursive: true) 前只有两道守卫：必须是绝对路径、盘符下至少两级目录。它从不校验这个路径是否位于当前配置的仓库根目录之内。路径值直接取自数据库列 backup_sets.repository_path。
影响
任何让该列出现错误值的途径——迁移出错、手工改库、仓库路径重配、上游拼接 bug——都会让后台工作器递归删除一个任意目录。C:\Program Files\PostgreSQL 有两级，E:\Windows\System32 有两级，全部通过守卫。
值得注意的对照
同一个代码库的写入路径（UploadCommitWorker）老老实实用了 PathSafety.ResolveUnderBase 做基目录约束，唯独销毁路径没有。这个不对称本身就说明是遗漏而非取舍。
建议
删除前取当前 repository_path，用 ResolveUnderBase 校验；不在根目录内则拒绝删除并升级为严重告警——绝不静默跳过。
02
高危缺陷
8 项 · 影响核心价值
备份系统的全部价值是"恢复出来的数据等于备份进去的数据"。这一节的前两项直接动摇这个前提，其余是功能承诺与实现之间的断裂。

P1-1
上传完整性校验可被客户端单方面跳过
数据完整性
位置
UploadSessionService.cs:305
现象
两个问题叠加。其一，整文件哈希比对写成 if (!string.IsNullOrWhiteSpace(request.Sha256) && ...)——客户端不传 sha256，这个校验就整段跳过，文件直接置为 Verified。其二，来自预检清单的权威期望值 UploadFileEntity.ExpectedSha256 在全仓从未被用于任何比对（我搜了全部 5 个引用点，只有写入和回填，没有比较）。
影响
服务端唯一的完整性依据，是上传方自己在最后一步声明的哈希，而且这个声明可选。分块层面同样宽松：非末块不校验长度，客户端可以造出带空洞的稀疏文件而不被发现。一个有 bug 的 Agent 完全可以持续上传残缺数据，系统全程标记为"可用"。
建议
把 ExpectedSha256 作为强制比对基准，客户端声明值仅作为附加交叉验证；ExpectedSha256 为空时应拒绝建会话而不是放行。
P1-2
一个通过校验的保留策略即可删光某任务全部备份
数据安全
位置
RetentionDtos.cs:45-61 · RetentionCleanupWorker.cs:381
现象
四个 Keep*Count 全部可空且无"至少填一项"的跨字段校验，MinimumRetentionDays 允许 0，RecycleBinDays 允许 0。四项留空 + 两个 0 是一份完全合法、能通过全部 [Range] 校验的策略。
影响
MarkGfsRetained 返回空集合 → 该任务全部备份集在下一轮进入回收站 → RetentionUntil = now + 0 天 → 再下一轮全部物理删除。管理员在界面上填一份看似"先不设保留规则"的策略，两个清理周期后备份全没了。
建议
加跨字段校验：至少一项 Keep*Count > 0；MinimumRetentionDays 与 RecycleBinDays 下限提到 1。另外建议给清理器加一个"单轮回收比例超过阈值就暂停并告警"的熔断。

03
中低缺陷
13 项
这些不会造成数据损失，但会造成误判、体验断裂或后续排障困难。按类型归并列出。

安全与认证
P2-1
账号停用状态在验密前泄露。AuthService.cs:78 处 Disabled 检查排在密码校验之前，且返回专有 403 文案"账号已停用"。上一行的注释刚写完"统一错误信息，不暴露用户是否存在"，实现却与之矛盾——未认证攻击者可据此枚举有效用户名。把该检查移到密码校验之后即可。
P2-2
登录只有按账号锁定，没有 IP 级限速。没有接入 RateLimiter。这既让分布式撞库（每账号 5 次以内横扫）不受限，也让攻击者可以故意锁死任意管理员账号造成拒绝服务。建议加 IP 维度限流。
P2-3
恢复下载令牌出现在 URL 路径中。/api/v1/downloads/{token} 会被 nginx access_log 和 Serilog 请求日志原文记录。有日志读取权限的人可在 TTL 内重放，直接取走整个备份集。建议改为请求头或 POST 换取一次性短时会话。
P2-4
刷新令牌 Cookie 有效期与令牌真实 TTL 可能不一致。Cookie 的 MaxAge 取自配置 AuthController.cs:106，令牌 TTL 取自数据库设置 AuthService.cs:318。两者不一致时，用户要么提前掉线，要么持有一张早已失效的 Cookie。应统一取同一来源。
P2-5
弱口令表是象征性的。CommonWeakPasswords 硬编码了 11 条。真实弱口令字典是百万量级，11 条提供的防护约等于零，却会让人误以为已有弱口令防线。要么接真实字典，要么删掉它、只保留长度与用户名校验并在文档里说清。
P2-6
PathSafety 未拦截 Windows 保留设备名。PathSafety.cs:38 检查了 ..、尾随空格与点、非法字符，但 CON / NUL / COM1–COM9 / LPT1–LPT9 全部放行。恶意或异常的 Agent 送来名为 NUL 的条目，写入会静默成功且内容丢失。
数据与一致性
P2-7
备份集编码会在删除后被复用。UploadCommitWorker.cs:491 用 COUNT(*) + 1 生成 BS-yyyy-NNNN。保留策略删掉 BS-2026-0005 后，计数回落，下一个新备份集会重新拿到这个编码。编码出现在清单、审计和告警里，复用会直接破坏可追溯性。改用数据库序列。
P2-8
清单与数据库记录的哈希来源不同。manifest.json 写的是 ExpectedSha256（客户端声明值），BackupFile.Sha256 写的是 ServerSha256 ?? ExpectedSha256（服务端实测值优先）。两者可能不一致，而恢复前校验用的是后者。应统一为服务端实测值。
P2-9
原始文件修改时间在入库时被丢弃。BackupFile.LastModifiedAt 硬写 DateTime.UtcNow，而同一段代码生成 manifest 时用的是真实的 CandidateFile.LastModifiedAt。数据库里因此没有源文件时间戳——对备份系统而言这是实质性的元数据丢失。
P2-10
同一文件的分块无法并发上传。WriteChunkAsync 以 FileShare.Read 打开暂存文件，第二个并发写入会直接抛 IOException。同时 useAsync: false 配合 WriteAsync 会阻塞线程池线程。断点续传协议设计支持并行，实现不支持。
界面与交互
P2-11
confirmModal 被 Esc 关闭时 Promise 永不 resolve。ui.js:122 只在点击遮罩或关闭按钮时 resolve(false)，但全局 Esc 处理器走的是 closeModal()。所有 if (!await confirmModal(...)) return; 的调用方会静默永久挂起——用户按了 Esc，之后那个操作再也不会响应，也没有任何提示。
P2-12
待办页计数不含自动登记条目。views/todo.js:41 的 count 漏掉了 recentAutoEnrollments，但这些条目会被渲染进列表。结果是顶部横幅显示"✓ 没有待处理事项"，下方却列着若干条待办。
P2-13
零散一致性问题。部署状态卡直接输出未格式化的 ISO UTC 字符串（views/clients.js:73，全站其他地方都走 fmtDT）；客户端与备份集空态标题对 esc() 双重转义；筛选 chip 在客户端页用 <strong>、告警页用 <b>，导致后者丢失等宽数字；.todo-item:nth-child(-n+1) 只给第一条图标上色，明显是遗留写法；.onboarding-steps li::before 用 font-weight:700，违反自身令牌里"只用 400/500/600"的约定。
04
界面评估
实机渲染核实
先说结论：这个界面不土，也基本没有 AI 味，在我审查过的自研运维控制台里属于中上水平。但它的完成度停在"设计做完了、交付没做完"。

做得对的地方
信息架构是按运维工作分的，不是按 REST 端点排的。侧栏分"值守 / 机群 / 数据 / 管理"，概览页是"状态条 + 待办队列 + 容量 + 任务×日期矩阵"。这是真实备份产品的形态，不是把接口列表翻译成菜单。
状态用形状 + 文字 + 颜色三重编码。● 在线、▲ 异常、○ 等待、⊘ 停用，且带背景的胶囊只留给真正的异常状态。色盲可用，且异常在满屏绿色里能一眼跳出来。
设计令牌体系自洽。颜色、字号、间距、圆角、动效全部走 CSS 变量，组件层不写字面值；暗色是手动优先 + 跟随系统 + 持久化三态；prefers-reduced-motion 有处理；正文 13px + 等宽数字 + 4px 间距栅格，密度合适。
刻意避开了 AI 默认审美。登录页没有装饰渐变，主色选在语义色相之外的靛紫，没有 emoji 图标、没有大圆角卡片堆砌、没有巨型 hero、零外部资源。空态还分了"首次为空 / 筛选为空 / 正常的空"三类——最后一类当好消息说，这是有想法的细节。
概览页实机渲染：顶部状态条显示 6 项需要关注，左列待办队列四条，右列容量与入库趋势，下方为 8 个任务 × 14 天的执行状态矩阵
概览页（实机渲染）。整体是称职的值守台。但右上"入库趋势"折线只占了卡片约五分之一宽度并居中留白——原因是 renderTrend 用了 viewBox="0 0 100 70" 而未设 preserveAspectRatio="none"，SVG 按比例内缩了。基线也因此没能贯穿卡片。另外待办队列四条的数字全部渲染成错误红，"客户端等待审批"并不是错误。
客户端管理页实机渲染：顶部工具条右侧「下载客户端安装程序」显示为纯文字链接，紧邻的「高级设置」为带边框按钮
客户端管理页（实机渲染）——P1-4 的直接证据。请看工具条右上：「下载客户端安装程序」是一行普通蓝色文字，而它右边的「高级设置」有完整按钮外观。差别正是 <a class="button"> 与 <button>。同一画面还能看到两处：「部署状态」右上角是未格式化的 2026-08-20T13:32:28.469Z；"服务状态 ● 运行中"是硬编码值，页面能渲染出来就说明服务在跑，这一格永远是绿的。
需要改的地方
侧栏默认折叠成一列无标签图标，这是首次使用的硬伤。store.get('sidebar') === 'expanded' 意味着默认值是折叠。新管理员第一次登录，看到的是一竖排抽象几何符号（⌂ ○ ▲ ◉ ▣ ▤ ↺ ◫ ✉ ↑ ▤ ≡）——而且"备份集"和"作业历史"用了同一个字符 ▤，折叠态下无法区分。分组标签在折叠时是 visibility:hidden，留下几段无法解释的空隙（截图里能看到）。建议默认展开。
操作列按钮过多且不分主次。客户端列表每行三个按钮（刷新指标 / 禁用 / 注销），8 行就是 24 个按钮在争夺注意力。"注销"是不可逆操作，却和"刷新指标"完全同权重。告警页每行四个。建议只留一个主操作，其余收进溢出菜单。
告警列表每行出现两个视觉相同的红色胶囊（等级"严重"与状态"未处理"）。设计文档说胶囊只留给真正异常，但两列同时命中时就成了冗余噪声。建议等级用左侧色条，只让状态保留胶囊。
命令面板没有任何入口提示。Ctrl+K 面板、j/k 行导航、g d 跳转、? 快捷键表都实现了，但顶栏既没有搜索框也没有 ⌘K 提示，不看文档的人永远不会知道它存在。加一个顶栏搜索框占位即可。
关于"AI 味"
视觉层面几乎没有。真正的 AI 痕迹不在样式上，而在一种更隐蔽的模式里：把"看起来完备"当作完成。具体表现为——

永远为绿的"服务状态 ● 运行中"：一个不可能显示其他值的状态位。
11 条硬编码的弱口令表：安全防线的姿态，没有安全防线的效果。
对只读流调用 Flush(flushToDisk: true)：耐久性的形式，没有耐久性。
排序状态机、aria-sort、SortBy 字段全部就位，唯独没有任何一端真正使用。
注释密度显著高于实现完成度——几乎每个方法都精确引用了"设计书 14.3""OPEN-ISSUES #8"，但引用的行为本身未必接通。
这不是审美问题，是验收问题：这些东西都能通过阅读代码的检查，只有真跑一次才会露馅。而项目文档已经承认，那一次从来没跑过。

05
功能完整性
范围齐全 · 链路未验证
按功能说明书对照，模块覆盖是齐的：注册审批、心跳遥测、指令下发、预检、分块续传、入库校验、GFS 保留、回收站、恢复下载、告警通知、审计、批量操作、Agent 升级、局域网自动发现与一键安装。这是完整的产品范围，不是 demo。

但项目自己的验收文档写得很清楚：批次 B–G 全部标注"代码实现 + 单元测试通过；环境 / E2E / 浏览器验收未闭环"。没有在干净机器上装过一次，没有一个真实 Agent 完成过注册→心跳→扫描→上传→入库的全链路，没有做过浏览器交互验收。这份坦诚值得肯定，但它也精确解释了本报告 P0-2、P1-3、P1-4 为什么能存活至今。
范围内的功能空白
恢复没有审批分离。创建恢复请求和签发下载令牌可以是同一个管理员，没有第二人复核。对一个能把全部备份数据打包带走的操作，这是缺失的控制点。Purpose 字段做了审计留痕，但留痕不等于管控。
下载令牌不是一次性的。TTL 内可重复使用，Completed 状态的请求也仍可再次下载。若为支持断点续传是有意为之，应显式记录该决策。
仓库没有孤儿对帐机制。UploadCommitWorker 在数据库事务内部执行 Directory.Move 到正式目录。若进程在改名之后、事务提交之前崩溃，仓库里会留下一个没有数据库记录的目录。回滚路径处理了异常，但处理不了崩溃，而且没有任何巡检任务会发现这类孤儿。
恢复只支持整集（full）。代码显式拒绝其他 Selection.Type，DTO 也已预留。这是明确的 V1 范围裁剪，非缺陷，但要让使用方知道。
06
测试与 CI 缺口
覆盖偏向已知问题
49 个测试方法，用 Testcontainers 起真实 PostgreSQL，质量不低。问题是覆盖分布：测试集中在历次审查已经发现过的地方，而不是核心价值路径。

核心路径	业务重要性	自动化测试
恢复请求 / 下载 / ZIP / Range	系统存在的理由	无
UploadCommitWorker 入库与回滚	数据落地的唯一路径	无
mTLS 客户端证书认证	Agent 侧唯一的认证门	无
告警产生 / 去重 / 通知投递	监控的输出端	仅投递 1 项
指令下发与签名	服务端控制面	无
ReportService（概览全部数据）	值守台数据源	无
上传分块与断点续传	采集主链路	6 项
保留清理	数据销毁	3 项
路径安全 / 认证回归	历史问题	15 项
前端（2,945 行）	全部人机交互	无
CI 不构建两个安装器。ci.yml 只编译 Api、Tests、Agent、Agent.Tray 四个项目。BackupMonitor.Agent.Setup 和 BackupMonitor.Server.Setup——整个"一键交付"故事所依赖的两个双击 EXE——不在 CI 里。其中任何一个编译中断都不会被发现。
CI 完全不检查前端。连验收文档里提到的 node --check 都没进 workflow。P1-4 那种缺失的 CSS 类，一个最简单的样式检查就能拦住。
建议的最小补强：先给恢复下载和入库回滚各补一组集成测试（这两处出问题等于产品失效），把两个 Setup 项目加进 CI 的 Windows job，再加一个前端语法与 CSS 类引用检查。
07
建议的修复次序
按投入产出排
不建议按严重度从上到下平推。下面这个顺序能让每一步都立刻降低最大的风险。

第一步
先堵三个洞，都是小改动
P0-1 加 must_change_password claim + 授权过滤器；P0-3 给删除路径加 ResolveUnderBase 围栏；P1-2 给保留策略加"至少一条保留规则"的跨字段校验。三处加起来不超过 100 行，消除的是全部三种数据/权限灾难场景。

第二步
用一次真实端到端跑通替代继续读代码
装一台服务端 + 一台 Agent，走完注册→心跳→扫描→上传→入库→恢复下载。P0-2 会在第一分钟暴露或被排除。这一步的信息量高于再做一轮静态审查——本报告里所有"从未通电"类问题都会在这里集中显形。

第三步
补上完整性链条
P1-1 把 ExpectedSha256 变成强制比对基准；P1-6 修正两处无效的落盘同步；P2-8 统一清单与数据库的哈希来源。做完这三条，"存进去的等于取出来的"才有代码层面的保证。

第四步
界面最后一公里
P1-4 补 .button 样式；P1-3 排序要么实现要么摘掉假控件；P1-5 换成 keyword 参数；侧栏默认展开并给两个重复图标换字符；P2-11 修 confirmModal 挂起。半天工作量，界面完成度会有肉眼可见的跃升。

第五步
把验证固化下来
恢复下载与入库回滚补集成测试，两个 Setup 项目进 CI，加前端检查。目的是让第二步的结论不再退化——这套系统真正缺的不是代码，是让代码保持可信的机制。
