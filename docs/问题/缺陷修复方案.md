### D1 · 保留策略没有任何字段校验，空策略会删光全部备份

**位置**
- `src/src/BackupMonitor.Infrastructure/Services/RetentionPolicyService.cs:175` `CreateAsync`
- `src/src/BackupMonitor.Infrastructure/Services/RetentionPolicyService.cs:203` `UpdateAsync`
- `src/src/BackupMonitor.Infrastructure/Services/RetentionCleanupWorker.cs:480` `MarkGfsRetained`
- `src/src/BackupMonitor.Infrastructure/Services/RetentionCleanupWorker.cs:424` 熔断首次豁免

**现状**

两个写入方法只校验了 `request.Name` 非空，四个份数字段、`MinimumRetentionDays`、`RecycleBinDays` 全部原样入库。
当四个份数字段都为 null 时 `MarkGfsRetained` 返回空集合；`MinimumRetentionDays` 默认 0，
于是该策略下每一个 `available` 备份集都进入回收候选。唯一的保险是 50% 熔断，
但 `everCleaned` 那条首次豁免在「任务此前没有任何 recycle_bin/deleted 记录」时直接放行——
新配的空策略第一轮就能推走 100%。`RecycleBinDays` 无下限，配 0 则下一轮物理删除，无撤销窗口。

**改法**

1. 在 `RetentionPolicyService` 里加一个私有静态校验方法，`CreateAsync` 与 `UpdateAsync` 开头都调用：

```csharp
/// <summary>
/// 保留策略的合法性校验。
///
/// 四项份数全空时 MarkGfsRetained 会返回空的保留集合，配合默认为 0 的最短保留天数，
/// 效果是「这个策略下的每一份备份都要删」。这不是一个人会有意配出来的策略，
/// 而表单里这四项都折叠在高级选项里、默认留空——也就是说照默认值点保存就能配出它。
/// 因此这道校验不是防御性编程，它挡的是最容易发生的那一种误操作。
/// </summary>
private static void Validate(RetentionPolicyUpsertDto request)
{
    if (string.IsNullOrWhiteSpace(request.Name))
        throw new ValidationFailedException("name 必填");

    static int? Positive(int? value) => value is > 0 ? value : null;

    var hasRule = Positive(request.KeepLastCount) is not null
        || Positive(request.KeepWeeklyCount) is not null
        || Positive(request.KeepMonthlyCount) is not null
        || Positive(request.KeepYearlyCount) is not null;
    if (!hasRule)
        throw new ValidationFailedException(
            "「保留最近 N 份」和周/月/年规则至少要填一项。四项都留空表示一份都不保留，"
            + "这个策略下的全部备份都会被清掉——需要「永不清理」请把份数填一个足够大的值。");

    if (request.KeepLastCount is < 0 || request.KeepWeeklyCount is < 0
        || request.KeepMonthlyCount is < 0 || request.KeepYearlyCount is < 0)
        throw new ValidationFailedException("保留份数不能为负数");

    if (request.MinimumRetentionDays < 0)
        throw new ValidationFailedException("最短保留天数不能为负数");

    if (request.RecycleBinDays < 1)
        throw new ValidationFailedException(
            "回收站保留天数至少为 1 天。填 0 意味着移进回收站的备份下一轮就被物理删除，等于没有撤销窗口。");
}
```

2. `RetentionCleanupWorker.MarkGfsRetained` 加一道运行期兜底（存量脏数据也可能已经是空策略）：

```csharp
private static HashSet<Guid> MarkGfsRetained(
    IReadOnlyList<BackupSet> setsDescending, Core.Entities.Retention.RetentionPolicy policy)
{
    var keep = new HashSet<Guid>();

    // 兜底：四项份数都没配的策略在 V033 之前是能存进库的。真遇上时按「保留最新一份」处理
    // 而不是按「一份都不留」，并让调用方把它记成一条告警——宁可清理不干净，不可清空。
    var hasRule = policy.KeepLastCount is > 0 || policy.KeepWeeklyCount is > 0
        || policy.KeepMonthlyCount is > 0 || policy.KeepYearlyCount is > 0;
    if (!hasRule)
    {
        if (setsDescending.Count > 0)
            keep.Add(setsDescending[0].Id);
        return keep;
    }
    // ...原有逻辑不变
}
```

在 `ApplyGfsRetentionAsync` 里对这种策略发一条 `AlertLevel.Critical`、
category `retention_policy_invalid` 的告警，alert_key 用 `retention_policy:{policy.Id}:invalid`。

3. 熔断的首次豁免加一条上限——豁免的本意是「第一次给老任务配策略必然大比例回收」，
不该覆盖 100%：

```csharp
// 100% 回收在任何情况下都不是正常轮换，首次豁免也不适用它
if (everCleaned || percent >= 100)
{
    // ...原有的熔断告警与 continue
}
```

**验证**：新建一个四项全空的策略应当被拒绝；已有的空策略在下一轮清理时只保留最新一份并产生 Critical 告警。

### D2 · 计划驱动的任务没有漏备份检测；停用计划等于静默停掉备份

**位置**
- `src/src/BackupMonitor.Infrastructure/Services/AgentConfigService.cs:68` `plannedTaskIds`
- `src/src/BackupMonitor.Infrastructure/Services/AgentConfigService.cs:97` `ScanSchedule = planned ? null : ...`
- `src/src/BackupMonitor.Infrastructure/Services/MissedBackupWorker.cs:106` 任务筛选
- `src/src/BackupMonitor.Infrastructure/Services/BackupPlanService.cs:169` `plan.Enabled = request.Enabled`

**现状**

两个独立缺口：

1. `plannedTaskIds` 只看 `BackupPlanItems` 有没有行，**不看计划是否启用**。而
   `SequentialExecutionWorker.PromoteDuePlansAsync` 只推进 `Enabled` 的计划。
   停用一个计划之后：计划不再触发，Agent 侧任务自己的 cron 也仍然被抹成 null，
   **这些任务从此一次都不再备份**。
2. `MissedBackupWorker` 只处理 `t.ScanSchedule != null` 的任务。挂进计划的任务库里
   `scan_schedule` 通常是空的（界面显示「不自动扫描」），于是整个漏备份巡检对它们不生效；
   worker 里也没有任何一处引用 `BackupPlan`。两者合起来：备份停了好几天，系统一声不响。

**改法**

1. `AgentConfigService.cs:68` 加上计划启用条件：

```csharp
// 只有**启用中**的计划才接管任务的扫描。停用计划时 backup_plan_items 是原样保留的，
// 不看这个条件的话，停用计划 = 计划不再触发 + 任务自己的 cron 也被抹掉，
// 这些任务从此一次都不再备份，而且漏备份巡检看不见它们（它只认有 cron 的任务）。
var plannedTaskIds = await _db.BackupPlanItems
    .Where(i => i.Task.ClientId == clientId && i.Plan.Enabled)
    .Select(i => i.TaskId)
    .ToListAsync(ct);
```

> 确认 `BackupPlanItem` 上有 `Plan` 导航属性；没有的话改成先查启用计划的 Id 集合再过滤。

2. `MissedBackupWorker.RunPassAsync` 增加一段「按计划判定」的分支。要点：

- 取所有 `Enabled` 的 `BackupPlan`（含 `Items`），用
  `PlanSchedule.GetPreviousOccurrence(plan.ScheduleKind == Weekly, plan.RunAt, ParseDays(plan.DaysOfWeek), tz, now)`
  算出上一次应执行时刻，加上同一个 `grace`。
- 对该计划下每一个可执行的任务（复用 `ExecutionQueueService.SkipReason` 的判据），
  比较 `task.LastSuccessAt < prevDue` → 告警，否则 `RecoverAsync`。
- alert_key 沿用 `task:{taskId}:missed`，与按 cron 的那条**共用同一个键**，
  避免同一个任务同时挂两条漏备份告警。
- 把这些 taskId 一并加进 `judgedTaskIds`，否则结尾那段「本轮没判定过的统一恢复」会立刻把它们恢复掉。

3. 现有按 cron 的分支要排除掉「已被启用中的计划接管」的任务，否则同一个任务会按两套时刻判两次：

```csharp
var planManagedTaskIds = await db.BackupPlanItems
    .Where(i => i.Plan.Enabled)
    .Select(i => i.TaskId)
    .ToHashSetAsync(ct);
// cron 分支里：if (planManagedTaskIds.Contains(task.Id)) continue;
```

**验证**：把一个任务挂进计划、计划设为每天 03:00，把 `LastSuccessAt` 手工改到两天前，
跑一轮 `RunPassAsync`，应当产生 `backup_missed` 告警；停用该计划后，
Agent 拉到的配置里这个任务的 `scanSchedule` 应当恢复成它自己的 cron。

### D3 · Agent 状态文件损坏时静默重置身份，机器会重新注册成新客户端

**位置**
- `src/agent/BackupMonitor.Agent/AgentStateStore.cs:433` `LoadState`
- `src/agent/BackupMonitor.Agent/AgentStateStore.cs:448` `SaveUnsafe`

**现状**

`LoadState` 反序列化失败时记一条日志然后 `return new()` —— 返回全空状态，
里面本该装着 `ClientId`、服务端地址覆盖、证书引用和全部本地候选。
随后任何一次 `Update` 都会用这个空状态覆盖原文件，原身份彻底消失。

写入侧配套：`SaveUnsafe` 用「临时文件 + `File.Move`」保证改名原子，
但 `File.WriteAllText` 之后**没有刷盘**就改名。掉电时完全可能留下一个 0 字节或半截的
`state.json`——正好触发上面那条静默重置。

**改法**

1. 写入刷盘：

```csharp
var tempPath = _statePath + ".tmp";
var payload = JsonSerializer.Serialize(_state, JsonOptions);

// 先建再设 ACL 再写，最后刷盘——顺序不能变：ACL 要在写入内容之前生效，
// 而刷盘必须在改名之前完成。File.Move 保证的是改名这一步原子，
// 它不保证临时文件的内容已经落盘；少了 Flush(true)，掉电后拿到的是一个
// 名字正确、内容为空的 state.json，而空状态在下面会被当成「这台机器还没注册过」。
using (var fs = new FileStream(tempPath, FileMode.Create, FileAccess.Write, FileShare.None))
{
    SecureFileSystem.ApplyFileAcl(tempPath, _options.EnforceAcl);
    var bytes = System.Text.Encoding.UTF8.GetBytes(payload);
    fs.Write(bytes, 0, bytes.Length);
    fs.Flush(flushToDisk: true);
}
File.Move(tempPath, _statePath, true);
SecureFileSystem.ApplyFileAcl(_statePath, _options.EnforceAcl);
```

2. 读取失败不再静默重置。区分「文件不存在」（首次运行，正常）和「文件存在但读不出来」（异常）：

```csharp
private AgentState LoadState()
{
    if (!File.Exists(_statePath))
        return new();   // 首次运行，正常路径

    try
    {
        var state = JsonSerializer.Deserialize<AgentState>(File.ReadAllText(_statePath), JsonOptions);
        if (state is not null)
            return state;
    }
    catch (Exception ex)
    {
        _logger.LogCritical(ex, "Agent 状态文件损坏：{Path}", _statePath);
    }

    // 状态文件存在却读不出来时，绝不能返回空状态继续跑。
    // 空状态里没有 ClientId，Agent 会当成「没注册过」重新登记——
    // 于是这台机器在管理端变成一台待审批的新客户端，原客户端转离线、
    // 它名下所有任务停摆，而没有任何一条告警在说「某台机器丢了身份」。
    // 坏文件改名留档（人工还能捞回 ClientId），进程退出等人处理。
    var quarantine = $"{_statePath}.corrupt-{DateTime.UtcNow:yyyyMMddHHmmss}";
    try { File.Move(_statePath, quarantine); }
    catch (Exception moveEx) { _logger.LogError(moveEx, "损坏的状态文件改名失败"); }

    throw new InvalidOperationException(
        $"Agent 状态文件损坏，已改名为 {quarantine}。"
        + "请从备份恢复该文件，或确认这台机器需要重新登记后再删除它。");
}
```

> 这里刻意抛异常而不是继续。构造函数里抛 → 服务启动失败 → Windows 服务显示启动错误，
> 这是能让人看见的失败。静默重新注册是看不见的失败，代价大得多。
> 如果不接受「服务起不来」，退而求其次：保留空状态但**禁止自动注册**，
> 心跳循环里持续记 Critical 日志并在托盘提示。

**验证**：手工把 `state.json` 截断成半截 JSON，重启 Agent 服务，应当启动失败并留下
`.corrupt-*` 文件，而不是出现一台新的待审批客户端。

### C10 · 删除备份集后无法重新备份（四道应用层闸 + 一条数据库唯一约束）

**位置**
- `src/src/BackupMonitor.Infrastructure/Services/AgentConfigService.cs:145` 快速指纹基线
- `src/src/BackupMonitor.Infrastructure/Services/AgentPrecheckService.cs:122` 预检提交闸
- `src/src/BackupMonitor.Infrastructure/Services/CommandService.cs:153` `uploadNeverLanded`
- `src/src/BackupMonitor.Infrastructure/Services/UploadSessionService.cs:127` 建会话闸
- `src/src/BackupMonitor.Infrastructure/Services/BackupTaskService.cs:623` 手动上传闸
- `src/src/BackupMonitor.Infrastructure/Services/BatchOperationService.cs:174` 批量上传闸
- `src/database/V001__initial_schema.sql:779` `uq_backup_sets_candidate UNIQUE (source_candidate_id)`

**现状**

删除备份集是软删（回收站 → `status=recycle_bin`；彻底删除 → `status=deleted`），
两种删法**行都还在**。上面六处 `BackupSets.AnyAsync(b => b.SourceCandidateId == ...)`
全都不看 status，加上数据库那条无条件唯一约束，导致源文件没变时那份备份永久无法重新入库。

**改法**

1. **新增迁移 `src/database/V033__allow_reupload_after_delete.sql`**，把唯一约束改成部分索引：

```sql
-- V033：删掉的备份集不该继续占着「这个候选已经入过库」的位置
--
-- uq_backup_sets_candidate 原先是无条件唯一索引，含义是「一个候选只能产生一个正式版本」。
-- 这个含义在「备份集被删掉之后」不成立：人删掉一份备份，正常预期是还能再备一次，
-- 而删除是软删（recycle_bin / deleted），行仍然在，唯一约束于是永久挡住重新入库。
-- 改成部分唯一索引：只有「还活着」的版本参与唯一性判定。
ALTER TABLE backup_sets DROP CONSTRAINT IF EXISTS uq_backup_sets_candidate;
DROP INDEX IF EXISTS uq_backup_sets_candidate;

CREATE UNIQUE INDEX uq_backup_sets_candidate_live
    ON backup_sets (source_candidate_id)
    WHERE status NOT IN ('recycle_bin', 'deleted');
```

> 执行前先确认没有存量违反新索引的数据：
> ```sql
> SELECT source_candidate_id, count(*) FROM backup_sets
> WHERE status NOT IN ('recycle_bin','deleted')
> GROUP BY source_candidate_id HAVING count(*) > 1;
> ```

2. EF 配置同步：`src/src/BackupMonitor.Infrastructure/Data/Configurations/BackupConfigurations.cs:308`

```csharp
builder.HasIndex(e => e.SourceCandidateId)
    .IsUnique()
    .HasDatabaseName("uq_backup_sets_candidate_live")
    .HasFilter("status NOT IN ('recycle_bin', 'deleted')");
```

3. 六处应用层判断统一加状态过滤。建议在 `Core/Enums` 里加一个共享判据，避免又写六份：

```csharp
// BackupSetStatuses.cs（新建，与 UploadSessionStatuses 同一个位置、同一个理由）

    [
        BackupSetStatus.Verifying, BackupSetStatus.Available,
        BackupSetStatus.VerificationFailed, BackupSetStatus.Quarantined

```

> 请先核对 `BackupSetStatus` 枚举的实际成员（`src/src/BackupMonitor.Core/Enums/Enums.cs`），
> 用「排除 RecycleBin / Deleted」而不是逐个列举更稳妥。

然后六处改成：

```csharp
await _db.BackupSets.AnyAsync(
    b => b.SourceCandidateId == candidate.Id && BackupSetStatuses.Live.Contains(b.Status), ct)
```

`CommandService.cs:149` 那条判 committed 会话的条件同样要放宽，否则 `uploadNeverLanded`
只解了一半（会话还是 committed）——把它改成「存在 committed 会话**且**该会话对应的备份集还活着」。

4. **`RecycleAsync` / `PurgeAsync` 里清掉快速指纹基线**，否则 Agent 依然直接回 `no_new_backup`：

```csharp
// 备份集删掉之后，Agent 那边的两段式扫描基线必须跟着失效。
// 不清的话，源文件没变 → 快速指纹命中上一次的候选 → 直接回 no_new_backup，
// 人在界面上看到的是「没有新备份」，而他刚刚删掉的正是那一份。
await _db.CandidateBackupSets
    .Where(c => c.Id == set.SourceCandidateId)
    .ExecuteUpdateAsync(s => s.SetProperty(c => c.QuickFingerprint, (string?)null), ct);

await _db.BackupTasks
    .Where(t => t.Id == set.TaskId)
    .ExecuteUpdateAsync(s => s.SetProperty(t => t.ConfigVersion, t => t.ConfigVersion + 1), ct);
```

`ConfigVersion + 1` 是必须的：Agent 只在配置版本变高时才重新拉配置。

5. `RestoreFromRecycleBinAsync` 加一道校验——还原一份备份时，同一候选可能已经有新版本了：

```csharp
var hasLive = await _db.BackupSets.AnyAsync(
    b => b.SourceCandidateId == set.SourceCandidateId
        && b.Id != set.Id
        && BackupSetStatuses.Live.Contains(b.Status), ct);
if (hasLive)
    throw new BusinessException("CONFLICT",
        "这份备份删除之后已经重新备份过了，还原会和新版本冲突。"
        + "需要旧版本的话请先处理掉新的那一份。", 409);
```

**验证**：备份一次 → 删除（回收站）→ 源文件不动，再点「立即备份」→ 应当能重新扫描、重新上传、重新入库。

### D4 · 跑过一次的备份任务永远删不掉，提示指向一条不存在的解法

**位置**：`src/src/BackupMonitor.Infrastructure/Services/BackupTaskService.cs:225 / :229 / :241`

**现状**

三道守卫都没有状态过滤，且都没有可满足的路径：
`hasSets` 认所有 `backup_sets` 行（回收站/已删除的行都还在）；
`hasCandidates` 认所有候选，而**候选备份集全系统没有任何删除入口**；
`hasUploadSessions` 认所有历史会话，那是永久保留的。
错误提示写的是「请先处理保留策略」，但处理保留策略并不会让任务变得可删。

**改法**

```csharp
// 只有「还活着」的备份版本才挡删除。回收站里的和已彻底删除的行仍然在表里，
// 拿它们挡住删除，等于任何成功备份过一次的任务永远删不掉——
// 而原先的提示「请先处理保留策略」指向的是一条走不通的路：
// 清空回收站、物理删除之后这些行照样在。
var hasLiveSets = await _db.BackupSets.AnyAsync(
    s => s.TaskId == taskId && BackupSetStatuses.Live.Contains(s.Status), ct);
if (hasLiveSets)
    throw new BusinessException("CONFLICT",
        "任务下还有可用的备份版本。请先在「备份集」页面把它们删除（会进回收站），再删除任务。", 409);

var hasActiveSessions = await _db.UploadSessions.AnyAsync(
    s => s.TaskId == taskId && ActiveUploadStatuses.Contains(s.Status), ct);
if (hasActiveSessions)
    throw new BusinessException("CONFLICT", "任务存在正在进行的上传，等它结束或先取消再删除", 409);
```

然后把候选、历史会话、已删除的备份集连同任务一并级联清理——它们都是任务的附属记录，
处理方式与文件里已有的 Commands / Alerts 清理段落保持一致（同样要先取消关联的
`notification_deliveries`，顺序不能反）。删除顺序：

```
upload_chunks → upload_files → upload_sessions
backup_files  → backup_sets（仅 recycle_bin / deleted 的）
candidate_files → candidate_backup_sets
business_units
execution_run_items（该任务的）
commands / alerts（已有逻辑）
→ backup_tasks
```

物理文件：被级联删掉的 `backup_sets` 若 `status=recycle_bin` 且仓库目录还在，
删除前要调 `RepositoryDirectory.DeleteUnderRoot` 清掉，否则留下孤儿目录
（`RepositoryReconcileWorker` 会报出来，但那是事后补救）。

**注意**：`src/tests/BackupMonitor.Infrastructure.Tests/BackupTaskDeletionTests.cs` 会失败，需要一并更新。

## 批次三：队列与取消

### C1 · 全局上传闸把预检项也挡住，计划可以永久停在「排队中」

**位置**：`src/src/BackupMonitor.Infrastructure/Services/SequentialExecutionWorker.cs:359`

**现状**

```csharp
var activeUploads = await CountActiveUploadsAsync(db, ct);
if (activeUploads >= globalUploadLimit)
    break;   // item.CommandType 是 PrecheckTask 时也会走到这里
```

计划执行的每一项都是 `PrecheckTask`——它只让客户端扫目录算哈希，**一个上传名额都不占**，
却被上传闸拦住。而 Pending 项没有超时（`ItemTimeoutMinutes` 只对 Running 项生效），
`CreatePlanRunAsync` 又规定「上一次没跑完就不再建新的」——**一次卡住 = 这个计划永久不再执行**。

**改法**

```csharp
foreach (var item in pending)
{
    if (running >= run.MaxConcurrent)
        break;

    ct.ThrowIfCancellationRequested();

    // 全局上传闸只对真的会建上传会话的项生效。预检只是让客户端扫一遍目录算哈希，
    // 一个上传名额都不占；拿上传闸挡住它，等于「服务端有 4 个会话在传」
    // 就让所有计划连扫描都不许开始。而 Pending 项没有超时、计划又不允许叠一次执行，
    // 于是这一挡是永久的——现场表现是计划停在「排队中」，此后再也不执行。
    var consumesUploadSlot = item.CommandType is CommandType.UploadCandidate or CommandType.UploadLatest;
    if (consumesUploadSlot)
    {
        var activeUploads = await CountActiveUploadsAsync(db, ct);
        if (activeUploads >= globalUploadLimit)
        {
            _logger.LogInformation(
                "全局上传并发已达上限（{Active}/{Limit}），执行 {RunId} 的剩余上传项继续排队",
                activeUploads, globalUploadLimit, run.Id);
            break;
        }
    }
    // ...原有下发逻辑
}
```

另外给 Pending 项加一道兜底超时：一项在 Pending 状态停留超过
`run.ItemTimeoutMinutes` 的 2 倍就判失败并告警，让计划能够收尾、下一次得以重建。

**注意**：`src/tests/BackupMonitor.Infrastructure.Tests/ManualBackupConcurrencyTests.cs`
里的 `全局上传并发达到上限时不再放行新项` 断言的正是「预检项也被挡住」，
测试意图需要跟着改——改成播种真实的 upload 项来验证闸仍然有效。

### C2 · retry_wait 会话占用并发名额 6 小时，单客户端两次失败即锁死

**位置**
- `src/src/BackupMonitor.Core/Enums/UploadSessionStatuses.cs:29` `Active`
- `src/src/BackupMonitor.Infrastructure/Services/UploadSessionService.cs:154` 单客户端上限
- `src/src/BackupMonitor.Infrastructure/Services/LifecycleExpiryWorker.cs` 6 小时超时

**现状**

`retry_wait`（Agent 上传出错后保留断点用的状态）计入 `Active`，
既占单客户端上限（默认 2）也占全局上限（默认 4），回收要等 `upload_session_timeout_seconds`（默认 6 小时）。
U8 这类多账套任务只要两个单元失败，这台机器接下来 6 小时所有上传一律 409。

**改法**（两者都做）

1. 给 `retry_wait` 单独一条更短的回收线。在 `LifecycleExpiryWorker` 里加：

```csharp
/// <summary>retry_wait 会话的回收时限（秒）。它保留的是断点，不是正在进行的传输——
/// 拿「多久没动静才算废了」的 6 小时去卡它，一次失败就锁住这台机器半天。</summary>
public const string RetryWaitTimeoutKey = "upload_retry_wait_timeout_seconds";
public const int DefaultRetryWaitTimeoutSeconds = 1800;   // 30 分钟
```

`ExpireStaleSessionsAsync` 里按状态分两组算 deadline。**注意**：过期时不要立刻删暂存目录——
`staging_cleanup_retention_hours` 那条保留期照旧，这样 30 分钟内重试仍然能续传。

2. 单客户端上限的计数排除 `retry_wait`：

```csharp
// 单客户端上限数的是「这台机器同时有几路在往上传」，retry_wait 一路都没在传。
// 把它算进来的后果是：一次失败留下的断点会挡住这台机器接下来所有单元的上传，
// 而多账套任务（U8 一台机器 18 个账套）必然踩中。全局闸那边同理由分开处理。
var countedStatuses = new[] { UploadStatus.Created, UploadStatus.Uploading, UploadStatus.Paused };
var activeSessions = await _db.UploadSessions
    .CountAsync(s => s.ClientId == clientId && countedStatuses.Contains(s.Status), ct);
```

`paused` 保留在内是对的（它确实占着暂存空间且是人为的）。

### C4 / C5 · 多单元任务绕开执行队列的并发度，且成败判定只看最新一个会话

**位置**
- `src/src/BackupMonitor.Infrastructure/Services/AgentPrecheckService.cs:305` 自动下发上传
- `src/src/BackupMonitor.Infrastructure/Services/SequentialExecutionWorker.cs:309` `FindSessionAsync`

**现状**

预检结果一到，`AgentPrecheckService` 就逐个单元下发上传指令，完全绕开执行队列的
`MaxConcurrent`——所以「严格顺序（1）」对多单元任务名不副实。
而 `FindSessionAsync` 给计划项定位会话时是
`OrderByDescending(s => s.CreatedAt).FirstOrDefaultAsync()`，**只看最新一个**：
5 个账套只要最后一个成功，整项就记「成功」，另外 4 个失败被吞掉。

**改法**

`FindSessionAsync` 改成返回**该项开跑之后该任务产生的全部会话**，由调用方汇总：

```csharp
// 一个任务可以有很多个业务单元（U8 一台机器 18 个账套是常态），每个单元一个候选、
// 一个会话。只看最新那一个的话，这一项的结论由「最后一个账套」单方面决定——
// 最后一个成功就报成功，另外 17 个失败一声不响。
private static async Task<List<UploadSession>> FindSessionsAsync(
    AppDbContext db, ExecutionRunItem item, DateTime startedAt, CancellationToken ct)
{
    var sessions = db.UploadSessions.AsNoTracking();

    if (item.CandidateBackupSetId is not null)
        return await sessions
            .Where(s => s.CandidateBackupSetId == item.CandidateBackupSetId)
            .ToListAsync(ct);

    return await sessions
        .Where(s => s.TaskId == item.TaskId && s.CreatedAt >= startedAt)
        .ToListAsync(ct);
}
```

`EvaluateRunningItemAsync` 的判定改成：
- 全部会话都 `Committed` → 项成功
- 还有任何一个处于 `InFlight` → 继续等
- 其余（存在终态失败且没有在途的）→ 项失败，`Message` 写明「N 个单元中 M 个失败」

同时 `AgentPrecheckService` 那条自动下发要受执行队列约束：
候选属于某个还在跑的 `ExecutionRunItem` 时，走 `TryDeferUploadAsync` 排队而不是当场下发。

### C6 / C7 · 取消不生效：不通知客户端，且随后被自动重新下发

**位置**
- `src/src/BackupMonitor.Infrastructure/Services/UploadSessionControlService.cs:105` `CancelAsync`
- `src/src/BackupMonitor.Infrastructure/Services/CommandService.cs:146` `uploadNeverLanded`
- `src/src/BackupMonitor.Infrastructure/Services/UploadSessionService.cs:104` 幂等键释放
- `src/agent/BackupMonitor.Agent/AgentWorker.cs:1986` `NonRetryableUploadErrorCodes`
- `src/src/BackupMonitor.Infrastructure/Services/ExecutionQueueService.cs:340` `CancelRunAsync`

**现状**

取消一次传输只是服务端改个状态，客户端不知道，继续推分块撞 409；
而 `UPLOAD_SESSION_CONFLICT` 不在 Agent 的不可重试清单里，每块还要退避重试 3 次。
更致命的是随后的自动重新下发：`uploadNeverLanded` 判据是「没有 committed、也没有 InFlight 会话」，
被取消的会话正好满足 → 指令复位重发 → 建会话时因旧会话是 `cancelled` 而释放幂等键 →
**建一个全新会话从 0 重传**。取消 ≈ 几分钟后从头再传一遍。

「取消这次执行」同理：只取消还没开跑的项，在跑的预检继续，跑完照样自动下发全部单元的上传。

**改法**

1. **候选上记住「这是人主动取消的」**。加一列（并入 V033）：

```sql
ALTER TABLE candidate_backup_sets
    ADD COLUMN cancelled_at TIMESTAMPTZ NULL,
    ADD COLUMN cancelled_by UUID NULL REFERENCES users(id);

COMMENT ON COLUMN candidate_backup_sets.cancelled_at IS
    '管理员主动取消这一份的上传。取消若只落在会话上，下一轮预检会因为「没有已入库的痕迹」'
    '把上传指令复位重发，于是取消变成「几分钟后从头重传」。';
```

`UploadSessionControlService.CancelAsync` 里同时写这两列。
`AgentPrecheckService` 的自动下发、`CommandService` 的 `uploadNeverLanded`、
`UploadSessionService.CreateSessionAsync` 三处都要检查 `cancelled_at is null`。
重新备份的正道是重新预检产生新候选，或界面上提供一个显式的「重新上传这一份」按钮清掉这个标记。

2. Agent 的不可重试清单加上 `UPLOAD_SESSION_CONFLICT`：

```csharp
private static readonly HashSet<string> NonRetryableUploadErrorCodes = new(StringComparer.Ordinal)
{
    PausedSessionErrorCode,
    // 会话状态不允许写入（被取消、已终结）。退避重试对它没有意义——
    // 状态不会因为等 4 秒就变回可写，重试只是让「取消」多花十几秒才生效。
    "UPLOAD_SESSION_CONFLICT",
    "CANDIDATE_EXPIRED", "CANDIDATE_CHANGED", "CANDIDATE_ALREADY_ARCHIVED",
    "MANIFEST_MISMATCH", "CHUNK_INVALID", "FILE_HASH_MISMATCH",
    "UPLOAD_NOT_PERMITTED", "FORBIDDEN"
};
```

3. `CancelRunAsync` 要真的停住。在跑的项：取消它的指令（`commands.status = cancelled`），
并把该项这次执行产生的、仍在 InFlight 的上传会话一并取消；同时给该 run 下所有
已产生的候选打上 `cancelled_at`，堵住预检回来后的自动下发。
确认框文案也要改成与实际行为一致。

### C8 · 速率采样返回 0 导致「合计 0 B/s」

**位置**：`src/src/BackupMonitor.Infrastructure/Services/UploadProgressService.cs:212`

```csharp
// 采样窗口内 uploaded_bytes 没动就返回 null，让调用方退回全程平均。
// 返回 0 的话 `Observe(...) ?? averageRate` 这个回退根本不生效（0 不是 null），
// 一次正常的采样间隔就把「正在传」显示成「0 B/s、预计剩余 —」。
// 分块 8MB 才推进一次计数，而界面 5 秒一刷，采到 0 是常态而不是异常。
var delta = Math.Max(0, uploadedBytes - previous.Bytes);
long? rate = delta > 0 ? (long)(delta / gap.TotalSeconds) : null;
_samples[sessionId] = new Sample(uploadedBytes, nowUtc, rate);
return rate;
```

`Sample.LastRate` 已经是 `long?`，类型不用改。

### C9 · 队列状态把两种「排队」混成一个数

**位置**：`src/src/BackupMonitor.Infrastructure/Services/UploadProgressService.cs:63`

**改法**：`UploadQueueStatusDto` 拆成两个字段——
`WaitingForUploadSlot`（等全局名额的上传项）和 `WaitingInRun`（等本次执行并发度的项），

### C11 · 业务单元清单只在「立即备份」弹窗里出现

**位置**：`src/src/BackupMonitor.Api/wwwroot/js/views/tasks.js:838` `unitQueueHtml`
