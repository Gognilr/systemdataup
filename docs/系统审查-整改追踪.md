## 二、审查清单之外新发现的缺陷

### 🔴 告警系统从未产生过任何告警

`AlertingService.RaiseAsync` 的去重前置守卫判断方向写反：

```csharp
var hasActiveAlert = await _db.Alerts.AnyAsync(a => a.AlertKey == alertKey && ActiveStatuses.Contains(a.Status), ct);
if (!hasActiveAlert)
    return;   // ← 「不存在活动告警」恰恰是需要新建的情形
```

结果是下面创建新告警的 `else` 分支成为**死代码**，全系统任何 `RaiseAsync` 都不产生告警——
入库失败、保留删除失败、恢复校验失败、回收熔断，监控的输出端整体失效。

这一项严重度不低于原报告的 P1，且完美印证了报告 §06 的判断：
告警「产生」环节此前**零测试覆盖**，已有测试只覆盖投递环节，所以它能一直存活。
发现过程也正是这样——新写的熔断测试查不到告警，回溯才找到根因。

**修复**：去掉方向写反且与下方 `existing` 查询重复的前置守卫。
**测试**：新增 `AlertingServiceTests` ×4（首次必须新建 / 同键累加不新建 / 等级只升不降 / 恢复后再触发新建）。

### 提交后收尾动作可摧毁已成功的备份

`UploadCommitWorker` 中 `CleanupSessionAsync` 与 `RecoverAsync` 位于事务提交**之后**却仍在同一 try 内，
而对应 catch 会回滚事务并删除正式目录。此前未出事仅因「对已提交事务调 `RollbackAsync` 会先抛异常」
这一实现细节恰好挡在删除动作之前——换个 EF/Npgsql 版本即可能真的删下去。

**修复**：提交后置 `committed = true`，收尾动作各自兜住异常仅记日志；catch 增加 `if (committed) throw;` 闸门。

## 四、仍未处理

**需要产品决策**

## 六、2026-08-27 客户端 IP 可见性

原先 `clients.ip_addresses` 只在 `AgentRegistrationService` 里写过一次，之后永不刷新：
DHCP 续租或换网段之后库里那份就永久过期，而界面上看不出它是旧的；
列表页完全没有 IP 列，详情页又把 jsonb 原文直接显示成
`["192.168.1.37","fe80::…"]`。

改动分两条独立的线：

| 线 | 数据 | 刷新时机 | 用途 |
| --- | --- | --- | --- |
| `clients.ip_addresses` | Agent 自报的本机网卡地址列表 | 并入心跳快照摘要，变化时才上报 | 看多网卡 / 网段分布 |
| `clients.last_remote_ip` | 服务端连接层观测到的对端地址（经 `UseForwardedHeaders` 还原） | 每次心跳 | 「现在用的是哪个地址」，必然连得通 |

- 协议：`HeartbeatRequest` 新增 `IpAddresses`，跟随 `SnapshotUnchanged` 语义——
  为 `null` 表示「没变」而不是「没有」，服务端不得据此清空已有值。
  `SystemProbe.ComputeSnapshotDigest` 相应扩成四块，网卡地址排序后入摘要
  （枚举顺序不保证稳定，不排序会让「没变」被误判成「变了」）。
- API：`ClientDetailDto.IpAddresses` 由 jsonb 原文字符串改为 `List<string>`，
  解析失败退化成空列表；`ClientListItemDto` 新增 `LastRemoteIp`。
- 界面：客户端列表新增 IP 列（取对端 IP，只有一个值且永远最新）；
  详情与运行页统一走 `ipDetailRows()`，分行显示「对端 IP」与「本机网卡地址」。

新增迁移：V024（`clients.last_remote_ip`，并补 `ip_addresses` 的列注释）。
测试：`ClientIpVisibilityTests` ×6、`AgentHeartbeatCadenceTests` +1。

## 七、2026-08-27 仓库对帐 · 界面收口 · 端到端清单

### 仓库孤儿目录对帐（新增机制）

入库最后两步是 `Directory.Move`（提交目录改名为正式目录）和 `SaveChangesAsync`
（备份集写库）。进程崩在这两步之间——断电、蓝屏、手工重启服务——文件留在仓库里
而数据库没有记录：**界面显示那次备份失败，实际盘上已有一份完整备份，
而且此前没有任何东西会发现它**，仓库一点点被填满直到写不下。
`UploadCommitWorker` 的回滚路径处理了异常，处理不了进程根本没机会跑回滚。

新增 `RepositoryReconcileWorker`，识别两类残骸：

| 类型 | 特征 | 对应崩溃点 |
| --- | --- | --- |
| `CommitTemp` | 目录名含 `.commit-xxxxxxxx` | 崩在复制文件或写清单过程中 |
| `Missing` | 正式命名 + 含 `manifest.json` + `backup_sets` 查不到 | 崩在 Move 之后、SaveChanges 之前 |

判定要点：

- **只报不删。** 每个目录都可能是货真价实的备份，删错了没有第二份。
  告警列出路径与占用大小，处置交给人；下一轮无孤儿时自动 `RecoverAsync`。
- 已知目录集合取 `backup_sets` **全量**而非只取 `available`——回收站里的、
  校验失败的、待删除的，目录都还在盘上，都不是孤儿。
- 路径先 `GetFullPath` + `TrimEndingDirectorySeparator` 再比对：库里存的是入库当时
  拼出来的字符串，写法差异会把真备份误报成孤儿，而这种误报最伤人。
- 静默期（默认 24 小时）：正在进行的入库本来就是「目录已建、库里无行」的样子。
- 没有清单的空目录**不报**——刻意选择漏报而非误报，报出来会让人以为有份备份可以救。
- 遍历用显式栈 + 逐目录 try/catch，一个无权限的子目录不会让整轮什么都查不出来。

### 产品决策记录

- **恢复审批分离：不做。** 这是单人运维的备份工具，不引入需要第二个人参与的流程。
- **下载令牌在 TTL 内可重复使用：有意为之。** `BeginDownloadAsync` 只校验哈希与过期时间，
  不消费令牌；重新签发会覆盖 `DownloadTokenHash` 使旧令牌失效。
  一次性令牌会直接打死 `?path=` 单文件下载的 Range 断点续传。TTL 默认 30 分钟
  （`download_token_ttl_minutes`）。
- **P2-3 令牌移出 URL：不做。** 日志泄露路径已切断，剩余风险是本机浏览器历史里
  一条 30 分钟过期的链接；引入一次性会话交换只会让恢复下载更难用。

## 八、传输可见性 + 一个必现的上传阻断缺陷

起因是一个很朴素的问题：「正在备份数据，数据比较大传输慢，这个过程中我怎么能看到状态？」
排查过程中先撞上了一条更要命的东西。

### P0 · 进度上报器溢出，导致任何上传都完不成

现场：客户端 WIN-I35ROM0LHQL 的告警「upload_candidate 指令执行失败」，
原因写着 `TimeSpan overflowed because the duration is too long.`，结果码 `upload_failed`。

根因在 `AgentWorker.ProgressReporter`：

```csharp
private TimeSpan _lastReportedAt = TimeSpan.MinValue;   // ← 这里
...
if (_clock.Elapsed - _lastReportedAt < MinInterval || ...)
```

`TimeSpan.MinValue` 的 ticks 是 `long.MinValue`，`Elapsed` 减它必然溢出 Int64，
.NET 抛 `OverflowException`。`ReportAsync` 在**每个分块传完后**都会调，
所以第一块一传完就炸——**不是偶发，是所有机器、所有上传 100% 失败**。

放大它的是第二个问题：`ReportAsync` 里的 `try/catch` 只包住了那次 HTTP 上报调用，
没包住上面的节流判断。于是这个异常绕过了本类明写的约定
「上报只是装饰，绝不能把正在进行的上传搞失败」，一路冒到 `ExecuteUploadAsync`
的兜底 catch，取消会话后重新抛出。**一个纯展示功能整整挡住了备份主链路。**

两处都改了：初值改成 `-MinInterval`（语义与旁边那行 `-MinPercentDelta` 一致，
让第一次调用直接放行），`try` 扩到整个方法体。

这行代码是审计 B-15 加的，而 `src/tests/` 下**只有 Infrastructure 一个测试项目，
Agent 侧零覆盖**——这就是它编译通过就发布出去的原因。这个缺口本身还没补。

### 传输进度可见性

改之前：管理端只有一个「上传中」徽标和「正在上传：某任务」。
没有百分比、没有已传字节、没有速度、没有剩余时间。传两小时，界面上三个字不变。

而 `UploadSessionService` 每收一个分块就重算 `uploaded_bytes` 并刷新 `last_activity_at`，
数据一直是准的，只是从来没有一个管理端接口把它读出来。

- 新增 `GET /api/v1/admin/upload-sessions/active`（`perm:clients.read`，只读）。
  与 `api/v1/agent/upload-sessions` 是两回事：那组走客户端证书，一个会话只看得到自己。
- 新增 `UploadProgressService` + `UploadRateSampler`（进程内单例）。
  速度取两次观测之间的增量而不是全程平均——全程平均在传输变慢或卡住时不会跟着掉，
  而那正是最需要看出问题的时刻。首次观测没有可比对象时退回全程平均。
  相邻两次不足 3 秒不更新基准：多开两个浏览器就会有毫秒级的相邻请求，
  拿那个时间差去除会算出剧烈跳动的速度，看着像故障其实是采样噪声。
- **卡死判定**是这一块唯一有风险的判断，阈值随实测速度放大：
  `clamp(chunkSize / 平均速度 × 3, 180s, 30min)`。固定 180 秒会把窄带上正常传一个
  8MB 分块（50 KB/s 要 164 秒）报成卡死，而窄带正是最需要看进度的场景；
  没有上限则一条真死掉的会话永远不会被标出来。
  用全程平均而不是瞬时速度算阈值——真卡住时瞬时速度掉到 0，阈值会自己涨到无穷大。
- 速度或剩余时间算不出来时一律给 `—` 而不是 0。「剩余 0 秒」看起来像个结论，
  实际是「不知道」，而人正是靠这两个数判断该不该去查网络。
- 界面：侧栏「值守 → 传输中」新页面（有会话时 5 秒轮询，空闲 15 秒），
  概览页新增「正在传输」卡片，客户端列表的「上传中」徽标做成到该页的链接。
  排序口径：卡住的最前，其次剩余量最大的——前者要人动手，后者决定整批何时结束。

测试：`UploadProgressSamplerTests` ×10（纯计算，不需要 Docker）、
`UploadProgressQueryTests` ×8（需要 Docker）。无新增迁移，无新增配置项。
