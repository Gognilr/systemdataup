## 二、审查清单之外新发现的缺陷

### 🔴 告警系统从未产生过任何告警

`AlertingService.RaiseAsync` 的去重前置守卫判断方向写反：

```csharp
var hasActiveAlert = await _db.Alerts.AnyAsync(a => a.AlertKey == alertKey && ActiveStatuses.Contains(a.Status), ct);
if (!hasActiveAlert)
    return;   // ← 「不存在活动告警」恰恰是需要新建的情形
```

结果是下面创建新告警的 `else` 分支成为**死代码**，全系统任何 `RaiseAsync` 都不产生告警——
入库失败、保留删除失败、恢复校验失败、回收熔断，监控的输出端整体失效。

这一项严重度不低于原报告的 P1，且完美印证了报告 §06 的判断：
告警「产生」环节此前**零测试覆盖**，已有测试只覆盖投递环节，所以它能一直存活。
发现过程也正是这样——新写的熔断测试查不到告警，回溯才找到根因。

**修复**：去掉方向写反且与下方 `existing` 查询重复的前置守卫。
**测试**：新增 `AlertingServiceTests` ×4（首次必须新建 / 同键累加不新建 / 等级只升不降 / 恢复后再触发新建）。

### 提交后收尾动作可摧毁已成功的备份

`UploadCommitWorker` 中 `CleanupSessionAsync` 与 `RecoverAsync` 位于事务提交**之后**却仍在同一 try 内，
而对应 catch 会回滚事务并删除正式目录。此前未出事仅因「对已提交事务调 `RollbackAsync` 会先抛异常」
这一实现细节恰好挡在删除动作之前——换个 EF/Npgsql 版本即可能真的删下去。

**修复**：提交后置 `committed = true`，收尾动作各自兜住异常仅记日志；catch 增加 `if (committed) throw;` 闸门。

## 四、仍未处理

**需要产品决策**

## 六、2026-08-27 客户端 IP 可见性

原先 `clients.ip_addresses` 只在 `AgentRegistrationService` 里写过一次，之后永不刷新：
DHCP 续租或换网段之后库里那份就永久过期，而界面上看不出它是旧的；
列表页完全没有 IP 列，详情页又把 jsonb 原文直接显示成
`["192.168.1.37","fe80::…"]`。

改动分两条独立的线：

| 线 | 数据 | 刷新时机 | 用途 |
| --- | --- | --- | --- |
| `clients.ip_addresses` | Agent 自报的本机网卡地址列表 | 并入心跳快照摘要，变化时才上报 | 看多网卡 / 网段分布 |
| `clients.last_remote_ip` | 服务端连接层观测到的对端地址（经 `UseForwardedHeaders` 还原） | 每次心跳 | 「现在用的是哪个地址」，必然连得通 |

- 协议：`HeartbeatRequest` 新增 `IpAddresses`，跟随 `SnapshotUnchanged` 语义——
  为 `null` 表示「没变」而不是「没有」，服务端不得据此清空已有值。
  `SystemProbe.ComputeSnapshotDigest` 相应扩成四块，网卡地址排序后入摘要
  （枚举顺序不保证稳定，不排序会让「没变」被误判成「变了」）。
- API：`ClientDetailDto.IpAddresses` 由 jsonb 原文字符串改为 `List<string>`，
  解析失败退化成空列表；`ClientListItemDto` 新增 `LastRemoteIp`。
- 界面：客户端列表新增 IP 列（取对端 IP，只有一个值且永远最新）；
  详情与运行页统一走 `ipDetailRows()`，分行显示「对端 IP」与「本机网卡地址」。

新增迁移：V024（`clients.last_remote_ip`，并补 `ip_addresses` 的列注释）。
测试：`ClientIpVisibilityTests` ×6、`AgentHeartbeatCadenceTests` +1。

## 七、2026-08-27 仓库对帐 · 界面收口 · 端到端清单

### 仓库孤儿目录对帐（新增机制）

入库最后两步是 `Directory.Move`（提交目录改名为正式目录）和 `SaveChangesAsync`
（备份集写库）。进程崩在这两步之间——断电、蓝屏、手工重启服务——文件留在仓库里
而数据库没有记录：**界面显示那次备份失败，实际盘上已有一份完整备份，
而且此前没有任何东西会发现它**，仓库一点点被填满直到写不下。
`UploadCommitWorker` 的回滚路径处理了异常，处理不了进程根本没机会跑回滚。

新增 `RepositoryReconcileWorker`，识别两类残骸：

| 类型 | 特征 | 对应崩溃点 |
| --- | --- | --- |
| `CommitTemp` | 目录名含 `.commit-xxxxxxxx` | 崩在复制文件或写清单过程中 |
| `Missing` | 正式命名 + 含 `manifest.json` + `backup_sets` 查不到 | 崩在 Move 之后、SaveChanges 之前 |

判定要点：

- **只报不删。** 每个目录都可能是货真价实的备份，删错了没有第二份。
  告警列出路径与占用大小，处置交给人；下一轮无孤儿时自动 `RecoverAsync`。
- 已知目录集合取 `backup_sets` **全量**而非只取 `available`——回收站里的、
  校验失败的、待删除的，目录都还在盘上，都不是孤儿。
- 路径先 `GetFullPath` + `TrimEndingDirectorySeparator` 再比对：库里存的是入库当时
  拼出来的字符串，写法差异会把真备份误报成孤儿，而这种误报最伤人。
- 静默期（默认 24 小时）：正在进行的入库本来就是「目录已建、库里无行」的样子。
- 没有清单的空目录**不报**——刻意选择漏报而非误报，报出来会让人以为有份备份可以救。
- 遍历用显式栈 + 逐目录 try/catch，一个无权限的子目录不会让整轮什么都查不出来。

### 产品决策记录

- **恢复审批分离：不做。** 这是单人运维的备份工具，不引入需要第二个人参与的流程。
- **下载令牌在 TTL 内可重复使用：有意为之。** `BeginDownloadAsync` 只校验哈希与过期时间，
  不消费令牌；重新签发会覆盖 `DownloadTokenHash` 使旧令牌失效。
  一次性令牌会直接打死 `?path=` 单文件下载的 Range 断点续传。TTL 默认 30 分钟
  （`download_token_ttl_minutes`）。
- **P2-3 令牌移出 URL：不做。** 日志泄露路径已切断，剩余风险是本机浏览器历史里
  一条 30 分钟过期的链接；引入一次性会话交换只会让恢复下载更难用。

测试：`RepositoryReconcileTests` ×8（纯文件系统，不需要 Docker）。

## 八、传输可见性 + 一个必现的上传阻断缺陷

起因是一个很朴素的问题：「正在备份数据，数据比较大传输慢，这个过程中我怎么能看到状态？」
排查过程中先撞上了一条更要命的东西。

### P0 · 进度上报器溢出，导致任何上传都完不成

现场：客户端 WIN-I35ROM0LHQL 的告警「upload_candidate 指令执行失败」，
原因写着 `TimeSpan overflowed because the duration is too long.`，结果码 `upload_failed`。

根因在 `AgentWorker.ProgressReporter`：

```csharp
private TimeSpan _lastReportedAt = TimeSpan.MinValue;   // ← 这里
...
if (_clock.Elapsed - _lastReportedAt < MinInterval || ...)
```

`TimeSpan.MinValue` 的 ticks 是 `long.MinValue`，`Elapsed` 减它必然溢出 Int64，
.NET 抛 `OverflowException`。`ReportAsync` 在**每个分块传完后**都会调，
所以第一块一传完就炸——**不是偶发，是所有机器、所有上传 100% 失败**。

放大它的是第二个问题：`ReportAsync` 里的 `try/catch` 只包住了那次 HTTP 上报调用，
没包住上面的节流判断。于是这个异常绕过了本类明写的约定
「上报只是装饰，绝不能把正在进行的上传搞失败」，一路冒到 `ExecuteUploadAsync`
的兜底 catch，取消会话后重新抛出。**一个纯展示功能整整挡住了备份主链路。**

两处都改了：初值改成 `-MinInterval`（语义与旁边那行 `-MinPercentDelta` 一致，
让第一次调用直接放行），`try` 扩到整个方法体。

这行代码是审计 B-15 加的。它能编译通过就发布出去，是因为 **`AgentWorker` 本身一行覆盖都没有**。
（更正一处早先的说法：Agent 并非零覆盖——`BackupMonitor.Infrastructure.Tests` 引用了 Agent 项目，
`BackupScanner` / `AgentStateStore` / 协议加固 / 命令签名等已有 7 个测试文件。
没被测到的是 `AgentWorker` 里那几个嵌套私有类型。）见下节。

### 传输进度可见性

改之前：管理端只有一个「上传中」徽标和「正在上传：某任务」。
没有百分比、没有已传字节、没有速度、没有剩余时间。传两小时，界面上三个字不变。

而 `UploadSessionService` 每收一个分块就重算 `uploaded_bytes` 并刷新 `last_activity_at`，
数据一直是准的，只是从来没有一个管理端接口把它读出来。

- 新增 `GET /api/v1/admin/upload-sessions/active`（`perm:clients.read`，只读）。
  与 `api/v1/agent/upload-sessions` 是两回事：那组走客户端证书，一个会话只看得到自己。
- 新增 `UploadProgressService` + `UploadRateSampler`（进程内单例）。
  速度取两次观测之间的增量而不是全程平均——全程平均在传输变慢或卡住时不会跟着掉，
  而那正是最需要看出问题的时刻。首次观测没有可比对象时退回全程平均。
  相邻两次不足 3 秒不更新基准：多开两个浏览器就会有毫秒级的相邻请求，
  拿那个时间差去除会算出剧烈跳动的速度，看着像故障其实是采样噪声。
- **卡死判定**是这一块唯一有风险的判断，阈值随实测速度放大：
  `clamp(chunkSize / 平均速度 × 3, 180s, 30min)`。固定 180 秒会把窄带上正常传一个
  8MB 分块（50 KB/s 要 164 秒）报成卡死，而窄带正是最需要看进度的场景；
  没有上限则一条真死掉的会话永远不会被标出来。
  用全程平均而不是瞬时速度算阈值——真卡住时瞬时速度掉到 0，阈值会自己涨到无穷大。
- 速度或剩余时间算不出来时一律给 `—` 而不是 0。「剩余 0 秒」看起来像个结论，
  实际是「不知道」，而人正是靠这两个数判断该不该去查网络。
- 界面：侧栏「值守 → 传输中」新页面（有会话时 5 秒轮询，空闲 15 秒），
  概览页新增「正在传输」卡片，客户端列表的「上传中」徽标做成到该页的链接。
  排序口径：卡住的最前，其次剩余量最大的——前者要人动手，后者决定整批何时结束。

测试：`UploadProgressSamplerTests` ×10（纯计算，不需要 Docker）、
`UploadProgressQueryTests` ×8（需要 Docker）。无新增迁移，无新增配置项。

## 九、Agent 测试项目

上一节那个缺陷暴露的不是一行代码写错，而是 `AgentWorker` 这个文件从来没被测过。
补一个独立的测试项目：`src/tests/BackupMonitor.Agent.Tests`（已登记进 sln 的 tests 目录）。

**为什么不直接加进 `BackupMonitor.Infrastructure.Tests`**——它已经引用了 Agent 项目，
里面也确实有 7 个 Agent 相关的测试文件。但那个项目引了 Testcontainers 和 Npgsql，
无 Docker 环境下 118 条用例是红的。**红成常态之后没人会再去看它**，
Agent 的回归就是这么漏出去的。新项目只引 Agent 一个工程，
不引数据库、不引 Api、不引 Server.Setup，任何机器上 20 毫秒跑完并且全绿。

### 为了可测做的改动

- `ProgressReporter` 改成注入 `Func<CommandProgressRequest, CancellationToken, Task>` 发送委托，
  不再直接吃 `AgentApiClient`。后者是 sealed、方法非虚、构造还要 `HttpClient`，
  挡着这个类没法被测；而这里真正容易写错的是节流判断，跟 HTTP 一点关系都没有。
- `ChunkThrottle` 的等待时长拆成静态纯函数 `ComputeDelay(bytesPerSecond, sentBytes, elapsed)`。
  原来的写法要真的跑起 `Stopwatch` 和 `Task.Delay` 才验得了，等于验不了——
  而限速算错的表现是「传得慢」，所有故障里最不容易被发现的那一种。
- `ProgressReporter` / `ChunkThrottle` / `ExpandMissing` 由 private 提到 internal，
  配 `InternalsVisibleTo`。开到 internal 好过为了可测把实现细节变成公开 API。

### 顺带修掉的两个隐患

- **限速换算 int 溢出**：`kbps * 1024` 按 int 算，kbps 超过 2²¹ 就溢出，
  绕回来可能是个很小的正数——「限速 4 GB/s」实际变成限速 1 KB/s，
  而这种错误界面上完全看不出来，只表现为传得莫名其妙地慢。改成先转 `long` 再乘。
- **限速等待可能 TimeSpan 溢出**：`FromSeconds` 超出表示范围会抛 `OverflowException`。
  同一个文件刚因为一次 TimeSpan 溢出把所有上传打挂过，不给它第二次机会：
  秒数夹一个一天的上界。限速配错了应该表现为「等得久」，不是「备份失败」。

### 覆盖范围（31 条，全部不需要 Docker）

- `ProgressReporterTests` ×7 —— 第一块传完就上报、涨幅/间隔两个门槛各自生效、
  上报失败不搞挂上传、**节流判断自己抛异常也不漏出去**、取消照常抛出、百分比夹在 0–100。
- `ChunkThrottleTests` ×8 —— 没配/负数限速不等、kbps 换算、极大值不溢出、
  超速补等待、本来就慢不叠加、会话级平均而非每块独立、荒唐值不算到溢出。
- `ExpandMissingTests` ×7 —— 明细列表、闭区间范围、多段拼接、空列表 ≠ 没说、
  服务端没说时按大小全传、末尾不满块、空文件。
- `UpgradePackageOriginTests` ×9 —— 同 host:port 放行（scheme 和大小写不敏感）、
  换主机或端口拒绝、服务端地址解析不出来时拒绝、默认端口补齐后再比。

### 回归用例确实抓得住

把缺陷改回去验证过，不是写完就算：

| 改回的缺陷 | 转红的用例 |

## 十、保留策略：让它真的会清理（待办方案 C）

### 问题：配了一整套保留策略，却一份备份也不会被清掉

三件事凑在一起，结果是仓库无限增长：

- `RetentionCleanupWorker` 只处理 `retention_policy_id` 非空的任务，
  而任务表单里「保留策略」在高级折叠区、默认留空——按默认值建出来的任务永远不清理。
  「留空 = 永不清理」这个默认值是反的。
- `minimum_retention_days` 默认 30，语义是「不满 30 天一律不回收」，
  会直接压过「只留最近 N 份」。每天备份的话实际会攒到 30 份以上，配了「只留 3 份」也没用。
- 唯一的种子策略是一份 GFS（8 周 + 6 月 + 2 年），
  对「我就想留最近几份」这个绝大多数人的诉求属于过度设计，于是没人会去建策略。

还有第四件事：50% 回收熔断本身是对的，但它恰好挡住「第一次给一个已经攒了几十份的任务
配上保留策略」这个最常见的场景——那一次必然是大比例回收，被整体停手之后，
现象仍然是「配了策略一份不删」。

### 改法

- **V027 迁移**：两个天数的列默认值改成「最短保留 0 天 / 回收站 7 天」；
  预置三份策略（只留最近 3 份 / 只留最近 7 份 / 日备留 7 天 + 月末留 12 个月）；
  新增 `system_settings.default_retention_policy_id` 指向「只留最近 7 份」；
  把既有的未绑定任务一并绑到默认策略上——它们正是「永远不清理」的那批。
- **服务端兜底**：`BackupTaskService.CreateAsync` 在没选策略时绑默认策略。
  只在建任务时兜底，想要永不清理仍然可以在建完之后显式解绑。
  默认策略被删掉/配错时退回不绑定并告警，不让「建任务」整个失败；
  同时禁止删除当前的默认策略（409），否则之后新建的任务会重新掉回「永不清理」。
- **首次清理豁免熔断**：任务此前从没被清理过（没有任何备份集处于 recycle_bin / deleted）时，
  大比例回收放行并记一条 Warning。豁免只发生一次——本轮回收之后就有 recycle_bin 记录，
  下一轮再出现大比例回收就是真的配错了。回收先进回收站，7 天内可撤销。
- **表单收口**：策略表单只留「保留最近 N 份」和「删掉的先放回收站几天」两项，
  周/月/年和最短保留天数收进高级选项，并写清「最短保留天数会盖过份数设置」。
  任务表单的「不绑定」改写成「不绑定 —— 永不清理，仓库会一直涨」，新建时默认选中默认策略。

### 顺带修掉的一个时间炸弹

`AlertEscalationTests.真的漏了备份的任务告警仍然保持活动` 写死 `"0 2 * * *"`，
而实体默认时区是 `Asia/Shanghai`——每天中国时间 02:00~04:00 这两小时里，
上一次计划仍在 120 分钟宽限期内，判不出漏备份，这条用例必然失败。
改成相对当前时刻取「4 小时前的那一分钟」并显式钉在 UTC，任何时候跑都稳定。

### 验收

新建任务不填任何保留设置 → 默认绑「只留最近 7 份」→ 产生第 8 份备份后第 1 份自动进回收站，
7 天后物理删除，全程不需要管理员做任何配置。

测试：466 条全绿（新增 5 条：首次豁免、默认绑定 ×2、默认策略不可删、预置策略装好）。

## 十一、备份计划与顺序执行器（待办方案 A + B）

A 和 B 是同一件事的两半，因此共用一套机制、一起做。

### 问题

- **跨客户端的顺序执行做不到**：调度完全在客户端——Agent 从签名配置里解析各任务的 cron
  自己触发扫描，服务端没有任何备份调度器。A 机器无从知道 B 机器传完没有，
  于是「先备财务库、跑完再备 ERP」这种要求没有任何地方能表达。
- **批量备份的并发闸是个摆设**：`upload_batches.max_concurrent_clients`（默认 2）会存进库、
  历史页还显示成「2 客户端 × 1」，但没有任何调度逻辑读它——`BatchOperationService`
  是一次性把所有候选的上传指令全下发出去。真正在限流的只有「服务端按客户端限 2 条会话」
  和「Agent 串行执行指令」，多台客户端之间完全没有闸门。
- `max_concurrent_per_client` 更是个死字段：Agent 天生串行，这个值填几都一样。

### 改法：一套队列，两个入口

V028 建 `backup_plans` / `backup_plan_items`（编组与顺序）和
`execution_runs` / `execution_run_items`（一次执行与其中的每一项）。
计划到点产生一次 run，批量上传也产生一次 run，由同一个 `SequentialExecutionWorker` 推进：

1. 到点的计划产生执行（`scheduled_for` 上的唯一索引挡住重复触发与多实例竞态）；
2. 判定在跑的项是否终结——指令失败 / 上传会话终结 / 超时；
3. 按 `max_concurrent` 放行还没开跑的项，并发度 1 就是严格一个接一个。

「终结」的判定里，上传会话是主线：预检指令成功之后等这个任务的新会话，
committed 判成功，failed/cancelled/expired 判失败；宽限期内一直没有会话，
说明这次压根没有新备份要传，同样算成功并写明原因。

### 两个当时拍板的决定

- **双重触发做成互斥**：任务进了计划之后，`AgentConfigService` 下发配置时把它的
  `scanSchedule` 置空，任务表单里那一栏也换成「由备份计划 X 驱动」的只读说明。
  否则同一个任务一天会跑两次——一次 Agent 按 cron 触发，一次计划驱动。
  进出计划都会递增任务的 `config_version`，Agent 下一次心跳即感知。
  数据库上 `uq_backup_plan_items_task` 保证一个任务只能属于一个计划。
- **每项设超时，默认 4 小时（可配）**：超时即判该项失败、发一条告警、继续下一项。
  否则一台关机的客户端能让整晚的计划全部不执行。批量上传的单项超时放宽到 12 小时——
  那是人挑好候选点下去的历史大备份集，不该按夜间计划的节奏判超时。

### 顺带

- `max_concurrent_per_client` 从表、实体、DTO 和界面上一并删除。
- 批次详情的清单改成以队列为准：排队中的项此前根本不存在（没有指令就查不到），
  而并发闸的效果恰恰要靠「有几项在排队」才看得出来。

### 验收

含 3 个任务的计划设为每天 02:00 → 三项依次执行而不是同时开跑；
把中间那台客户端关机 → 它超时失败后第三项照常执行；
批量上传并发度设 2 → 任意时刻最多两项在动，其余排队。

测试：477 条全绿（新增 5 条顺序执行器用例 + 3 个新枚举域的对照）。

## 十二、备份集删除与回收站（待办方案 D）

### 问题

`AdminBackupController` 只有 list / detail / files / lock / unlock / quarantine / unquarantine / verify，
**没有任何删除接口**——想删掉一份误传的、或者一份确认不要了的备份，界面上无路可走。
另外两处小事同样每天被撞见：列表的备份时间用的是相对时间（「3 天前」），
精确值只藏在鼠标悬停的 title 里；详情页显示了仓库路径，但没有任何把它拿出来的手段。

### 改法

- `POST /backups/{id}/recycle` 移入回收站而不是物理删除，复用现有的 recycle_bin 状态与
  策略上的回收站天数（没绑策略时 7 天），误删还能捞回来；
  `restore-from-recycle-bin` 还原；`purge` 立即彻底删除。
- 三条守卫与保留清理判的是同一件事——已锁定 / 有生效中的保留锁 / 正在被恢复下载，
  一律 409。自动清理不敢删的东西，人在界面上点一下也不该能删掉。
- 「立即彻底删除」只对回收站开放：不可撤销的操作不该有从「可用」一键直达的路径。
  物理删除的三道路径守卫抽成 `RepositoryDirectory.DeleteUnderRoot`，
  与 RetentionCleanupWorker 共用同一份代码而不是各抄一遍。
- 列表的业务时间改成精确时间为主、相对时间为副；工具条加「回收站」直达按钮
  （它就是「状态 = 回收站」这一档，不另起一个页面）；详情页仓库路径旁加「复制路径」。

### 「打开目录」没做，是刻意的

管理界面是浏览器里的网页：它启动不了服务器上的资源管理器，也点不开 `file://` 链接
（Chrome / Edge 一律拦截）。做一个「服务端执行 explorer.exe /select」的接口技术上可行，
但那是开一个能在服务器上起进程的口子，且只有管理员正好坐在服务器控制台前才有意义。
推荐的组合是：复制路径按钮 + 把仓库根做成只读 SMB 共享，
路径直接显示成 `\服务器\repo\…`，复制出来粘到资源管理器就能用。

## 十三、暂停、恢复，以及让「出错」也能续传（待办方案 E）

### 问题

- `CommandType.PauseUpload` 有枚举值、连中文名都翻好了，全代码库零调用；
  `UploadStatus.Paused` 有定义，却被列在 `WritableStatuses` 里——
  就算把会话置成 paused 也拦不住客户端继续写，这个状态等于只是个标签。
- 「传输中」页面是纯只读表格，一个按钮都没有。白天发现某台机器正在把带宽占满时，
  唯一能做的是等它传完。
- **更要紧的一条**：Agent 遇到异常一律调 cancel 取消会话，暂存随后被清 → 下次从头传。
  也就是「断网能续传（会话还活着），出错不能续传」。6GB 传到 90% 出一次错就全部重来。
- 会话 3600 秒无分块写入即过期，对大文件偏短。

### 改法

- `paused` 从可写状态里拿掉，另设 `ActiveStatuses`（含 paused）用于并发额度与超时判定——
  暂停中的会话不能写，但仍然占着暂存空间和并发名额，两件事不能混为一谈。
- 新增 `POST /admin/upload-sessions/{id}/pause | resume | cancel`，
  「传输中」页面加对应按钮。恢复时把会话放回可写并重新下发一条上传指令，
  客户端凭幂等键拿回同一个会话，从缺哪块传哪块继续——和断网续传走同一条路。
- 新增 `POST /agent/upload-sessions/{id}/interrupt`：Agent 的异常收尾从「取消会话」
  改成「标记中断但保留会话与暂存」（停在 retry_wait）。**这一条的收益比暂停功能本身还大。**
- `upload_session_timeout_seconds` 3600 → 21600（V029）。它不是「一次上传最多能传多久」，
  而是「多久没有任何动静才认定它废了」：放宽的代价是废会话在库里多留一会儿，
  收窄的代价是真的重传一遍。

### 验收

传到一半点暂停 → 进度停住、写入被 409 拒绝、会话不被回收；点恢复 → 从断点继续；
人为制造一次上传错误 → 重试时只补缺的那几块，不从 0 开始。

测试：483 条全绿（新增 4 条删除/回收站用例 + 2 条暂停/中断续传用例）。

## 十四、恢复下载、登记窗口文案、入库硬链接（待办方案 F / G / H）

### F 恢复下载：大集合的断点续传

现状是「能力有一半，界面没引导过去」：整包 ZIP 是流式打包、无 `Content-Length`、
中断不能续，6GB 下到一半断了就得重来；而单文件下载**本来就支持 Range**，只是没人知道。

改法：

- 两条路径都补上 `Accept-Ranges` 头——单文件 `bytes`，ZIP `none`。
  不写这个头，下载工具会自己发 Range 请求、被 ZIP 路径当成普通请求全量重发，
  表现成「续传了但进度回到 0」，比直接说不支持更难排查。
- 签发下载令牌后列出**逐文件清单**：每个文件一个可续传的链接 + 单独复制，
  另有「复制全部链接（一行一个）」交给下载工具批量下。
  集合 ≥ 2GB 或 ≥ 50 个文件时，清单排在 ZIP 前面并标注「推荐」，
  ZIP 那一块明确写出「中断不能续传」。

方案里那条可选的 `restore_download` 指令（让 Agent 把备份拉回本机）**没有做**，
理由与方案一致：自动往生产机推数据的风险远大于收益。

### G 登记窗口：功能是对的，文案在骗人

窗口确实在起作用（关了就 401），但界面把两件事混成了一句话：
按钮写「开放登记 30 分钟」，旁边显示的却是安装默认的 24 小时窗口——
两个数字对不上，管理员自然怀疑它没生效。

改法：

- 部署状态接口新增 `enrollmentWindowOpen` / `enrollmentExtendMinutes` /
  `enrollmentWindowIsInstallDefault`。延长时长由服务端给出，界面不再自己写死一个数——
  数字对不上这类问题的根因就是同一个常量存在两份。
- 界面分开显示「当前窗口：开放中 / 已关闭，到期时间，（安装默认窗口，没人开过）」
  和「再开放 30 分钟」这个动作。
- 界面与部署说明都写清窗口的作用域：**只管新机器不带令牌的局域网登记**；
  已注册客户端走 mTLS 证书、带令牌的机器走令牌校验，都不受影响——
  窗口关着不会让任何已有客户端掉线。

### H 入库：同卷时用硬链接代替整份复制

`UploadCommitWorker` 把暂存文件整份复制进仓库，6GB 备份 = 6GB 读 + 6GB 写。
同卷 NTFS 时改用 `CreateHardLinkW`：一次元数据操作，瞬间完成。

为什么是硬链接而不是 `File.Move`：**暂存文件仍然在**（链接计数为 2）。
入库是多步过程（进仓库 → 写 manifest → 落库 → 原子重命名），中间失败都要能重试；
Move 走过之后暂存已经没了，重试无从谈起。共享同一份数据是安全的——
暂存文件在提交之后只会被删除、不会被改写，删掉暂存那个名字只是把链接计数减一。

跨卷、非 NTFS、非 Windows、目标已存在、权限不足时一律返回 false 回退到复制，
不抛异常：这是优化路径，它自己不能成为入库失败的原因。

顺带修了一处测试的注入点：`UploadCommitClosureTests` 的两个故障桩件此前只覆盖
`OpenStagedFileAsync`，而入库现在优先走硬链接、根本不打开暂存流——
同卷部署下那两次故障注入会静默失效，用例从此测不到它要测的东西。

### 验收

6GB 备份集下载中断后能接着下（走单文件 + Range）；
管理员看一眼就知道登记窗口什么时候关、关了会影响谁；
暂存与仓库配在同一个卷上时入库耗时接近 0，配在不同卷上时行为与从前一致。

测试：487 条全绿（新增 4 条硬链接用例）。
