## #1 · P0 · LAN Turnkey 模式下 Agent 无法通过认证

**位置**
[ServerInstaller.cs:215](../src/server/BackupMonitor.Server.Setup/ServerInstaller.cs:215)、
[AgentSystemController.cs:12](../src/src/BackupMonitor.Api/Controllers/AgentSystemController.cs:12)、
[ClientCertificateAuthenticationHandler.cs:64](../src/src/BackupMonitor.Api/Security/ClientCertificateAuthenticationHandler.cs:64)、
[LocalServerBootstrap.cs:167](../src/src/BackupMonitor.Api/Bootstrap/LocalServerBootstrap.cs:167)、
[AgentApiClient.cs:41](../src/agent/BackupMonitor.Agent/AgentApiClient.cs:41)

**证据链**

1. 服务端安装器写死监听明文 HTTP：`"Url": "http://0.0.0.0:5080"`，没有配置任何 HTTPS 端点。
2. 全部 Agent 业务端点要求客户端证书认证方案：`AgentSystemController`（心跳/配置）、`AgentCommandController`、
   `AgentUploadController`、`AgentPrecheckController` 均为
   `[Authorize(AuthenticationSchemes = ClientCertificateAuthenticationHandler.SchemeName)]`。
3. 该认证处理器只有三条取证书路径：Kestrel 直接终结 mTLS、可信代理透传 `X-Client-Verify`/`X-Client-Fingerprint`、
   开发回退头 `X-Client-Id`。
4. `LocalServerBootstrap` 在 Turnkey 下把 `Security:ClientAuth:AllowDevelopmentHeader` 强制置为 `false`，
   且该值通过最后加载的内存配置源写入，无法被环境变量覆盖。
5. Agent 把客户端证书挂在 `HttpClientHandler.ClientCertificates` 上，但 `BaseAddress` 是 `http://`。
   没有 TLS 握手，客户端证书永远不会被发送。

**后果**

匿名的注册接口能成功（客户端会被创建并签发证书），此后**心跳、配置同步、指令领取、预检、分块上传全部返回 401**。
即：批次 C/D/E 描述的「双击安装后自动上线」链路在默认交付形态下不成立。

当前唯一能跑通的组合是把服务端跑在 Development 环境（`AllowDevelopmentHeader=true`），
而那条路径只凭一个 `X-Client-Id` 请求头就认定客户端身份——局域网内任何人都能冒充任意客户端上传数据、领取指令。
也就是说现状是「要么不通，要么无客户端认证」。

**方案（推荐 A）**

*A. 让 Kestrel 直接终结 HTTPS + mTLS（同时解决 #5）*

- 服务端安装器生成自签服务器证书（SAN 覆盖机器名、FQDN 与全部局域网 IPv4），存入 `%ProgramData%\BackupMonitor\Server`，
  与 `server-secrets.json` 同级、同 ACL；证书有效期 2 年，维护模式提供「重新签发服务器证书」。
- `appsettings.Turnkey.json` 改为 HTTPS 端点，`Kestrel.ConfigureHttpsDefaults` 已有
  `ClientCertificateMode.AllowCertificate`，无需改动认证处理器。
- `/api/v1/agent/bootstrap` 增加返回服务器证书指纹与根证书 PEM；Agent 安装器把它写入 Agent 配置，
  运行时用 `ServerCertificateCustomValidationCallback` 做**指纹固定**校验（不是 `DangerouslyAcceptAny`），
  从而不依赖 Windows 证书信任链。
- 管理网页：安装完成页提供「导入根证书」一键操作与说明，避免浏览器告警劝退。
- 保留 `AllowInsecureTls` 开关仅供开发，默认 false。

*B. 备选：为 LanSimple 增加独立的 Agent 承载凭据*

登记成功时下发一次性高熵 client secret（服务端只存哈希），Agent 每次请求用
`clientId + timestamp + nonce + body hash` 做 HMAC 签名，新增一个认证 scheme；mTLS 保留给 Secure 模式。
改动面比 A 大，但不需要处理证书信任问题。

*C. 明确不采纳*：继续使用 `X-Client-Id` 头 —— 等同于没有客户端认证。

**验证**

1. 干净环境安装服务端与客户端；
2. 抓取一次 `POST /api/v1/agent/heartbeat`，确认返回 200 且服务端日志中的 `client_id` 来自证书而非请求头；
3. 手工构造一个不带证书、只带 `X-Client-Id` 的请求，必须返回 401；
4. 完成一次完整备份上传，`upload_sessions.status = committed`。

**工作量** 方案 A 约 1.5~2 天（含安装器证书生成与网页说明）。

## #2 · P0 · 分区表只建到 2027-01-01

**位置**
[V001__initial_schema.sql:394](../src/database/V001__initial_schema.sql:394)（`client_heartbeats`）、
[V001__initial_schema.sql:966](../src/database/V001__initial_schema.sql:966)（`audit_logs`）

两张表都是 `PARTITION BY RANGE`，只预建了 2026-07 至 2026-12 六个月分区，**没有 DEFAULT 分区**。
全仓 `.cs` 文件中没有任何创建分区的代码，尽管
[AgentHeartbeatService.cs:61](../src/src/BackupMonitor.Infrastructure/Services/AgentHeartbeatService.cs:61)
的注释写着「分区缺失时由数据库维护任务兜底」——该任务并不存在。

**后果（从 2027-01-01 00:00 UTC 起）**

- 心跳明细插入抛 `no partition of relation "client_heartbeats" found for row`，
  整个心跳事务回滚 → 所有客户端在网页上变成离线。对备份监控系统而言这是最坏的一类故障：
  以为在监控，其实全线失明。
- 审计日志写入同样失败。`DbAuditRecorder` 吞掉异常并只记一条错误日志
  （[AuditService.cs:120](../src/src/BackupMonitor.Infrastructure/Services/AuditService.cs:120)），
  所以登录仍然可用，但**审计从此静默停止**——比直接报错更危险。
- 客户端注册：审计写在注册事务内部，PostgreSQL 报错会把事务置为 aborted，注册随之失败。

**方案**

1. 新增迁移 `V009`：为两张表各建一个 `DEFAULT` 分区兜底（数据不丢，只是不再按月分离）：
   ```sql
   CREATE TABLE IF NOT EXISTS client_heartbeats_default PARTITION OF client_heartbeats DEFAULT;
   CREATE TABLE IF NOT EXISTS audit_logs_default PARTITION OF audit_logs DEFAULT;
   ```
   注意：有 DEFAULT 分区后，再 `ATTACH` 新月份分区需要扫描 DEFAULT 分区，数据量大时会加锁；
   因此维护任务要提前建，而不是等到当月。
2. 新增 `PartitionMaintenanceWorker`（或并入现有 `RetentionCleanupWorker`）：每天执行一次，
   保证「当前月 + 未来 3 个月」的分区存在，复用 `ScheduledLockService` 防止多实例重复执行。
3. `/health/db` 增加只读检查项：未来 30 天的分区是否齐备，缺失则 `Degraded`。
4. 对已投产实例：先手工建到 2027-06 再上代码。

**验证**

把系统时间/插入时间调到 2027-02，心跳与审计写入成功；停掉维护任务后 `/health/db` 变为 Degraded。

**工作量** 半天。

## #3 · P0 · 遥测三表零清理

**位置** [RetentionCleanupWorker.cs](../src/src/BackupMonitor.Infrastructure/Services/RetentionCleanupWorker.cs)
（只处理恢复请求、回收站备份集、任务保留策略）

| 表 | 写入频率 | 现状 |
| --- | --- | --- |
| `client_service_states` | 每次心跳 × 每个受监控服务 1 行 | 永不删除。1 客户端 × 5 服务 × 60 秒心跳 ≈ **7200 行/天/客户端** |
| `client_heartbeats` | 每次心跳 1 行 | 表注释写「原始数据保留 30 天」，无任何实现 |
| `agent_notifications` | 告警/备份完成时 | 有 `expires_at` 与索引，但没有任何地方删除过期行 |

叠加 #2（分区无法轮转），一年内数据库体积会成为主要故障源，且 `client_service_states` 上的
`idx_client_service_states_client` 会持续膨胀，拖慢客户端详情页。

**方案**

在 `RetentionCleanupWorker` 中增加一个每日清理阶段（可配置，写入 `system_settings`）：

- `client_service_states`：只保留每个 `definition_id` 的最近 N 条（默认 7 天），用
  `DELETE ... WHERE sampled_at < now() - interval` 分批删除（每批 5000 行，避免长事务）；
  更根本的做法是改成「当前状态快照表 + 状态变更事件表」，只在状态发生变化时写一行。
- `client_heartbeats`：按分区 `DROP PARTITION` 而不是 `DELETE`（与 #2 的维护任务合并，保留 30 天）。
- `agent_notifications`：`DELETE WHERE expires_at < now()`。

**验证** 造 10 万行遥测数据，跑一次清理，确认行数按策略下降且无长时间锁表。

**工作量** 半天（不含快照表重构）。

## #4 · P1 · 超级用户口令与应用角色口令相同

**位置** [ServerInstaller.cs:87](../src/server/BackupMonitor.Server.Setup/ServerInstaller.cs:87)

```csharp
await new PostgreSqlManager().InitializeAsync(
    payloadRoot, PostgreSqlDataDirectory, request.PostgresPort,
    postgresPassword,      // postgres 超级用户
    postgresPassword,      // backup_monitor_app 应用角色 —— 同一个值
    ct);
```

任何能读到应用连接串的主体（API 进程、`server-secrets.json`、诊断包）同时拿到了 postgres 超级用户口令。
虽然实例只监听 127.0.0.1，但这让「专用应用角色」这层隔离完全失去意义：应用侧的任意 SQL 注入或凭据泄露
都直接升级为数据库完全控制。

**方案**

- `LocalServerSecrets` 增加 `PostgresSuperuserPassword` 字段，与 `PostgresPassword` 分别生成；
- 连接串只使用应用角色口令；超级用户口令仅安装/迁移期使用，不进入运行时配置；
- 迁移完成后回收多余权限：`REVOKE ALL ON DATABASE backup_monitor FROM PUBLIC;`，
  应用角色只保留所需 schema 权限（当前迁移直接用应用角色执行 DDL，若要收紧需引入独立的 owner 角色，可放到后续迭代）。

**验证** 用应用角色口令尝试 `psql -U postgres` 登录，必须失败。

**工作量** 1 小时。

## #5 · P1 · 明文 HTTP 与缺失的安全响应头

**位置** [ServerInstaller.cs:211](../src/server/BackupMonitor.Server.Setup/ServerInstaller.cs:211)、
[Program.cs](../src/src/BackupMonitor.Api/Program.cs)、
[deploy/nginx/backup-monitor.conf:51](../deploy/nginx/backup-monitor.conf:51)

Turnkey 形态没有 nginx，Kestrel 直接以明文 `0.0.0.0:5080` 对局域网提供服务。传输的内容包括：
管理员登录口令、JWT access/refresh token、全部备份与客户端元数据。同网段任意主机可嗅探并重放。
`Cors:AllowedOrigins` 为空、`AllowedHosts: "*"`，这两项本身没问题，但都建立在传输安全成立的前提上。

另外全系统没有设置任何安全响应头：没有 `Content-Security-Policy`、`X-Content-Type-Options`、
`X-Frame-Options` / `frame-ancestors`、`Referrer-Policy`。nginx 配置里只有一条 HSTS，而 Turnkey 根本不经过 nginx。

**方案**

- 传输层随 #1 方案 A 一并解决（Kestrel 自签 HTTPS + Agent 指纹固定）。
- 新增 `SecurityHeadersMiddleware`（放在 `RequestIdMiddleware` 之后、静态文件之前），统一写入：
  `X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、
  `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'`。
  CSP 落地需要先做 #21 的内联事件处理器改造，可分两步：先加除 `script-src` 外的其余指令，
  改造完成后再收紧到 `script-src 'self'`。
- HTTPS 生效后再加 HSTS（自签证书环境下 HSTS 会放大误配代价，需在文档中说明）。

**工作量** 中间件 1 小时；HTTPS 部分计入 #1。

## #6 · P1 · 免令牌自动登记无法关闭

**位置** [LocalServerBootstrap.cs:156](../src/src/BackupMonitor.Api/Bootstrap/LocalServerBootstrap.cs:156)、
[Program.cs:45](../src/src/BackupMonitor.Api/Program.cs:45)

`BuildConfigurationValues` 返回的字典通过 `AddInMemoryCollection` **最后**加入配置管道，
优先级高于环境变量与 `appsettings.Turnkey.json`。其中三项被硬写死：

```csharp
["DeploymentMode"] = "LanSimple",
["LanMode:AutomaticEnrollment"] = "true",
["LanMode:PrivateNetworkOnly"] = "true",
```

后果：只要 Turnkey 安装过一次，就**没有任何配置手段能关闭免令牌自动登记**，也无法切回 Secure 模式。
这和文件自身注释声明的「显式配置 > 持久化 > 首次生成」优先级相矛盾——机密字段遵守了该优先级，
这三个策略开关没有。

结合免令牌登记的语义（[AgentRegistrationService.cs:52](../src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs:52)）：
任何接入私网的机器都能自助获得签名的客户端证书，进而上传任意数据、占满备份仓库、领取指令。
方案文档接受了这个取舍，但没有给出任何收敛手段。

**方案**

1. 三个策略键改为与机密同样的优先级：显式配置/环境变量 > 持久化 > 默认，即
   `configuration["LanMode:AutomaticEnrollment"] ?? persisted ?? "true"`；
2. 增加**登记窗口**：`LanMode:EnrollmentOpenUntil`（默认安装后 24 小时），窗口外的免令牌登记一律拒绝；
   管理网页提供「开放登记 30 分钟」按钮，供后续新装机器使用；
3. 网页「待办」页增加「最近自动登记的客户端」条目，即使自动放行也要让管理员看见；
4. 自动登记成功时写一条 `Info` 级告警（复用现有 `AlertingService`），便于事后追溯；
5. 保留 `Security:AllowLegacyCommandHmac=false` 与 `AllowDevelopmentHeader=false` 的强制写死——
   这两个是安全下限，不应可覆盖，但应在注释中说明为何与其它键处理方式不同。

**验证** 设置 `LanMode__AutomaticEnrollment=false` 重启，免令牌注册返回 401；窗口过期后同样返回 401。

**工作量** 半天。

## #7 · P1 · Agent 身份私钥保护不足

**位置** [AgentStateStore.cs:183](../src/agent/BackupMonitor.Agent/AgentStateStore.cs:183)、
[AgentInstaller.cs](../src/agent/BackupMonitor.Agent.Setup/AgentInstaller.cs)（`Directory.CreateDirectory(dataDir)`）

```csharp
private static byte[] Protect(byte[] bytes) =>
    ProtectedData.Protect(bytes, null, DataProtectionScope.LocalMachine);
```

`LocalMachine` 作用域 + `optionalEntropy = null`，意味着**本机任意用户的任意进程都能解密**。
而 `state.json`（内含 `ProtectedPrivateKey` 与 `ProtectedCertificatePfx`）落在
`%ProgramData%\BackupMonitor\Agent`，安装器只创建目录、未收紧 ACL，ProgramData 默认对 Users 组可读。

**后果** 工作电脑上的任意标准用户可以复制 `state.json`、在本机解出客户端私钥与证书，
冒充该客户端向服务端上传伪造备份、领取指令、读取配置。这直接抵消了 mTLS 的价值。

**方案**

1. 安装器对 `%ProgramData%\BackupMonitor\Agent` 应用 ACL：断开继承，只保留 SYSTEM 与 Administrators
   完全控制（与服务端 `ApplySecretAcl` 同一套逻辑，可提取到共享工具类）；
2. `Protect/Unprotect` 传入固定的应用 entropy（例如由安装时写入的实例标识派生），提高误用成本；
3. 更彻底的做法：私钥改为存入机器级 CNG 密钥容器（`CngKey.Create` + `MachineKey` + 非导出），
   证书用 `X509KeyStorageFlags.MachineKeySet | NonExportable` 导入本机存储，`state.json` 只存指纹。
   这样即使文件被复制也无法离机使用。
4. 卸载时清理密钥容器/证书存储条目。

**验证** 以标准用户身份读取 `state.json` 必须被拒绝；用另一台机器上的副本无法完成 mTLS 握手。

## #9 · P1 · CA 与密钥文件的配对失效，以及锁文件残留

**位置** [LocalServerBootstrap.cs:67](../src/src/BackupMonitor.Api/Bootstrap/LocalServerBootstrap.cs:67)、
[:227](../src/src/BackupMonitor.Api/Bootstrap/LocalServerBootstrap.cs:227)

**9a · CA 静默作废**
代码只防了「有 secrets、无 CA」这一个方向。反方向没有保护：若 `server-secrets.json` 丢失而
`client-ca.pfx` 仍在，则 `firstCreation = true` → 生成全新的随机 `ClientCaPassword` → 因 CA 文件存在而跳过生成
→ 运行时 `CertificateAuthority` 用错误口令加载 PFX 失败 → **全部 Agent 的 mTLS 报废，且要重新审批**。

**9b · 锁文件残留导致永久无法启动**
`AcquireCrossProcessLock` 用 `FileMode.CreateNew` 创建锁文件，`Dispose` 时删除。进程崩溃、断电或
被强制结束后锁文件残留 → 下次启动重试 15 秒后抛出 `IOException` → **服务再也起不来**，
而错误信息完全看不出问题在一个 `.lock` 文件上。SCM 的失败重启策略只会不断重复失败。

**方案**

- 9a：启动时校验 CA 文件与 secrets 的配对关系。若 CA 文件存在但当前口令无法打开，直接抛出带处置指引的
  `InvalidOperationException`（提示：恢复 `server-secrets.json`，或显式确认后重建 CA 并重新登记全部客户端）。
  同时在维护模式中提供「导出/导入服务端密钥包」（secrets + CA 打包），并在部署文档明确「这两个文件必须一起备份」。
- 9b：锁改为 `new FileStream(lockPath, FileMode.OpenOrCreate, FileAccess.ReadWrite, FileShare.None)`——
  文件残留不影响下次获取，只有活着的持有者才会阻塞；或改用命名 Mutex（`Global\BackupMonitorBootstrap`）。
  超时后的异常消息中明确写出锁文件路径与处置方式。

**验证** 删除 secrets 保留 CA，启动必须给出明确错误而不是生成新 CA；强杀进程后再次启动必须正常。

**工作量** 2 小时。

## #14 · P2 · 心跳写放大与缺失的上报上限

**位置** [AgentHeartbeatService.cs:96](../src/src/BackupMonitor.Infrastructure/Services/AgentHeartbeatService.cs:96)、
[:159](../src/src/BackupMonitor.Infrastructure/Services/AgentHeartbeatService.cs:159)、
[:240](../src/src/BackupMonitor.Infrastructure/Services/AgentHeartbeatService.cs:240)

每次心跳（默认 60 秒/客户端）执行：

- `client_disks` 全量 `ExecuteDelete` + 逐行 Insert；
- `client_user_sessions` 全量 `ExecuteDelete` + 逐行 Insert；
- 每个受监控服务插一行 `client_service_states`；
- 一行 `client_heartbeats`；
- 随后 `EvaluateResourceAlertsAsync` 对 CPU、内存、每块源盘各执行一次 `RaiseAsync` 或 `RecoverAsync`——
  **即使从来没有过任何告警，每次心跳也会执行 3 次以上 UPDATE**。

50 台客户端就是持续的写入与 WAL 压力，且大部分行内容与上一次完全相同。

另外没有对 `request.Disks`、`ServiceStates`、`UserSessions` 的条数做上限校验，

**方案**

- 磁盘与会话改为按业务键 upsert（`ON CONFLICT ... DO UPDATE`）+ 删除本次未上报的行，
  避免每次删光重插；或先比对内容哈希，无变化时只更新 `sampled_at`；
- `client_service_states` 改为「状态变化才写一行」，当前状态放快照列（与 #3 的重构合并）；
- `RecoverAsync` 先按 `alertKey` 查是否存在活动告警，无则直接跳过；
- DTO 上加 `[MaxLength]` 或在服务层校验条数上限（磁盘 64、服务 128、会话 128），超限截断并记一次警告；
- 心跳间隔从 `system_settings` 读取，允许运维按规模调大。

## #17 · P2 · 签名规范化脆弱

**位置** [AgentSignatureCanonicalizer.cs:14](../src/src/BackupMonitor.Shared/Security/AgentSignatureCanonicalizer.cs:14)

两个隐患：

1. `CommandPayload` 用 `expiresAt.ToString("O")` 参与签名。`DateTimeKind` 一旦两端不一致
