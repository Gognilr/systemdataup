# 运维可见性与自愈能力审查 2026-09-10

## 审查角度

不看代码风格，不看功能有没有，只问一句话：

> **作为管理员，什么时候我会不知道出事了？出事了有没有人管？**

起因是现场的一个真实场景：卸载重装了一套新服务端，数据库还是原来那个，
开机后管理页面上出现一屏「未按计划产生备份」——指向的是六天前那个周五。
管理员并不是被通知到的，是**碰巧打开网页看见的**。

这个「碰巧」就是本轮审查的主线。

## 结论摘要

**告警的「判定层」做得相当扎实，缺的全在「送达层」和「自愈层」。**

系统里有 19 类告警、11 个后台工作器，连「客户端掉线」「服务端磁盘要满」这种
「什么都没发生」型故障都有主动巡检。但是：

- 新装的系统**默认一条通知都不发**，告警只活在网页里；
- 服务端**没有常驻界面**，关掉窗口就什么都看不见；
- 客户端托盘的绿灯**只代表 Windows 服务在跑**，不代表备份在工作；
- 这套备份系统**自己没有备份**。

## 一、本轮已修

### 漏备份巡检在服务端启动前的时刻上翻旧账

`MissedBackupWorker` 原先只有一道「任务刚建出来不算漏」的守卫
（`now - task.CreatedAt < grace`），防的是新建任务，防不住**新装的服务端**。

重装 / 迁移 / 整夜停机之后，第一轮巡检会把服务端根本没在运行的那段时间里
每一次到点都翻出来判一遍——而那段时间没有服务端在下发指令，
这些告警没有任何人能处理，也不代表今天有什么问题。

**修法**：新增 `ServerStartedAtUtc`（worker 由 DI 在主机启动时构造，构造时刻即启动时刻），
判据是**整个「到点 + 宽限期」窗口**都落在启动之前才跳过：

- 上周五 08:00 到点、10:00 过完宽限期，服务端今天才装好 → 跳过；
- 服务端 08:30 重启、10:00 才到期限 → 照旧判定，短暂重启不吞真实的漏备份。

顺带修掉告警正文里写死的宽限期配置值（固定「多等了 120 分钟」，
而实际可能已经过去六天），改为真实时长。

回归测试：`服务端启动前的计划时刻不在开机第一轮里报漏备份`。

## 二、缺陷清单

### A 级：会丢数据或整体停摆，而且没人告诉你

#### A1. 这套备份系统自己没有备份

配置备份包（`.bmbp`）的内容是 `server-secrets.json` + `client-ca.pfx` +
`server-certificate.pfx` + **整库 pg_dump**
（`ServerMaintenance.ExportBackupPackageAsync`，src/server/BackupMonitor.Server.Setup/ServerMaintenance.cs:295）。
这一个包等于整个系统的命。

现状：

- **只有服务管理台上一个手动按钮**。28 个 API 控制器里没有任何对应端点，
  远程管理的人没有入口，必须人肉坐到服务器前面点。
- **没有计划、没有定时、没有提醒**，界面上没有「上次导出于 N 天前」。
- 从没导出过也不会有任何告警。

后果：服务器系统盘挂掉 → 仓库里的备份文件可能还在，但**哪个文件属于哪台机器、
哪个任务、哪一天，全在库里，一起没了**；同时 client-ca 没了，所有 Agent 身份作废，
必须逐台重装重新登记。

#### A2. PostgreSQL 崩了没人拉起来，而界面还是绿灯

| 服务 | 开机自启 | 崩溃重启 |
| --- | --- | --- |
| BackupMonitor.Server | `delayed-auto`（ServerInstaller.cs:463） | ✅ `restart/5s,15s,60s`（ServerInstaller.cs:474） |
| BackupMonitor.PostgreSQL | `pg_ctl register -S auto`（PostgreSqlManager.cs:490） | ❌ **没有** |
| BackupMonitor.Agent | `delayed-auto`（AgentInstaller.cs:556） | ✅ `restart/5s,15s,60s`（AgentInstaller.cs:559） |

`pg_ctl register` 不设恢复动作，仓库里也没有任何地方给它补 `sc failure`。

之所以是 A 级而不是 B 级：**API 服务不会跟着死**。服务管理台上
BackupMonitor.Server 依然绿灯「运行中」，客户端托盘也全绿，
实际上所有备份、所有页面全废。这是最坏的一种故障——看着健康的死亡。

#### A3. 磁盘「快满了」会报警，磁盘「整个不见了」反而不报警

`SystemWatchdogWorker.RunStorageSelfCheckAsync`：

- src/src/BackupMonitor.Infrastructure/Services/SystemWatchdogWorker.cs:223 —
  解析仓库/暂存根目录抛异常（路径被删、NAS 掉线、权限丢了）→
  `LogWarning` 然后 `return`，**本轮磁盘自检整个跳过，不产生任何告警**。
- 同文件 :241 — `drive.IsReady == false`（外挂盘 / 网络盘掉线）→ `continue`，同样无声。

与漏备份是**同一族的病**：失败模式是「什么都没发生」，
于是没有任何代码路径被触发。可用率 14% 会响，盘没了不响。

#### A4. 保真度做到了，可用性完全没做

入库前的端到端哈希核对做得很扎实（详见第三节），但它证明的是
**「仓库里的字节 = 客户端当时读到的字节」**，不是**「这个文件能用」**。

全仓库 grep 过 `.bak` 文件头 / MTF-TAPE 魔数 / zip 完整性测试 / `RESTORE VERIFYONLY`
——**一处都没有**。没有任何一行代码看过备份文件的内容长什么样。

具体的失败场景：

> U8 那天的备份跑了一半，SQL Server 中断了 / 磁盘写满了，留下一个残缺的 `.bak`。
> 客户端老老实实算了它的哈希，服务端老老实实收下、比对通过、入库、绿灯，
> 之后每 24 小时还认认真真复查一遍——**一份坏备份，被完美地保存和守护了三年**。
> 直到某天真要恢复，才发现它从来就打不开。

与 A1 是同一类问题：**平时完全看不出来，需要用的那天才发现没用。**

### B 级：出事了有记录，但没人会看见

#### B1. 全新装完的系统，默认一条通知都不发

`AlertingService.CreateDeliveriesForAsync`
（src/src/BackupMonitor.Infrastructure/Services/AlertingService.cs:306）
第一件事是读 `system_settings` 里的通知配置，**这行不存在就直接 return**。
邮件 / 企业微信 / 钉钉三个渠道都要管理员手动配。

新装的系统没人配过 → 所有告警只活在网页和客户端托盘气泡里，
而且**没有任何地方提示「你还没配通知渠道」**。

现场那次靠打开网页才发现告警，不是偶然，是当前设计的必然。

#### B2. 没有日报

报表全是拉取式（`AdminReportController` 清一色 `HttpGet`），没有任何定时推送。

对备份产品来说日报比告警更重要：**告警只在坏的时候响，日报证明这套系统本身还活着**。
现在服务端整个死了不会有任何告警——因为发告警的就是它。

#### B3. 客户端托盘的绿灯不代表备份在工作

`TrayApplicationContext.RefreshStatusAsync`
（src/agent/BackupMonitor.Agent.Tray/TrayApplicationContext.cs:82）
只读 Windows `ServiceController` 的状态，**从不读 Agent 自己的 state.json**——
而 `LastError`、上次心跳、上次成功备份、证书状态全在那里面。

后果：Agent 服务正常跑着，但连不上服务端 / 证书被拒 / 一直登记失败 /
干脆一个任务都没配——托盘照样绿色「运行中」。

#### B4. 服务端没有托盘

全仓库只有一个 `NotifyIcon`，在 Agent.Tray 里。服务端那个窗口是安装器兼服务管理台，
关掉就什么都看不见。

单独看是体验问题，跟 B3 合起来是**结构性盲区**：服务端死了，
服务端这边没界面看得见，客户端那边全是绿灯，通知渠道又默认没配。三重静默叠加。

好消息是数据源现成：`/health` 与 `/health/db` 端点已经有了（Program.cs:465、:473）。

#### B5. 服务管理台按钮不跟随服务状态

按钮可用性只跟「是否正忙」和「是否已安装」走
（`SetBusy` / `SetMaintenanceEnabled`，SetupForm.cs:679）。

服务状态其实每 2 秒刷新一次（`RefreshServiceStatus`，SetupForm.cs:817），
但拿到 `serverRunning` 之后只用来决定哪个按钮染成蓝色主按钮
（`UpdatePrimaryButton`，SetupForm.cs:407），**没有任何一处按状态禁用按钮**。

后果不止是不好看：`sc start` 一个已运行的服务返回 1056，
`ProcessRunner` 默认 `throwOnError: true` → 弹一个红叉「启动失败」。

#### B6. 备份「可疑」时的处置是拒收，而不是收下并标记

`ValidateSizeThresholds`（AgentPrecheckService.cs:408）判出 `SizeAbnormal` 之后，
候选的 `PrecheckStatus` 就不是 `Passed` 了，于是：

- `UploadSessionService.cs:141` → 直接抛 `UPLOAD_NOT_PERMITTED` 409
- `BatchOperationService.cs:159` → 批量上传时跳过，记一句「预检未通过」

也就是说：**今天的备份只有平时的 10% 大小，系统的反应是「一个字节都不收」**。

对备份产品来说这个方向很可能是反的——**一份可疑的备份，比没有备份好**。
正确的处置应该是「收下 + 标记为可疑 + 告警」，把「这份能不能用」的判断权交给人，
而不是替人决定「这份不要了」。

连带效果：不收 → 这一天仓库里是空的 → `LastSuccessAt` 不更新 →
漏备份巡检过了宽限期再报一条 `backup_missed`。同一件事报两条不同的告警，
而其中一条（「未按计划产生备份」）会把人引向错误的方向——
备份其实产生了，只是被系统拒收了。

另外三个阈值字段（`min_total_bytes` / `max_total_bytes` / `min_file_count`）
建表时就是可空、无默认值——**不配就等于完全不检查**。而且是固定死数，
不是从历史学出来的基线，抓不到最有价值的那个信号：
「今天这份比过去 30 天的中位数小了 90%」。

### C 级：会在某个时间点突然爆掉

#### C1. 服务端 TLS 证书：2 年、不续签、不提醒、重签要全网重装

- 有效期 2 年（`ServerCertificateFactory.ValidityYears`，
  src/src/BackupMonitor.Api/Bootstrap/ServerCertificateFactory.cs:15）
- 启动时只检查文件在不在（LocalServerBootstrap.cs:94），过期照样加载照样用
- Agent 只按指纹校验（AgentApiClient.cs:225），**过期了照样连得上**
- 但管理网页会开始报证书过期；而一旦点「重新签发服务端证书」，
  指纹就变了，**所有 Agent 都得重跑客户端安装器更新指纹**——目前没有指纹轮换机制

#### C2. 客户端 CA：10 年、不续签、不提醒，且到期前会先静默缩水

- 有效期 10 年（`GenerateClientCa`，LocalServerBootstrap.cs:430）
- 客户端证书默认 365 天，但签发时会被 CA 的 `NotAfter` 截断
  （CertificateAuthority.cs:53-55）——第 9 年起签出来的客户端证书会越来越短，
  没有任何提示；到第 10 年，续签只能签出已经过期的证书，全体 Agent 同时失效

#### C3. Agent 版本漂移无提醒

升级只有一个手动批量下发接口（`AdminAgentUpgradeController`，单个 `HttpPost`），
没有「这台机器还在旧版本」的任何提示。漏装一台，系统不会说话。

### D 级：小刺，但都是同一类

- **D1. 服务端日志没有单文件大小上限**：appsettings.json:22 只配了
  `rollingInterval: Day` + `retainedFileCountLimit: 30`，没有 `fileSizeLimitBytes` /
  `rollOnFileSizeLimit`。Serilog 默认 1GB 封顶后**当天日志静默停写**
  （排障时最需要日志的那天，日志没了），最坏 30 天 × 1GB = 30GB。
- **D2. 托盘自启是 HKCU Run 键**（AgentInstaller.cs:567），只对安装时那个登录用户生效，
  换个账号登录就没有托盘；用户手动关掉后也没有守护把它拉回来。

## 三、已经具备的能力

避免重复造，也避免把「已经做好的」当成缺口再提一遍：

- **主动巡检**：客户端离线判定 + 服务端磁盘预警（`SystemWatchdogWorker`），
  不等任何人上报
- **入库前的端到端哈希核对**（这是全系统最扎实的一条链，值得单独记一笔）：

  | 环节 | 谁算 | 算什么 | 出处 |
  | --- | --- | --- | --- |
  | ① 预检 | **客户端** | 读真实源文件算 SHA256，随清单上报，服务端存为权威基准 | BackupScanner.cs:324 |
  | ② 传输 | 两端 | 每个分块 `expected_hash` / `server_hash` | `upload_chunks` |
  | ③ 入库前 | **服务端** | 从落盘文件**整份重算**，与①比对 | UploadCommitWorker.cs:178 |
  | ④ 清单 | 服务端 | manifest 自身也算哈希存档 | 同上 :357 |
  | ⑤ 入库后 | 服务端 | 定期重读仓库文件重算比对 | `BackupReverifyWorker` |
  | ⑥ 恢复前 | 服务端 | 下载前再校验一次 | VerificationWorker.cs:245 |

  第③步有两个设计细节值得保留：一是**比对通过才算备份完成**，
  不一致直接 `FILE_HASH_MISMATCH`，**一个字节都不进仓库**；
  二是这个比对刻意放在**创建任何仓库目录之前**，失败路径不留垃圾。
  因此不存在「先入库、再核对、发现不对已经晚了」的窗口。

  它对「扫描之后源文件又变了」也免疫：上传读的是文件当前的字节，
  落地哈希就是当前内容的哈希，与预检基准不符一样拦下。**失败安全。**

- **生命周期推进**：上传会话 / 指令的过期状态转移 + 暂存清理（`LifecycleExpiryWorker`），
  挡住了「永久 uploading 会话把客户端锁死在 409 → .part 文件填满暂存盘 → 全体 507」
  这条完整故障链
- **数据校验**：仓库与数据库对账（`RepositoryReconcileWorker`）、
  备份集定期重校验（`BackupReverifyWorker`）、恢复前校验（`VerificationWorker`）
- **保留策略熔断**（`retention_breaker_tripped`）：防止清理策略配错把备份删光
- **告警机制**：按 `alert_key` 去重聚合、等级提升推送、长期未恢复按间隔重发、
  静默规则（`AlertingService`）
- **客户端证书自动续签**：服务端在心跳响应里对剩余 ≤30 天的置
  `CertificateRenewalRequired`（AgentHeartbeatService.cs:236），
  Agent 收到立刻续（AgentWorker.cs:300、:748），并提前 30 天告警、7 天内升 Critical。
  **这是全系统唯一一条完整的证书生命周期闭环**
- **客户端自动重连**：连接层失败固定 10 秒退避重试（AgentWorker.cs:332），
  服务端恢复后最迟约 10 秒重连；连续失败还会触发局域网地址重发现
  （要求实例 ID 与 TLS 指纹都匹配）
- **健康检查端点**：`/health`、`/health/db`
- **SCM 崩溃重启**：Server 与 Agent 两个服务已配

## 五、明确不做的事

记录下来，避免以后重复提出。

### 恢复演练（定期抽样实际恢复验证）—— 本轮决定不做

提出过的形态：定期抽一份备份实际恢复一遍，并在 `backup_sets` 上记录
「上次验证恢复于」，界面提示「这个任务的备份从来没有人成功恢复过」。

**不做的理由**：服务端要真正验证一份 U8 备份能不能用，等于要拉起一个
SQL Server 实例做实际还原——这已经超出「备份采集与监控」的产品边界，
运行成本和现场复杂度都不成比例。

**替代方案**：原计划用 A4 的「结构快检」拿大部分收益，但那一项也已决定不做（见下）。
最终的兜底是 R16 的历史基线大小告警——它抓的是同一类信号里最有价值的那部分：
「备份跑了但是空的 / 只剩十分之一」。

### 备份文件的结构快检（A4）—— 2026-09-10 决定不做

提出过的形态：入库时顺带检查 `.bak` 文件头 / 压缩包完整性 / 0 字节与尾部截断，
抓「哈希对得上但文件根本打不开」的坏备份。

**不做的理由**：`.bak` 的结构判定要靠现场真实样本才敢写，误报的代价是让人不再相信
这个标记；而历史基线大小告警（R16）已经覆盖了同一类信号里最有价值的那部分。

**残留风险**：A4 描述的那个场景仍然成立——一份哈希完整但内容损坏的备份，
系统会绿灯保存并长期守护，直到真要恢复那天才发现打不开。**这是明知并接受的风险。**

### 配置备份的自动化（A1 的一半）—— 2026-09-10 决定只做手动

导出保持手动触发，不做定时自动导出与保留策略，默认落点在数据目录旁。
保留下来的是「远程也能导出」的 API 入口和「上次导出于 N 天前」的提醒。

**残留风险**：默认落点与数据同机同盘，服务器系统盘挂掉时两者一起没；
异地副本依赖管理员自己把 `.bmbp` 拷走。

## 六、建议动手顺序

见 [整改清单-2026-09-10.md](./整改清单-2026-09-10.md)。

一句话版本：**A2 + A3 + B5 先一起做掉**（都是小改，加起来半天不到），
然后 **A1 单独一轮**（最大的洞，值得单独设计：导出到哪、留几份、怎么提醒），
托盘（B3 + B4）作为第三轮。
