## 【共通前置】

```
## 项目背景

BackupMonitor：局域网内部使用的轻量级集中备份采集与监控系统，包含服务端、Windows Agent、
托盘程序和两个双击安装器。典型现场是用友 U8 / OA 的数据库备份文件采集与集中监控。

技术栈与结构：
- .NET 8 + PostgreSQL + EF Core（Npgsql），解决方案 src/BackupMonitor.sln
- 服务端四层：src/src/BackupMonitor.{Api,Infrastructure,Core,Shared}
- 客户端：src/agent/BackupMonitor.{Agent,Agent.Tray,Agent.Setup}
- 服务端安装器：src/server/BackupMonitor.Server.Setup（内置 PostgreSQL payload）
- 数据库迁移：src/database/V001~V035__*.sql，由安装器的 MigrationRunner 顺序执行并记 checksum。
  新增迁移从 V036 起编号。
- 管理控制台：wwwroot 下原生 ES module + 三个 CSS 文件，零构建、零外部依赖
- 后台工作器 11 个，均为 BackgroundService + scheduled_locks 数据库锁的单实例模式
- 两种部署形态：Secure（nginx 终结 TLS/mTLS）与 LanSimple/Turnkey（安装器一键部署）

## 产品定位（很重要，决定取舍方向）

这是**备份工具**，不是合规管控系统。每加一个流程/开关/审批之前先问一句：
它是否服务于「数据会不会丢」「丢了能不能发现」。不服务于这两条的管控流程不要主动加。

对应地，凡是「可疑就拒收 / 可疑就阻断」的设计一律要重新想一遍：
**一份可疑的备份，比没有备份好。** 正确的处置通常是「照收 + 标记 + 告警」，
把判断权交给人，而不是替人决定不要了。

## 硬约束

1. 代码注释与用户可见文案一律中文。注释写「为什么这么做」，不写「这行在做什么」；
   踩过的坑要把坑本身写进注释（现有代码大量如此，照着来）。
2. 匹配现有代码风格：BusinessException / ApiResponse<T> 封装、EnumMapping 的 snake_case、
   AsNoTracking + 投影的查询写法、工作器的 scheduled_locks 单实例模式。
3. 机密（数据库口令、JWT 密钥、签名私钥、CA 口令）绝不写入任何 appsettings*.json、源码、
   日志、接口响应或客户端安装包。
4. 不新增第三方依赖，除非提示词里明确允许。
5. 不扩大范围。只做当前批次明确要求的事。发现别的问题记下来，在报告末尾列出，不要顺手改。
6. 不要执行任何 git 操作（commit / push / reset / checkout / clean / stash）。
   版本控制由项目主人自己管理。也不要在报告里讨论仓库管理或代码托管平台。
7. 不得为了实现功能而削弱已有的 mTLS、指令签名、哈希校验、路径安全或数据库事务边界。
8. 客户端支持的最低系统是 Windows Server 2012 R2，不要提出更低系统的兼容方案。
9. 项目尚未进入生产，部署方式是快照全新安装。不需要考虑存量升级顺序与向后兼容。

## 批次一 · 服务与磁盘的自愈（R1 + R2 + R3）

```
读 docs/整改清单-2026-09-10.md 的 R1、R2、R3 三节，以及
docs/REVIEW-2026-09-10-运维可见性与自愈.md 的 A2、A3、B5 三节。

三件小事，共同点是「故障已经发生但系统一声不响」。

### R1 — PostgreSQL 加崩溃恢复动作

现状：BackupMonitor.Server 与 BackupMonitor.Agent 两个服务都配了
sc failure reset= 86400 actions= restart/5000/restart/15000/restart/60000 + failureflag 1，
只有 PostgreSQL 没有——pg_ctl register 不设恢复动作，仓库里也没有任何地方补。

后果：库进程崩了没人拉起来，而 API 服务不会跟着死，服务管理台上
BackupMonitor.Server 依然绿灯「运行中」，实际上所有备份和页面全废。

改：PostgreSqlManager.EnsureServiceRegistrationAsync 在 pg_ctl register 之后补同样的
sc failure / failureflag。注意升级路径：已存在的服务（老装机）走「修复 / 升级安装」时
也要打上，不能只在新建分支里加。
顺带在服务管理台的「运行诊断」里显示两个服务各自的恢复动作配置。

验收：sc qfailure BackupMonitor.PostgreSQL 能看到三档重启；
taskkill 掉 postgres 进程后能自行拉起。

### R2 — 仓库 / 暂存盘不可达要报警

现状：SystemWatchdogWorker.RunStorageSelfCheckAsync 里有两条静默路径：
- 根目录解析抛异常（路径被删、NAS 掉线、权限丢了）→ LogWarning 然后 return，
  本轮磁盘自检整个跳过，不产生任何告警
- drive.IsReady == false（外挂盘 / 网络盘掉线）→ continue，同样无声

也就是「磁盘快满了」会报警，「磁盘整个不见了」反而不报警。

改：这两种情形都 RaiseAsync 一条 Critical。
关键点：用与现有 server_storage_low **不同的 alert_key**——
「盘没了」和「盘快满了」是两件事，共用键会互相覆盖。恢复正常时 RecoverAsync。
测试补两条：路径不存在、盘未就绪。

### R3 — 服务管理台按钮跟随服务状态

现状：SetupForm 的按钮可用性只跟「是否正忙」和「是否已安装」走（SetBusy /
SetMaintenanceEnabled）。服务状态每 2 秒刷新一次（RefreshServiceStatus），
但拿到 serverRunning 之后只用来决定哪个按钮染成蓝色主按钮（UpdatePrimaryButton），
没有任何一处按状态禁用按钮。
后果：服务运行中点「启动服务」→ sc start 返回 1056 → ProcessRunner 默认
throwOnError: true → 弹一个红叉「启动失败」。

改：运行中禁用「启动服务」；已停止禁用「停止服务」「重启服务」「打开管理网页」。
两条原则不能违反：
- 忙碌态优先级高于状态态，SetBusy(true) 期间一律禁用
- **状态读取失败时保持全部可用**——读不到状态不该把出路一起藏起来
  （与客户端托盘 catch 分支同一条原则，那里有注释可参考）
```

## 批次二 · 配置备份包的入口与提醒（R4）

```
读 docs/整改清单-2026-09-10.md 的 R4 节与 docs/REVIEW-2026-09-10-运维可见性与自愈.md 的 A1 节。

配置备份包（.bmbp）= server-secrets.json + client-ca.pfx + server-certificate.pfx +
整库 pg_dump，等于整个系统的命：它丢了，仓库里的备份文件即使还在，
「哪个文件属于哪台机器、哪个任务、哪一天」也全没了，同时所有 Agent 身份作废。

**范围已定板，不要扩大**：导出保持手动触发，**不做定时自动导出，不做保留策略**，

本批次只做两件事——入口和提醒：

1. 服务管理台的导出对话框（SetupForm.ExportBackupPackageAsync 里的 SaveFileDialog）
   预填 InitialDirectory 到数据目录旁的固定子目录，不存在则创建；文件名沿用现有格式。
2. 新增 API 端点：手动触发导出 / 查询上次导出时间与结果 / 下载最近一份。
   **这是本批次最主要的价值**——远程管理的人现在完全没有入口，必须坐到服务器前面点。

   导出逻辑本身在 ServerMaintenance.ExportBackupPackageAsync（属于安装器工程），
   API 侧要么复用要么按同样口径重写，**不要写出两套会分家的导出格式**。
3. 概览页显示「上次配置备份：X 天前」，从没导出过时显著提示。
4. 新增告警 config_backup_overdue：超过 N 天（默认 30）没成功导出 → Critical。
   手动模式下这是唯一的兜底，没有定时任务替人记着这件事。

验收：远程通过管理页面就能导出并下载一份可用的 .bmbp；超过阈值没导出过时
概览页和告警中心都能看见。

## 批次三 · 可疑备份的处置与大小基线（R15 + R16）

```
读 docs/整改清单-2026-09-10.md 的第六批（R15、R16）与
docs/REVIEW-2026-09-10-运维可见性与自愈.md 的 B6 节。

### R15 — 「可疑」时收下并标记，不再拒收

现状：ValidateSizeThresholds 判出 SizeAbnormal 后候选的 PrecheckStatus 不是 Passed，
于是 UploadSessionService 抛 UPLOAD_NOT_PERMITTED 409、BatchOperationService 直接跳过。
也就是「今天的备份只有平时 10% 大小」→ 系统的反应是「一个字节都不收」。

改为：正常上传入库 → 备份集标记「大小可疑」→ 保留现有 size_abnormal 告警。
判断权交给人，不要替人决定这份不要了——**一份可疑的备份，比没有备份好**。

顺带消掉一个连带效果：现在被拒收的那一天 LastSuccessAt 不更新，过了宽限期
MissedBackupWorker 还会再报一条 backup_missed——同一件事报两条，而且其中一条
（「未按计划产生备份」）把人引向错误方向：备份其实产生了，是被系统拒收了。

验收：把某任务的 min_total_bytes 设成大于实际备份的值，这一份仍然能入库、
带可疑标记、有告警，且不再额外产生漏备份告警。

### R16 — 大小/文件数改用历史基线

现状：三个阈值字段（min_total_bytes / max_total_bytes / min_file_count）建表时就是
可空、无默认值，不配等于完全不检查；而且是固定死数，抓不到最有价值的信号
「今天这份比过去 30 天的中位数小了 90%」。

改：保留固定阈值作为硬下限，新增历史基线判据——与该任务近 N 次成功备份的**中位数**
比较，偏离超过比例阈值即告警（默认给宽松值，例如小于中位数的 50%）。
两条注意：
- 样本不足 N 次时不判。新任务不该因为没有历史就报警
  （与漏备份巡检「刚建出来的任务不算漏」同一条原则）
- **文件数必须用宽带宽**：U8 附件库个数随启用年度不同，个数波动是常态，
  不能拿它当缺失判据。真正敏感的是总字节数。

R16 现在还兼了另一个角色：结构快检（原 R14）已决定不做，
「备份跑了但是空的 / 只剩十分之一」这类信号**全靠这一条兜底**，实现时按这个分量对待。

验收：连续 10 次正常备份后人为造一次只有 10% 大小的备份能告警；附件库个数正常波动不误报。

### 明确不做

以下两项本轮决定不做，不要顺手加，也不要在报告里再提议：
- 结构快检（.bak 文件头 / 压缩包完整性 / 截断检测）
- 恢复演练（定期抽样实际恢复验证）
理由见审查报告第五节「明确不做的事」。
```

- 菜单里显示「上次成功备份：…」
- 保留现有 catch 分支的原则：读不到状态时两个操作项都留着，不要把出路藏起来

## 批次五 · 通知与日报（R5 + R8）

```
读 docs/整改清单-2026-09-10.md 的 R5、R8 与 docs/REVIEW-2026-09-10-运维可见性与自愈.md
的 B1、B2 两节。

### R5 — 未配通知渠道的常驻提示

现状：AlertingService.CreateDeliveriesForAsync 第一件事是读 system_settings 里的通知配置，
这行不存在就直接 return。新装的系统没人配过 → 所有告警只活在网页和客户端托盘气泡里，
而且没有任何地方提示「你还没配通知渠道」。

改：通知配置为空（或三个渠道全部 Enabled = false）时，概览页顶部常驻横幅，
文案说清后果：「当前没有任何通知渠道，告警只会出现在本页面」。
可跳转到通知配置页，但**不可关闭**——关掉就等于回到静默。
用常驻横幅，不要用一次性 toast。

### R8 — 每日摘要推送

现状：报表全是拉取式（AdminReportController 清一色 HttpGet），没有任何定时推送。
对备份产品来说日报比告警更重要：告警只在坏的时候响，日报证明这套系统本身还活着。

新增 worker：按配置时刻汇总昨日执行情况（成功 / 失败 / 未按计划 / 离线机器数）。
- 复用 notification_deliveries 通道，不另起投递链路
- **「一切正常」也要发**——日报的意义就是证明系统还活着
- 不受静默规则影响（静默是给「维护窗口内某台机器刷屏」用的，不是用来关掉日报的）

## 批次六 · 证书与版本（R9 + R10 + R11）

```
读 docs/整改清单-2026-09-10.md 的第四批与 docs/REVIEW-2026-09-10-运维可见性与自愈.md 的 C1~C3。

三种证书的现状：客户端证书（365 天）已经是完整闭环，**不要动它**；
另外两种既不续签也不提醒。

### R9 — 服务端 TLS 证书生命周期

现状：有效期 2 年（ServerCertificateFactory.ValidityYears），启动时只检查文件在不在
（LocalServerBootstrap），过期照样加载照样用。Agent 只按指纹校验，过期了照样连得上；
但管理网页会开始报证书过期，而一旦点「重新签发服务端证书」，指纹就变了，
所有 Agent 都得重跑客户端安装器更新指纹——目前没有指纹轮换机制。

改：
1. 启动时检查 NotAfter，剩余 ≤60 天告警，≤14 天 Critical
2. Agent 侧支持**新旧两个指纹并存**的过渡期配置，让轮换不必全网重装。
   这是本批次的核心，先把过渡流程设计出来写进报告再动手。
3. 服务管理台「重新签发」前明确提示影响范围与过渡步骤

### R10 — 客户端 CA 到期告警

现状：有效期 10 年（LocalServerBootstrap.GenerateClientCa）。客户端证书签发时会被 CA 的
NotAfter 截断（CertificateAuthority），也就是第 9 年起签出来的客户端证书会越来越短，
没有任何提示；到第 10 年，续签只能签出已经过期的证书，全体 Agent 同时失效。

改：CA 剩余 ≤180 天开始告警；签发时若 notAfter 被 CA 截断，记日志并告警——
那是唯一的早期信号。

### R11 — Agent 版本漂移提醒

## 批次八 · 客户端升级下发（R20）

```
读 docs/整改清单-2026-09-10.md 的第八批（R20）与
docs/REVIEW-2026-09-10-运维可见性与自愈.md 的 A5 节。

这一条是整改做完、打完包、准备升级客户端时才发现的，级别 A。

**现状**：管理页面「客户端 → 升级」能选机器、填版本 / URL / SHA-256 并下发，
Agent 收到后执行 AgentWorker.StageUpgradeAsync（AgentWorker.cs:2317）：
校验 URL 必须在本机的服务端上、下载、校验 SHA-256、解压到数据目录下的
updates/<版本>/、写 pending-update.json，然后回报 UPGRADE_STAGED 成功，
文案是「升级包已安全解压，将在受控重启时切换」。

全仓库 grep：pending-update.json 只有这一处写入，零个读取方。
没有任何一处应用这个暂存包。**界面说成功、指令回报成功、运行的程序一个字节没变。**

先自己跑一遍 grep 确认这个结论，把结果贴进报告。如果实测与结论不符，
立刻停下来汇报，不要按错误前提改代码。

### 第一步：止损（先做，单独提交）

把回报文案改成实话：「升级包已下载并校验，需要人工到这台机器上完成安装」，
结果码从 UPGRADE_STAGED 换成能看出「没装上」的值。
即使后面的都没做完，也不能留着这句假成功。

### 第二步：做成真正能用的

绕不过去的限制：**Windows 服务不能替换自己正在运行的程序文件**——
进程活着时它的 exe 和已加载的 dll 都被锁住。Agent 是自包含发布，一个包 502 个文件。
所以必须有一个住在被替换范围之外的第三方来做交换。

1. 新建 BackupMonitor.Agent.Updater：独立小工程，装在安装目录的同级子目录，
   **不在升级包的覆盖范围内**，否则它自己也会被锁。
   build-turnkey.ps1 与 AgentInstaller 都要跟着改（发布、安装、卸载清理）。
2. Agent 侧加「空闲判定」——这就是那句注释里说的**受控**：
   没有扫描 / 预检在跑、没有上传会话在传、不在备份计划的执行窗口内。
   不空闲就推迟到下一个空闲点，不要一刀切下去让传了一半的备份作废。
3. updater 流程：停服务 → 确认真的停了 → 备份当前目录 → 覆盖新文件 →
   启动服务 → 等心跳恢复并确认新版本号 → 删除备份。
4. **回滚是这件事的命门**：任一步失败立刻回滚旧目录并重新启动服务。
   升级失败 = Agent 起不来 = 这台机器再也收不到任何指令，包括修复指令——
   它连不上，就没法远程救它，只能上门。回滚路径要简单到不可能出错，
   不要在回滚路径上调用任何可能失败的复杂逻辑。
5. 托盘一起换：它是登录用户会话里的另一个进程，跟服务不是一回事。
6. **分批下发（金丝雀）**：先 1 台，等它心跳恢复且版本号变了，再放 5 台，再铺开。
   一个坏包同时推给 29 台就是 29 次上门。界面上要能看到每一批的结果。
7. 新 Agent 起来后主动上报「升级完成 + 新版本号」，服务端据此判成功——
   不要拿「指令执行完了」当成功，那正是现在这个 bug 的形状。
8. 下发表单自动填充：服务端已经通过 AgentVersionService 读
   wwwroot/downloads/agent-version.txt 知道随附版本（R11 用的就是它）；
   再让 build-turnkey.ps1 顺手写一份 zip 的 SHA-256，
   表单里的版本 / URL / 哈希三项就不必人工敲——手抄 64 位哈希本身就是个故障源。

### 不要做

- 不要为了省事让 Agent 自己 kill 自己再靠 SCM 拉起：SCM 拉起的还是旧文件，
  而且这条路上没有任何回滚余地。
- 不要动现有的两道安全检查：URL 必须在本机服务端上（IsSameServerAuthority）、
  SHA-256 必须是 64 位十六进制。升级是全系统唯一一条「服务端说什么就执行什么代码」
  的路径，这两道锁一个都不能少。

### 验收

- 在管理页面选 1 台客户端下发升级，无需上门，该机器在数分钟内自动完成切换、
  心跳恢复、上报的版本号变成新版本
- 人为投一个坏包（哈希对但内容是坏的），该机器能回滚并恢复心跳，不掉线
- 分批下发时，第一批失败不会继续推给后面的机器
```
