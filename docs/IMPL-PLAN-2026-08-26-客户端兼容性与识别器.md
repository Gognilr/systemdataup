# 客户端兼容性与识别器整改实施方案（2026-08-26）

本文档覆盖两组互不相干但都阻塞现场交付的问题：

- **批次 P（部署）**：客户端在 Windows Server 2012 R2 上装不上。两个独立原因，都会在现场表现为"点了没反应/弹个看不懂的框"。
- **批次 R（识别器）**：年/月分层的备份目录识别不了；更严重的是，向导会推荐一条**把真正的数据文件排除在外**的规则，且失败得毫无声响。

每条都标注了证据位置、根因、落地方案、验收标准和工作量。

## 范围与前提

已经定死、**不要再动摇**的边界：

- 客户端系统支持底线是 **Windows Server 2012 R2**。不做 .NET Framework / net462 产线，不做 netstandard2.0 多目标。
- 全客户群只有**一台** Server 2008 R2，单独处理（邻机 UNC 代理或不纳管），不进本方案。
- **现有安装包形态保持不变**：`BackupMonitor.Agent.Setup.exe` 和 `BackupMonitor.Agent.zip` 的产出方式、下载入口都不改。
- **不引入 app-local UCRT**（不把 `ucrtbase.dll` / `api-ms-win-crt-*.dll` 塞进包里）。理由见 P2。
- Linux 产线、升级通道 lane 隔离不在本方案内，另行排期。

# 批次 P：让客户端在 2012 R2 上装得上

现场看到的是一个弹窗（缺 `api-ms-win-crt-string-l1-1-0.dll`），但那只是**两个独立故障中的一个**。
走 Setup.exe 撞 UCRT，走 ZIP + PowerShell 撞 P1。两条部署路径都断了，必须一起修。

<a id="p1"></a>
## P1 · 安装/卸载脚本用了 PowerShell 5.0 语法

**级别**：P0　**工作量**：0.25 人日

### 现象

在 Server 2012 R2 上运行 `install-agent.ps1`，脚本在权限检查那一行直接抛异常退出，没有安装任何东西。

### 证据

- `src/agent/BackupMonitor.Agent/install-agent.ps1:16`
- `src/agent/BackupMonitor.Agent/uninstall-agent.ps1:12`

两处都是：

```powershell
$principal = [Security.Principal.WindowsPrincipal]::new($identity)
```

### 根因

`[Type]::new()` 这种静态构造语法是 **PowerShell 5.0** 才引入的。Windows Server 2012 R2 出厂是 **PowerShell 4.0**，
除非单独装过 WMF 5.1，否则这一行是方法解析错误。

脚本里其余的新语法（`[pscustomobject]`、`ConvertFrom-Json`、`ConvertTo-Json`、`-notin`、`-LiteralPath`）
都是 PowerShell 3.0 起就有的，在 4.0 上没有问题。**所以真正的阻塞点只有这两行。**

### 方案

1. 两个文件各改一行：

```powershell
$principal = New-Object Security.Principal.WindowsPrincipal($identity)
```

2. 两个文件顶部各加一行版本声明，让不满足条件时给出可读的错误而不是运行到一半崩：

```powershell
#Requires -Version 3.0
```

放在 `[CmdletBinding()]` **之前**（`#Requires` 必须在脚本首个语句之前才生效）。

3. 全仓扫一遍还有没有别的 PS 5.0-only 语法进了随包分发的脚本。至少要覆盖
   `src/agent/BackupMonitor.Agent/*.ps1`；`scripts/build-turnkey.ps1` 只在构建机跑，不受此限。

### 验收标准

- 用 PSScriptAnalyzer 的兼容性规则跑通（这是能在开发机上做的客观验证，不依赖真机）：

```powershell
Invoke-ScriptAnalyzer -Path src\agent\BackupMonitor.Agent\install-agent.ps1,src\agent\BackupMonitor.Agent\uninstall-agent.ps1 -Settings @{ Rules = @{ PSUseCompatibleSyntax = @{ Enable = $true; TargetVersions = @('3.0','4.0','5.1') } } }
```

  必须零 `PSUseCompatibleSyntax` 告警。

- 真机验证（与 P2 合并进同一次上机）：在一台 Server 2012 R2 上完整跑一次 ZIP 部署，
  服务能注册、能心跳。

### 影响面

只改两个随包分发的脚本，不触碰任何 C# 代码和构建流程。

<a id="p2"></a>
## P2 · UCRT 缺失：全链路没有任何提示

**级别**：P0　**工作量**：0.5 人日

### 现象

在未打补丁的 Server 2012 / 2012 R2 上双击 `BackupMonitor.Agent.Setup.exe`，
弹出系统错误框"无法启动此程序，因为计算机中丢失 api-ms-win-crt-string-l1-1-0.dll"，没有任何我方信息。

### 根因

`api-ms-win-crt-*.dll` 属于 **Universal C Runtime（UCRT）**。Windows 10 / Server 2016 及以上在系统内自带，
Server 2012 / 2012 R2 / 8.1 / 7 需要通过 KB2999226 或 VC++ 2015+ 运行库补进去。

`scripts/build-turnkey.ps1:175-178` 的所有产物都是 `--self-contained` 的 `net8.0-windows`，
apphost 与 coreclr 都依赖 UCRT。**进程在 `Main` 之前就死了，所以任何 C# 侧的友好提示都不可能生效**——
提示必须放在非 .NET 的外壳里（见 P3）或者放在下载入口的文案里（本条）。

### 为什么不做 app-local UCRT

把 UCRT DLL 随包分发、放在 exe 同目录，技术上可行且微软允许，但在本项目里性价比是负的：

1. 客户端底线已经收敛到 2012 R2，**打一次补丁就与 2016+ 完全同构**，一套包、一套升级通道，长期成本为零；
2. app-local 会让 `ucrtbase.dll` 的安全更新变成我方责任；
3. 更实际的雷：远程升级包 `BackupMonitor.Agent.zip` 里不含这些 DLL，
   将来实现"升级切换"步骤时会把手工放进安装目录的 UCRT 覆盖掉，客户端起不来且远程无法挽救。

**结论：走打补丁，不走 app-local。**

### 方案

**1. 下载入口写清系统要求**

- `src/src/BackupMonitor.Api/wwwroot/js/views/clients.js:22` 与 `:30` 两个下载按钮旁边；
- `src/src/BackupMonitor.Api/wwwroot/js/views/registration-tokens.js:59-60` 令牌弹窗里的两个下载链接旁边。

文案要点（一句话，不要写成免责声明）：

> Windows Server 2016 及以上可直接安装。Server 2012 / 2012 R2 需先安装 VC++ 2015-2022 运行库（同页下载），否则安装程序无法启动。

**2. 把运行库随包分发**

在 `wwwroot/downloads/` 下增加 `VC_redist.x64.exe`，下载页给出第三个链接。

选 VC++ 运行库而不是 KB2999226 的 MSU，有两个原因：**它是微软明确允许再分发的**，
而 MSU 补丁的再分发授权是灰的；且它一个包覆盖 2012 / 2012 R2 / 8.1，不用按 OS 分版本。

构建侧改 `scripts/build-turnkey.ps1`：

- 二进制来源与校验方式沿用 `scripts/payload-lock.json` 的既有模式（URL + SHA-256 锁定），
  新增一个 `vcredist` 节点，构建时校验哈希后再拷入 `wwwroot/downloads/`；
- **必须**把 `api\wwwroot\downloads\VC_redist.x64.exe` 加进 `Invoke-VerifiedCompress` 的
  `$payloadRequired` 清单（约 `build-turnkey.ps1:250` 附近）。不加的话，某次构建漏了这个文件不会报错，
  表现是线上下载页 404——与该清单里其他条目的理由完全一致。

**3. 部署文档补一节**

`docs/局域网部署使用说明.md` 增加"客户端系统要求"章节：支持范围（Server 2012 R2 及以上）、
2012 R2 的前置运行库、以及 P3 的自检工具用法。

### 验收标准

- 构建产物 `artifacts/turnkey-stage/api/wwwroot/downloads/` 下存在 `VC_redist.x64.exe`，SHA-256 与锁文件一致；
- 故意从 stage 目录删掉该文件后重新打包，`Invoke-VerifiedCompress` 必须**报错**而不是静默通过；
- 下载页三个链接都能下到东西，文案在页面上可见（不是 title 提示）；
- 真机：一台未打补丁的 2012 R2，按文档装完运行库后，Setup.exe 能正常启动。

### 影响面

前端两个视图文件的文案、构建脚本、部署文档。不改任何 C# 逻辑，不改安装包本身。

## P3 · 现场自检工具

**级别**：P1　**工作量**：0.25 人日

### 问题

P1 和 P2 是两个不同的坑，现场看到的现象却都是"装不上"。没有工具的话，
运维只能靠试——而其中一个坑（UCRT）连日志都不会留。

### 方案

新增 `src/agent/BackupMonitor.Agent/check-prereq.cmd`，**纯批处理**，
不依赖 PowerShell（PowerShell 版本本身就是被检测项之一），也不依赖 .NET。

检测项与输出：

| 检测项 | 取法 | 不满足时的结论 |
|---|---|---|
| 操作系统版本 | `ver` | 低于 6.3（2012 R2）→ 明确说明不在支持范围 |
| CPU 架构 | `%PROCESSOR_ARCHITECTURE%` | 非 AMD64 → 当前只提供 x64 版本 |
| UCRT | `if exist "%SystemRoot%\System32\ucrtbase.dll"` | 缺失 → 提示先装同目录的 `VC_redist.x64.exe` |
| PowerShell 版本 | `reg query "HKLM\SOFTWARE\Microsoft\PowerShell\3\PowerShellEngine" /v PowerShellVersion` | 缺该键或版本 < 3.0 → 提示用 Setup.exe 而非 ZIP 脚本部署 |
| 系统盘剩余空间 | `dir %SystemDrive%\` 末行 | 不足 1 GB 时提醒 |

最后打印一行结论：`可以安装` 或 `需要先处理：<清单>`，并 `pause` 住窗口——
双击运行时不 pause 的话，现场什么都看不到。

分发到两处：

- 加进 `client-package` 暂存目录（`build-turnkey.ps1:202` 附近，与 `install-agent.ps1` 同批拷贝），
  并加进 `Invoke-VerifiedCompress` 的 `-RequiredEntry` 清单；
- 单独放一份到 `wwwroot/downloads/`，下载页给链接。

### 验收标准

- 在 Windows 11 开发机上双击运行，结论为"可以安装"，且不闪退；
- 临时把 UCRT 的检测路径改成一个不存在的文件名，重跑必须报缺 UCRT（验证判定分支真的通了）；
- 脚本内不出现任何 `powershell` 调用。

# 批次 R：识别器

以致远 OA（Seeyon A6）这个真实场景为例，目录结构是：

```
D:\Seeyon\A6\Backup\
  2025\                             ← 年（可能已被清理）
  2026\
    07\                             ← 月（空目录，或已被删除）
    08\
      2026-08-17@02_00.properties   ← 元数据，约 1 KB
      2026-08-17@02_00.zip          ← 真正的备份数据
      2026-08-18@02_00.properties
      2026-08-18@02_00.zip
      ...（一个月约 30 组）
```

**一份备份 = 同名的 .zip + .properties 两个文件。**服务器只保留一个月，旧月份目录会被清空或删除。

现有实现在这个结构上有三处失效，R1 是其中危害最大的一处。

<a id="r1"></a>
## R1 · 向导推荐的规则会把真正的数据文件排除掉

**级别**：**P0（正确性缺陷，且静默）**　**工作量**：0.5 人日

### 现象

把源目录选到 `...\Backup\2026\08` 走向导，产出的识别规则是
`{"includePatterns":["*.properties"]}`，预演文件列表里**一个 zip 都没有**。

### 根因

`src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs` 的 `InferFlatDirectory`：

```csharp
var byExtension = files
    .GroupBy(f => Extension(f.Name), StringComparer.OrdinalIgnoreCase)
    .OrderByDescending(g => g.Count())
    .ToList();
var largest = byExtension[0];
```

`.properties` 30 个、`.zip` 30 个，**数量完全相同**。`OrderByDescending` 是稳定排序，
平局时保持原有顺序，而文件枚举按名字排——`...properties` 的 `p` 排在 `...zip` 的 `z` 前面。
于是 `.properties` 拿到第一名，被写进 `includePatterns`。

后果由 `RecognizerRules.IsAllowedFile` 放大：

```csharp
if (Includes.Count > 0 && !matchesInclude) return false;
```

**所有 zip 被彻底排除**——不扫描、不哈希、不上传、不参与缺失判定。
而 `.properties` 每天准时出现，任务天天判定 `passed`。
真正的故障（zip 是 0 字节、压缩中断、磁盘满导致只写了元数据）**不会产生任何告警**。

这不是"体验不好"，是监控系统给出的最危险的那种错误答案——与
`RecognizerRules` 文件头注释里对规则分叉的担忧属于同一类问题。

### 方案

改 `InferFlatDirectory`，两件事：

**1. 平局按总字节数决胜**

```csharp
.OrderByDescending(g => g.Count())
.ThenByDescending(g => g.Sum(f => f.SizeBytes))
```

zip 与 properties 的体积差四到五个数量级，一比就分出来了。

**2. 识别"成对文件"模式——这才是根本修复**

在按扩展名分组之前，先按 **basename**（去掉扩展名的文件名）分组统计。
若 60% 以上的 basename 拥有 ≥2 个不同扩展名，说明"一份备份由多个文件构成"，
此时**不能**产出单扩展名的 `includePatterns`。应当：

- 把该模式下出现的全部扩展名都写进 `requiredFiles`（如 `["*.zip","*.properties"]`）；
- `includePatterns` 要么不写，要么写全部扩展名，**绝不可只写一个**；
- Evidence 里说清楚："08 里有 30 组同名文件，每组包含 .zip 和 .properties"；
- R2 落地后，识别器类型改提 `multi_file_set` 并带上 `groupBy`；R2 未落地前先提
  `multi_file_set`（不带 `groupBy`），至少保证 zip 不被排除。

**3. 阈值常量化**

新加的 60% 与文件里已有的 `RequiredThreshold` / `DateLayerThreshold` 并列为具名常量，
不要写魔法数字。

### 验收标准

新增测试（`src/tests/BackupMonitor.Infrastructure.Tests/RecognizerWizardTests.cs`）：

- 构造 30 组 `2026-08-NN@02_00.zip`（大文件）+ `.properties`（小文件）的扁平目录快照，
  断言产出的规则中 **`*.zip` 必须出现在 `requiredFiles` 里**；
- 断言 `includePatterns` 若存在，则 `*.zip` 必须在其中；
- 反向用例：目录里只有 30 个 `.bak`、没有成对文件时，仍然走原来的 `latest_single_file` 路径（不要改坏已有行为）；
- 平局用例：两种扩展名各 5 个但体积悬殊，断言选中的是大的那个。

### 影响面

只改服务端推断逻辑，不影响已保存的任务（它们的规则已经落库）。
**但是**：现存任务里可能已经有被这个 bug 生成的错误规则。

**必须**在改动落地后出一份排查清单——扫描 `backup_tasks` 表中
`recognizer_config` 含单扩展名 `includePatterns` 的任务，逐一人工确认是否漏了数据文件。
这一步不能省：修了代码不等于修了已经错掉的存量配置。

<a id="r2"></a>
## R2 · 引入"文件组"：一次备份 = 同目录下的一组文件

**级别**：P0　**工作量**：2 人日

### 问题

即使规则写对（`includePatterns` 含 `*.zip`），语义仍然是错的。

`BackupScanner.SelectRoots` 的 `latest_single_file` 分支只用"最新文件"来**定位目录**，
随后 `CollectFiles` 收集该目录下**所有**匹配文件：

```csharp
var files = SafeEnumerateFiles(root, option, rules).Where(f => IsAllowed(f, root, rules))
```

于是 08 目录里 30 天的备份被当成**一份**，直接后果有两个：

1. **语义错**：manifest 含 30 组文件，每天变一次，`candidateKey` 跟着变，
   "这一份备份"永远不代表某一天的那份；
2. **性能不可接受**：`ComputeSha256Async` 是整文件读全量 SHA-256，
   每次扫描要把 30 个 zip 全部读一遍。按每个 2 GB 算，一次扫描 60 GB 磁盘 I/O。

现有四种识别器都无法表达"同目录下按文件名分组、只认最新一组"。
另外，UI 下拉里的 `multi_file_set`（`wwwroot/js/ui.js:21`）在
`BackupScanner.SelectRoots` 和 `SnapshotRecognizer.SelectRoots` **两处都没有分支**，
落到默认的"整个源目录算一份"。这个默认行为在"目录里正好放一份备份"时恰好是对的，
所以一直没暴露——**那是巧合，不是设计**。

### 方案

**核心设计决策：把分组做成与识别器类型正交的一步，而不是新增一种识别器。**

理由：`SelectRoots` 的返回值是"目录"，而文件组不是目录。要让它返回文件组就得改签名，
波及两处 `SelectRoots` 的全部分支。而"分组"在语义上是**收集文件之后的一次筛选**，
插在 `CollectFiles` 之后只需要一个切入点，且任何识别器类型都能叠加使用。

**1. 规则模型**（`src/src/BackupMonitor.Shared/Recognition/RecognizerRules.cs`）

- record 增加 `string? GroupBy` 字段；
- `Parse` 解析 `"groupBy"` 键；
- **`KnownKeys` 里必须加 `"groupBy"`**——这份清单存在的理由就是让拼错的键当场被指出来，
  漏加会让 `groupBy` 敲错时静默失效；
- `Empty()` 同步更新。

`groupBy` 的取值：

| 值 | 语义 |
|---|---|
| 不设置 | 保持现有行为，收集到的文件全部算一份（**默认，老任务零影响**） |
| `basename` | 按去掉扩展名的文件名分组 |
| 其他字符串 | 当作正则，用**第一个捕获组**作为分组键；无法编译或不匹配的文件归入"未分组"并保留 |

**2. 共享的分组实现**

在 `RecognizerRules` 里新增静态方法，**两侧共用同一份实现**：

```csharp
public IReadOnlyList<T> SelectLatestGroup<T>(
    IReadOnlyList<T> files,
    Func<T, string> relativePathOf,
    Func<T, DateTime> lastWriteOf)
```

规则：按分组键归组 → 每组取"组内最新文件时间"作为该组时间 → 取时间最大的一组；
时间相同则按分组键倒序（保证结果稳定，不依赖枚举顺序——R1 的教训）。
`GroupBy` 为空时原样返回。

放在 `RecognizerRules` 而不是各自实现，理由与该文件头部注释完全一致：
分组语义一旦两侧分叉，表现是"向导说会识别出这些文件、实际扫描是另一批"，且无人察觉。

**3. 两处接入点（必须对称）**

- `src/agent/BackupMonitor.Agent/BackupScanner.cs` · `ScanAsync`：
  `var files = CollectFiles(...)` 之后立即套一层 `SelectLatestGroup`，
  在 `files.Count == 0` 判断**之前**（分组后为空同样应走 `no_new_backup`）；
- `src/src/BackupMonitor.Infrastructure/Recognition/SnapshotRecognizer.cs`：
  在其对应的文件收集之后套同一层。

**4. 显式实现 `multi_file_set`**

两处 `SelectRoots` 都补上 `if (normalized == "multi_file_set") return [(source, null)];`，
并写注释说明"整个源目录算一份备份"是这个类型的**定义**，而不是 fallback。

**5. 检查签名与下发链路**

`recognizerConfig` 是随配置签名下发的（`src/src/BackupMonitor.Shared/Security/AgentSignatureCanonicalizer.cs`）。
确认它按原始字符串参与规范化——若是，新增 JSON 键不影响既有任务的签名校验。
**这一条要实际读代码确认，不要假设。**

### 验收标准

- **一致性测试必须扩展**：`RecognizerWizardTests.预演结果与实际扫描一致`（约 `:322`）是个 `[Theory]`，
  给它加上带 `groupBy` 的 `InlineData`。这是防止两侧分叉的唯一自动化防线；
- 新增 `BackupScannerTests` 用例：目录内 30 组 `NAME.zip` + `NAME.properties`，
  配 `{"groupBy":"basename"}`，断言返回的 `Files` **恰好 2 个**，且都属于时间最新的那一组；
- 断言 `BackupBusinessTime` 等于该组的最新时间，而不是整个目录的最新时间；
- 正则形式用例：`groupBy` 写 `^(\d{4}-\d{2}-\d{2})` 时按日期前缀分组；
- 非法正则用例：`groupBy` 写一个编译不过的正则，断言**不抛异常**、退化为不分组
  （沿用 `RegexMatches` 已有的异常吞掉策略）；
- 回归：所有不带 `groupBy` 的既有测试全绿——这是"老任务零影响"的证明；
- `FindUnknownKeys` 不把 `groupBy` 报成未知键。

### 影响面

Shared 的规则模型 + Agent 扫描 + 服务端预演。默认不启用，存量任务行为完全不变。

<a id="r3"></a>
## R3 · 源路径支持通配

**级别**：P1　**工作量**：1 人日

### 问题

源目录必须写死到 `D:\Seeyon\A6\Backup\2026\08`。到了 9 月、到了 2027 年，
任务配置就失效了，而失效的表现是 `path_not_found`——需要人记得去改。
`ScanAsync` 只做 `Environment.ExpandEnvironmentVariables`，不支持任何通配或日期占位。

### 方案

允许 `SourcePath` 中出现 `*`，如 `D:\Seeyon\A6\Backup\*\*`。

**展开语义**（写进代码注释，避免日后被改成"取全部"）：

逐段展开，每一段的多个候选中**只取最新的一个**，最终得到唯一的实际目录。
"最新"的判定沿用 `SelectLatestChildDirectory` 已有的口径——按目录内最新的、
符合规则的文件时间，而不是目录自身时间戳（很多备份程序先建目录再慢慢写，目录时间没有参考价值）。
候选目录里一个文件都没有时（例如被清空的 `07`），其时间为 `DateTime.MinValue`，自然排在后面。

实现位置：`BackupScanner.ScanAsync` 开头，在 `Directory.Exists(source)` 判断**之前**。

必须处理的边界：

- 展开后无匹配 → 走现有的 `path_not_found` 失败路径，`FailureMessage` 要说清楚是通配没匹配上，
  而不是让人以为路径写错了；
- **路径安全**：展开结果必须仍在原始通配前缀之下，防止 `..` 之类的穿越。
  仓库已有 `src/tests/BackupMonitor.Infrastructure.Tests/PathSafetyTests.cs` 和
  `src/src/BackupMonitor.Shared/Security/SecureFileSystem.cs`，复用既有校验，不要另写一套；
- 通配只允许出现在目录段，不允许出现在盘符段。

**服务端同步改动**：

- `BackupTaskService` 的源路径校验要放行 `*`（确认现有校验是否会拒绝）；
- `SnapshotRecognizer` 要能在快照上做同样的展开，否则预演与实际扫描分叉；
- 任务表单（`src/src/BackupMonitor.Api/wwwroot/js/views/tasks.js`）源路径输入框加一行说明：
  "支持 `*` 通配，多个匹配时取最新的一个，例如 `D:\Backup\*\*`"。

### 验收标准

- `BackupScannerTests` 新增：构造 `root\2025\12`、`root\2026\07`（空）、`root\2026\08`（有文件），
  `SourcePath` 写 `root\*\*`，断言扫到的是 `2026\08`；
- 断言空目录 `2026\07` 不会被选中（验证"按内容时间而非目录时间"）；
- 无匹配用例：`root\9999\*` 断言返回 `path_not_found` 且消息中包含通配相关说明；
- 安全用例：`root\..\*` 被拒绝；
- `预演结果与实际扫描一致` 的 `[Theory]` 补一条带通配路径的用例。

## R4 · 结构推断认出年/月分层

**级别**：P1　**工作量**：1 人日

### 问题

源目录选 `D:\Seeyon\A6\Backup` 时，向导给出"没能看懂 Backup 的结构"，置信度 25。

### 根因

`StructureInference.LooksLikeDate` 要求目录名里至少 **6 位数字**。
`2026` 是 4 位、`08` 是 2 位，两层都判定为非日期目录。于是：

- 情形一（本层是日期层）：`dateRatio = 0` → 不成立；
- 情形二（本层是业务单元、下层是日期）：`HasDateChildren(2026)` 中 `08` 不是日期 → 不成立；
- 情形三（单元里直接放文件）：`2026` 下没有直接文件 → 不成立；
- → 落到"看不懂"。

**这个 6 位下限本身是对的**，不要去改它——它正是用来把 `ZT001`、`账套001` 挡在外面的，
放宽会引入更糟的误判。正确做法是**新增**对"纯数字分层"的识别。

顺带确认：快照深度不是瓶颈。向导推断时请求 `maxDepth: 3`
（`src/src/BackupMonitor.Api/wwwroot/js/views/recognizer-wizard.js:112`），
从 `Backup` 下钻是 `2026`(1) → `08`(2) → 文件(3)，数据抓到了，是推断逻辑没认出来。

### 方案

**1. 新增两个判定函数**（与 `LooksLikeDate` 并列，各自独立可测）

- `LooksLikeYear(name)`：纯 4 位数字且落在 1990–2100；
- `LooksLikeMonthOrDay(name)`：纯 1–2 位数字且 1–31。

两者都要求**整个目录名只有数字**，不接受 `2026年`、`08月` 这类——
宁可认不出来交给人选模板，也不要认错（该文件头部注释的既定原则）。

**2. 新增"数字分层"情形**

插在现有情形一之前（它更具体，先判不会抢走原有分支）：

源目录下 60% 以上的子目录是年 → 取最新的年 → 其下 60% 以上是月 → 取最新的月 →
考察该月目录里的文件，复用 R1 的成对检测得出分组方案。产出：

```json
{
  "sourcePath": "D:\\Seeyon\\A6\\Backup\\*\\*",
  "recognizerType": "multi_file_set",
  "recognizerConfig": {
    "recursive": false,
    "groupBy": "basename",
    "requiredFiles": ["*.zip", "*.properties"]
  }
}
```

注意 `RecognizerProposalDto` 目前带的是 `SourcePath`——确认它能承载"带通配的路径"，
并且前端拿到后会回填到源路径输入框。**这一条要实际读前端代码确认。**

**3. Evidence 与 Summary 必须说人话**

这是整个向导的立论点（见 `StructureInference` 文件头注释）：只给结论不给依据，
"确认"就退化成盲点头。至少要有：

- "Backup 下有 1 个年份目录（2026），最新的是 2026"
- "2026 下有 2 个月份目录（07、08），最新的是 08"
- "08 里有 30 组同名文件，每组包含 .zip 和 .properties"
- "每次只认最新的一组：2026-08-20@02_00"

Summary 一句话说清"每天一组、只看最新那组、跨月自动跟随"。

**4. 置信度**

结构完全规整（年/月/组三层都清晰）给 85。任一层比例落在 60%–90% 之间给 70。
`HasGaps` 时沿用现有的减 20 逻辑，不要另开一套。

**5. 考虑把推断深度提到 4**

若客户结构再深一层（`Backup\2026\08\17\`），maxDepth=3 就抓不到文件了。
`RecognizerWizardService:88` 的 clamp 上限是 6，`recognizer-wizard.js:112` 请求的是 3。
建议把推断请求改为 4，并确认 `HasGaps` 在触顶时确实置位（已有测试
`规则超出快照深度时预演声明自己不完整` 覆盖了这条链路）。

### 验收标准

- `LooksLikeYear` / `LooksLikeMonthOrDay` 的 `[Theory]`：`2026`→年，`08`→月，
  `ZT001`→都不是，`20260817`→都不是（走原有 `LooksLikeDate`）；
- 端到端：构造 `Backup\2025\12\*`、`Backup\2026\07\`（空）、`Backup\2026\08\`（30 组）的快照，
  断言 `Infer` 返回的 `SourcePath` 带通配、`RecognizerConfig` 含 `groupBy` 与
  含 `*.zip` 的 `requiredFiles`、`Confidence >= 70`；
- 断言 Evidence 至少 3 条且提到了 `08` 和成对文件；
- 回归：`日期目录识别` 那个 `[Theory]` 全部用例不变（证明没有放宽 `LooksLikeDate`）。

# 实施顺序

分三批，每批可独立合入与验证。

| 批次 | 内容 | 产出 | 工作量 |
|---|---|---|---|
| 一 | P1 → P3 → P2 | 客户端在 2012 R2 上装得上，现场能自助判断 | 1 人日 |
| 二 | R1 | 止血：向导不再推荐排除数据文件的规则 | 0.5 人日 |
| 三 | R2 → R3 → R4 | OA 这类年/月分层结构完整支持 | 4 人日 |

顺序理由：

- 批次一是现场阻塞，先做。P1 排在 P3 之前是因为它只要 10 分钟；P2 最后是因为它要等运行库二进制到位。
- **R1 必须独立于 R2/R3/R4 先合**。它是正确性缺陷，且影响的不只是 OA——
  任何"同目录多扩展名"的备份结构现在都可能被推荐错规则。不要等三批一起上。
- R2 是 R4 的前提（R4 要产出 `groupBy`）；R3 也是 R4 的前提（R4 要产出通配路径）。
  所以批次三内部的顺序不能调换。
