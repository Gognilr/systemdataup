# R1 存量识别规则排查清单（2026-08-26）

R1 修的是「以后不会再生成把数据文件排除在外的规则」。**已经生成的错规则不会自己好。**

向导曾经在「同目录下多种扩展名、数量相同」的结构上产出只含单一扩展名的
`includePatterns`。被 `RecognizerRules.IsAllowedFile` 放大后，未命中的扩展名会被
**彻底排除**：不扫描、不哈希、不上传、不参与缺失判定。而命中的那种扩展名每天准时
出现，任务天天判 `passed`——真正的故障（数据包 0 字节、压缩中断、磁盘满只写了元数据）
不会产生任何告警。

所以这份清单要逐条销账，不能只是跑一遍 SQL 看看。

## 一、拉出嫌疑任务

```sql
-- 单一扩展名 includePatterns 的任务。includes 是 includePatterns 的别名，一并查。
WITH rules AS (
    SELECT
        t.id,
        t.name,
        t.application_name,
        t.source_path,
        t.recognizer_type,
        t.enabled,
        c.hostname,
        COALESCE(
            t.recognizer_config -> 'includePatterns',
            t.recognizer_config -> 'includes'
        ) AS includes,
        COALESCE(
            t.recognizer_config -> 'requiredFiles',
            t.recognizer_config -> 'requiredPatterns',
            t.recognizer_config -> 'required'
        ) AS required
    FROM backup_tasks t
    JOIN clients c ON c.id = t.client_id
)
SELECT
    id,
    hostname,
    name,
    application_name,
    source_path,
    recognizer_type,
    includes,
    required,
    enabled
FROM rules
WHERE jsonb_typeof(includes) = 'array'
  AND jsonb_array_length(includes) = 1
ORDER BY hostname, name;
```

> `backup_tasks` 没有软删除列，所以这条查询会连 `enabled = false` 的任务一起列出来——
> 这是有意的：停用的任务将来可能被重新启用，规则错了照样要改。

**重点看**：`recognizer_type` 是 `latest_single_file` 的、`application_name` 是致远
OA / 用友 / SQL Server 这类会同时产出数据文件与元数据文件的，以及 `source_path`
指向按月/按日归档目录的。

## 二、逐条确认

对上一步列出的每个任务，回答一个问题：

> **`includePatterns` 里那个扩展名，是不是这份备份里真正的数据文件？**

确认方式（三选一，按可靠性排序）：

1. **在向导里重新预演一次**。改动落地后，同一个源目录会走新的成对检测，
   预演出来的文件列表里应当能看到数据包。预演结果与旧规则的差异就是答案。
2. **让运维在客户端机器上 `dir` 一下源目录**，看同一批备份是不是由多个同名文件构成。
3. 看该任务历史备份的 `manifest.json` 文件清单和总字节数——只有元数据文件时，
   总字节数会小得离谱（KB 量级），而真实数据包通常在百 MB 到 GB 量级。

## 三、销账表

| 任务 ID | 客户端 | 任务名 | 源目录 | 当前 includePatterns | 是不是数据文件 | 处理 | 确认人 | 日期 |
|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |

「处理」一列只有三种取值：

- **无需改动** —— 该扩展名确实是数据文件，源目录里也没有别的成分；
- **改规则** —— 走向导重新生成，或人工把 `includePatterns` 补全 / 直接删掉改用
  `requiredFiles`；改完必须重新预演确认数据包在列表里；
- **重新纳管** —— 结构本身不适合当前识别器，重建任务。

## 四、改完之后

规则改动会让 `config_version` 递增并重新下发签名配置，Agent 下一轮扫描即生效。
改完的任务要盯一轮实际扫描结果：`manifest` 里出现数据文件、总字节数跳到合理量级，
才算这一条真的销账。

**已入库的历史备份不会追溯补齐**——那段时间里数据包没有被采集过。
如果这些任务的备份具有保留价值，需要单独安排一次全量重采。

## 附：2026-08-28 的识别器行为变更（需要一并排查）

同一批修改改掉了三处**语义**，不只是修缺陷。存量任务里命中这几条的，判定结果会变。

### 1. `latest_single_file` 现在只收一个文件

它此前只用「最新」挑出那个文件所在的**目录**，随后照常收集整个目录 ——
名字说的是「最新的单个文件」，实际行为是「那个目录里的全部文件」。

用了这个识别器、且源目录里堆着历次备份的任务，此前每次扫描都在把整个目录
读一遍算 SHA-256、整个目录上传，`manifest` 每天都变。改动之后回归到字面语义。

排查：

```sql
SELECT t.id, c.hostname, t.name, t.source_path, t.recognizer_config
FROM backup_tasks t JOIN clients c ON c.id = t.client_id
WHERE t.recognizer_type = 'latest_single_file' AND t.enabled;
```

逐条确认「一次备份就是一个文件」是不是本意。**如果本意是「这一批文件一起算一份」，
这个任务本来就选错了识别器**，应改用 `multi_file_set`（配 `groupBy`）。
改动之后它的行为才是正确的，但备份集的体量会明显变小 —— 那是修正，不是丢数据。

### 2. 没配 `requiredFiles` 时不再把所有文件标成「必需」

`IsRequiredFile` 在 `Required` 为空时原先返回 `true`。这只影响
`candidate_files.is_required` 这个**展示**字段与向导界面的角标，
缺失判定（`HasMissingRequired`）一行都没变，不会有任务的通过/失败结论改变。

存量数据里那些被标成 `is_required = true` 的记录不会追溯修正，也不必修正 ——
没有任何逻辑读它做判定。

### 3. 业务单元的定位多了两种模式

新增 `unitLayout: "date_leaf"`（按结构自适应）与 `businessUnitPaths`（人工指定通配）。
两者都只在配置里**显式写了**才生效，`businessUnitDepth` 的行为逐字节不变，
存量任务不受影响。

需要主动排查的是反过来的那一类：**源目录下层级不齐的任务**。
它们此前只能用一个固定深度，必然有一部分业务单元没被纳管，而且没有任何提示。

```sql
SELECT t.id, c.hostname, t.name, t.source_path,
       t.recognizer_config ->> 'businessUnitDepth' AS depth,
       (SELECT count(*) FROM business_units u WHERE u.task_id = t.id) AS units
FROM backup_tasks t JOIN clients c ON c.id = t.client_id
WHERE t.recognizer_type = 'subdirectory_units' AND t.enabled;
```

`units` 明显少于运维预期的账套数，就是命中了这一条 —— 走一遍向导重新推断即可，
新的推断会把分组容器识别出来并给出真实的单元数。
