## 0. 三个问题的一句话结论

| # | 现象 | 真实根因 | 严重性 |
|---|---|---|---|
| 1 | 点「暂停」几秒后自己又传上了 | 记录分块的那条裸 SQL **无条件**把会话状态写回 `uploading`，在途分块落库即把暂停抹掉；Agent 又把 409 当成可重试错误 | **暂停功能等于不存在** |
| 2 | `自动备份\` 下 ZT001/ZT002 与 ZT201-ZT216\ZT2xx 层级不一致；`UFFile_001_2022.dat` 这类文件不知道算不算必需 | `businessUnitDepth` 是**全树统一深度**，表达不了混合层级；必需文件只按**精确文件名**统计，名字带年份的一律消失 | **会把 16 个账套的 7 天备份混成一份，且判 passed 不告警** |
| 3 | `数据库备份\` 里 14 个 .bak 应该是「7 天 × 2 个库」，被当成一次备份 | 分组只认「同名不同扩展名」，不认「文件名里的日期」；`latest_single_file` 实际收整个目录；无 requiredFiles 时所有文件都被标「必需」 | **每次上传 10.59 GB 而不是 1.5 GB** |

三个问题里有两条共同的暗线，方案的重点在这两条上，而不是各打各的补丁：

- **A. 状态/事实只能有一个来源。** 问题 1 是一条裸 SQL 绕过了会话状态机；问题 2 的「说 3 个单元、其实只考察了 2 个」是摘要、必需文件、预演三处各自数了一遍单元。
- **B. 识别器缺一个「文件名模式」原语。** 问题 2 的 `UFFile_001_2022.dat`、问题 3 的 `dzwl_product_backup_2026_08_22_000004_4679193.bak`，都是「名字每次不同、模式每次相同」。现在系统只会精确比名字或退回比扩展名，中间那一档（模式）完全没有，于是这两类结构都认不出来。

## 1. 问题一：暂停几秒后自动恢复

### 1.1 根因（已在代码中定位，非推测）

**主因** —— `src/src/BackupMonitor.Infrastructure/Services/UploadSessionService.cs:407`

每收到一个分块，最后那条 CTE 语句是：

```sql
UPDATE upload_sessions SET
    uploaded_bytes   = uploaded_bytes + ...,
    status           = 'uploading',      -- ← 无条件
    last_activity_at = ..., updated_at = ...
WHERE id = {sessionId}
```

管理端把会话置 `paused`（`UploadSessionControlService.cs:71`）之后，**任何一个已经通过写入校验、还在路上的分块落库，都会把状态改回 `uploading`**。

而在途分块几乎必然存在：Agent 默认 4 路并行、每块 8 MB（`AgentOptions.cs:23,36`）。点暂停的那一刻，通常有 1–4 个分块正在传输或正在服务端落盘。

**放大器** —— `src/agent/BackupMonitor.Agent/AgentWorker.cs:1791`

```csharp
catch (Exception ex) when (ex is AgentApiException or HttpRequestException)
{
    last = ex;
    await Task.Delay(TimeSpan.FromSeconds(Math.Min(attempt * 2, 10)), ct);
}
```

Agent 对**所有** API 异常一律重试 3 次（2s / 4s 退避），包括 `409 UPLOAD_SESSION_CONFLICT`。于是：某一路撞 409 → 睡 2 秒 → 期间另一路的在途块落库把状态刷回 `uploading` → 重试成功 → 这一块落库又刷成 `uploading` → 传输完全自愈。**暂停在事实上从未生效过一次。**

**为什么表现是「几秒」** —— 传输中页面 5 秒轮询一次（`transfers.js:15`）。点击后前端弹「已暂停」，下一次轮询拿回的状态已经被刷成 `uploading`。

### 1.2 同源缺陷（举一反三，同一批一起修）

| 位置 | 问题 |
|---|---|
| `UploadSessionService.CompleteFileAsync` (:420) | 不检查 `paused`。暂停时若分块恰好已收齐，Agent 仍能完成文件校验 |
| `UploadSessionService.CompleteSessionAsync` (:482) | 同上，暂停中的会话可以一路走到 `verifying` → 入库 |
| `UploadSessionService.CreateSessionAsync` (:83) | 幂等键命中 `paused` 会话时照常返回「可续传」。自动模式下预检再跑一轮就会用 `auto-upload:{candidateId}` 重下上传指令（`AgentPrecheckService.cs:298`），等于把暂停中的会话又交回给 Agent |
| `CommandService.cs:371` | Agent 因暂停最终失败 → 触发 `upload_failed` 告警。**管理员自己按的暂停变成一条故障告警** |

### 1.3 方案

**(1) SQL 里加状态守卫（核心修复）**

```sql
UPDATE upload_sessions SET
    uploaded_bytes   = uploaded_bytes + COALESCE(...),
    status           = CASE WHEN status = 'paused' THEN status ELSE 'uploading' END,
    last_activity_at = ..., updated_at = ...
WHERE id = {sessionId}
```

字节数与 `last_activity_at` **照常累加**：这一块确实收到了、确实落在暂存目录里，进度不能倒退，否则恢复后 `missing-chunks` 与 `uploaded_bytes` 会对不上。只有状态不许被改回去。

**(2) 给「暂停」一个可识别的错误码**

写块时 `status == Paused` 抛 `UPLOAD_SESSION_PAUSED`（409），与泛化的 `UPLOAD_SESSION_CONFLICT` 分开。没有这个区分，Agent 无法把「管理员按了暂停」和「会话状态异常」区别对待。

**(3) Agent：区分「可重试」与「语义拒绝」**

`UploadChunkWithRetryAsync` 增加不可重试错误码集合，命中即立刻抛出、不退避重试：

```
UPLOAD_SESSION_PAUSED, CANDIDATE_EXPIRED, CANDIDATE_CHANGED,
CANDIDATE_ALREADY_ARCHIVED, MANIFEST_MISMATCH, CHUNK_INVALID,
FILE_HASH_MISMATCH, FORBIDDEN
```

对一个语义拒绝重试 3 次，除了浪费 6 秒和刷日志没有任何作用 —— 这一条本身就该修，不只是为了暂停。

**(4) 暂停走「优雅停下」而不是「失败」**

`UPLOAD_SESSION_PAUSED` 命中时：取消其余并行路 → **不调** `interrupt`（服务端本来就会忽略 paused 会话）→ 指令以 `UPLOAD_PAUSED` 结束。`CommandService` 的失败告警分支排除这个结果码。人为暂停不该在告警中心留下一条「上传失败」。

**(5) 关掉其余几个后门**

- `CompleteFileAsync` / `CompleteSessionAsync` 遇 `paused` 抛 409；
- `CreateSessionAsync` 幂等命中 `paused` 会话时抛 `UPLOAD_SESSION_PAUSED`，不把它交出去；
- `ResumeAsync` 维持现状（已经重下指令 + `restartIfNotActive`），不需要改。

**(6) 结构性收口（建议同批做，代价很小）**

新增一处 `UploadSessionStatus` 判定（`CanWrite` / `CanTransitionTo`），把 `WritableStatuses`、`ActiveStatuses`、`PausableStatuses`、`CancellableStatuses` 以及这条裸 SQL 的守卫全部收进去。问题 1 的本质是「状态机有四份互相不知道的副本，其中一份是 SQL 字符串」，不收口的话下一个绕过它的写入点迟早还会出现。

**明确不做**：不改成「暂停时给客户端下一条指令」。指令轮询 10 秒一次，比撞 409 慢，且新增一条需要保证送达的控制通道。撞 409 的路子是对的，缺的只是让 Agent 认得这个 409。

## 2. 问题二：混合层级 + 名字带年份的必需文件

### 2.1 层级：根因

目录实况：

```
D:\自动备份\
├── ZT001\20260822\{UFDATA.BAK, UfErpAct.Lst, UFFile_001_2022..2026.dat}   ← 单元在第 1 层
├── ZT002\20260828\{...}                                                    ← 单元在第 1 层
└── ZT201-ZT216\                                                            ← 纯容器，不是单元
    ├── ZT201\20260828\{...}                                                ← 单元在第 2 层
    └── ... ZT216\20260828\{...}
```

`StructureInference.cs:90` 的情形二判据是「直接子目录里，有日期子目录的占比 ≥ 0.6」：ZT001 ✓、ZT002 ✓、ZT201-ZT216 ✗ → **2/3 = 0.667，勉强过线**，于是：

- 摘要用 `directories.Count` 说「有 3 个业务单元」；
- 必需文件只考察了 2 个 leaf（截图里「考察的 2 个备份目录里」）；
- 预演按 `businessUnitDepth:1` 列出 3 个单元，其中 ZT201-ZT216 取「最新子目录」= `ZT216`（一个容器目录），递归收集把 ZT216 的 7 天全收进来 → **判 passed**。

同一份推断，三个数字（3 个 / 2 个 / 3 个单元）来自三段独立代码。这是「事实没有单一来源」的直接后果。

真正落地后的危害（比向导显示错更严重）：任务建出来后，`ZT201-ZT216` 这个「单元」每次扫描收的是 ZT216 下 7 天的全部文件，manifest 每天变、体积是真实备份的 7 倍、`candidateKey` 永远不代表某一天的那份备份，而 **ZT201–ZT215 这 15 个账套完全不在监控范围内，且没有任何提示**。

**根本原因**：`businessUnitDepth` 是一个整数，语义是「全树统一深度」（`BackupScanner.cs:204` 用 `DirectoryDepth(source, p) == depth` 过滤）。任何深度值都覆盖不了这个目录：

- `depth=1` → ZT201-ZT216 被当成一个单元（现状）
- `depth=2` → ZT001 的**日期目录**被当成单元，而 16 个 ZT2xx 才是对的

### 2.2 层级：方案

**(1) 新增 `unitLayout: "date_leaf"` —— 按结构找单元，而不是按深度**

定义：**业务单元 = 其直接子目录中日期目录占多数的那一层目录**。从源目录开始逐层下探（上限 4 层），命中即停、不再往下找；命中不了但下面还有子目录的，视为纯容器继续下探。备份采集根 = 该单元下最新的日期目录（沿用现有 `SelectLatestChildDirectory`）。

对本例的结果：单元 = `ZT001`、`ZT002`、`ZT201-ZT216/ZT201` … `ZT201-ZT216/ZT216`，共 **18 个**。`ExternalKey` 已经取相对路径（`BackupScanner.cs:216` 有注释说明为什么），`ZT201-ZT216/ZT201` 与 `ZT001` 天然不撞键，这块不用改。

**前置重构（必须做）**：`LooksLikeDate` / `LooksLikeYear` / `LooksLikeMonthOrDay` 目前在 `BackupMonitor.Infrastructure.Recognition.StructureInference`，Agent 引用不到。要下沉到 `BackupMonitor.Shared/Recognition/DateName.cs`，Agent 与服务端共用 —— **Agent 现在完全不懂「什么是日期目录」，这正是层级自适应做不了的根本原因**。这与 `RecognizerRules` 当初下沉到 Shared 是同一个理由：规则语义只能有一份实现，否则向导说的和实际扫的会分叉。

**(2) 手动兜底：`businessUnitPaths`**

给「不太对，我自己调」的人一条不需要理解「深度」这个概念的路：

```json
{ "businessUnitPaths": ["ZT0*", "ZT201-ZT216/*"] }
```

相对源目录的通配列表，命中的目录即业务单元。它同时是 `date_leaf` 猜错时的逃生门 —— 自适应必须配一个手动覆盖，否则猜错了就是死局。

**(3) 深层结构：按需补抓，而不是一律抓深**

深度不能一律调大（快照条目数是乘出来的，很容易顶到 3000 条上限，反而让本来看得懂的结构被标成「没抓全」），所以改成**只在确实被深度卡住时才多花一次往返**：

- 服务端在「抓得不全（`HasGaps`）**且**置信度 < 70」时置 `NeedsDeeperScan`——抓得不全但结论已经清楚的不重来，多一次往返换不到新信息。
- 向导收到这个标志就把同一个目录重抓一次到 6 层（服务端硬上限）再推断一次，且只重试一次：抓到 6 层还看不懂，就是真的看不懂了。
- 这同时修掉一个现存的哑巴行为：现在遇到 `DepthLimited` 只是扣 20 分置信度 + 一句「没抓全」，然后给一句「没能看懂」——而实际上往往只差一层没看到。
- 扫描端（Agent 真扫文件系统）没有快照限制，给一个宽松上限（`BusinessUnitResolver.DefaultMaxDepth = 6`）即可。

> 实现时相对原方案做了简化：原计划是「只对断掉的那一枝补抓、再合并进快照」，实际是整棵重抓。合并两份根不同的快照需要新增快照合并机制，而「只在需要时才抓深」这个关键性质两种做法都成立。

**(4) 推断侧：先算单元集合，再由它派生一切**

把 `Infer` 情形二重构成：

```
单元集合 units = ResolveUnits(source)      ← 唯一事实来源
  ↓
summary（"18 个业务单元，其中 16 个在 ZT201-ZT216 下面"）
evidence（"ZT201-ZT216 自己不是账套，它下面的 16 个才是"）
requiredFiles（考察全部 18 个 leaf，不是 2 个）
preview（跑在同一个 units 上）
```

这条改动的价值不止于本例：它让「摘要说的数」和「预演跑的数」在结构上不可能再不一致。

`businessUnitDepth` 保留，作为 `date_leaf` 和 `businessUnitPaths` 都没给时的默认行为（既有任务与既有测试不受影响）。

### 2.3 必需文件：根因

`InferRequiredFiles`（`StructureInference.cs:476`）只有两档：

1. 按**精确文件名**跨单元统计 → `UFDATA.BAK` 3/3、`UfErpAct.Lst` 3/3 → 推荐；
2. 只有当精确名**一个都没达标**时，才退回按扩展名统计。

`UFFile_001_2022.dat` 这类名字每个账套都不一样（年份不同、个数不同），精确名统计里出现率低于下限 `floor`，直接从候选里消失 —— 界面上连「只出现在 1/3 个目录里，没有默认勾选」这行提示都看不到。而第 2 档因为第 1 档已经达标，永远走不到。

即：**系统只会「精确比名字」或「粗略比扩展名」，中间那一档「比模式」不存在。**

补充一个事实，避免把问题说得比实际严重：这些 `.dat` 文件目前**仍然会被采集和上传**（`IsAllowedFile` 在没有 `includePatterns` 时默认放行），只是不参与「缺失判定」，也不在界面上露面。所以现状不是「漏传数据」，而是「向导对它们完全失语」——用户看着这几个文件，得不到任何关于它们算不算数的说法。方案要解决的是这个失语，而不是给它们加检查（见 2.4(3)）。

### 2.4 必需文件：方案

**(1) 新增文件名归一化原语 `FileNamePattern`（Shared）**

```
UFFile_001_2022.dat                                  → UFFile_001_*.dat
UFDATA.BAK                                           → UFDATA.BAK        （无可归一化片段，原样）
dzwl_product_backup_2026_08_28_000002_2768823.bak    → dzwl_product_backup_*.bak
beeServer_backup_2026_08_22_000004_2256969.bak       → beeServer_backup_*.bak
2026-08-17@02_00.zip                                 → *.zip
```

规则：识别并替换「4 位年份」「6/8 位日期串」「`YYYY_MM_DD` / `YYYY-MM-DD`」「≥4 位的纯数字段」，合并相邻 `*`。归一化后若整个名字只剩 `*` + 扩展名，等价于按扩展名统计 —— 旧的第 2 档被它自然涵盖。

**(2) 必需文件分三档呈现**

| 档 | 判据 | 产出 | 界面 |
|---|---|---|---|
| 固定名必需 | 精确名在 ≥90% 单元出现 | `"UFDATA.BAK"` | 默认勾选 |
| **模式必需**（新） | 归一化模式在 ≥90% 单元出现，**且各单元里该模式的文件个数一致** | `"beeServer_backup_*.bak"` | 默认勾选，标注「按模式」 |
| 附带文件 | 其余，**含个数不一致的模式** | 不写入 `requiredFiles` | 列出但不勾选，注明原因 |

**(3) 个数是否稳定，决定它能不能当判据**（2026-08-28 确认后定稿）

原先设想给模式候选加一个 `minCount`（个数少于历史最小值即判缺失）。**这条取消。**

理由是领域事实：U8 的 `UFFile_001_YYYY.dat` 是按**年度**分的附件库，而各账套的**启用年度不同** —— ZT001 从 2022 年起用就有 5 个，ZT002 从 2024 年起用就只有 3 个。两者都是完整备份。个数在账套之间不一致是这个结构的**正常形态**，不是缺失信号，拿它做判据只会制造假警报。

由此提炼出一条通用规则，写进推断逻辑：

> **一个模式能不能作为完整性判据，取决于它在各单元里的个数是否一致。**
> 个数一致（问题 3 的 `beeServer_backup_*.bak`：每天每组恰好 1 个）→ 模式必需，默认勾选。
> 个数波动（`UFFile_001_*.dat`：3 / 4 / 5 个）→ 降级为附带文件，列出但不勾选，界面注明「各单元个数不一致（3–5 个），不作完整性判据」。

这条规则同时给了人一个可以自己推翻的判断：候选仍然列在界面上，认为该勾的人手动勾上即可。系统只是不替他做这个决定。

**这些 `.dat` 文件照常被采集和上传**（`IsAllowedFile` 默认放行），不进 `requiredFiles` 只意味着「不参与缺失判定」，不是「不备份」。

**(4) 顺手修一个显示矛盾**

`RecognizerRules.IsRequiredFile`（`RecognizerRules.cs:328`）在 `Required.Count == 0` 时返回 `true` → 没配必需文件时**所有文件都被标「必需」**。问题 3 的截图里，标题写着「这次没有看出固定出现的文件，暂不检查」，下面 14 个文件却个个挂着「必需」角标 —— 就是这一行。改成返回 `false`。

影响面已核对：`HasMissingRequired` 在 `Required` 为空时本来就返回 false，判定逻辑不变；`IsRequired` 只用于 `CandidateFile.IsRequired` 这个展示字段。

## 3. 问题三：平铺目录里的「一天一组、多个库」

### 3.1 根因

目录实况：`D:\数据库备份\` 无子目录，14 个 .bak，文件名自带日期：

```
beeServer_backup_2026_08_22_000004_2256969.bak      5.09 MB
dzwl_product_backup_2026_08_22_000004_4679193.bak   1.49 GB
... 7 天 × 2 个库
```

`InferFlatDirectory` 的判定链（`StructureInference.cs:162`）：

1. `DetectPairedFiles` 按**精确 basename** 分组 → 14 个文件 14 个组、0 个成对组 → 返回 null；
2. 落到按扩展名分支 → `.bak` 14 个 ≥ 3 → 判 `latest_single_file` + `includePatterns: ["*.bak"]`。

于是摘要说「每次取最新的那个」。**但预演列出了全部 14 个文件，并且个个标「必需」** —— 两个独立缺陷叠加：

**缺陷 A：`latest_single_file` 名不副实。** `SelectRoots` 只用「最新」挑出那个文件所在的**目录**（`BackupScanner.cs:283`、`SnapshotRecognizer.cs:211`），随后 `CollectFiles` 把该目录下所有 `.bak` 全部收进来。所以这个识别器的实际语义是「整个目录」，不是「最新的单个文件」。

后果不是显示问题，是**每次扫描算 14 个文件的 SHA-256、每次上传 10.59 GB 而不是 1.5 GB，且 manifest 每天变化**。这个缺陷独立于问题 3 存在 —— 任何用了 `latest_single_file` 的任务都在这么跑。

**缺陷 B：** 全部标「必需」= 2.4(4) 那一行。

### 3.2 方案

**(1) 新增 `DetectDatedFileSets`：按文件名里的日期分组**

在 `DetectPairedFiles` 之后、按扩展名兜底之前插一档：

- 从各文件名提取日期 token（复用 2.4(1) 的 `FileNamePattern`）；
- 按日期 token 分组 → 本例得 7 组，每组 2 个文件；
- 用归一化模式描述组成员 → `{beeServer_backup_*.bak, dzwl_product_backup_*.bak}`；
- 成立条件：**≥2 个日期组**，且 **≥60% 的组拥有相同的模式集合**，且**模式集合含 ≥2 个不同模式**（只有 1 个模式 = 单库每天一份，那是 `latest_single_file` 的场景，走下一档）。

产出：

```json
{
  "recursive": false,
  "groupBy": "_(\\d{4}_\\d{2}_\\d{2})_",
  "requiredFiles": ["beeServer_backup_*.bak", "dzwl_product_backup_*.bak"]
}
```

识别器类型 `multi_file_set`。运行时 `SelectLatestGroup`（`RecognizerRules.cs:263`，Agent 与预演共用）按日期分组、取最新一组 → **一次备份 = 2 个文件 ≈ 1.5 GB**；某天某个库没转储出来 → 该组只有 1 个文件 → `required_file_missing` → 告警。这正是要的判定。

摘要文案改成：「`数据库备份` 里每天一组备份，每组 2 个库（beeServer、dzwl_product），共 7 天；每次只认最新的一组：2026_08_28」。

**产出 `groupBy` 正则前必须自检**：拿样本文件跑一遍，确认能分出 ≥2 组且无文件落入 `UngroupedKey`，否则不写这条规则。`GroupKeyOf` 对匹配不上的文件是「归入未分组并保留」（刻意的容错），推断阶段不做自检的话，一条写坏的正则会静默退化成「不分组」，回到今天的错误结果。

**(2) 修 `latest_single_file` 的语义**

在收集管线里加一步「只保留最新的那一个文件」，服务端预演与 Agent 扫描共用同一份实现 —— 挂在 `SelectLatestGroup` 旁边（同样是「收集之后的一次筛选」，切入点已经现成：`BackupScanner.cs:104` 与 `SnapshotRecognizer.cs:70`）。

这是行为变更。按「项目未进生产、快照全新安装」的既定前提直接改，并在 `docs/R1-存量识别规则排查清单.md` 补一条记录。

## 6. 取舍与风险，以及明确不做的事

**风险**

- `date_leaf` 自适应可能在「单元下既有日期目录又有别的目录」时判错。缓解：沿用现有 0.6 比例阈值 + 置信度下调 + evidence 把观察到的现象原样列出；并且必须有 `businessUnitPaths` 手动覆盖 —— **自适应没有逃生门就是死局**。
- `latest_single_file` 语义变更会改变已有任务的行为。按「未进生产」的前提直接改，在 R1 清单留痕。
- 「个数一致才作判据」这条规则，在**单元只有一个**时无从判断（没有可比对象）。此时按现有 `BuildCandidates` 的既定做法处理：列出来供人勾选，不替他判断稳定性。

**明确不做**

- 不给暂停加控制指令通道（10 秒轮询比撞 409 慢，且要新增送达保证）。
- 不在前端做乐观状态/本地假状态遮盖服务端的错误状态 —— 那是把问题一藏起来而不是修掉。
- 不对「文件个数变化」做任何自动判定或告警。判据只有一条：**这件事是否影响「数据会不会丢」**。附件库个数随启用年度天然不同，个数变化不代表丢数据（见 2.4(3)），因此不加。
