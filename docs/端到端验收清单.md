# 端到端验收清单

一次全新安装，把整条链走通：**注册 → 心跳 → 扫描 → 上传 → 入库 → 恢复下载**。

这份清单要回答的只有一个问题:**这套东西能不能替代手工备份。**
每一步都写了「该看到什么」和「不对时去哪查」——不对的时候先看日志再改配置，
不要跳过某一步继续往下走，链条是有先后依赖的。

- 环境：两台机器（或两台虚拟机快照）。服务端一台，客户端一台。
- 全程用 `dist/` 里的两个安装包，不要用开发目录里的二进制。
- 服务端日志：安装目录下 `logs/`；Agent 日志：`%ProgramData%\BackupMonitor\Agent\logs\`。
- 数据库连接：安装时设定的口令，`psql -U backupmonitor -d backupmonitor`。

---

## 第 0 步 · 装服务端

1. 跑 `check-prereq.cmd`，确认没有红项。
2. 双击 `BackupMonitor.Server.Setup.exe`，按向导装完。
3. 浏览器打开管理台，用向导里设的管理员账号登录。

**该看到什么**
- 「部署状态」卡片：服务状态运行中、数据库状态正常。
- 数据库里迁移跑到最新：
  ```sql
  SELECT version FROM schema_migrations ORDER BY version DESC LIMIT 5;
  ```
  最上面一条应当是 **`V025__repository_reconcile_settings`**（`version` 列存的是脚本文件名）。

**不对时**
- 迁移没跑到 V025 → 看服务端日志里 `Migration` 相关行，多半是某个迁移脚本报错后停在半路。
- 数据库状态不正常 → 先确认 PostgreSQL 服务起来了，再看连接串。

---

## 第 1 步 · 注册

1. 客户端机器跑 `BackupMonitor.Agent.Setup.exe`。局域网模式下装完会自动发现服务端。
2. 回管理台「客户端」页。

**该看到什么**
- 列表里出现这台机器。
- LAN 自动登记模式：状态直接是「在线」；Secure 模式：状态是「待审批」，点「审批」后转在线。
- **IP 列有值**（本轮新增），并且和客户端机器 `ipconfig` 看到的地址对得上。
- 点进详情，「对端 IP」和「本机网卡地址」两行都有内容。

**不对时**
- 列表里根本没出现 → Agent 日志搜 `注册`。看是卡在「等待服务器审批」还是连不上。
- 连不上 → 确认防火墙放行、服务端地址写对。LAN 模式确认客户端和服务端在同一网段
  （`LanMode:PrivateNetworkOnly` 默认只接受私网地址的免令牌登记）。

---

## 第 2 步 · 心跳

在客户端页停留两分钟。

**该看到什么**
- 「最近心跳」从「刚刚」开始规律跳动，间隔与服务端配置一致。
- 详情页有 CPU/内存/磁盘/服务状态。
- 数据库里心跳在累积：
  ```sql
  SELECT count(*), max(received_at) FROM client_heartbeats;
  ```

**顺带验本轮的改动**：在客户端机器上改一个网卡地址（或插拔一次网线），
等两个心跳周期，管理台「IP 列」应当跟着变。这条验的是
「网卡列表不再是注册那一刻的死值」。

**不对时**
- 心跳停了但 Agent 进程还在 → Agent 日志搜 `心跳`。B-02 之前执行指令期间会断心跳，
  如果又出现这个现象，说明主循环拆分回退了。

---

## 第 3 步 · 建任务并扫描

1. 客户端机器上准备一个备份源目录，塞几个文件进去。
2. 管理台「备份任务」→ 新建：选这台客户端、填源路径、选识别器（先用「最新单文件」最简单）。
3. 等一个扫描周期，或者在客户端详情页手工下发一次扫描。

**该看到什么**
- 「候选备份集」出现一条，预检状态「通过」。
- 文件数和字节数与源目录对得上。

**不对时**
- 预检状态是「仍在变化」→ 正常，源文件刚写完还在稳定窗口内，等一轮。
- 「路径不存在 / 拒绝访问」→ Agent 是以服务账号跑的，确认那个账号对源目录有读权限。
- 一直「未扫描」→ Agent 日志搜 `扫描`，看指令有没有下到。

---

## 第 4 步 · 上传

对候选备份集发起上传（自动模式会自己发起，手动模式在候选列表点上传）。

**该看到什么**
- 客户端列表该行「运行状态」变成「上传中」，点这个徽标能跳到「传输中」页。
- 侧栏「值守 → 传输中」出现这条会话：进度条在涨，百分比、已传/总量、速度、
  预计剩余时间都有值，页面每 5 秒自动刷新。概览页也会多出一个「正在传输」卡片。
- 「静默」那一列应当一直在几秒到几十秒之间跳动，**不会一路往上涨**。
- 服务端暂存盘出现会话目录：`<staging_path>/sessions/<uuid>/`。

**这一步是这一轮改动的主验收点。** 传一份足够大的文件（建议 ≥ 2 GB，
或者临时把带宽限速调低），确认这几件事：
1. 上传**能跑完**。此前 Agent 的进度上报器有一个必现缺陷（`TimeSpan.MinValue`
   参与减法溢出），第一个分块传完就抛 `TimeSpan overflowed because the duration is too long.`，
   指令判 `upload_failed`——**任何上传都完不成**。看到这条报错说明装的还是旧 Agent 包。
2. 传输过程中数字一直在动，不需要手工刷新页面。
3. 中途拔掉客户端网线，「静默」列开始往上涨，超过阈值后该行变成「疑似卡住」
   （阈值随实测速度放大，窄带链路上不会被误报）。插回网线后恢复正常。

**不对时**
- 「传输中」页一直空着，但客户端确实在传 → 先确认会话状态在
  `created/uploading/paused/retry_wait/received/verifying` 之内；终态会话不显示是对的。
- 速度一列显示「—」→ 第一次采样没有可比对象，等一个刷新周期；
  仍然是「—」说明 `started_at` 和 `uploaded_bytes` 都还是空的，会话还没真正开始收数据。

**顺带验一条**：传大文件时中途把 Agent 服务停掉，会话应当在
`upload_session_timeout_seconds`（默认 3600 秒）之后被 LifecycleExpiryWorker 判为过期，
暂存目录随后被清理。**这条以前是不会发生的**——僵尸会话会一直占着并发额度，
攒够 `max_concurrent_uploads` 之后这台机器再也传不了东西。
不想等一小时的话，先把这个配置项改小再测。

**不对时**
- 一直 409 CLIENT_BUSY → 这台客户端有没清掉的活动会话。查：
  ```sql
  SELECT id, status, created_at, last_activity_at FROM upload_sessions
  WHERE client_id = '<客户端ID>' AND status IN ('created','uploading','paused','retry_wait');
  ```
- 507 → 暂存盘满了。

---

## 第 5 步 · 入库

上传完成后等入库队列处理。

**该看到什么**
- 「备份集」页出现一条，状态「可用」，编号形如 `BS-000001`。
- 仓库目录里有正式目录：`<repository_path>/<主机名>/<任务名>/<yyyy-MM-dd_HHmmss>/`，
  里面有备份文件和 `manifest.json`。
- `manifest.json` 里的文件数、大小、SHA-256 与源文件一致。

**这是整条链最关键的一步**：到这里为止，数据已经从客户端安全地落到了服务端仓库。

**顺带验本轮的改动（仓库孤儿对帐）**：
1. 手工在仓库里造一个假孤儿：复制一个已有的备份集目录，改名成一个新的版本目录名
   （比如 `2020-01-01_000000`），保留里面的 `manifest.json`。
2. 把它的修改时间改到一天以前（PowerShell：
   `(Get-Item '<路径>').LastWriteTimeUtc = (Get-Date).AddDays(-2)`）。
3. 把对帐间隔临时改小：
   ```sql
   UPDATE system_settings SET setting_value = '300'::jsonb
   WHERE setting_key = 'repository_reconcile_interval_seconds';
   ```
   重启服务端服务让它重新读配置。
4. 等一轮，「告警」页应当出现一条 **「仓库发现 N 个无数据库记录的目录」**，
   正文里列出路径和占用大小。

**这条告警不会自动删任何东西**——确认之后手工处理，然后下一轮对帐会自动恢复该告警。

**不对时**
- 备份集状态是「校验失败」→ 服务端日志搜备份集编号，多半是 SHA-256 对不上。
- 一直卡在「校验中」→ 看 VerificationWorker 有没有起来。

---

## 第 6 步 · 恢复下载

1. 「备份集」页对刚入库那条点「恢复」，填用途，提交。
2. 「恢复请求」页等状态变成「就绪」。
3. 点「签发下载令牌」，复制链接，在浏览器里打开。

**该看到什么**
- 下载下来一个 ZIP，解开之后文件内容和第 3 步放进源目录的**逐字节一致**。
- 恢复请求详情里「已下载」字节数对得上，「下载端 IP」有值。

**这一步走通，才算真的能替代手工备份**——备份不是写进去就完了，是能拿回来。

**不对时**
- 状态卡在「校验中」→ 详情里会显示「校验队列」还有几个任务在前面。
- 令牌打开报「下载链接已过期」→ TTL 默认 30 分钟，重新签发一次。
  注意**令牌在 TTL 内可以重复使用**，这是为了支持断点续传，是有意的设计。

## 附：mTLS 正向用例（Secure 模式才需要）

LAN 一键部署模式跳过这一节。Secure 模式下：

1. 客户端证书应当在注册审批时签发，详情页「证书指纹」和「证书有效期」有值。
2. 用 `curl` 不带客户端证书访问 Agent 接口，应当被拒：
   ```bash
   curl -k https://<服务端>/api/v1/agent/config
   ```
   期望 401/403，**不是** 200。
3. 带上客户端证书访问，应当通过：
   ```bash
   curl -k --cert client.pem --key client.key https://<服务端>/api/v1/agent/config
   ```
4. 在客户端详情页点「吊销」之后，同一张证书再访问应当被拒。

第 2 步是最容易出问题的一条：nginx 配成 `optional` 而不是 `on` 时，
无证书请求会直接放行到 Kestrel，等于 mTLS 形同虚设。

---

## 走完之后

链路通了，说明这套东西作为备份工具是可用的。
剩下的都是可靠性问题——断电、断网、磁盘满这些场景，
建议至少补做一次：**入库过程中直接断电，重启后看仓库对帐能不能把残骸报出来。**
