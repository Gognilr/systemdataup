# 实施方案：服务端配置备份恢复 + 客户端可维护性

日期：2026-08-28
范围：服务端安装器（BackupMonitor.Server.Setup）、Agent（BackupMonitor.Agent）、管理端 API 与前端

起因：两个现场问题。
一是「服务端重装后，客户端要不要重装」——现状是换机重装必须逐台重装客户端；
二是客户端列表里 IP 显示成 `fe80::…` 链路本地地址、名称改不了。

追加三项：保留策略的默认值只能改数据库、待办事项只能看不能处理、
概览的待办队列与待办页对不上。

下面八项 A–H，A 是主线，B/C 是 A 失效时的兜底，D/E/F 是日常可维护性，
G/H 是待办这条链路上的两个缺陷（其中 G 的动作分发和 H 的口径分裂都是确定的 bug，不是需求）。

---

## A. 服务端配置备份与恢复（密钥 + 数据库）

### 现状

安装器里已经有「导出密钥包 / 导入密钥包」（`.bmkp`），
实现在 `ServerMaintenance.ExportKeyPackageAsync` / `ImportKeyPackageAsync`
（src/server/BackupMonitor.Server.Setup/ServerMaintenance.cs:143、:189），
UI 按钮在 src/server/BackupMonitor.Server.Setup/SetupForm.cs:134-135。

包内固定三个文件（ServerMaintenance.cs:601 `GetKeyPackageFiles`）：

| 文件 | 内容 | 客户端为什么依赖它 |
| --- | --- | --- |
| `server-secrets.json` | InstanceId、JWT 签名密钥、**指令签名 RSA 私钥**、CA 与证书口令、PG 超级用户口令 | Agent 固定了对应公钥（`AgentOptions.ServerSigningPublicKey`），换了就拒收所有指令和配置 |
| `client-ca.pfx` | 签发客户端证书的 CA（含私钥） | 换了以后客户端已有证书的链验不过 |
| `server-certificate.pfx` | 服务端 TLS 证书 | Agent 固定了它的 SHA-256 指纹（`AgentOptions.ServerCertificateFingerprint`），换了以后 TLS 直接失败 |

**结论：服务端的密码学身份已经能备份、能还原。**

### 缺口

**数据库完全没有备份。** 全代码没有任何 pg_dump / pg_restore 调用。

这不是「少了历史数据」这么简单——客户端 mTLS 认证是拿证书指纹去 `client_certificates` 表查客户端
（src/src/BackupMonitor.Api/Security/ClientCertificateAuthenticationHandler.cs:66
`AuthenticateByThumbprintAsync`）。新装出来的库是空的，客户端证书虽然仍能通过 CA 链校验，
但查不到记录，结果是**每次心跳都 401，永远不恢复**。任务、计划、识别规则、用户、告警历史同样全丢。

另外要说清楚一个现状：**原机重装、卸载时不勾「删除数据」，今天这条路是通的**——
安装器见到已有 PostgreSQL 集群会跳过 initdb 保护存量数据
（src/server/BackupMonitor.Server.Setup/PostgreSqlManager.cs:204，
以及 ServerMaintenance.cs:424 的注释）。真正没解决的是**换机器、或清盘重装**。

### 方案

把「密钥包」升级为「配置备份包」：密钥 + 数据库一起打包。

pg_dump.exe 随 PostgreSQL 16.14 载荷一起安装，路径 `<安装目录>\PostgreSQL\bin\pg_dump.exe`
（载荷清单见 dist/payload-manifest.json；安装器已经在用同目录下的 pg_ctl.exe，
ServerMaintenance.cs:486），不需要额外分发任何东西。

包格式（建议扩展名 `.bmbp`，zip）：

```
manifest.json          包版本、导出时间、服务端 InstanceId、产品版本、数据库 schema 版本
keys/server-secrets.json
keys/client-ca.pfx
keys/server-certificate.pfx
db/backupmonitor.dump  pg_dump -Fc 自定义格式
```

导出流程：

1. 校验三个密钥文件存在（复用 `EnsureKeyPackageFilesExist`）；
2. 调 `pg_dump -Fc --no-owner --no-privileges`，口令从 server-secrets.json 取，
   走 `PGPASSWORD` 环境变量而不是命令行参数（命令行参数在任务管理器里全局可见）；
3. 打包 → 临时文件 → `SecureFileSystem.ApplyFileAcl` → 原子 Move。
   这套顺序照抄现有 `ExportKeyPackageAsync`，包括「不允许覆盖当前密钥文件」那条自检。

导入流程（顺序不能变）：

1. 校验 manifest：schema 版本高于当前安装包 → 直接拒绝并说明要先升级服务端；
   低于当前 → 允许，恢复后由 `MigrationRunner` 补迁移；
2. 停 `BackupMonitor.Server` 服务，**保持 PostgreSQL 运行**（要用它来 restore）；
3. 覆盖三个密钥文件（复用现有 `ReplaceProtectedFile` 与失败回滚逻辑，
   ServerMaintenance.cs:205-245 已经写好了备份/回滚，直接扩展）；
4. `pg_restore --clean --if-exists`；
5. 跑一次迁移；
6. 启动服务。

失败要能回滚：密钥有现成的 `.import-backup` 机制；数据库在 restore 之前先自动导出一份
到数据目录下的 `pre-restore-<时间戳>.dump`，restore 失败时提示用它回退。

**必须在 UI 和文档里写明的一点**：备份包只覆盖「配置与身份」，
不含仓库（Repository）和暂存区（Staging）里的实际备份文件。
只恢复库不恢复仓库，会得到一堆指向不存在文件的 `backup_files` 记录。
仓库目录需要管理员另行复制，导入完成后的提示里要点名这件事。

### 落点

- src/server/BackupMonitor.Server.Setup/ServerMaintenance.cs
  新增 `ExportBackupPackageAsync` / `ImportBackupPackageAsync`；
  现有密钥包导出/导入保留不动（跨版本迁移密钥仍然有用）。
- src/server/BackupMonitor.Server.Setup/SetupForm.cs
  加「导出配置备份 / 导入配置备份」两个按钮，与密钥包按钮并列。
- 新增 `PostgreSqlManager.DumpAsync` / `RestoreAsync`，与现有 initdb/pg_ctl 调用同风格。

### 验收

在 A 机安装 → 接入 2 台客户端跑通心跳与一次备份 → 导出配置备份包 →
在 B 机（全新系统）安装 → 导入备份包 → **客户端零操作**，5 分钟内恢复心跳，
任务、计划、历史与 A 机一致。前提是 B 机的机器名或 IP 与 A 机一致，否则见 C。

## B. Agent 身份失联自愈

### 现状

Agent 启动时串行走一次注册（src/agent/BackupMonitor.Agent/AgentWorker.cs:98
`WaitForRegistrationAsync`），一旦 state.json 里存在 ClientId 和证书，
就永远进入心跳/指令/扫描三条循环，**再也不会回到注册流程**。

心跳收到 401 时只做一件事：回收 HTTP 连接后重试
（AgentWorker.cs:232，本意是解决「连接池里的旧连接携带旧证书身份」）。
服务端库丢了的场景下，这个重试是无限的、且永远不会成功。

服务端侧已经补上了让位逻辑：同一 machineId 重新注册时，
若旧身份已被 `SystemWatchdogWorker` 判定 Offline，就吊销旧身份让位
（src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs
`SupersedeOfflineClientAsync`）。但**没有任何客户端会去触发它**——
现役 Agent 不会重新注册。

### 方案

给 Agent 加一条「身份已失效」的判定与自愈路径：

1. 服务端在按指纹查不到证书时，返回一个可区分的响应体
   （现在是笼统的 401 / NoResult，见 ClientCertificateAuthenticationHandler.cs:100 的日志分支）。
   建议在 401 响应里带 `code = "CLIENT_IDENTITY_UNKNOWN"`，
   与「证书被吊销」「客户端被禁用」区分开——**被禁用绝不能触发重新注册**，
   否则管理员刚禁用的机器自己就转回来了。
2. Agent 侧：连续 N 次（建议 5 次，约 5 分钟）收到 `CLIENT_IDENTITY_UNKNOWN`，
   清除本地 ClientId / 证书 / RegistrationId（**保留 machineId 和私钥**），
   回到 `WaitForRegistrationAsync`。
3. 与服务端的 Offline 让位配合：新库里根本没有旧记录，直接注册成功；
   老库里有旧记录且已判 Offline，走让位；旧记录还在线，返回 409，
   Agent 安静重试（AgentWorker.cs 已有 409 分支）。

代价说清楚：这条路径恢复的是「连接」，不是「配置」。
库如果是空的，任务和计划要重配。它的定位是**备份包也丢了时的兜底**，不是 A 的替代品。

### 落点

- src/src/BackupMonitor.Api/Security/ClientCertificateAuthenticationHandler.cs：细化失败原因。
- src/agent/BackupMonitor.Agent/AgentWorker.cs：心跳循环的 401 分支加计数与重置。
- src/agent/BackupMonitor.Agent/AgentStateStore.cs：加一个「清除身份、保留机器指纹」的方法。

### 验收

客户端正常运行中，服务端换空库重启 → 客户端 5 分钟内自动重新登记、恢复心跳，
无需登录客户机做任何操作；
把该客户端在服务端「禁用」→ 客户端**不得**自动重新登记。

## C. Agent 地址失联重发现

### 现状

LAN 发现只在安装向导里用一次
（src/agent/BackupMonitor.Agent.Setup/SetupForm.cs:26 持有 `LanDiscoveryClient`），
之后服务地址固化在 Agent 的 appsettings.json 里（`AgentOptions.ServerUrl`）。
运行期的 Agent 不做任何发现。

服务端换 IP 时：ServerUrl 填的是机器名且机器名不变的话，靠 DNS/NetBIOS 能兜住；
填的是 IP 就彻底断联，只能逐台改配置。

（本次已改进的部分：发现探测改为多轮 + 逐网卡定向广播，
防火墙规则 profile 从 private 改为 any——这些解决的是「装的时候发现不到」，
不解决「装完之后服务端搬家」。）

### 方案

在 Agent 里加一个「地址失联」路径：

1. 触发条件收紧：只在**连接层失败**（DNS 解析失败 / 连接被拒 / 连接超时）
   连续 N 次后触发。已经建立 TLS 但返回 4xx/5xx 的，说明地址是对的，不触发。
2. 触发后跑一次 LAN 发现（把 `LanDiscoveryClient` 从 Setup 提到共享程序集，两边复用）。
3. **接受候选服务端的条件必须同时满足**：
   - `ServerInstanceId` 与本地记录的一致；
   - TLS 证书指纹与本地固定的 `ServerCertificateFingerprint` 一致。

   缺了这一步，同网段任何人广播一个应答就能把全部客户端劫走——
   发现协议本身是无认证的明文 UDP，只能靠这两个固定值兜底。
4. 命中后改写本地 ServerUrl 并持久化，记一条本地日志，下次启动直接用新地址。

前置：Agent 要先把 `ServerInstanceId` 存进 state.json。现在只有安装向导见过它，
Agent 运行期并不知道自己该连哪个实例——这一条要先补。

### 落点

- 把 LanDiscoveryClient 移到 Shared（或 Agent 与 Setup 共用的程序集）。
- src/agent/BackupMonitor.Agent/AgentStateStore.cs：持久化 ServerInstanceId。
- src/agent/BackupMonitor.Agent/AgentApiClient.cs：暴露「地址已变更，重建 HttpClient」。
- Agent 安装向导：把发现到的 InstanceId 写进初始 state。

### 验收

客户端正常运行 → 服务端换 IP（机器名也改）→ 客户端在 N 分钟内自动找回并恢复心跳；
同网段起一个伪造的发现应答服务 → 客户端**不得**切过去，且本地日志记录拒绝原因。

## D. 客户端 IP 显示成 IPv4

### 现状

列表 IP 列显示 `lastRemoteIp`（src/src/BackupMonitor.Api/wwwroot/js/ui.js:227 `ipCell`），
值来自服务端看到的对端地址
（`AuditService.ClientIp` = `Connection.RemoteIpAddress?.ToString()`，
src/src/BackupMonitor.Infrastructure/Services/AuditService.cs:42
→ AgentHeartbeatService.cs:101）。

现场看到的是 `fe80::3d6c:5d72:c0ab:128b%12` 这类**链路本地 IPv6**。
这说明 Agent 确实是走 IPv6 连上来的，不是显示格式问题：
发现服务默认播的地址是 `https://{机器名}:{端口}`
（src/src/BackupMonitor.Api/Discovery/LanDiscoveryHostedService.cs:172 `ResolveApiAddress`），
Windows 名称解析（LLMNR/NetBIOS/DNS）优先返回 fe80 地址，于是 TCP 走了 IPv6。

同时 Agent 自报的网卡列表也是脏的：`SystemProbe.GetIpAddresses`
（src/agent/BackupMonitor.Agent/SystemProbe.cs:133）只排除了回环，
fe80 链路本地和 169.254 APIPA 全都上报，详情抽屉里那一串同样没法看。

### 方案（三层，建议都做）

**D1 采集层**——`SystemProbe.GetIpAddresses` 过滤掉
IPv6 链路本地（`IsIPv6LinkLocal`）、IPv6 站点本地、169.254/16 APIPA，
并让 IPv4 排在 IPv6 前面。这是最省事、收益最直接的一改。
注意它参与心跳摘要计算（SystemProbe.cs:49 `ComputeSnapshotDigest`），
过滤后首次心跳会因摘要变化重报一次，属于预期行为。

**D2 显示层**——两件事：

- `AuditService.ClientIp` 里对 IPv4 映射地址做还原：
  `IsIPv4MappedToIPv6` 时 `MapToIPv4()`，否则双栈监听下 IPv4 客户端会存成 `::ffff:192.168.1.10`；
- 列表 IP 列改成「优先 IPv4」：`lastRemoteIp` 本身是 IPv4 就直接用；
  不是（如 fe80）就回落到自报网卡里的第一个 IPv4，
  `title` 里保留真实对端地址并标注来源。
  需要在 `ClientListItemDto` 补一个 IPv4 字段（自报列表目前只在详情 DTO 里，
  src/src/BackupMonitor.Shared/Models/Admin/ClientDtos.cs:83），
  在 `ClientAdminService.GetListAsync` 的投影里算出来
  （src/src/BackupMonitor.Infrastructure/Services/ClientAdminService.cs:148）。

**D3 根因层**——让 Agent 优先用 IPv4 建连。
`AgentApiClient.RebuildClient` 现在用的是 `HttpClientHandler`
（src/agent/BackupMonitor.Agent/AgentApiClient.cs:89），它没有 `ConnectCallback`。
改成 `SocketsHttpHandler`：

- 客户端证书 → `SslOptions.ClientCertificates`；
- 指纹固定的回调 → `SslOptions.RemoteCertificateValidationCallback`（签名不同，要改写）；
- 新增 `ConnectCallback`，DNS 结果里优先 `AddressFamily.InterNetwork`，IPv4 连不上再回落 IPv6。

D3 不改任何配置地址，只改连接偏好，副作用最小，
而且做完以后 `lastRemoteIp` 自然就是 IPv4 了，D2 的回落逻辑退化成保险。

### 验收

客户端列表 IP 列全部显示 IPv4；详情里的「本机网卡地址」不再出现 fe80 和 169.254；
只有 IPv6 的环境下仍能显示对端 IPv6 地址而不是显示「—」。

## E. 客户端名称与分组可在服务端修改

### 现状

**改不了。** `AdminClientController`
（src/src/BackupMonitor.Api/Controllers/AdminClientController.cs）
只有 approve / reject / disable / enable / revoke / refresh-metrics 六个写操作，
没有任何更新端点。

名称来自注册请求：`DisplayName` 为空时回退成主机名
（AgentRegistrationService.cs:168）。之后**心跳完全不碰** DisplayName 和 Hostname
（AgentHeartbeatService.cs 只更新时间偏移、对端 IP、网卡列表、状态），
所以服务端改的名字不会被 Agent 覆盖——这是加改名功能的安全前提。

分组同理：只在注册时由注册令牌带入 `ClientGroupId`（AgentRegistrationService.cs:169），
之后没有任何途径调整，现场看到的「分组」列因此全是空的。

### 方案

新增 `PATCH /api/v1/admin/clients/{clientId}`，权限 `perm:clients.manage`
（与审批/禁用同级，权限种子见 src/database/V001__initial_schema.sql:1016，不需要新增权限项）。

请求体两个可选字段：`displayName`、`clientGroupId`。语义：

- 字段缺省 = 不改；
- `clientGroupId` 显式传 null = 移出分组。

约束与配套：

- `displayName` 非空、去首尾空白、长度上限对齐 `clients.display_name` 列定义；
- 走 `AuditService` 记一条 `client.updated`，带改前改后值——改名会让「这台机器是谁」
  的历史线索断掉，审计里必须留痕；
- 走现有 RowVersion 并发控制（`Client : IHasRowVersion`）。

**关键配套（否则改名会莫名其妙丢失）**：
`SupersedeOfflineClientAsync`（AgentRegistrationService.cs:272）在客户端重装时
吊销旧行、新建一行，管理员改过的名字和分组会回到 Agent 自报值。
让位时要把旧行的 `DisplayName`、`ClientGroupId` 继承到新行——
仅当旧行的名字被人工改过（即与 `Hostname` 不同）时才继承，避免把旧主机名黏在改过名的机器上。

前端：客户端列表的「更多操作」菜单里加「重命名 / 改分组」，
复用 `formModal`（clients.js 已有同类用法，见监控服务编辑 clients.js:488）。

### 验收

在列表里把某客户端改名并分组 → 刷新后保持；该客户端重启、重新心跳后名字不变；
把该客户端卸载重装（触发 supersede 重新登记）后名字与分组仍然保持；
审计日志里能查到这次改名的改前改后值。

## F. 保留策略的默认值可在界面上设置

### 现状

「新建任务默认绑定哪份策略」这个机制 **V027 已经做了**：

- 配置项 `system_settings.default_retention_policy_id`，
  种子值指向预置策略「只留最近 7 份」`d0000002-0000-0000-0000-000000000007`
  （src/database/V027__retention_defaults_and_presets.sql:52）；
- 读取入口 `RetentionPolicyService.GetDefaultPolicyIdAsync`
  （src/src/BackupMonitor.Infrastructure/Services/RetentionPolicyService.cs:52），
  值为空串或不是 GUID 一律当作「不自动绑定」；
- 建任务不选策略时由服务端兜底绑上默认策略，
  已有测试覆盖（src/tests/BackupMonitor.Infrastructure.Tests/RetentionDefaultBindingTests.cs）；
- 前端已经能**看见**：策略列表有「新建任务默认」徽标
  （src/src/BackupMonitor.Api/wwwroot/js/views/retention.js:21），
  任务表单下拉里标「（默认）」（views/tasks.js:243）。

**缺口：全是只读的，改不了。**
`AdminRetentionPolicyController`
（src/src/BackupMonitor.Api/Controllers/AdminRetentionPolicyController.cs）
只有 list / get / create / update / delete 五个动作，没有「设为默认」；
系统也没有通用的 system_settings 编辑 API
（只有通知渠道和存储路径各自开了专用端点）。
想换默认策略，今天只能直接改数据库。

由此还带出一处自相矛盾：删除默认策略会被 409 挡下，提示
「该策略是新建任务的默认策略，请先改配默认策略再删除」
（RetentionPolicyService.cs:175）——**而界面上根本没有「改配默认策略」这个动作**。
提示指向了一个不存在的操作，实际效果是那份种子策略谁也删不掉。

另一层（优先级低）：新建策略表单的字段初值——保留最近 7 份、回收站 7 天、最短保留 0 天——
是前端硬编码（retention.js:41-49）加实体默认值（RetentionPolicy.cs）。
可以做成可配，但真正该配的是「默认用哪份策略」，字段初值改起来收益很小，本方案不做。

### 更要紧的一点：现在的「默认」只是建任务那一刻的一次性拷贝

V027 的实现是**建任务时把默认策略 ID 写死**进 `backup_tasks.retention_policy_id`。后果：

- 改默认策略只影响此后新建的任务，**存量任务纹丝不动**；
- V027 迁移把历史上所有 `retention_policy_id IS NULL` 的任务也硬绑成了 `…007`
  （V027__retention_defaults_and_presets.sql 末尾的 UPDATE），
  从此再也分不清「用户特意选了只留 7 份」和「当年兜底绑上的」。

问「能否自己设置默认值」，期待的多半是**改了以后，那些没特意配过的任务跟着变**。
当前模型给不了。因此本项分两档交付。

### 方案 F1（最小可交付）：默认策略可在界面上切换

新增一个动作，权限 `perm:backups.manage`（与策略的增删改同级，不新增权限项）：

- `POST /api/v1/admin/retention-policies/{policyId}/set-default`

要点：

- 写 `system_settings.default_retention_policy_id` 之后必须调
  `SystemSettingsProvider.Invalidate()`。该 Provider 是**单例**、带 60 秒缓存
  （src/src/BackupMonitor.Infrastructure/Services/SystemSettingsProvider.cs:19-21），
  不失效的话「设为默认」要等一分钟才生效，界面上会表现为设置没保存。
- **刻意不做「清除默认」**。清除后新建任务会回到「不绑策略 = 永不清理」，
  正是 V027 花力气堵上的坑；给它一个界面按钮等于把坑重新挖开再立个警示牌。
  真要回到旧行为改 SQL 就够了，这种事一年不会有一次。
  （初稿把它设计成「危险动作 + 二次确认」，是错的——默认必须是安全的，不给自毁开关。）
- 走审计 `retention.default_changed`，记改前改后的策略 ID 与名称。
  保留策略决定数据什么时候被删，改配默认策略必须留痕。
- 目标策略必须存在；策略被删时的 409 提示保持不变——
  这次改动之后，那句提示指向的动作才真正存在。

前端：策略列表每行的操作里加「设为默认」（已是默认的那行置灰并说明原因，
沿用 `actBtn` 的 `allowed=false` + `why` 惯例），
页面顶部补一行当前默认策略的说明文字。

### 方案 F2（模型修正）：NULL 表示「跟随默认」而不是「永不清理」

把语义倒过来：

- `backup_tasks.retention_policy_id IS NULL` = **跟随默认策略**；
- 清理器读取时回落到 `default_retention_policy_id`
  （src/src/BackupMonitor.Infrastructure/Services/RetentionCleanupWorker.cs:335
  现在是 `Where(t => t.RetentionPolicyId != null)`，直接把没绑策略的任务跳过了）；
- 建任务不选策略就真的留 NULL，`BackupTaskService` 里那段兜底写死可以撤掉；
- 「永不清理」如果确实需要，做成一份**显式策略**（份数与周期全留空），
  而不是靠「字段为空」这种隐式语义——隐式语义正是 V027 事故的根源。

配套：

- 任务表单的策略下拉加一项「跟随默认（当前：只留最近 7 份）」，值为 NULL；
- **存量那批被 V027 写死的任务不回填 NULL**。分不清哪些是用户特意选的，
  批量回填等于替用户改了保留规则，风险高于收益。让它们保持现状，
  用户想改成「跟随默认」自己在任务里改一次即可。
- `RetentionDefaultBindingTests` 的断言要跟着改：从「绑上默认策略 ID」
  改成「留 NULL 且清理时按默认策略执行」。

### 落点

- src/src/BackupMonitor.Api/Controllers/AdminRetentionPolicyController.cs：F1 端点。
- src/src/BackupMonitor.Infrastructure/Services/RetentionPolicyService.cs：
  `SetDefaultAsync`，与现有 `GetDefaultPolicyIdAsync` 放一起。
- src/src/BackupMonitor.Api/wwwroot/js/views/retention.js：行操作。
- F2：RetentionCleanupWorker.cs:334-342 的任务查询与策略解析、
  BackupTaskService 的兜底绑定、views/tasks.js:243 的下拉。

### 验收

F1：把默认策略改成另一份 → 立即（不等 60 秒）新建一个不选策略的任务，绑定的是新默认策略；
删除当前默认策略被 409 挡下，按提示改配后可以删除；审计里能查到变更记录。

F2：建一个「跟随默认」的任务 → `retention_policy_id` 为 NULL →
清理器按当前默认策略清理它；切换默认策略后，同一个任务改按新策略清理，无需逐个任务改配。

## G. 待办事项要能就地处理

### 现状

待办页 5 类事项里，**只有 1 类带真正的处理动作**
（src/src/BackupMonitor.Api/wwwroot/js/views/todo.js:56-68）：

| 待办类型 | 按钮 | 实际行为 |
| --- | --- | --- |
| 客户端等待审批 | 去审批 | 跳 `#/clients` |
| 最近自动登记 | 查看 | 跳客户端详情 |
| 任务需要检查 | 查看 | 跳任务详情 |
| 恢复请求等待签发 | 签发 | `kind:'act'` —— 唯一的真动作 |
| 严重告警未确认 | 去确认 | 跳 `#/alerts` |

**而唯一那个真动作在待办页上必然失败。** 动作分发是
`ACTIONS[view + ':' + action]`（js/app.js:84 `App.act`），
而 `ACTIONS['restores:token']` 在 views/restores.js:100 模块求值时才注册。
视图是按路由懒加载的（js/app.js:461 `VIEW_LOADERS`），
待办页只加载 todo.js，restores.js 根本没进来 → 查不到函数 →
`toast('该动作暂不可用')`。

只有在同一次会话里先访问过「恢复」页、再回到待办，才碰巧能用——
开发时按顺序点过来恰好绕开了，所以这个 bug 活到了现在。

### 方案

**G1 先修分发（根治，一处改动）**：`App.act` 查不到动作时，
按 view 名去 `VIEW_LOADERS` 懒加载对应模块，然后重试一次；
仍然查不到才提示「该动作暂不可用」。
所有跨页动作（待办、命令面板、以后概览上的按钮）都受益，
不需要每加一个跨页按钮就记得手工 import。

**G2 再补动作**：待办页把「跳过去」换成能就地做完的事：

- 客户端等待审批 → 就地「审批」（`ACTIONS['clients:approve']` 已存在，clients.js:237）；
- 严重告警未确认 → 就地「确认」（`ACTIONS['alerts:ack']` 已存在，alerts.js:126）；
- 任务需要检查 → 保持跳转。任务出问题的原因各不相同，
  待办页给不出「一键处理」的正确语义，跳过去看是对的；
- 最近自动登记 → 保持跳转（本来就是知会性质，不是待办）。

每个就地动作都要带 `data-after-loader="todo"`（现有机制，app.js:210），
处理完自动刷新待办队列，让事项从列表里消失。

批量审批也值得做：局域网模式下一次上线一批机器是常态，
逐台点「审批」很快就会让人放弃用待办页。

### 落点

- src/src/BackupMonitor.Api/wwwroot/js/app.js：`App.act` 的懒加载重试。
- src/src/BackupMonitor.Api/wwwroot/js/views/todo.js：动作定义。

### 验收

浏览器强刷后**直接**进待办页（不先访问其他页），点「签发」能正常弹出令牌对话框；
点「审批」能就地审批并让该条待办消失；
处理完最后一项后横幅变成「没有待处理事项」。

## H. 概览的待办队列与待办页口径统一

### 现状

现象：概览的「待办队列」显示「一切正常」，点进待办页却有若干条事项。

原因是**「什么算待办」有两份互不相识的实现**：

- 待办页走服务端聚合 `GET /api/v1/admin/reports/todo-summary`
  （src/src/BackupMonitor.Infrastructure/Services/ReportService.cs:316）；
- 概览完全没调它，而是拉四个 summary 端点在浏览器里重算一遍
  （src/src/BackupMonitor.Api/wwwroot/js/views/dashboard.js:23 `renderTodoQueue`，
  以及 dashboard.js:178 的 `todoCount`）。

todo.js 顶部注释写着「不再有浏览器/服务端两份规则」——
那次改造只覆盖了待办页，概览被落下了。四处差异：

| 项 | 待办页（服务端） | 概览（浏览器重算） |
| --- | --- | --- |
| 最近自动登记 | 7 天内 `lan_simple` 登记的客户端 | **完全不统计** |
| 问题任务 | 预检异常，或超 24h 没扫描且超 3 天没成功 | 14 天热力图里存在 `failed` 日的任务数 |
| 严重告警 | 只算 `Open` | 算 `Open + Acknowledged + InProgress`（ReportService.cs:25 `ActiveStatuses`） |
| 恢复请求 | `CountAsync`，不受分页影响 | `items.length`，pageSize=100 封顶 |

**局域网自动登记形态下第一条必然触发**：客户端不需要审批，
`pending_approval` 恒为 0，待办页列出来的是「最近自动登记」的机器，
而概览压根不统计这一类 → 四项全 0 → 概览显示「一切正常」。

第二条同样能造成这个现象：一个预检失败但从没跑过的任务，
热力图里没有 `failed` 日，概览看不见、待办页看得见。
第三条方向相反——概览会把已确认的严重告警也算进「需要关注」，偏多。

### 方案

概览改调 `todo-summary`，删掉 `renderTodoQueue` 里那套重算，
`todoCount` 也直接用服务端返回的各段 count 相加（与 todo.js 同一份算法）。
数据一次全给，概览只需要取 count 和前几条 items。

顺带：概览现在为了算待办拉了 `restore-requests?pageSize=100`，
改完之后这个请求可以去掉，首屏少一次往返。

判定规则从此只有服务端一份。以后再加待办类型，两个页面自动同步。

### 落点

- src/src/BackupMonitor.Api/wwwroot/js/views/dashboard.js:23（`renderTodoQueue`）、
  :164（并发请求列表）、:178（`todoCount`）。

### 验收

造一台 `lan_simple` 自动登记的客户端 → 概览待办队列与待办页同时出现该条目、计数一致；
确认一条严重告警 → 两个页面的计数同步减一；
任务数超过 100 个恢复请求时两边计数仍然一致。

## 实施顺序

| 顺序 | 项 | 理由 |
| --- | --- | --- |
| 0 | **G1** 动作分发懒加载 | 确定的 bug，改一处函数；待办页现在点「签发」必定失败 |
| 0 | **H** 概览与待办口径统一 | 确定的 bug，删掉浏览器侧重算即可；现场已经踩到 |
| 1 | **A** 配置备份与恢复 | 「服务端配置能备份、重装后客户端不用动」的正解，其余都是兜底 |
| 2 | **D** IPv4 显示（先 D1 + D2） | 改动小、现场立刻可见；D1 单独就能解决一大半 |
| 3 | **E** 改名与分组 | 独立、无风险，但必须连 supersede 继承一起做 |
| 3 | **F1** 默认策略可切换 | 纯服务端 + 前端，改动最小；顺带修掉「提示指向不存在的动作」 |
| 3 | **G2** 待办就地处理 | 依赖 G1；批量审批在局域网形态下收益明显 |
| 4 | **B** 身份自愈 | 备份包丢失时的兜底；依赖服务端已完成的 Offline 让位 |
| 5 | **F2** NULL = 跟随默认 | 语义修正，要动清理器和任务表单，独立成一次改动单独验证 |
| 6 | **C** 地址重发现 | 需要先补 InstanceId 持久化，验证成本最高，放最后 |
| — | **D3** IPv4 建连偏好 | 可并入 B 或 C 的 Agent 改动一起发，避免为它单独发一版客户端 |

G1 与 H 都是纯前端、互不依赖，建议先做掉——它们是现在就在误导使用者的缺陷。
A 与 D1/E/F1 之间没有依赖，可以并行。
B 与 C 都要改 Agent 并发布新客户端版本，建议合并成一次客户端升级。
F2 会改变「不选策略」的含义，不要和 F1 挤在同一次发布里。
