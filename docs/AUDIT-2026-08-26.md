# 批次 A · P0 · 上传会话生命周期闭环

## A-03 · 上传会话永不过期，客户端会被永久锁死

### 现状与证据

`src/src/BackupMonitor.Infrastructure/Services/UploadSessionService.cs:131`：

```csharp
var sessionTimeout = await _settings.GetIntAsync("upload_session_timeout_seconds", 3600, ct);
var now = DateTime.UtcNow;
```

`sessionTimeout` 赋值之后**再也没有出现过**。编译器不报 CS0219，因为它来自方法调用而不是常量。

- `grep -rn "UploadStatus.Expired" --include=*.cs` → 只有 `UploadSessionService.cs:68` 一处**读**，零处写。
- `RetentionCleanupWorker` 管的是恢复请求、回收站、GFS 保留、遥测清理，全程不碰 `upload_sessions`。
- `BuildCreateResponse` 里的 `ExpiresAt = session.LastActivityAt?.AddSeconds(3600)` 是硬编码，
  返回给 Agent 看的装饰，服务端自己不认这个值。

同一文件 `:120-124` 的并发闸门：

```csharp
var maxConcurrent = await _settings.GetIntAsync("max_concurrent_uploads", 2, ct);
var activeSessions = await _db.UploadSessions
    .CountAsync(s => s.ClientId == clientId && WritableStatuses.Contains(s.Status), ct);
if (activeSessions >= maxConcurrent)
    throw new BusinessException("UPLOAD_SESSION_CONFLICT", …, 409);
```

`WritableStatuses` = `Created / Uploading / Paused / RetryWait`。这四个状态**没有任何时间驱动的出口**。

**后果**：Agent 断网、进程被杀、磁盘满、条目 10 那种中途 return，都留下一个永久 `uploading` 会话。
攒到 2 个，这台客户端此后所有上传一律 409「客户端活动上传已达上限」，**永久**，只能手工改库。

### 方案

新增 `src/src/BackupMonitor.Infrastructure/Services/LifecycleExpiryWorker.cs`，
形状完全照 `SystemWatchdogWorker`（`IServiceScopeFactory` + `IScheduledLockService` 单实例锁 + 可配间隔）：

```csharp
/// <summary>
/// 生命周期到期巡检（审计 A-03 / A-04 / D-05）。
///
/// 系统里几张表的状态机都定义了「过期」这一格，却没有任何生产者——
/// upload_sessions.expired、commands.expired 都是只读不写。缺的不是判断逻辑，
/// 是「时间推动状态转移」这件事本身没人做。这个 worker 就是那个人。
/// </summary>
public class LifecycleExpiryWorker : BackgroundService
{
    public const string IntervalKey = "lifecycle_expiry_interval_seconds";      // 新增，默认 300
    public const string StagingRetentionKey = "staging_cleanup_retention_hours"; // 新增，默认 24
    public const string LockKey = "worker:lifecycle_expiry";
    private static readonly TimeSpan LockTtl = TimeSpan.FromMinutes(10);
```

`RunPassAsync` 分三段（第三段属于批次 D，先留空方法占位）：

**第一段 · 会话超时**

```csharp
var timeoutSeconds = Math.Max(60, await settings.GetIntAsync("upload_session_timeout_seconds", 3600, ct));
var deadline = DateTime.UtcNow.AddSeconds(-timeoutSeconds);

// 用 LastActivityAt 判定；它在每个分块写入时刷新（UploadChunkAsync），
// 是「这个会话还有没有人在推进」的唯一可靠依据。
// 为空（建了会话一个块都没传）时退回 CreatedAt。
var stale = await db.UploadSessions
    .Where(s => WritableStatuses.Contains(s.Status)
                && (s.LastActivityAt ?? s.CreatedAt) < deadline)
    .ToListAsync(ct);

foreach (var session in stale)
{
    session.Status = UploadStatus.Expired;
    session.ErrorCode = "SESSION_TIMEOUT";
    session.ErrorMessage = $"超过 {timeoutSeconds} 秒无分块写入，已自动过期";
    session.CompletedAt = now;
    session.UpdatedAt = now;
}
await db.SaveChangesAsync(ct);
```

注意：**不要**用 `ExecuteUpdateAsync`。过期的会话要逐个交给第二段做暂存清理，
批量 UPDATE 拿不到这个集合——这一点与 `SystemWatchdogWorker` 里对客户端存活判定的取舍是同一个理由。

**第二段 · 暂存清理（A-04）**

见下一条。

配套改动：

1. **`CreateSessionAsync` 补写 `StagingPath`**。`UploadSession.StagingPath` 这一列建表时就有
   （`V001:staging_path varchar(2048)`）、EF 也映射了（`UploadConfigurations.cs:56`），
   但**全代码库没有任何地方给它赋过值**。现在给它一个真实职责：
   ```csharp
   var sessionDirectory = await _storage.EnsureSessionDirectoryAsync(session.Id, ct);
   // …EnsureSessionDirectoryAsync 现在的调用点在 SaveChangesAsync 之后，
   // 挪到之前，并把返回值写进 session.StagingPath，再一起保存。
   ```
   这样「暂存目录是否还需要清理」不必新增列——`StagingPath` 非空即待清理，清完置 null，天然幂等。

2. **`BuildCreateResponse` 用真实超时**。签名加一个 `int timeoutSeconds` 参数，
   `ExpiresAt = (session.LastActivityAt ?? session.CreatedAt).AddSeconds(timeoutSeconds)`，
   删掉硬编码的 3600。

3. **注册**：`DependencyInjection.cs` 在 `services.AddHostedService<MissedBackupWorker>();` 之后加一行
   `services.AddHostedService<LifecycleExpiryWorker>();`

4. **新迁移 `V022__lifecycle_expiry_settings.sql`**（见本文末「发布注意事项」）。

### 验收标准

- 建一个会话、不传任何分块，把 `upload_session_timeout_seconds` 临时调到 60，
  等一轮巡检后该会话状态为 `expired`，`error_code = SESSION_TIMEOUT`。
- 同一客户端连续制造 3 个僵尸会话后，第 4 次 `CreateSession` 在巡检跑过之后能正常创建（不再 409）。
- 新增集成测试 `UploadSessionExpiryTests`：过期判定用 `LastActivityAt`、终态会话不被重复处理、
  `Committed` 会话不受影响。

## A-04 · 暂存目录只在成功入库时清理

### 现状与证据

`grep -rn "CleanupSessionAsync" --include=*.cs` 全代码库只有一个调用点：
`UploadCommitWorker.cs:298`，入库成功后的收尾段落里。

`UploadSessionService.CancelSessionAsync` 的注释写着：

> 取消后临时文件按策略保留（由定时清理任务处理，设计书 14.7）

**那个定时清理任务不存在。** 入库失败（`COMMIT_FAILED`）路径同样不清。

**后果**：每一次取消、失败、中断，都在暂存盘留下一份与备份等大的 `.part` 文件，永远不删。
暂存盘被填满后 `GetStagingFreeBytesAsync` 让所有新会话以 507 被拒——表现是
「所有客户端突然都传不上来了」，而磁盘上全是没人认领的残留分块。

### 方案

`LifecycleExpiryWorker.RunPassAsync` 第二段：

```csharp
// 终态会话的暂存目录清理。StagingPath 非空 = 还没清过（CreateSessionAsync 写入，清完置 null），
// 因此这一步天然幂等，不必新增「已清理」列。
var retentionHours = Math.Max(1, await settings.GetIntAsync(StagingRetentionKey, 24, ct));
var cleanupBefore = DateTime.UtcNow.AddHours(-retentionHours);

// Committed 也在内：入库成功时已经清过一次，但那次可能失败（那里是 try/catch 吞掉的），
// 这里兜底。保留期是给排障留的窗口——失败的会话现场别马上毁掉。
var terminal = new[] { UploadStatus.Committed, UploadStatus.Failed, UploadStatus.Cancelled, UploadStatus.Expired };

var cleanable = await db.UploadSessions
    .Where(s => terminal.Contains(s.Status)
                && s.StagingPath != null
                && (s.CompletedAt ?? s.UpdatedAt) < cleanupBefore)
    .Take(200)                       // 单轮上限，避免一次删太多把巡检卡在锁 TTL 内
    .ToListAsync(ct);

foreach (var session in cleanable)
{
    await storage.CleanupSessionAsync(session.Id, ct);   // 内部已经 try/catch，失败只记日志
    session.StagingPath = null;                           // 只有走到这里才认为清过
    session.UpdatedAt = DateTime.UtcNow;
}
await db.SaveChangesAsync(ct);
```

**孤儿目录扫描**（每轮巡检的最后一步，进程崩在「建目录」与「写库」之间时留下的）：

```csharp
// staging/sessions/ 下的目录名是 sessionId.ToString("N")。
// 目录存在但数据库里没有对应行 = 孤儿。只删修改时间超过保留期的，
// 避免误删正在创建中的会话目录。
var sessionsRoot = Path.Combine(await storage.GetStagingRootAsync(ct), "sessions");
if (Directory.Exists(sessionsRoot))
{
    foreach (var dir in Directory.EnumerateDirectories(sessionsRoot))
    {
        if (!Guid.TryParseExact(Path.GetFileName(dir), "N", out var id))
            continue;                                    // 不认识的目录不碰
        if (Directory.GetLastWriteTimeUtc(dir) >= cleanupBefore)
            continue;
        if (await db.UploadSessions.AnyAsync(s => s.Id == id, ct))
            continue;
        try { Directory.Delete(dir, recursive: true); }
        catch (Exception ex) { logger.LogWarning(ex, "孤儿暂存目录清理失败 {Dir}", dir); }
    }
}
```

同时把 `CancelSessionAsync` 那句误导性的注释改掉，改成指向本 worker。

### 验收标准

- 取消一个已传过分块的会话，把 `staging_cleanup_retention_hours` 调到 1 秒级等价值后跑一轮巡检，
  `staging/sessions/{id}/` 目录消失、`upload_sessions.staging_path` 变为 NULL。
- 手工在 `staging/sessions/` 下造一个不存在于库的 GUID 目录并把修改时间改早，一轮巡检后被删除。
- 造一个名字不是 GUID 的目录，巡检后**仍然存在**（不认识的目录不碰）。

## A-10 · Agent 上传中途失败不取消会话

### 现状与证据

`src/agent/BackupMonitor.Agent/AgentWorker.cs:862`：

```csharp
var local = candidate.Files.FirstOrDefault(f => …);
if (local is null || !File.Exists(local.FullPath))
    return CommandResult.FromFailure("LOCAL_FILE_MISSING", $"本地文件不存在：{remoteFile.RelativePath}");
```

会话已经建好了，直接 return，不管它。分块上传抛异常时同样——异常一路冒到
`ExecuteCommandAsync` 的 catch，那里只回报指令失败，不碰会话。

而 `AgentApiClient` 里**根本没有实现取消会话的方法**：服务端的
`POST /api/v1/agent/upload-sessions/{id}/cancel` 没有任何客户端调用者。

**后果**：这是 A-03 最主要的触发源。源文件在预检之后被删或改名（增量备份场景很常见），
指令失败一次就漏一个永久会话，两次锁死这台机器。

### 方案

1. `AgentApiClient` 补一个方法，紧挨着现有的上传相关方法：

   ```csharp
   public Task CancelUploadSessionAsync(Guid sessionId, CancellationToken ct) =>
       SendEmptyAsync(HttpMethod.Post, $"api/v1/agent/upload-sessions/{sessionId}/cancel", null, ct);
   ```

2. `ExecuteUploadAsync` 把「建会话之后」的整段包进 try/catch，任何非成功出口都尽力取消一次：

   ```csharp
   var session = await _api.CreateUploadSessionAsync(…, ct);
   try
   {
       // …现有的逐文件上传与完成逻辑原样保留…
       var completed = await _api.CompleteUploadSessionAsync(…, ct);
       return CommandResult.FromSuccess("UPLOAD_ACCEPTED", …);
   }
   catch (Exception ex) when (ex is not OperationCanceledException)
   {
       await TryCancelSessionAsync(session.UploadSessionId, ct);
       throw;
   }
   ```

   注意 `LOCAL_FILE_MISSING` 那条现在是 `return` 不是 `throw`，catch 接不住。
   把它改成抛一个内部异常，或者在 return 之前显式调一次 `TryCancelSessionAsync`——
   **推荐前者**：让所有失败出口共用同一条收尾路径，比在每个 return 前面记得加一句可靠。

3. 取消本身绝不能掩盖原始错误：

   ```csharp
   /// <summary>
   /// 尽力取消会话。取消失败只记日志——它是收尾动作，
   /// 让它的异常盖掉真正的失败原因，排障时看到的就会是「取消失败」而不是「文件不存在」。
   /// </summary>
   private async Task TryCancelSessionAsync(Guid sessionId, CancellationToken ct)
   {
       try
       {
           await _api.CancelUploadSessionAsync(sessionId, ct);
           _logger.LogInformation("上传失败，已取消会话 {SessionId}", sessionId);
       }
       catch (Exception ex)
       {
           _logger.LogWarning(ex, "上传失败后取消会话未成功 {SessionId}（服务端超时巡检会兜底）", sessionId);
       }
   }
   ```

**服务端仍然必须有 A-03 的过期兜底**——客户端可能是被 kill 的，根本没机会执行取消。
这两条是纵深关系，不是二选一。

### 验收标准

- 建任务、预检通过、在下发上传指令之前删掉源文件，下发上传：指令回报 `LOCAL_FILE_MISSING`，
  且服务端该会话状态为 `cancelled`（不是 `uploading`）。
- 上传过程中拔网线：Agent 重连后指令失败回报，会话最终由超时巡检置 `expired`（验证兜底路径）。

# 批次 B · P0 · Agent 主循环拆分

三条问题同一个根因：`AgentWorker` 只有一条顺序循环，心跳、指令执行、计划扫描共用它。

## B-02 · 执行指令期间不发心跳，大备份上传必被判离线

### 现状与证据

`src/agent/BackupMonitor.Agent/AgentWorker.cs:84-103`：

```csharp
var heartbeat = await _api.HeartbeatAsync(_probe.BuildHeartbeat(state.ConfigVersion, config, _activeCommands), stoppingToken);
…
if (heartbeat.CommandsAvailable || _activeCommands.Count == 0)
    await ClaimAndExecuteCommandsAsync(stoppingToken);   // ← await 到底

await RunScheduledScansAsync(config, stoppingToken);     // ← 同样 await 到底
await RetryPendingRestabilizeScansAsync(config, stoppingToken);

await Task.Delay(TimeSpan.FromSeconds(Math.Clamp(Math.Min(heartbeatDelay, _options.CommandPollIntervalSeconds), 2, 60)), stoppingToken);
```

`ClaimAndExecuteCommandsAsync` 里 `foreach` 逐条 `await ExecuteCommandAsync`，
上传一份 50 GB 的备份要几小时，这几小时里一次心跳都发不出去。
`RunScheduledScansAsync` 同样阻塞——`BackupScanner` 要把整个源目录哈希一遍。

服务端 `SystemWatchdogWorker` 按 `client_offline_threshold_seconds`
（`V001:1084`，默认 **300 秒**）判离线并发 `AlertLevel.Critical` 告警。

**后果**：**每一次正经的备份上传都会在 5 分钟后把这台机器判成离线，并发一条严重告警**——
而它其实正在老老实实干活。上传结束后心跳恢复、告警自动 recover，运维看到的是一串
莫名其妙的离线告警，正好落在备份窗口。这会把 A1 巡检训练成「狼来了」，然后被关掉。

附带损失：第 94 行的 `_activeCommands.Count == 0` 恒成立（指令是同步执行完才回到这里的），
`_activeCommands` 在心跳组装时也恒为空集，服务端 `client_heartbeats.active_command_count`
永远是 0——「这台机器正在执行什么」这个信息从来没有真正上报过。

### 方案

把 `AgentWorker` 拆成三条独立节奏。保留一个 `AgentWorker` 作为宿主，
在 `ExecuteAsync` 里启动三个长任务并 `Task.WhenAll`，共享状态放在字段上：

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    // 注册与证书是所有节奏的前置，仍然串行完成
    await EnsureRegisteredLoopAsync(stoppingToken);

    await Task.WhenAll(
        RunHeartbeatLoopAsync(stoppingToken),   // 按服务端下发间隔
        RunCommandLoopAsync(stoppingToken),     // 按 CommandPollIntervalSeconds
        RunScheduleLoopAsync(stoppingToken));   // 按 cron，内部自己算下次触发
}
```

关键点：

1. **`_activeCommands` 换成 `ConcurrentDictionary<Guid, byte>`**（`HashSet` 不是线程安全的，
   现在跨线程了）。心跳循环读它组装 `ActiveCommands`；指令循环写它。
   `BuildHeartbeat` 的第三个参数类型是 `IReadOnlyCollection<Guid>`，传 `.Keys.ToList()` 即可。

2. **心跳循环负责响应式动作**：`RequiredConfigVersion` 变化触发同步配置、
   `CertificateRenewalRequired` 触发续签、`Notifications` 进托盘队列。
   `CommandsAvailable` 不再直接执行，而是给指令循环一个信号
   （`SemaphoreSlim(0)` 或 `Channel`），让它提前一轮醒来。

3. **配置读取要线程安全**。现在 `LoadVerifiedConfig()` 每次都从 `_configStore` 读并验签，
   三条循环都要用。做一个带 `volatile` 引用的缓存字段，`SyncConfigAsync` 成功后整体替换引用；
   读的一侧只做一次快照读，不加锁。**不要**让三条循环各自反复验签——RSA 验签不便宜。

4. **`SyncConfigAsync` 必须互斥**。心跳循环和指令循环（`sync_config` 指令）都会调它，
   用一个 `SemaphoreSlim(1,1)` 包住，避免两边同时写 `config.json`。

5. **指令仍然串行执行**。拆的是「心跳 vs 指令」，不是「指令之间」。
   `ClaimAndExecuteCommandsAsync` 内部的 `foreach` 保持顺序，
   `MaxItems = 3` 也保持不变——并发跑多个上传会把源盘 IO 打满。

6. **计划扫描循环单独一条**，因为扫描（哈希整个目录）耗时同样不可控，
   不能挂在指令循环上，否则「正在扫描时下发不了预检指令」。
   `RetryPendingRestabilizeScansAsync` 归它管。

7. **异常隔离**：三条循环各自 try/catch，一条挂掉不能拖垮另外两条。
   `catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested) break;`
   的写法逐条照抄现有的。原来那个「401 时 `RecycleConnections()`」的自愈逻辑
   放进心跳循环即可——那是连接层的事，不必三条都做。

### 为什么不用「在上传循环里插补心跳」

那是止血不是修复：扫描阶段的长哈希（`BackupScanner` 内部一个文件一个文件地算）
覆盖不到，而扫描一个大目录同样能超过 5 分钟。而且每加一个耗时动作就要记得插一次补心跳，
迟早会漏。拆循环是一次性把这类问题整体消掉。

### 验收标准

- 造一个足够大的备份集（或把 `BandwidthLimitKbps` 调到很低），下发上传指令，
  上传持续 10 分钟以上：期间服务端 `clients.last_heartbeat_at` 持续刷新，
  客户端状态保持 `online`，**没有** `client:{id}:offline` 告警。
- 上传期间管理端客户端详情页能看到「正在执行 1 条指令」（`active_command_count = 1`）。
- 上传期间下发一条 `refresh_metrics` 指令，能在下一个轮询周期内被领取——
  验证指令循环没有被扫描循环阻塞。

## B-09 · 服务端配的心跳间隔完全不起作用

### 现状与证据

`AgentWorker.cs:100-103`：

```csharp
var heartbeatDelay = heartbeat.HeartbeatIntervalSeconds > 0
    ? heartbeat.HeartbeatIntervalSeconds
    : _options.HeartbeatIntervalSeconds;
await Task.Delay(TimeSpan.FromSeconds(
    Math.Clamp(Math.Min(heartbeatDelay, _options.CommandPollIntervalSeconds), 2, 60)), stoppingToken);
```

`CommandPollIntervalSeconds` 默认 10，服务端下发的 `heartbeatDelay` 默认 60
（`V001:1082` `heartbeat_interval_seconds = 60`）——取 `Min` 永远是 10。
而这个循环里心跳和领指令是同一趟，所以 **`heartbeat_interval_seconds` 只要大于 10 秒就毫无效果**。

**后果**：心跳量是设计值的 6 倍。而每次心跳是一份**全量快照**：
插一行 `client_heartbeats`、按业务键 upsert 全部磁盘、全部用户会话、全部服务状态，
更新 `clients` 行（连带 `row_version` 自增），再跑 CPU / 内存 / 每块源盘的告警判定
（`EvaluateResourceAlertsAsync` 每个判定至少一次 `AnyAsync`）。
100 台客户端就是每秒 10 次全量快照写入。分区表和保留策略能兜住磁盘，兜不住 WAL 与连接压力。

附带副作用：`clients.row_version` 每 10 秒动一次（`AppDbContext.IncrementRowVersions`），
管理端「禁用客户端」这类读-改-写正好撞上心跳时会以 409 并发冲突失败。

### 方案

批次 B 的拆分天然解决主要部分：心跳循环按 `heartbeat.HeartbeatIntervalSeconds` 走
（下限保护改成 `Math.Clamp(delay, 5, 300)`），指令循环按 `CommandPollIntervalSeconds` 走，
**指令轮询不携带任何快照**——它只调 `commands/claim`。

在此之上再做一层「快照只在变化时上报」：

```csharp
// 磁盘 / 用户会话 / 服务状态这三块在绝大多数心跳里一个字节都没变。
// 算一个稳定摘要，没变就整块不发，服务端沿用上一次的。
var snapshotHash = ComputeSnapshotHash(disks, userSessions, serviceStates);
if (snapshotHash == _lastSnapshotHash)
{
    request.Disks = null;
    request.UserSessions = null;
    request.ServiceStates = null;
    request.SnapshotUnchanged = true;      // HeartbeatRequest 新增字段
}
```

服务端 `AgentHeartbeatService` 侧对应：`request.Disks is null` 时**跳过** `UpsertDisksAsync`
（现在的代码已经是这个语义——`if (disks is not null)`，所以服务端几乎不用改），
但要注意 `EvaluateResourceAlertsAsync` 的磁盘告警分支在 `disks` 为 null 时会整段跳过，
需要改成回落到库里已有的 `ClientDisks` 记录做判定，否则磁盘告警会因为「快照没变」而不再评估。

**关于 `clients.row_version`**：心跳只写 `last_heartbeat_at` / `agent_version` /
`time_offset_seconds` / `status` 这几个遥测字段，不该推进用于管理端乐观锁的版本号。
最小改法是在 `AgentHeartbeatService` 里改用 `ExecuteUpdateAsync` 更新这几列（绕开变更跟踪，
不触发 `IncrementRowVersions`）；注意这样一来 `client.Status` 的读改写要自己拿最新值。
若嫌改动大，可接受现状，但要在 `ClientAdminService` 的禁用/启用/注销路径上加一次并发重试
（捕获 `DbUpdateConcurrencyException` 后重载实体重试一次）。

### 验收标准

- 把 `heartbeat_interval_seconds` 改成 120，观察 Agent 日志：心跳请求间隔确实变成约 120 秒，
  而指令轮询仍然是 10 秒一次。
- 连续 10 次心跳（磁盘/会话/服务状态无变化）后，`client_disks` 与 `client_user_sessions`
  的 `sampled_at` 不再每次都动，但磁盘不足告警仍能正常触发与恢复。
- 心跳期间反复调管理端「禁用客户端」，不出现 409 并发冲突。

## B-15 · 指令进度上报没有生产者

### 现状与证据

- 服务端实现了 `POST /api/v1/agent/commands/{id}/progress`（`AgentCommandController` + `CommandService.ReportProgressAsync`）。
- Agent 也实现了客户端方法：`AgentApiClient.cs:169 ReportProgressAsync`。
- **`AgentWorker` 里一次都没调过**（`grep -n "ReportProgressAsync" AgentWorker.cs` 无结果）。

**后果**：一次几小时的上传，管理端看到的只有 `running`，没有百分比、没有阶段、没有已传字节。
要判断它是在传还是卡住了，只能去查 `upload_sessions.uploaded_bytes`。
这也正是判断 B-02 那种「离线告警」是误报还是真掉线的关键信息，现在拿不到。

### 方案

`ExecuteUploadAsync` 的分块循环里按节流上报。**必须节流**——每块一次会把 `commands` 表写爆
（一个 50 GB / 8 MB 分块的备份是 6400 次写）：

```csharp
// 进度上报本身不能成为失败源：它是给人看的，报不上去不该让上传失败。
var reporter = new ProgressReporter(_api, command.Id, _logger,
    minInterval: TimeSpan.FromSeconds(30), minPercentDelta: 5);

foreach (var remoteFile in session.Files)
{
    …
    foreach (var index in indexes)
    {
        await UploadChunkWithRetryAsync(…);
        sentBytes += chunkLength;
        await reporter.TryReportAsync(
            percent: sentBytes * 100m / Math.Max(1, candidate.TotalBytes),
            stage: "uploading",
            message: $"{remoteFile.RelativePath}（{fileIndex}/{session.Files.Count}）",
            ct);
    }
}
```

`ProgressReporter` 内部记住上次上报的时刻与百分比，两个条件都不满足就直接返回；
上报本身 try/catch 吞掉异常只记 `LogDebug`。

扫描阶段同理可以报「已扫描 N 个文件」，但优先级低于上传——先做上传。

**服务端配套**：`CommandService.ReportProgressAsync` 现在把进度整个覆盖 `ResultPayload`。
这没错（指令还在跑，还没有真结果），但要和批次 D 的 `ResultPayload` 大小限制对齐，
别让进度对象把 jsonb 撑大。

### 验收标准

- 一次持续 5 分钟以上的上传，管理端任务详情/作业历史能看到百分比随时间推进。
- 上报频率符合节流：一次 6400 分块的上传，`commands` 表上的写入次数是几十次量级而不是几千次。
- 断开服务端连接再恢复，上传不因为进度上报失败而中断。

# 批次 C · P0 · 指令签名 v2

## C-01 · 指令签名不覆盖 payload

### 现状与证据

`src/src/BackupMonitor.Shared/Security/AgentSignatureCanonicalizer.cs:18`：

```csharp
public static byte[] CommandPayload(
    Guid commandId, string nonce, string commandType, Guid clientId, DateTime expiresAt) =>
    Utf8(CurrentVersion + "|" + JoinFields(
        "command", commandId.ToString("D"), nonce, commandType,
        clientId.ToString("D"), ToUnixMilliseconds(expiresAt).ToString(…)));
```

只有 `id · nonce · type · clientId · expiresAt`。而 `CommandDto`
（`src/src/BackupMonitor.Shared/Models/Agent/CommandDtos.cs:29-33`）里真正决定指令做什么的三个字段
——`TaskId`、`CandidateBackupSetId`、`Payload`——**完全在签名之外**。

对照 `ConfigPayload`：它逐字段覆盖了 `SourcePath`、`RecognizerConfig`、`ScanSchedule` 等等，
做得很完整。唯独指令这条漏了。

**后果**：能改写响应体的人可以把 `upgrade_agent` 的 `packageUrl` 和 `sha256` **一起**换掉，
Agent 会照着攻击者给的哈希校验通过、解压、写 `pending-update.json` 等待重启切换——
`VerifyCommand` 全程返回 true。攻击面：

- Secure 形态由 nginx 终结 TLS 后**明文回环**到 Kestrel `127.0.0.1:5080`，这中间就是一个可插入点；
- 能写 `commands.payload` 的数据库账号同样够用；
- `browse_path` 的 `path`、`upload_candidate` 的 `candidateBackupSetId` 同样可改写。

指令签名这套机制存在的全部意义就是防这个，现在恰好对最危险的字段不生效。

### 方案

**1 · 规范化器加 v2**（`AgentSignatureCanonicalizer.cs`）：

```csharp
public const string CurrentVersion = "v2";          // 从 v1 提升
public const string PreviousVersion = "v1";

public static byte[] CommandPayload(
    Guid commandId, string nonce, string commandType, Guid clientId, DateTime expiresAt,
    Guid? taskId, Guid? candidateBackupSetId, string? payload) =>
    Utf8(CurrentVersion + "|" + JoinFields(
        "command",
        commandId.ToString("D"),
        nonce,
        commandType,
        clientId.ToString("D"),
        ToUnixMilliseconds(expiresAt).ToString(CultureInfo.InvariantCulture),
        taskId?.ToString("D"),                       // null → JoinFields 写 "~"
        candidateBackupSetId?.ToString("D"),
        payload));                                   // jsonb 原文，Base64Url 编码后入串
```

`JoinFields` 已经处理了 null（写 `~`）和 Base64Url 编码，不需要改。

把现有的 v1 版本原样保留、改名为 `CommandPayloadV1`，供灰度窗口验签使用——
这跟现有的 `LegacyCommandPayload`（更早的一版）是同一套做法，形成三级兼容链。

> **payload 必须逐字节一致。** `commands.payload` 是 jsonb，PostgreSQL 会重排键、
> 规范化空白。签名和验签用的都是 `Command.Payload` 这个从库里读回来的字符串
> （`CommandService.ClaimAsync` 每次下发都用当前算法重签），所以两端拿到的是同一份
> 规范化后的文本，一致。**不要**在中间对它做任何 `JsonSerializer` 往返。

**2 · 服务端签名**（`CommandSigner.SignCommand`）：把新增的三个字段传进去。

**3 · Agent 验签**（`AgentSignatureVerifier.VerifyCommand`）：三级回退

```csharp
return Verify(AgentSignatureCanonicalizer.CommandPayload(
           command.Id, command.Nonce, command.Type, clientId, command.ExpiresAt,
           command.TaskId, command.CandidateBackupSetId, command.Payload), command.Signature)
    || Verify(AgentSignatureCanonicalizer.CommandPayloadV1(…), command.Signature)
    || Verify(AgentSignatureCanonicalizer.LegacyCommandPayload(…), command.Signature);
```

灰度窗口（建议一个升级周期）结束后删掉后两个分支。删除时机写进
`docs/系统审查-整改追踪.md`，别靠记忆。

**4 · 升级包来源白名单（纵深防御，不依赖签名不出错）**

`AgentWorker.StageUpgradeAsync` 现在只校验 scheme 是 http/https。加一条：

```csharp
// 升级包只能从本 Agent 已经信任的服务端拿。签名覆盖了 payload 之后这一条是冗余的，
// 但升级是唯一一条「服务端说什么就执行什么代码」的路径，值得两道锁。
var serverBase = new Uri(_options.ServerUrl, UriKind.Absolute);
if (!string.Equals(packageUri.Host, serverBase.Host, StringComparison.OrdinalIgnoreCase)
    || packageUri.Port != serverBase.Port)
{
    return CommandResult.FromFailure("UPGRADE_PACKAGE_URL_FORBIDDEN",
        $"升级包地址 {packageUri.Host}:{packageUri.Port} 不是当前服务端，拒绝下载");
}
```

顺带给 `DownloadBytesAsync` 加一个大小上限（读 `Content-Length`，超过比如 512 MB 直接拒绝）——
现在它把整包读进 `byte[]`，没有任何限制。

### 验收标准

- 新增单元测试 `CommandSignatureTests`：
  - 改动 `payload` 任意一个字节 → `VerifyCommand` 返回 false；
  - 改动 `taskId` / `candidateBackupSetId` → 同样 false；
  - 用 v1 算法签的指令仍然验签通过（灰度兼容）；
  - `payload` 为 null 与为空串产生**不同**的签名原文（`~` vs 空 Base64）。
- `upgrade_agent` 的 `packageUrl` 指向外部主机时，Agent 回报 `UPGRADE_PACKAGE_URL_FORBIDDEN`。
- 现网存量 `pending` 指令在服务端升级后仍能被老 Agent 领取执行（`ClaimAsync` 每次重签，
  老 Agent 拿到的是 v2 签名——**所以 Agent 必须先于服务端升级**，这一点写进发布顺序）。

> **发布顺序有硬性要求**：Agent 先升（能验 v1 和 v2），服务端后升（开始签 v2）。
> 反过来会让所有老 Agent 拒收全部指令。

# 批次 D · P1 · 指令生命周期与结果收口

## D-05 · 指令没有超时回收

### 现状与证据

`grep -rn "CommandStatus.Expired" --include=*.cs` → 只有 `CommandService.cs:89` 一处**读**，零处写。

`ClaimAsync` 只挑 `Status == Pending`，一旦 `ExecuteUpdateAsync` 把它翻成 `Claimed`，
就再没有回到 `Pending` 的路径——即使 `ExpiresAt` 早就过了。

**后果**：Agent 在领取和回报之间挂掉（进程被杀、机器重启、回报请求 500 见 D-06），
这条指令永远停在 `claimed` 或 `running`：

- 管理端显示一条「正在执行」且永不结束的指令；
- `ClientAdminService.cs:65` 那份把 `Pending / Claimed / Running` 视为「进行中」的判断跟着失真；
- 带幂等键的重发也救不了——`CreateCommandAsync` 只对 `Failed / Cancelled / Expired / Rejected` 复位。

### 方案

`LifecycleExpiryWorker.RunPassAsync` 的第三段（批次 A 留的占位）：

```csharp
var now = DateTime.UtcNow;

// 一、真正过期的：TTL 到了就是到了，无论处于哪个未完成状态。
await db.Commands
    .Where(c => (c.Status == CommandStatus.Pending
                 || c.Status == CommandStatus.Claimed
                 || c.Status == CommandStatus.Running)
                && c.ExpiresAt < now)
    .ExecuteUpdateAsync(s => s
        .SetProperty(c => c.Status, CommandStatus.Expired)
        .SetProperty(c => c.CompletedAt, now)
        .SetProperty(c => c.ResultCode, "COMMAND_EXPIRED")
        .SetProperty(c => c.ResultMessage, "指令在有效期内未完成执行"), ct);

// 二、认领了却迟迟不上报开始的：退回 pending 让别人重领。
// 这才是断线重连该有的行为——机器重启后应该继续干活，而不是等 TTL 熬完。
var claimTimeout = Math.Max(60, await settings.GetIntAsync(ClaimTimeoutKey, 900, ct));   // 新增，默认 900
var claimDeadline = now.AddSeconds(-claimTimeout);
await db.Commands
    .Where(c => c.Status == CommandStatus.Claimed
                && c.ClaimedAt < claimDeadline
                && c.ExpiresAt > now)
    .ExecuteUpdateAsync(s => s
        .SetProperty(c => c.Status, CommandStatus.Pending)
        .SetProperty(c => c.ClaimedAt, (DateTime?)null), ct);
```

**`Running` 不退回 `Pending`**：它已经上报过开始，可能正在传一份几十 GB 的备份，
重发会造成重复执行。`Running` 只等 TTL。相应地，长耗时指令的 TTL 要配够
（`CreateCommandAsync` 的 `DefaultTtl` 是 24 小时，够用）。

这里用 `ExecuteUpdateAsync` 是可以的——与 A-03 不同，这两段不需要拿到受影响的集合做后续动作。

### 验收标准

- 造一条 `claimed` 状态、`claimed_at` 早于阈值的指令，一轮巡检后回到 `pending` 并能被重新领取。
- 造一条 `running` 状态、`expires_at` 已过的指令，一轮巡检后为 `expired`，`result_code = COMMAND_EXPIRED`。
- `running` 且未过期的指令**不被**巡检碰到。

## D-06 · 结果消息无服务端截断

### 现状与证据

`src/src/BackupMonitor.Infrastructure/Data/Configurations/BackupConfigurations.cs:245-247`：

```csharp

builder.Property(e => e.ResultMessage).HasColumnName("result_message").HasMaxLength(2000);
builder.Property(e => e.ResultPayload).HasColumnName("result_payload").HasColumnType("jsonb");
```

`src/src/BackupMonitor.Infrastructure/Services/CommandService.cs:248-250`：

```csharp

command.ResultMessage = request.ResultMessage;

```

中间没有任何长度检查。**EF Core 的 `HasMaxLength` 只影响建表 DDL，运行时不截断。**

**后果**：Agent 的失败回报走 `ex.Message`，一条带完整路径的 `IOException` 或
`AggregateException` 轻易超过 2000 字节 → PostgreSQL 抛 `22001 value too long`
→ 接口 500 → Agent 的 catch 分支再报一次、再 500 → 这条指令永远留在 `running`（接上 D-05）。

`result_payload` 更糟：不校验是不是合法 JSON（非法 JSON 进 jsonb 直接 500），也不限大小。
`browse_path` 的结果最多 `BrowseMaxEntries = 20000` 个条目，序列化后能有几 MB，
每条指令一份塞进 `commands.result_payload`。Agent 自己在 `ExecuteRecognitionTestAsync` 里
写了「塞进指令结果里会把 commands 表撑坏」的注释并限制到 50 个文件，浏览这条路径却没设限。

### 方案

在 `ReportCompletedAsync` 里收口。**服务端截断，不要信客户端**——
`UploadCommitWorker` 对 `ErrorMessage` 已经是这个写法（`ex.Message[..1900]`），照抄：

```csharp
private const int MaxResultMessageLength = 1900;   // 列宽 2000，留余量
private const int MaxResultPayloadBytes = 256 * 1024;

command.ResultCode = Truncate(request.ResultCode, 64);
command.ResultMessage = Truncate(request.ResultMessage, MaxResultMessageLength);
command.ResultPayload = NormalizeResultPayload(request.Result, command.Id);
```

```csharp
/// <summary>
/// 结果载荷入 jsonb 之前必须验形并限量。
/// 非法 JSON 会让 Npgsql 直接抛，而抛出去的后果是 Agent 永远报不完这条指令；
/// 超大载荷（browse_path 能到几 MB）会把 commands 表撑坏。
/// 两种情况都不该让指令失败——它已经执行完了，坏的只是结果的呈现。
/// </summary>
private string? NormalizeResultPayload(string? raw, Guid commandId)
{
    if (string.IsNullOrWhiteSpace(raw))
        return null;

    var bytes = System.Text.Encoding.UTF8.GetByteCount(raw);
    if (bytes > MaxResultPayloadBytes)
    {
        _logger.LogWarning("指令 {CommandId} 结果载荷 {Bytes} 字节超限，已替换为摘要", commandId, bytes);
        return JsonSerializer.Serialize(new
        {
            truncated = true,
            originalBytes = bytes,
            note = "结果过大已丢弃，请改用对应的专用接口获取完整数据"
        });
    }

    try
    {
        using var _ = JsonDocument.Parse(raw);
        return raw;
    }
    catch (JsonException ex)
    {
        _logger.LogWarning(ex, "指令 {CommandId} 结果载荷不是合法 JSON，已替换为摘要", commandId);
        return JsonSerializer.Serialize(new { invalidJson = true, length = raw.Length });
    }
}
```

同样的收口要加到 `ReportProgressAsync`（它也写 `ResultPayload`）。

**配套**：`DirectoryBrowser` 的返回条目数上限从纯客户端配置（`BrowseMaxEntries`）
改成「服务端下发的上限与客户端配置取小」——服务端在 `browse_path` 的 payload 里带一个
`maxEntries`，Agent 取 `Math.Min`。这样服务端能约束自己会收到多大的东西。

### 验收标准

- Agent 回报一条 5000 字符的 `resultMessage`：接口返回 200，库里存的是前 1900 字符，指令状态正常流转。
- Agent 回报 `result = "not json"`：接口 200，`result_payload` 是 `{"invalidJson":true,...}`，不再 500。
- `browse_path` 在一个有 20000 个条目的目录上执行：`result_payload` 不超过 256 KB。

# 批次 E · P1 · 入库收口

## E-07 · 入库成功后的收尾异常会把成功的备份标记为失败

### 现状与证据

`src/src/BackupMonitor.Infrastructure/Services/UploadCommitWorker.cs`：

- `:291` `committed = true;`（事务已提交，正式目录已就位）
- `:344-350` 内层 catch：`if (committed) throw;` ——这一步是对的，注释也解释得很清楚，
  绝不能回滚或删目录。
- 但这个 `throw` 会被 **`:365` 的外层 catch** 接住，而外层无条件执行：
  ```csharp
  session.Status = UploadStatus.Failed;          // :371
  session.ErrorCode = "COMMIT_FAILED";
  …
  await alerting.RaiseAsync($"session:{session.Id}:commit_failed", AlertLevel.Critical, …);
  ```

**后果**：备份集实际是 `Available`、正式目录已就位、文件都在，会话却被记成 `Failed`
并伴随一条严重告警。更麻烦的是数据不自洽——`CommandService.CreateCommandAsync` 的
`uploadAcceptedButCommitFailed` 分支专门查「该候选存在 `Failed` 会话」，
于是会把**已经成功的上传指令复位重发**，客户端再传一遍。

停机时的 `OperationCanceledException` 走的也是这条路：`stoppingToken` 一取消，
文件复制中断抛 OCE → 外层 catch → 试图用已取消的 ct 做 `SaveChangesAsync` 和 `RaiseAsync`
→ 再抛 → 会话留在 `Verifying`（重启后能恢复，结果碰巧是对的，但过程是失控的）。

### 方案

把「已提交」这个事实带到外层。最干净的做法是包一层专用异常：

```csharp
/// <summary>
/// 事务已提交、正式目录已就位之后才发生的异常。
/// 存在的唯一目的是让外层 catch 能区分「入库失败」和「入库成功但收尾出了岔子」——
/// 后者绝不能改会话状态、更不能发严重告警：备份是好的。
/// </summary>
private sealed class PostCommitException(Exception inner)
    : Exception("入库已提交后的收尾阶段异常", inner);
```

内层 catch：

```csharp
catch (Exception ex)
{
    if (committed)
        throw new PostCommitException(ex);
    …现有回滚与目录清理逻辑原样保留…
    throw;
}
```

外层 catch 分三种情况：

```csharp
catch (PostCommitException ex)
{
    // 备份是成功的。只留日志，不改状态、不告警。
    _logger.LogError(ex.InnerException, "会话 {SessionId} 入库成功但收尾异常（备份可用，无需处理）", sessionId);
}
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    // 停机不是失败。会话留在 verifying，RecoverPendingWorkAsync 重启后会重新入队。
    _logger.LogInformation("会话 {SessionId} 入库因服务停止而中断，将在重启后重试", sessionId);
    throw;      // 交给 ExecuteAsync 的 OCE 分支 break 掉循环
}
catch (Exception ex)
{
    …现有的置 Failed + 告警逻辑…
    // 但 SaveChangesAsync / RaiseAsync 改用 CancellationToken.None，
    // 否则 ct 已取消时这段收尾自己也会抛。
}
```

## E-16 · 备份集编码不按年重置

### 现状与证据

`UploadCommitWorker.GenerateBackupSetCodeAsync`：

```csharp
var year = DateTime.UtcNow.Year;
command.CommandText = "SELECT nextval('backup_set_code_seq')";
…
return $"BS-{year}-{next:0000}";
```

序列 `backup_set_code_seq`（V011）是全局的，年份换了不重置。

**后果**：格式暗示「某年的第 N 个」，实际是「有史以来的第 N 个，前面贴了个年份」。
跨年后从 `BS-2026-8931` 直接变成 `BS-2027-8932`，四位补零也早就溢出成五位。
不影响唯一性，影响的是人对编码的理解和按年份对账。

### 方案

**推荐：承认它是全局流水号**，改成 `BS-{next:000000}`，把会误导人的年份去掉。
理由：按年重置需要「年份 + 序号」的复合唯一约束加重试，跨年那一刻还有并发窗口，
为一个纯展示属性付这个代价不值得。

存量编码不迁移——它们已经写进 `manifest.json`、审计日志和告警文本里了，
改了会破坏可追溯性。在 `BackupSet.BackupSetCode` 的 XML 注释里写清楚
「2026-08 之前的编码带年份段，之后是全局流水号，两种格式并存」。

若产品明确要求按年重置，则改用「每年一个序列」：
`nextval(format('backup_set_code_seq_%s', year))`，序列不存在时先 `CREATE SEQUENCE IF NOT EXISTS`。
这条路要在迁移脚本里预建未来几年的序列，别在运行时建。

### 验收标准

- 新入库的备份集编码形如 `BS-000123`，且并发入库不产生重复。
- 存量 `BS-2026-xxxx` 编码原样保留，恢复、审计、告警里的引用全部仍然有效。

# 批次 F · P1 · Agent 状态文件瘦身

## F-08 · 状态文件每次读写都全量序列化，候选清单永不清理

### 现状与证据

`src/agent/BackupMonitor.Agent/AgentStateStore.cs:123-129`：

```csharp
public AgentState Snapshot()
{
    lock (_sync)
        return JsonSerializer.Deserialize<AgentState>(
            JsonSerializer.Serialize(_state, JsonOptions), JsonOptions) ?? new();
}
```

深拷贝语义没错，代价是每调一次就把整个状态对象走一遍 JSON。

`:167-174` `Update()` 每次都 `SaveUnsafe()`；`:298-313` `SaveUnsafe()` 建临时文件、
打 ACL、全量写、`File.Move`、再打一次 ACL。

而 `state.Candidates` 里装的是每个候选备份集的**完整文件清单**
（`LocalCandidateFile`：相对路径 + 绝对路径 + 大小 + SHA-256），并且**只写不删**：

- `ScheduledScans` 有清理僵尸条目的逻辑（`RunScheduledScansAsync` 里按 `live` 集合剔除）；
- `PendingRestabilizeScans` 有（`RetryPendingRestabilizeScansAsync` 里按 `liveTaskIds` 剔除）；
- **`Candidates` 没有**（`AgentWorker.cs:790` 只有写入）。

**后果**：一个 5 万文件的备份任务，单个候选就是 10 MB 量级的 JSON。主循环每轮（10 秒）
要 `Snapshot()` 好几次；`ProcessNotifications` 每条通知一次 `Update()`（一次心跳最多 20 条）；
每条指令 nonce 一次；每个扫描结果两次。也就是**每分钟几十次、每次几十 MB 的 JSON 序列化
加同步落盘**，全在同一把锁里。任务删掉之后那些候选还留在文件里，`state.json` 只增不减。
现场表现是 Agent 吃 CPU、磁盘 IO 异常、状态文件大得没法发回来排障。

### 方案

三件事，按收益排序：

**1 · 候选文件清单挪出 `state.json`（收益最大）**

`AgentState.Candidates` 只保留摘要，文件清单单独存：

```csharp
public sealed class LocalCandidateState
{
    public Guid? CandidateBackupSetId { get; set; }
    public Guid TaskId { get; set; }
    public string CandidateKey { get; set; } = string.Empty;
    public string SourceRoot { get; set; } = string.Empty;
    public string ManifestHash { get; set; } = string.Empty;
    public int TotalFiles { get; set; }
    public long TotalBytes { get; set; }
    public DateTime UpdatedAt { get; set; }
    // Files 移除——改存到 candidates/{sha256(candidateKey)}.json
}
```

新增 `AgentCandidateFileStore`（形状参考已有的 `AgentConfigStore`）：
`Save(candidateKey, files)` / `Load(candidateKey)` / `Delete(candidateKey)`，
文件落在 `%ProgramData%\BackupMonitor\Agent\candidates\` 下，
文件名用 `candidateKey` 的 SHA-256 十六进制（`candidateKey` 里有路径分隔符，不能直接当文件名）。

`ExecuteUploadAsync` 里 `candidate.Files` 的读取点改成从这个 store 加载。

**2 · `Candidates` 跟着任务生命周期清理**

`RetryPendingRestabilizeScansAsync` 里已经算好了 `liveTaskIds`，直接复用；
清理时同步删掉对应的候选文件清单文件：

```csharp
_stateStore.Update(state =>
{
    foreach (var stale in state.Candidates
                 .Where(kv => !liveTaskIds.Contains(kv.Value.TaskId))
                 .Select(kv => kv.Key).ToList())
    {
        state.Candidates.Remove(stale);
        staleKeys.Add(stale);            // 出锁之后再删文件，别在锁里做 IO
    }
});
foreach (var key in staleKeys)
    _candidateFiles.Delete(key);
```

再加一个总量上限：`Candidates` 超过比如 200 条时按 `UpdatedAt` 淘汰最旧的
（同样要删对应的清单文件），防止 `CandidateKey` 因为 `status` 段变化而无限累积。

**3 · 合并批量修改，减少落盘次数**

`ProcessNotifications` 现在是每条通知一次 `Update()`。改成循环外一次提交：

```csharp
var accepted = new List<Guid>();
foreach (var notification in notifications) { …; accepted.Add(notification.Id); }
if (accepted.Count > 0)
    _stateStore.Update(state => { /* 一次性合并 accepted */ });
```

`SubmitScansWithRestabilizeAsync` 里的多次 `Snapshot()` 也合并成开头取一次。

**不要做的事**：不要给 `SaveUnsafe` 加异步去抖后台写。状态文件的价值就在于
「进程被杀之后重启能接上」，延迟写会让这一点失效。降低写入次数可以，延迟写不行。

### 验收标准

- 造一个 5 万文件的候选，`state.json` 大小在 100 KB 量级（而不是 10 MB 量级）。
- 删掉任务后跑一轮主循环，`state.json` 里对应的 `Candidates` 条目和
  `candidates/` 下的清单文件都消失。
- 一次心跳带 20 条通知，`state.json` 只被重写一次（用文件修改时间或 IO 计数验证）。
- 升级兼容：老版本写的 `state.json`（`Candidates` 里带 `Files`）能被新版本读出来并自动迁移到新布局。
  **这一条必须有测试**，否则升级后所有候选丢失、已通过预检的备份要重新扫。

# 批次 G · P2 · 告警语义

三条问题共同指向一件事：告警模型只有「新建」和「恢复」两个通知触发点，
而真实运维关心的是三件事——出现、恶化、恢复。

## G-11 · 告警升级不产生新通知

### 现状与证据

`src/src/BackupMonitor.Infrastructure/Services/AlertingService.cs:95-103`：

```csharp
if (existing is not null)
{
    existing.LastOccurredAt = now;
    existing.OccurrenceCount++;
    existing.Message = message ?? existing.Message;
    if (level < existing.Level)
        existing.Level = level;          // Critical=0，数值小即等级高
}
else
{
    …CreateDeliveriesForAsync(alert)…    // ← 通知只在这个分支
    …_agentNotifications.EnqueueAsync(…) // ← 托盘推送也只在这个分支
}
```

**后果**：磁盘可用率从 14%（`Warning`）掉到 3%（`Critical`），告警等级在库里升上去了，
但**没有任何人收到通知**——第一封警告邮件可能是几天前发的、早被忽略了。
「事情变严重了」这个最该被推送的信号恰好是唯一不推送的。

### 方案

`existing` 分支里检测真实的等级提升，提升时补一次投递：

```csharp
var escalated = level < existing.Level;
if (escalated)
    existing.Level = level;

existing.LastOccurredAt = now;
existing.OccurrenceCount++;
existing.Message = message ?? existing.Message;

// 「变严重了」是最该推送的信号，而它原先是唯一不推送的。
// 只在真的升级时补发，且同样受静默规则约束——静默期内计数照加、通知不发。
if (escalated && !silenced)
{
    await CreateDeliveriesForAsync(existing, ct, titlePrefix: "【已升级】");
    if (existing.ClientId is not null)
        await _agentNotifications.EnqueueAsync(
            existing.ClientId.Value, "alert", SeverityOf(level),
            $"【已升级】{existing.Title}", message,
            $"alert:{existing.Id}:escalated:{EnumMapping.ToSnakeCase(level)}",   // 去重键带等级，同一等级只推一次
            existing.Id, backupSetId, ct);
}
```

去重键里带等级是关键：`Warning → Critical` 推一次，之后同等级的重复发生不再推。

`CreateDeliveriesForAsync` 现在的签名是 `(Alert alert, CancellationToken ct)`，
内部用 `Alert = alert` 建导航关系；补一个可选的标题前缀参数即可复用。

**可选加强**：长时间未恢复也做成触发点——巡检里对 `FirstOccurredAt` 超过 N 小时
仍活动的 `Critical` 告警补发一次提醒。这一条价值高但不紧急，可以放到后面。

## G-12 · 告警恢复不撤销待发通知

### 现状与证据

`AlertingService.RecoverAsync` 只把告警置 `Recovered`，对应的 `notification_deliveries`
仍是 `Pending`。`NotificationDispatchWorker.DispatchBatchAsync` 的查询：

```csharp
.Where(d => d.Status == NotificationStatus.Pending
            && d.AttemptCount < maxAttempts
            && (d.LastAttemptAt == null || d.LastAttemptAt < retryCutoff))
```

只看投递记录自身的状态，不回查告警是否已恢复。

**后果**：短暂抖动（CPU 冲高一次、一次心跳超时）产生的告警邮件，在告警早已恢复之后仍会照发。
重试间隔默认 5 分钟、最多 3 次，一次抖动最多能在恢复后继续发三轮。
结合 B-02 那种「上传期间被判离线」，收件箱会被没有意义的告警和恢复填满。

### 方案

两处都改，双保险：

**1 · `RecoverAsync` 里连带取消**（在现有的 `ExecuteUpdateAsync` 之后）：

```csharp
// 告警都恢复了，还没发出去的通知就没有意义了。
// 先查出告警 ID 再按 alert_id 更新——ExecuteUpdate 不支持跨表条件。
var recoveredIds = await _db.Alerts
    .Where(a => a.AlertKey == alertKey && a.Status == AlertStatus.Recovered && a.RecoveredAt == now)
    .Select(a => a.Id).ToListAsync(ct);

if (recoveredIds.Count > 0)
{
    await _db.NotificationDeliveries
        .Where(d => recoveredIds.Contains(d.AlertId) && d.Status == NotificationStatus.Pending)
        .ExecuteUpdateAsync(s => s
            .SetProperty(d => d.Status, NotificationStatus.Cancelled)
            .SetProperty(d => d.ErrorMessage, "告警已恢复，取消发送"), ct);
}
```

`NotificationStatus` 若没有 `Cancelled` 成员则需要新增，并在
`V0NN` 迁移里扩 `notification_status` DOMAIN——**注意** `EnumDomainParityTests`
会校验枚举与数据库 DOMAIN 一致，两边必须同时改。

**2 · 派发器加过滤**（防御性，覆盖并发窗口）：

```csharp
.Where(d => d.Status == NotificationStatus.Pending
            && ActiveAlertStatuses.Contains(d.Alert.Status)      // ← 新增
            && …)
```

## G-13 · 漏备份巡检的跳过分支不恢复告警

### 现状与证据

`MissedBackupWorker.RunPassAsync` 的任务查询：

```csharp
.Where(t => t.Enabled && t.ScanSchedule != null
            && t.TaskMode != TaskMode.Paused && t.TaskMode != TaskMode.MonitorOnly)
```

循环内还有四处 `continue`：新建不足一个宽限期、cron 解析失败、相邻计划间隔小于宽限期、
仍在宽限期内。**所有这些路径都不调 `RecoverAsync`。**

**后果**：一个任务先报了 `task:{id}:missed`，随后被停用 / 暂停 / 改成只监控 /
cron 改成分钟级，那条严重告警就**永远留在告警中心**，没有任何路径能自动恢复它——
只能人工关闭。而「先停掉这个任务再说」是排障时最自然的动作，正好触发它。

### 方案

每轮先把**不参与判定**的任务的告警恢复一遍：

```csharp
// 不参与判定 ≠ 判定通过，但两者对告警的处置是一样的：
// 这个任务现在没有「该备份而没备份」这回事，红点就不该留着。
var judgedTaskIds = new HashSet<Guid>();     // 循环里凡是真正做过判定的都加进来

var allTaskIds = await db.BackupTasks.Select(t => t.Id).ToListAsync(ct);
foreach (var taskId in allTaskIds.Except(judgedTaskIds))
    await alerting.RecoverAsync($"task:{taskId}:missed", ct);
```

`RecoverAsync` 内部已经有「没有活动告警就直接返回」的前置 `AnyAsync`（D2 那次优化留下的），
所以对绝大多数任务这是一次索引探测，不产生 UPDATE。

循环里那四处 `continue` 之前，把 `taskId` 加进 `judgedTaskIds` 的做法要**反过来**：
只有真正走到「比对 `LastSuccessAt` 与 `prevDue`」那一步的才算判定过。`continue` 的一律不算，
于是它们会被上面这段统一恢复。

**配套**：任务删除时同样要恢复其全部告警键。在 `BackupTaskService` 的删除路径上补：
`task:{id}:missed`、`task:{id}:upload_failed`，以及 `command:*:failed` 这类带任务关联的
（后者按 `TaskId` 批量置 `Recovered` 更实际）。

### 验收标准（批次 G）

- 制造一条 `Warning` 级磁盘告警，再让它升级为 `Critical`：收到第二封标题带「【已升级】」的邮件，
  且同等级重复发生不再发第三封。
- 制造一条告警后立刻恢复：`notification_deliveries` 里该告警的 `pending` 记录变为 `cancelled`，
  派发器不再发送。
- 制造一条 `backup_missed` 告警后把任务停用：下一轮巡检后该告警状态为 `recovered`。
- `EnumDomainParityTests` 全绿（如果新增了 `NotificationStatus.Cancelled`）。

# 批次 H · P2 · 零散收口

## H-14 · 刷新令牌重放检测不推进令牌版本

### 现状与证据

`src/src/BackupMonitor.Infrastructure/Services/AuthService.cs:171-177`：

```csharp
if (stored.RevokedAt is not null)
{
    _logger.LogWarning("检测到已吊销刷新令牌重用 user={UserId}，吊销该用户全部刷新令牌", stored.UserId);
    await RevokeAllUserTokensAsync(stored.UserId, "token_reuse", ct);
    throw new BusinessException("UNAUTHORIZED", "刷新令牌已失效，请重新登录", 401);
}
```

吊销了全部**刷新**令牌，但没有 `user.TokenVersion++`。
改密（`ChangePasswordAsync`）和登出（`LogoutAsync`）都做了这一步，唯独安全性最敏感的重放检测漏了。

另外 `TokenVersionCache.Invalidate()` 写好了却**一处都没被调用**
（`grep -rn "\.Invalidate(" --include=*.cs` 只有 `SystemSettingsProvider` 那个同名方法），
改密和登出实际都要等满 60 秒 TTL。

**后果**：确认令牌泄露的那一刻，攻击者手上的**访问令牌**仍然全权有效，最长一小时——
而这一小时正是最需要立刻切断的时候。

### 方案

```csharp
if (stored.RevokedAt is not null)
{
    _logger.LogWarning(…);
    await RevokeAllUserTokensAsync(stored.UserId, "token_reuse", ct);

    // 令牌重放是确认泄露的信号，此刻最该做的是让攻击者手上的访问令牌立刻作废。
    // 只吊销刷新令牌不够——访问令牌是无状态 JWT，还能再用满一个 TTL。
    var user = await _db.Users.FirstOrDefaultAsync(u => u.Id == stored.UserId, ct);
    if (user is not null)
    {
        user.TokenVersion++;
        await _db.SaveChangesAsync(ct);
        _tokenVersionCache.Invalidate(user.Id);
    }

    await _audit.RecordAsync("auth.token_reuse", AuditResult.Failure, "user", stored.UserId,
        errorMessage: "检测到刷新令牌重放，已吊销全部会话", ct: ct);

    throw new BusinessException("UNAUTHORIZED", "刷新令牌已失效，请重新登录", 401);
}
```

`AuthService` 构造函数注入 `TokenVersionCache`（它是单例，注入到 scoped 服务里没问题），
并在**三处**调 `Invalidate(userId)`：改密、登出、重放检测。
这样撤权即时生效，而不是最坏 60 秒。

顺带：审计里现在没有 `auth.token_reuse` 这个动作，加上——令牌重放是最该留痕的安全事件之一。

## H-17 · 路径分量截断后可能重新以点或空格结尾

### 现状与证据

`src/src/BackupMonitor.Shared/Security/PathSafety.cs` 的 `SanitizePathComponent`：

```csharp
var cleaned = sb.ToString().Replace("..", "_").Trim().TrimEnd('.');
if (string.IsNullOrWhiteSpace(cleaned)) cleaned = "unnamed";
if (IsReservedDeviceName(cleaned)) cleaned = "_" + cleaned;
return cleaned.Length > 100 ? cleaned[..100] : cleaned;    // ← 截断在净化之后
```

**截断是最后一步**，所以截断点恰好落在点或空格上时，`Trim()` / `TrimEnd('.')` 这层保护就被绕过了。

**后果**：NTFS 写盘时会静默剥掉结尾的点和空格，于是 `backup_sets.repository_path`
记的路径和磁盘上实际的目录名不一致。日常读写因为 Win32 会做同样的规范化而看不出问题，
但任何逐字符比对路径的逻辑都会踩到——保留清理前的 `PathSafety.IsUnderBase` 围栏、
跨平台迁移、目录审计。`IsValidRelativePath` 里对客户端提交路径的同一条规则是完整的，
只有服务端自己生成路径这条漏了。

### 方案

把截断挪到净化之前，并在截断后重跑一遍收尾净化与保留名检查：

```csharp
public static string SanitizePathComponent(string name)
{
    var invalid = Path.GetInvalidFileNameChars();
    var sb = new StringBuilder(name.Length);
    foreach (var c in name)
        sb.Append(Array.IndexOf(invalid, c) >= 0 ? '_' : c);

    var cleaned = sb.ToString().Replace("..", "_");

    // 先按码位截断，再净化收尾——顺序反过来就等于把 TrimEnd 的保护绕过去：
    // 截断点恰好落在点或空格上时，NTFS 会静默剥掉它，磁盘上的目录名与库里记的路径就此不一致。
    cleaned = TruncateByTextElements(cleaned, MaxComponentLength);
    cleaned = cleaned.Trim().TrimEnd('.');

    if (string.IsNullOrWhiteSpace(cleaned))
        cleaned = "unnamed";
    if (IsReservedDeviceName(cleaned))
        cleaned = "_" + cleaned;

    return cleaned;
}
```

`TruncateByTextElements` 用 `StringInfo` / `Rune` 按码位（或字素簇）截断，
避免 `cleaned[..100]` 切断代理对产生半个字符——中文是 BMP 内的所以现在看不出问题，
但主机名里出现 emoji 或生僻字（扩展 B 区）就会。

注意 `_ + cleaned` 可能让长度回到 101，需要在返回前再截一次或把上限设为 99。
测试要覆盖这个边界。

### 验收标准（H-17）

- `PathSafetyTests` 新增用例：长度 105、第 100 个字符是 `.` 的输入，输出不以 `.` 结尾且长度 ≤ 100。
- 同上但第 100 个字符是空格。
- 输入含代理对（如 `𝕏`）且恰好在截断边界，输出不含半个代理对。

## H-18 · 会话状态查询 N+1，入库工作器单消费者串行

### 现状与证据

**其一**，`UploadSessionService.GetSessionStatusAsync`：

```csharp
foreach (var file in files)
{
    if (file.Status is UploadFileStatus.Pending or UploadFileStatus.Uploading)
    {
        var received = await _db.UploadChunks
            .Where(c => c.UploadFileId == file.Id && …)
            .Select(c => c.ChunkIndex).ToListAsync(ct);      // ← 每个文件一次往返
```

**其二**，`DependencyInjection.cs` 里入库队列注册为 `SingleReader = true`，
`UploadCommitWorker.ExecuteAsync` 顺序处理所有 `WorkItem`：

```csharp
await foreach (var item in _channel.Reader.ReadAllAsync(stoppingToken))
```

`CommitSession`、`ReverifyBackupSet`、`VerifyRestoreRequest` 共用这一条队列。

**后果**：前者让「查看上传进度」在大备份集上变慢并占满连接池；
后者让一次几十 GB 的入库（要把暂存复制到仓库并逐文件算哈希）把队列后面的
备份集重校验和**恢复请求校验**全部堵住——「点了恢复之后等了半小时还在校验」，
而排队原因在界面上完全不可见。

### 方案

**其一**：一次性把整个会话的分块查回来，内存里分组：

```csharp
var receivedByFile = (await _db.UploadChunks
        .Where(c => c.UploadFile.UploadSessionId == session.Id && c.Status == UploadChunkStatus.Received)
        .Select(c => new { c.UploadFileId, c.ChunkIndex })
        .ToListAsync(ct))
    .GroupBy(x => x.UploadFileId)
    .ToDictionary(g => g.Key, g => g.Select(x => x.ChunkIndex).ToHashSet());
```

**其二**：把恢复校验拆到独立通道。恢复是有人在界面前等的交互操作，
入库是后台批处理，两者不该共享一条队列：

```csharp
// 恢复请求校验单独一条队列 —— 它是有人在等的交互操作，
// 不该排在一次几十 GB 的备份入库后面。
services.AddKeyedSingleton("commit", Channel.CreateUnbounded<WorkItem>(…));
services.AddKeyedSingleton("verify", Channel.CreateUnbounded<WorkItem>(…));
```

`UploadCommitWorker` 消费 `commit`，新增一个轻量的 `VerificationWorker` 消费 `verify`
（复用现有的 `VerifyRestoreRequestAsync` / `ReverifyBackupSetAsync` 方法，
把它们提到一个共享类里或直接搬过去）。
`RecoverPendingWorkAsync` 里的两段扫描分别写进两条队列。

同时把「队列位置」暴露到恢复请求详情 DTO 里（`Channel.Reader.Count` 是现成的），
让界面能显示「前面还有 N 个任务」而不是干等。

### 验收标准（H-18）

- 一个 500 文件的会话，`GET /upload-sessions/{id}` 的数据库往返次数从 500+ 降到个位数
  （用 EF 日志或 `MiniProfiler` 计数验证）。
- 一次大备份入库进行中，同时发起恢复请求校验：校验在秒级完成，不等入库。
