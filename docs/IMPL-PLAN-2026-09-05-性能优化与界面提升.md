# 实施方案 · 传输性能优化 与 界面提升（2026-09-05）

本文档来源是一次针对「系统在性能上还有什么可以优化」与「服务管理页面 / Web 管理端的界面还有什么可做」的通盘走查。走查范围是**上传链路、恢复下载链路、Web 管理控制台、服务端安装维护窗口**四处。

需要先说清楚的前提是：**存储层已经调得很干净了**。1MB 读写缓冲、每块一次 `FlushFileBuffers` 取代 `WriteThrough`、单文件 4 路并发分块、分块落库改成单条增量 CTE、入库同卷走硬链接——这几处是量级上的大头，都已经做完并留有完整的注释推理。本方案里没有一条是推翻它们，全部是**存储层之外**剩下的部分。

同样地，Web 管理端已经有令牌体系、状态的三重编码（形状+文字+颜色）、暗色主题、命令面板、键盘导航、骨架屏与分三类的空态文案。它的问题不是「没设计」，是**渲染策略吃掉了已经写好的设计意图**，以及**几处该有的东西没有**。

每条标注级别、证据位置、根因、方案、边界与风险、验收标准和工作量。

## 范围与前提

已经定死、**不要再动摇**的边界：

- 本系统是**备份工具**，不是合规管控系统。每一条改动都要先回答「它是否服务于『数据会不会丢』」；答不上来的不做。
- 客户端系统支持底线是 **Windows Server 2012 R2**。
- **系统未进生产**。语义变更直接改，不做存量兼容层、不考虑升级顺序。
- 完整性判定的权威基准不变：入库以 `upload_files.expected_sha256`（预检清单，服务端持有）为准，客户端声明值只作交叉验证。本方案中 T2、T5 都触碰哈希链路，两条都必须保持这个基准不变。
- 限速的唯一口径仍然是任务上的 `BandwidthLimitKbps`（服务端下发、管理员可见可调）。本方案里任何并发度参数都是**性能参数**，不得被当作限速手段。
- 界面上**不引入装饰性视觉**：渐变边框、发光数字、背景网格/粒子、毛玻璃、扫描线动画一律不做。理由见 U5。

### 度量前提

本方案的收益排序是**读代码得出的判断，不是实测**。动手前建议先做一次基线测量，否则无法证明改动有效：

1. 选一台真实客户端 + 一个真实账套（建议同时准备「单个 6GB 大文件」和「附件库式几千个小文件」两组样本）。
2. 在 `AgentWorker.ExecuteUploadAsync` 外围打点，分段记录：预检哈希耗时、建会话耗时、`missing-chunks` 往返总耗时、分块 PUT 总耗时、`complete-file` 总耗时、`complete-session` 耗时。
3. 服务端在 `UploadSessionService.UploadChunkAsync` 里分段记录：鉴权查询、上下文查询、`WriteChunkAsync`、`RecordReceivedChunkAsync` 各自耗时。

这两组数字一旦拿到，下面每条的预期收益都能直接验证。

# 批次 T · 传输链路

## T1 · 文件之间完全串行

**级别**：P0　**工作量**：2 人日

### 现象

一个账套里文件越多、单个文件越小，实测速率离带宽越远。附件库形态（几千个几十 KB 的文件）下，网卡基本是空的，时间全花在一问一答上。

### 证据

`src/agent/BackupMonitor.Agent/AgentWorker.cs:1719`：

```csharp
foreach (var remoteFile in session.Files)
{
    ...
    var missing = await _api.GetMissingChunksAsync(session.UploadSessionId, remoteFile.UploadFileId, ct);
    var indexes = ExpandMissing(missing, local.SizeBytes, session.ChunkSizeBytes);
    // 分块并行发送 —— parallel = Clamp(MaxParallelChunks, 1, 16)
    ...
    await _api.CompleteUploadFileAsync(...);
}
```

块内 4 路并发已经做了（同一处的注释把理由写得很清楚），**文件之间一路都没有**。

### 根因

每个文件固定三次串行往返：`GET missing-chunks` → `PUT chunk` → `POST complete`。大文件无所谓，往返被摊薄进几百兆数据里；小文件则完全相反——一个 40KB 的附件，三次往返的固定开销远大于它自己的传输时间。

分块并行解决的是「等上一块被处理才敢发下一块」，而文件级还停在同一个问题上，只是换了一层。

### 方案

引入**文件级工作池 + 全局分块信号量**，两层并发上限分开控制：

- 新增 `AgentOptions.MaxParallelFiles`，默认 **3**，夹取范围 1–8。
- 新增一个**会话级共享**的 `SemaphoreSlim(MaxParallelChunks)`，所有文件的所有分块 PUT 都要先拿这个信号量。这样无论多少个文件在并行，**在途分块总数仍然 ≤ `MaxParallelChunks`**，内存占用（每路一个分块缓冲）和服务端并发压力都和现在持平。
- 文件级并发带来的收益是**控制类往返重叠**：3 个文件的 `missing-chunks` / `complete` 同时在路上。

改造后的骨架（替换 `AgentWorker.cs:1719` 起的 `foreach`）：

```csharp
// 在途分块的全局闸门：文件级并发不得放大在途分块数，
// 否则「4 路并发」这个已经调好的参数会被悄悄变成 12 路。
using var chunkGate = new SemaphoreSlim(Math.Clamp(_options.MaxParallelChunks, 1, 16));
var fileQueue = new ConcurrentQueue<UploadFileDescriptor>(session.Files);
using var failFast = CancellationTokenSource.CreateLinkedTokenSource(ct);
Exception? firstFailure = null;

async Task RunFileWorkerAsync()
{
    while (fileQueue.TryDequeue(out var remoteFile))
    {
        try
        {
            failFast.Token.ThrowIfCancellationRequested();
            await UploadOneFileAsync(session, candidateFiles, remoteFile,
                chunkGate, throttle, progress, failFast.Token);
        }
        catch (OperationCanceledException) when (failFast.IsCancellationRequested && !ct.IsCancellationRequested)
        {
            // 另一路已经失败并叫停了全体，本路不是自己出错。
            // 不记录，好让真正的失败原因原样冒出去 —— 与现有分块级的处理保持一致。
            return;
        }
        catch (Exception ex)
        {
            Interlocked.CompareExchange(ref firstFailure, ex, null);
            failFast.Cancel();
            return;
        }
    }
}

var fileParallel = Math.Clamp(_options.MaxParallelFiles, 1, 8);
await Task.WhenAll(Enumerable.Range(0, fileParallel).Select(_ => RunFileWorkerAsync()));

ct.ThrowIfCancellationRequested();
if (firstFailure is not null)
    ExceptionDispatchInfo.Capture(firstFailure).Throw();
```

`UploadOneFileAsync` 就是现有 `foreach` 体的内容原样搬进去，只改两点：

1. 分块发送前后加 `await chunkGate.WaitAsync(ct)` / `chunkGate.Release()`（放在 `UploadChunkWithRetryAsync` 内部最外层，`finally` 里 Release）。
2. 「本地文件不存在」那条继续 `throw new UploadAbortedException(...)`，由上面的 worker catch 统一收口——**不要**改成 return，那会让缺文件变成静默跳过。

### 边界与风险

- **服务端已经支持**：`upload_files` 各行独立、分块记录按 `(file, index)` upsert、文件与会话的字节数在数据库侧增量累加（`UploadSessionService.cs:378` 起的 CTE 注释里已经论证过并发正确性）。多个文件并发不引入新的并发语义。
- **`ProgressReporter` 已经线程安全**（`AgentWorker.cs:1957` 的 `_gate`），`sentBytes` 已经用 `Interlocked.Add`，两处都不用改。
- **`ChunkThrottle` 已经线程安全**（`AgentWorker.cs:2179` 的 `_gate`）。限速仍然是会话级平均值，文件级并发不改变这个语义。
- **服务端全局上传闸不受影响**：它限的是并发**会话**数，不是会话内的并发度。
- **风险点**：文件级并发会让「哪个文件先完成」不再是清单顺序，`CompleteUploadSessionAsync` 之前必须确认**全部**文件都已完成。现有代码是靠顺序执行隐式保证的，改造后要靠 `Task.WhenAll` + `firstFailure` 检查显式保证——这一点在代码评审时必须专门看。

### 验收标准

- 附件库样本（≥2000 个文件、平均 <100KB）整体上传耗时下降 **≥50%**；大文件样本（单个 ≥4GB）耗时变化在 ±5% 以内（不应变慢）。
- 在途分块数实测不超过 `MaxParallelChunks`：在 `UploadChunkWithRetryAsync` 进出口打计数器，取峰值。
- 单元测试：新增 `UploadFileParallelismTests`，覆盖「一个文件失败时其余文件被叫停，且最终抛出的是那个真实异常而不是 `OperationCanceledException`」。
- 回归：`ExpandMissingTests`、`ChunkThrottleTests`、`ProgressReporterTests` 全绿。

## T2 · `complete-file` 同步重读整个文件算哈希

**级别**：P1　**工作量**：1.5 人日

### 现象

一个 6GB 的文件传完最后一块之后，客户端在 `POST .../complete` 上停住不动，要等服务端把这 6GB 从暂存目录重新顺序读一遍。慢存储上这一步是分钟级，而客户端的 HTTP 超时是 10 分钟——足够大的文件加上足够慢的盘，会以超时形式失败，而失败原因看起来跟哈希毫无关系。

### 证据

`src/src/BackupMonitor.Infrastructure/Services/UploadSessionService.cs:499`：

```csharp
var serverSha = await _storage.ComputeFileHashAsync(sessionId, file.Id, ct);
```

`ComputeFileHashAsync`（`UploadStorage.cs:246`）是整份顺序读 + SHA-256。客户端超时设置见 `AgentApiClient.cs:243`：`Timeout = TimeSpan.FromMinutes(10)`。

### 根因

整文件哈希放在了**同步请求路径上**，而它并不需要在那里。每一块写入时已经做过两件事：

- 块哈希双端比对（`UploadSessionService.cs:369`）
- 块长度校验，专门堵住「非末块传短块留空洞」（同文件 P1-1 那段注释）

再加上分块覆盖全文件且偏移严格划分，整文件哈希新增的覆盖面只剩一种：**上传过程中源文件被改**（客户端算块哈希时读到的已经是新内容，块自身自洽，只有整文件哈希对不上预检期望值）。这一种确实要防，但它不需要客户端在线上等着。

### 方案

把整文件复核从 `CompleteFileAsync` 移到入库阶段，会话状态机不变：

**1. `CompleteFileAsync` 改为只做便宜的检查**

```csharp
// 分块齐不齐、暂存文件在不在、长度对不对 —— 都是常数时间
var receivedChunks = await _db.UploadChunks.CountAsync(...);
if (receivedChunks < file.TotalChunks) throw ...;
var (exists, length) = await _storage.GetStagedFileInfoAsync(sessionId, file.Id, ct);
if (!exists) throw ...;
if (length != file.SizeBytes) throw new BusinessException("CHUNK_INVALID", "暂存文件长度与预检不符", 409);

file.Status = UploadFileStatus.Received;   // 注意：不是 Verified
file.SizeBytes = length;
```

`Received` 这个状态在 `UploadFileStatus` 里已经存在，且 `CompleteFileAsync` 开头的幂等分支已经把 `Verified or Received` 一并当作「做过了」处理——不需要新增枚举值。

**2. 整文件复核挪进 `UploadCommitWorker`**

在 `UploadCommitWorker.cs:202` 的文件循环里，**建硬链接/复制之前**先算哈希：

```csharp
var serverSha = await storage.ComputeFileHashAsync(session.Id, file.Id, ct);
if (!string.Equals(serverSha, file.ExpectedSha256, StringComparison.OrdinalIgnoreCase))
{
    // 与原 CompleteFileAsync 完全相同的失败语义：会话失败、审计留痕、告警
    await FailSessionAsync(session, file, serverSha, "FILE_HASH_MISMATCH", ct);
    return;
}
file.ServerSha256 = serverSha;
file.Status = UploadFileStatus.Verified;
```

**跨卷复制的场合可以省掉这一次读**：复制本来就要顺序读一遍暂存文件，把 `CopyToAsync` 换成「边复制边喂 `IncrementalHash`」的循环，一次读同时得到哈希和副本。同卷硬链接的场合没有复制，哈希这一遍读是省不掉的——但它已经不在客户端的等待路径上了。

**3. 客户端声明值的交叉验证**

`CompleteUploadFileRequest.Sha256` 现在没有地方比了。把它存进 `upload_files.client_declared_sha256`（新增列，可空），在入库复核时一并比对，保持原有的「双向交叉验证」语义不丢。

### 边界与风险

- **完整性基准不变**：仍然以 `expected_sha256`（预检清单）为权威，客户端声明值仍然只作交叉验证。
- **失败时机后移**：现在是「传完最后一块立刻知道哈希错」，改后是「入库时才知道」。对使用者的可见差别是失败会话在 `verifying` 状态多停留一小段时间。这是可接受的：哈希错本来就极罕见，而它换来的是**每一次正常上传**都不用等。
- **必须一并检查**：`CompleteSessionAsync` 里若有「所有文件都必须是 `Verified` 才能进 `verifying`」的判断，要放宽成 `Verified or Received`。改之前先 grep 一遍 `UploadFileStatus.Verified` 的全部使用点。
- 数据库变更：`upload_files` 新增 `client_declared_sha256 varchar(64) null`，走一条新迁移脚本。

### 验收标准

- 6GB 单文件样本：`POST .../complete` 的响应时间从「整文件读一遍」降到 **<200ms**。
- 故意在最后一块传完后篡改暂存文件，入库阶段必须以 `FILE_HASH_MISMATCH` 失败，且审计记录与告警与改动前一致。
- 新增测试 `UploadCommitHashVerificationTests`：覆盖「哈希不符时会话失败且仓库目录不留半份」。
- 回归：`BackupVerificationTests` 全绿。

## T3 · `VerifiedBytes` 全量 SUM 是 O(N²)

**级别**：P1　**工作量**：0.5 人日

### 现象

一个会话里文件越多，每个文件完成时的落库越慢，且是线性变慢——整体呈平方增长。

### 证据

`src/src/BackupMonitor.Infrastructure/Services/UploadSessionService.cs:530`：

```csharp
session.VerifiedBytes = await _db.UploadFiles
    .Where(f => f.UploadSessionId == session.Id && f.Status == UploadFileStatus.Verified)
    .SumAsync(f => f.SizeBytes, ct) + length;
```

### 根因

这正是 `RecordReceivedChunkAsync`（`UploadSessionService.cs:378`）的注释里花大段篇幅论证并改掉的那个反模式——「每收一块就把该文件已收的所有块重扫一遍」——只是从**块级**搬到了**文件级**，改块级时没有一起改掉。

N 个文件时总共扫 N(N+1)/2 行。5000 个文件约 1250 万行扫描，全部只为算一个本可以直接加出来的数。

### 方案

与块级完全同一套路，换成数据库侧增量累加：

```csharp
await _db.Database.ExecuteSqlInterpolatedAsync($"""
    UPDATE upload_sessions
       SET verified_bytes = verified_bytes + {length},
           updated_at     = {now}
     WHERE id = {session.Id}
    """, ct);
```

配合 T2 之后，这条语句挪到入库复核里，与 `status = 'verified'` 的写回放在同一条语句中。

### 边界与风险

- **重复完成不能重复累加**。`CompleteFileAsync` 开头已有幂等分支：文件已是 `Verified or Received` 就直接返回，不会走到累加。要在测试里专门覆盖「同一个文件调两次 complete，`verified_bytes` 只涨一次」。
- 若并发完成多个文件（T1 之后必然发生），增量在数据库里做，不存在应用层读-改-写的丢更新问题——与块级的理由完全相同。

### 验收标准

- 5000 文件会话：全部 `complete-file` 的累计耗时下降 **≥90%**。
- 新增测试：同一文件重复 complete 两次，`verified_bytes` 与单次一致。
- 并发完成 100 个文件后，`verified_bytes` 等于这 100 个文件 `size_bytes` 之和。

## T4 · nginx 的 upstream keepalive 实际没生效

**级别**：P1　**工作量**：0.25 人日　**仅影响 Secure（nginx）形态**

### 现象

高并发上传一段时间后，代理机上开始堆积 TIME_WAIT；极端情况下表现为「传着传着开始随机报连接失败」。

### 证据

`deploy/nginx/backup-monitor.conf:13-16` 声明了连接池：

```nginx
upstream backup_monitor {
    server 127.0.0.1:5080;
    keepalive 32;
}
```

但两个 `location` 块都只设了 `proxy_http_version 1.1`，**没有 `proxy_set_header Connection "";`**。

### 根因

nginx 默认会把客户端请求的 `Connection` 头透传给上游，客户端不带时则发 `Connection: close`。只有显式把它清空，upstream 的 `keepalive` 池才会被使用。现状是**每一个分块 PUT 都新建一条到 Kestrel 的 TCP 连接**，那 32 个连接的池一次都没派上用场。

回环连接的握手本身很便宜，所以这不是吞吐问题，是**连接数问题**：每条连接结束后进入 TIME_WAIT，高并发下累积到临时端口耗尽。

### 方案

在 `location /` 与 `location /api/v1/downloads/` 两处各加一行：

```nginx
proxy_http_version 1.1;
proxy_set_header   Connection "";   # 必须清空，否则上面的 upstream keepalive 形同虚设
```

`location = /health` 不需要（走的是默认 upstream 行为且量极小）。

### 边界与风险

- 与 `proxy_request_buffering off` / `proxy_buffering off` 不冲突，两者管的是缓冲，与连接复用无关。
- Turnkey 形态（Kestrel 直接监听）不经过 nginx，不受影响，也不需要对应改动。

### 验收标准

- 一次 ≥1000 分块的上传过程中，观察到的到 5080 的连接数稳定在 32 上下，而不是随分块数线性增长。
- 上传结束后 TIME_WAIT 数量比改动前下降一个量级。

## T5 · 客户端源盘被完整读两遍，且单元内任一变化触发全单元重哈希

**级别**：P0　**工作量**：2 人日

### 现象

两点，第二点在附件库形态下代价更大：

1. 一次备份里源文件被完整读了两遍——预检算全量 SHA-256 一遍，上传读分块又一遍。6GB 账套在 100MB/s 的盘上，光预检就是 60 秒，这段时间网卡完全是空的。
2. 附件库里只新增了一个附件，**这个单元里几千个文件全部重新全量哈希**。

### 证据

- 预检哈希：`src/agent/BackupMonitor.Agent/BackupScanner.cs:272`

  ```csharp
  for (var i = 0; i < files.Count; i++)
  {
      ...
      fileDtos[i].Sha256 = await ComputeSha256Async(files[i].FullName, ct);
  }
  ```

  串行、1MB 缓冲、**没有 `FileOptions.SequentialScan`**（`BackupScanner.cs:568`）。
- 上传读盘：`AgentWorker.cs:2085`。
- 跳过条件：`BackupScanner.cs:243` 起的快速指纹比对，**粒度是整个业务单元**——`quickFingerprintHash` 由该单元全部文件的 `(路径|大小|mtime|QuickHash)` 拼成，任何一个文件变化都会让整个指纹不一致，于是全单元重算。

### 根因

缓存粒度错了。判断「这个**文件**是不是上次那一份」所需的全部信息，在读它第一个字节之前就已经具备了——路径、大小、mtime、头尾各 64KB 的 `QuickHash`（后者本来就每次扫描都会算，见 `BackupScanner.cs:215`）。现在这套信息只被用在**单元级**的「要不要重算」上，没有下沉到文件级。

### 方案

**1. 新增文件级哈希缓存 `AgentFileHashCache`**

形状完全照抄 `AgentCandidateFileStore`：同一个数据目录、同样的 `SecureFileSystem.CreateDirectory` ACL 处理、**读失败一律当作「没有」而不是抛异常**。

- 目录：`%ProgramData%\BackupMonitor\Agent\hashcache\`
- 一个任务一个文件：`{taskId:N}.json`
- 条目：

```csharp
public sealed record FileHashCacheEntry(
    string FullPath,        // 大小写不敏感比较
    long SizeBytes,
    long LastWriteUtcTicks,
    string QuickHash,       // 头尾各 64KB 的采样哈希
    string Sha256);
```

**命中条件必须四项全等**：`SizeBytes` + `LastWriteUtcTicks` + `QuickHash` 三项与本次扫描实测一致，才复用 `Sha256`。

**2. 接进哈希循环**

```csharp
for (var i = 0; i < files.Count; i++)
{
    ct.ThrowIfCancellationRequested();
    await Report(progress, new ScanProgress(...));

    // forceFullHash（界面上的「强制完整校验」）必须绕过缓存 —— 它存在的全部意义
    // 就是「这一次我不信任何增量判据，全部重读」。
    var cached = forceFullHash ? null : hashCache.TryGet(files[i], fileDtos[i].QuickHash);
    fileDtos[i].Sha256 = cached ?? await ComputeSha256Async(files[i].FullName, ct);
}
hashCache.Save(task.TaskId, fileDtos, files);   // 只保留本次清单里出现过的路径，顺带完成淘汰
```

**3. 顺手两处**

- `ComputeSha256Async` 加 `FileOptions.SequentialScan`，与 `UploadStorage` / `UploadCommitWorker` 的读取参数对齐。
- 哈希循环允许 2–3 个文件并发（新增 `AgentOptions.MaxParallelHashes`，默认 3，夹取 1–8）。进度上报本来就是按「第几个文件」报的，并发后改为报「已完成 N / 共 M」，`ScanProgressReporter` 的节流逻辑不用动。

### 边界与风险

**这是本方案里唯一触碰完整性判据的一条，必须把边界说清楚。**

- 缓存命中条件（大小 + mtime + 头尾 64KB 采样）与**现有已被明确接受**的单元级快速指纹判据**完全相同**（`BackupScanner.cs:243` 的三点论证）。也就是说，本条改动**不降低**现有的覆盖水平，只是把同一把尺子从单元级下放到文件级。
- 已知且继续接受的边界仍然是那一条：「文件中段被改而 size、mtime、头尾 64KB 都没变」。正常的备份程序不会产生这种文件；真要防篡改，`forceFullHash` 是明路，且本方案显式让它绕过缓存。
- **入库 manifest 里的仍然是全量 SHA-256**，服务端的 `expected_sha256` 基准和入库复核链路一个字都没改。
- 缓存文件损坏 / 丢失 / 被删：`Load` 返回空 → 全部重算 → 与今天的行为完全一致。这是刻意的降级方向。
- 缓存不跨任务共享：不同任务可能配了不同的 `forceFullHash` 策略，共享会让边界变得难以推理。同一个文件被两个任务覆盖时多算一遍，可接受。

### 验收标准

- 附件库样本（≥2000 文件），第二次扫描只新增 1 个文件：预检耗时下降 **≥95%**，且新增文件的 `Sha256` 与全量重算一致。
- `forceFullHash = true` 时缓存被完全绕过：在 `ComputeSha256Async` 上打计数器，调用次数等于文件数。
- 篡改一个文件的内容但保持 size 与 mtime 不变、且改动落在头尾 64KB 之内 → 必须重算（`QuickHash` 变了）。
- 删掉 `hashcache` 目录后行为与改动前完全一致。
- 新增测试 `AgentFileHashCacheTests`（放 `BackupMonitor.Agent.Tests`，纯文件系统、不需要数据库）：覆盖命中、四项各自失配、`forceFullHash` 绕过、损坏文件降级。
- 回归：`BackupScannerTests` 全绿。

## T6 · 恢复下载与定期复查仍是 80KB 缓冲

**级别**：P2　**工作量**：0.75 人日

### 现象

恢复下载与定期复查这条链路一次都没有被优化过，与上传侧的参数差距很明显。

### 证据

| 位置 | 现状 |
|---|---|
| `DownloadsController.cs:175` | `FileStream(..., 81920, useAsync: true)`，无 `SequentialScan` |
| `DownloadsController.cs:178` | `new byte[81920]` 手写复制循环 |
| `DownloadsController.cs:81` | 整包 ZIP 用 `CompressionLevel.Fastest` |
| `DownloadsController.cs:83` | ZIP 内文件流同样 81920，无 `SequentialScan` |
| `VerificationWorker.cs:141` | 定期复查，81920，无 `SequentialScan` |
| `VerificationWorker.cs:220` | 下载前校验，同上 |

6GB 文件按 80KB 一轮是 7.8 万次循环。

### 方案

**1. 统一 IO 参数**（四处）

```csharp
new FileStream(path, FileMode.Open, FileAccess.Read, FileShare.Read,
    bufferSize: 1024 * 1024, FileOptions.Asynchronous | FileOptions.SequentialScan)
```

`UploadStorage.ChunkIoBufferBytes` 已经把 1MB 这个值和理由固化了。建议把它提到 `BackupMonitor.Infrastructure.Common` 里作为共享常量 `StreamIo.LargeFileBufferBytes`，避免四处各写一个字面值。

**2. 单文件整量下载走 `SendFileAsync`**

非 Range 的整文件请求不需要经过用户态缓冲：

```csharp
if (!isRangeRequest)
{
    // Kestrel 在 Windows 上会走 TransmitFile，内核态零拷贝。
    await Response.Body.SendFileAsync(fullPath, 0, length, ct);
    copied = length;
    fileFullyDelivered = true;
}
```

**待确认点**：`SendFileAsync` 在客户端中断时拿不到「已传了多少字节」，下载记账（`FinishDownloadAsync`）会记成 0，而「断在哪儿」在恢复场景里是有用的信息。若这个数字要保留，就仍用循环、只把缓冲换成 1MB + `ArrayPool`。**建议先保留循环**，等确认记账不需要精确值再换 `SendFileAsync`。

**3. 整包 ZIP 改为 store 模式**

```csharp
var entry = zip.CreateEntry(file.RelativePath.Replace('\\', '/'), CompressionLevel.NoCompression);
```

理由：备份文件（.bak、已压缩的附件包）压缩比很低，而单线程 Deflate 大约 100–200MB/s 封顶——这是拿确定的 CPU 和确定的延迟，换不确定的一点空间。ZIP 在这里的作用是**容器**（把多文件打成一个可下载的东西），不是压缩。

### 边界与风险

- ZIP 改 store 后包体变大。若某些部署确实在乎下载体积，可以做成 `system_settings` 里的一个开关（默认 store），但**不要**做成每次下载的 URL 参数——那会变成一个没人知道该怎么选的选项。
- `81920` 这个数字在项目里还有别的出现点，改之前 grep 一遍确认没有误伤。

### 验收标准

- 6GB 单文件恢复下载吞吐提升到接近盘速（对比改动前）。
- 一个 20GB 备份集的整包 ZIP 下载，CPU 占用从单核打满降到接近空闲，耗时下降。
- Range 请求（`bytes=start-end`、`bytes=-N`）行为不变，`206` / `Content-Range` / `416` 三条路径回归通过。
- 定期复查一轮全仓库的耗时下降。

## T7 · `MaxParallelChunks` 是客户端本地值，现场不可运维

**级别**：P2　**工作量**：0.5 人日

### 证据

`src/agent/BackupMonitor.Agent/AgentOptions.cs:36` 定义了 `MaxParallelChunks`，默认 4；但 `src/agent/BackupMonitor.Agent/appsettings.json` 的 `Agent` 段里**没有这个键**。

### 方案

- 把 `MaxParallelChunks`、以及 T1 引入的 `MaxParallelFiles`、T5 引入的 `MaxParallelHashes` 一并加入 `backup_tasks`，随任务配置由服务端下发（走 `AgentConfigService` 现有的下发链路，与 `ChunkSizeBytes` / `BandwidthLimitKbps` 并列）。
- `AgentOptions` 里的同名项降级为**下发缺失时的兜底默认值**，并补进 `appsettings.json` 让它可见。
- 管理端「备份任务」的「高级选项」折叠区里加这三项，配文案说明它们是性能参数、限速请用 `BandwidthLimitKbps`。

- 数据库变更：`backup_tasks` 新增三列，走一条新迁移脚本。

### 验收标准

- 在管理端改这三个值 → 下一次上传实测并发度随之改变，无需重启 Agent。
- 下发值越界（0、-1、999）时被服务端拒绝；直接改库塞进越界值时被客户端夹回默认区间。

## W1 · 全站没有任何压缩

**级别**：P1　**工作量**：0.25 人日

### 证据

- `src/src/BackupMonitor.Api/Program.cs:415` 是裸的 `app.UseStaticFiles()`，管道里没有 `UseResponseCompression`。
- `deploy/nginx/backup-monitor.conf` 全文没有一条 `gzip` 指令。

### 根因

两种部署形态都没兜住：Secure 形态下 nginx 没开 gzip，Turnkey 形态下 Kestrel 直接对外、更没有任何代理能补上。

结果是约 8900 行 JS/CSS 按原文传输，**所有 JSON 响应也一样**——审计日志、客户端列表、结束的传输那几页，一页 50 条 JSON 的压缩比通常在 8 倍以上。

### 方案

**1. Kestrel 侧（两种形态都覆盖）**

`Program.cs` 服务注册段：

```csharp
builder.Services.AddResponseCompression(options =>
{
    // HTTPS 上启用压缩需要显式打开。本系统的响应体是 JSON 与静态资源，
    // 不含用户可控的机密字段与攻击者可注入的反射内容，不具备 BREACH 的利用前提。
    options.EnableForHttps = true;
    options.Providers.Add<BrotliCompressionProvider>();
    options.Providers.Add<GzipCompressionProvider>();
    options.MimeTypes = ResponseCompressionDefaults.MimeTypes.Concat(
        ["application/json", "image/svg+xml"]);
});
```

管道里插在**静态文件之前**：

```csharp
app.UseResponseCompression();   // 必须在 UseStaticFiles 之前
app.UseDefaultFiles();
app.UseStaticFiles();
```

**2. nginx 侧（Secure 形态额外一层，避免回环上做无谓压缩）**

```nginx
gzip              on;
gzip_types        text/css application/javascript application/json image/svg+xml;
gzip_min_length   1024;
gzip_proxied      any;
```

`location /api/v1/downloads/` 里显式 `gzip off;`——备份文件不该被压第二遍。

### 边界与风险

- **恢复下载路径必须排除**：`application/octet-stream` 与 `application/zip` 不在 `MimeTypes` 里，默认就不压；但改完要实测确认，否则会在下载 6GB 备份时白烧 CPU。
- `EnableForHttps = true` 的安全考量已写进上面的注释，评审时按这条判断，不要凭「HTTPS 上不该压缩」的笼统印象否掉。

### 验收标准

- 首屏资源的 `Content-Encoding` 为 `br` 或 `gzip`，传输量下降 **≥70%**。
- 一页 50 条的审计日志响应，传输量下降 **≥80%**。
- 恢复下载的响应**没有** `Content-Encoding`，且吞吐与改动前一致。

## W3 · 轮询时整块 `innerHTML` 重建

**级别**：P0（观感 + 性能）　**工作量**：1.5 人日

### 现象

传输页每 5 秒把队列条、汇总条、整张表全部重建。可见后果有四条，其中第一条最要命：

1. **进度条是瞬移的，不是滑动的。**
2. 正在选中 / 准备复制的主机名被清空。
3. `title` 提示被打断、`tr:hover` 丢失。
4. 键盘导航的 `kbd-focus` 行位置重置。

### 证据

- 重建点：`js/views/transfers.js:161` —— `wrap.innerHTML = queueHtml(queue) + summaryHtml(rows) + tableHtml(COLUMNS, rows, {...})`
- 被吃掉的设计意图：`css/components.css:484`

  ```css
  .xfer-bar span{display:block;height:100%;background:var(--accent);
                 border-radius:inherit;transition:width .4s ease}
  ```

  这条 `transition` **从来没有触发过一次**——元素每 5 秒被全新创建，浏览器没有「上一个宽度」可以过渡。

### 根因

轮询渲染用的是「整块字符串拼接 + 一次性 `innerHTML`」，这在首屏是对的，在**周期性刷新**上是错的。CSS 里写好的过渡、浏览器维护的选中/焦点/悬停状态，全部依赖 DOM 节点的连续性。

### 方案

引入一个**极小的行级 diff**，不引框架、不引虚拟 DOM。

**1. 抽出通用工具 `js/ui.js` 新增 `patchRows(tbody, rows, keyOf, renderCells)`**

```js
/* 按稳定 key 增量更新表格行。
   只在「同一张表反复刷新」的场景用；首屏与筛选后的重建仍然走 tableHtml。

   为什么值得写：整块 innerHTML 重建会把 DOM 节点全换掉，于是
   —— CSS 过渡拿不到上一个值（.xfer-bar 的 .4s 从来没生效过）
   —— 用户正在选中的文本被清空
   —— hover / title / kbd-focus 全部重置
   这四条都不是性能问题，是「界面看起来很廉价」的直接来源。 */
export function patchRows(tbody, rows, keyOf, renderCells) {
  const existing = new Map([...tbody.children].map(tr => [tr.dataset.rowKey, tr]));
  let cursor = null;

  for (const row of rows) {
    const key = String(keyOf(row));
    let tr = existing.get(key);
    if (tr) {
      existing.delete(key);
      // 只改内容变了的单元格：改不动的 <td> 保持原节点，
      // 里面的 .xfer-bar 就能拿到「上一个宽度」，过渡才有意义。
      const cells = renderCells(row);
      for (let i = 0; i < cells.length; i++) {
        const td = tr.children[i];
        if (td && td.innerHTML !== cells[i]) td.innerHTML = cells[i];
      }
    } else {
      tr = document.createElement('tr');
      tr.dataset.rowKey = key;
      tr.innerHTML = renderCells(row).map((html, i) => `<td${COL_CLASS[i] || ''}>${html}</td>`).join('');
    }
    // 顺序对齐：insertBefore 到当前游标之后，避免整表重排
    const next = cursor ? cursor.nextSibling : tbody.firstChild;
    if (next !== tr) tbody.insertBefore(tr, next);
    cursor = tr;
  }

  for (const stale of existing.values()) stale.remove();
}
```

**2. `transfers.js` 的 `LOADERS.transfers` 改为两条路径**

```js
const wrap = $('#vwrap');
const table = wrap.querySelector('table tbody');

if (!table || !rows.length || wasEmpty) {
  // 首次、从空变有、从有变空 —— 结构变了，仍然整块重建
  wrap.innerHTML = queueHtml(queue) + summaryHtml(rows) + tableHtml(COLUMNS, rows, {...});
} else {
  // 稳态刷新 —— 只 patch
  patchStatusbar(wrap, queue, rows);            // 队列条与汇总条各自只改文本节点
  patchRows(table, rows, r => r.sessionId, r => COLUMNS.map(c => c.render(r)));
}
```

`COLUMNS` 已经是「每列一个 `render(r)` 返回 HTML 片段」的结构（`transfers.js:239` 起），天然适配，不用重写列定义。

**3. 进度条的过渡节奏对齐轮询节奏**

轮询是 5 秒一次，而 `transition:.4s` 会让进度条在 0.4 秒内跳完再等 4.6 秒——看起来仍然是「一顿一顿」。改成：

```css
.xfer-bar span{transition:width 1.2s cubic-bezier(.4,0,.2,1)}
```

1.2 秒的缓动配 5 秒轮询，观感上接近连续。**不要**做插值动画（按速率预测中间值），那是在界面上编造数据。

**4. 同样受益的页面**

`clients.js`（8 秒）、`restores.js`（5 秒）、`runs.js`、`run-detail.js`（5 秒）用同一个 `patchRows`。建议 transfers 先落地跑通，再推给其余四处。

### 边界与风险

- **必须有稳定 key**。传输页用 `sessionId`；客户端页用 `id`；恢复页用 `id`。没有稳定 key 的表不要用 patch，退回整块重建。
- **排序变化**：服务端返回顺序会变（卡住的排最前）。`patchRows` 里的 `insertBefore` 已经处理了重排，但要测「一条传输变成 stalled 跳到首位」时不闪。
- **批量选择状态**：传输页目前没有多选，其余页面有。推给 `clients.js` 时必须确认 checkbox 的 `checked` 状态在 patch 后仍然正确（`tableHtml` 是靠 `App.state[key].selected` 渲染的，patch 时要走同一份状态）。
- **不要引入框架**。这个 diff 只有 30 行，覆盖的是「同构表格反复刷新」这一个场景，不需要更多。

### 验收标准

- 传输页连续观察 60 秒：进度条平滑推进，不出现跳变。
- 刷新过程中选中一段主机名文本，跨过至少两次轮询后选中仍在。
- 用 `j`/`k` 定位到某一行，跨轮询后 `kbd-focus` 仍在同一行。
- 一条传输变为 `stalled` 并跳到首位时，该行不闪烁、不重建。
- DevTools Performance 面板中每次轮询的 Recalculate Style + Layout 时间下降。

## W4 · 轮询不看 `visibilityState`

**级别**：P2　**工作量**：0.5 人日

### 证据

`transfers`(5s/15s)、`clients`(8s)、`restores`(5s)、`runs`、`run-detail`(5s) 五处轮询，全仓库 grep `visibilityState` / `document.hidden` **零命中**。

### 根因

浏览器对后台标签页的 `setTimeout` 会节流到约每分钟一次，所以不至于失控；但几个管理员各挂一个页面时，服务端仍在为没人看的界面持续跑聚合查询。

### 方案

在 `js/app.js` 里加一个统一的轮询封装，五处共用：

```js
/* 轮询编排：页面不可见时停掉，回到前台立刻刷一次再排下一轮。
   「回到前台立刻刷」这一步不能省 —— 少了它，人切回来看到的是切走那一刻的旧数字，
   而这正是最容易被当成「系统卡住了」的场景。 */
export function schedulePoll(routeKey, fn, delayMs) {
  clearTimeout(App.timer);
  if (document.visibilityState === 'hidden') {
    App.pendingPoll = { routeKey, fn, delayMs };
    return;
  }
  App.timer = setTimeout(() => { if (location.hash === '#/' + routeKey) fn(); }, delayMs);
}

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState !== 'visible') return;
  const p = App.pendingPoll;
  App.pendingPoll = null;
  if (p && location.hash === '#/' + p.routeKey) p.fn();
});
```

五处的 `App.timer = setTimeout(...)` 全部换成 `schedulePoll(...)`。`route()` 里现有的 `clearTimeout(App.timer)` 保留，另加 `App.pendingPoll = null`。

### 验收标准

- 切到别的标签页 → Network 面板不再出现该页的轮询请求。
- 切回来 → 立刻发出一次请求，数字随即更新。
- 切页（改 hash）后旧页的轮询彻底停止，不会在后台复活。

## W5 · 概览页完全不刷新

**级别**：P1　**工作量**：0.5 人日

### 现象

概览是「值守」组的落地页，顶上还挂着「正在传输」，却一个定时器都没有——打开那一刻的快照会一直挂到手动刷新。而传输页 5 秒刷、客户端页 8 秒刷。

更糟的是**界面上没有任何地方说明数据截止到什么时候**：一个挂在墙上显示器的概览页，和一个刚打开的概览页，长得一模一样。

### 证据

`js/views/dashboard.js` 的 `vDashboard()` 里没有任何 `setTimeout` / `App.timer`。

### 方案

**1. 把 `vDashboard` 拆成 shell + loader**（与 `vTransfers` / `LOADERS.transfers` 同构）

```js
export async function vDashboard() {
  $('#app').innerHTML = shell('overview', '概览', loading());
  await LOADERS.overview();
}

LOADERS.overview = async function () {
  ... // 现有取数与渲染
  App.overviewFetchedAt = Date.now();
  renderFreshness();
  schedulePoll('overview', LOADERS.overview, POLL_MS);   // 复用 W4 的封装
};
```

轮询间隔 **20 秒**：概览上唯一会快速变的是「正在传输」，而真要盯传输的人会去传输页；20 秒足够让待办数、在线数、最近入库时间保持有意义。

**2. 状态条右侧加数据新鲜度**

顶部 `.dashboard-statusbar` 的 `.status-meta` 里追加一项：

```js
`<span class="freshness"><time datetime="${new Date(App.overviewFetchedAt).toISOString()}">
   更新于 ${hhmmss(App.overviewFetchedAt)}</time> · <span id="freshAge">刚刚</span></span>`
```

再挂一个 1 秒的计时器只更新 `#freshAge` 的文本（「12 秒前」「1 分钟前」）——**只改这一个文本节点**，不触发任何重排。

超过 3 倍轮询间隔（60 秒）仍未刷新成功时，给 `.freshness` 加 `is-stale` 类，用 `--warn-fg`：数据变旧本身是需要被看见的状态。

### 边界与风险

- 概览有 6 个接口，20 秒一轮对服务端是可接受的（`todo-summary` 是其中最重的，10 条查询）。若实测有压力，先给 `todo-summary` 加一层 30 秒的内存缓存，而不是把轮询间隔拉长——拉长会让「值守」这个定位名存实亡。
- 刷新失败时**不清空已有内容**，只把 `.freshness` 标成 `is-stale`。这与 `transfers.js` 现有的失败处理理由一致：上一次的数字仍然比空白有用。

### 验收标准

- 概览页挂 5 分钟，数字随后台变化自动更新。
- 断开服务端 90 秒，`.freshness` 变为告警色并显示真实的「N 分钟前」，页面内容不被清空。
- 切到后台标签页后停止轮询（W4 生效），切回立刻刷新。

# 批次 U · 界面提升

> 这一批的前提：现有视觉体系是对的，**不推翻**。`UI-REDESIGN §7.5` 明确写了「无装饰渐变」，这个判断要保留。下面每一条要么修复被吃掉的设计意图，要么补一处真信息——没有一条是往上加装饰。

## U1 · 传输页缺时间维度

**级别**：P1　**工作量**：1.5 人日

### 现象

每一行只回答「此刻传了多少、此刻多快」。但运维真正要判断的是三件事：链路正常、正在退化、已经卡住。前两者靠**速率的走势**才分得开，靠一个瞬时数字分不开。

现有的「静默」列只能判出第三种（已经卡住），这在 `transfers.js:265` 的注释里说得很清楚——但「正在退化」目前无处可读。

### 证据

- 服务端已经在算瞬时速率：`UploadProgressService.cs:249` 的 `_sampler.Observe(r.Id, r.UploadedBytes, now)`。
- 但 `UploadProgressDto` 只回传了当前值 `BytesPerSecond`，历史采样点全部丢弃。

### 方案

**1. 服务端：把采样序列一并回传**

`UploadProgressSampler` 内部本来就要保留上一次采样才能算出瞬时速率。把它改成保留最近 **12 个**采样点的环形缓冲（5 秒轮询 × 12 = 覆盖 1 分钟），并在 DTO 上加一列：

```csharp
/// <summary>最近 12 次采样的瞬时速率（字节/秒，旧→新）。
/// 用来在界面上画一条一分钟的走势线：一个瞬时数字分不出「慢」和「正在变慢」。
/// 采样点不足时返回已有的几个，不补零 —— 补零会画出一条从 0 开始的假曲线。</summary>
public IReadOnlyList<long> RecentRates { get; init; } = [];
```

内存开销：12 个 long × 并发会话数，可忽略。`_sampler.Forget(live)` 已经在做过期清理，不用另加。

**2. 前端：内联 SVG sparkline，不引图表库**

`js/ui.js` 新增：

```js
/* 速率走势线。48×14，不引图表库 —— 一条 polyline 就够，
   而任何图表库为了这条线带进来的都是几十 KB 加一套自己的主题。

   纵轴按本行自身的最大值归一化，不做跨行统一刻度：这条线要回答的是
   「这一条传输自己在变快还是变慢」，不是「哪一条最快」（那是「速度」列的事）。 */
export function sparkline(values, { width = 48, height = 14 } = {}) {
  if (!values || values.length < 2) return '<span class="spark-empty" aria-hidden="true">—</span>';
  const max = Math.max(...values, 1);
  const step = width / (values.length - 1);
  const points = values.map((v, i) => `${(i * step).toFixed(1)},${(height - (v / max) * height).toFixed(1)}`).join(' ');
  return `<svg class="spark" width="${width}" height="${height}" viewBox="0 0 ${width} ${height}"
               aria-hidden="true" focusable="false"><polyline points="${points}"/></svg>`;
}
```

```css
.spark{display:block;overflow:visible}
.spark polyline{fill:none;stroke:var(--accent);stroke-width:1.25;
                stroke-linejoin:round;stroke-linecap:round;vector-effect:non-scaling-stroke}
tr:has(.cell-warn) .spark polyline{stroke:var(--warn-fg)}
.spark-empty{color:var(--text-faint);font:var(--t-micro)}
```

「速度」列改为速率数字在上、走势线在下：

```js
{ l: '速度', num: true,
  render: r => `${fmtRate(r.bytesPerSecond)}${sparkline(r.recentRates)}` },
```

**3. 无障碍**

SVG 是纯装饰性重复（数字已经在旁边），标 `aria-hidden`。走势本身的语义（在变快 / 平稳 / 在变慢）用一个 `title` 补上，由最近 3 点与最早 3 点的均值比较得出。

### 边界与风险

- **不要补零**。采样点不足 2 个时显示 `—`。补零画出的曲线会让刚开始的传输看起来「刚从 0 冲上来」，那是编造的。
- **不要跨行统一刻度**，理由写在上面的注释里。
- 这一条依赖 W3：整块 `innerHTML` 重建的话，SVG 也是每 5 秒重画一次，没有连续性可言。**W3 必须先落地。**

### 验收标准

- 人为限速（把任务的 `BandwidthLimitKbps` 从 50000 改到 5000）→ 走势线在 1 分钟内可见地向下走。
- 拔网线制造卡死 → 走势线归零、该行「静默」列变告警色，两者一致。
- 新开始的传输前 10 秒显示 `—` 而不是一条贴地的假线。

## U3 · 数字排版

**级别**：P2　**工作量**：0.5 人日

### 证据

`js/ui.js:78`：

```js
export function fmtBytes(n) {
  ...
  return (i === 0 ? n : n.toFixed(2)) + ' ' + u[i];
}
```

永远两位小数（`6.24 GB`、`999.00 MB`），单位与数字在同一个文本流里。

### 方案

**1. 按量级给有效位数**

```js
/* 有效位数随量级走：998 MB / 12.4 GB / 1.24 TB。
   永远两位小数的问题在关键指标上最明显 —— 「6.24 TB」里最后那一位
   既没有决策价值，又把数字拉长、把量级冲淡了。 */
function scaleBytes(n) {
  const u = ['B', 'KB', 'MB', 'GB', 'TB'];
  let i = 0, v = Number(n);
  while (v >= 1024 && i < u.length - 1) { v /= 1024; i++; }
  const digits = i === 0 ? 0 : v >= 100 ? 0 : v >= 10 ? 1 : 2;
  return { value: v.toFixed(digits), unit: u[i] };
}

export function fmtBytes(n) {
  if (n == null) return '—';
  const { value, unit } = scaleBytes(n);
  return `${value}<span class="unit">${unit}</span>`;
}
```

**2. 单位降级为次要信息**

```css
.unit{margin-left:.25em;font-size:.82em;font-weight:400;color:var(--text-muted)}
```

**3. 注意事项**

`fmtBytes` 的返回值从纯文本变成了 HTML 片段。全仓库 grep 它的每一个调用点，确认：

- 用在 `innerHTML` / 模板字符串里的 → 不用改；
- 用在 `textContent` 或被 `esc()` 二次转义的 → 会显示出标签源码，必须改；
- `fmtRate` 是 `fmtBytes(bps) + '/s'`，`/s` 也应该进 `.unit`：`fmtBytes(bps)` 返回的 `</span>` 之前插入。

保守做法是新增 `fmtBytesHtml`，`fmtBytes` 保留纯文本语义，只在确认安全的展示点换过去。

表格里 `tabular-nums` 已经有了（`css/components.css:20`），底子是好的，这条只补有效位数与单位。

### 验收标准

- 概览的容量 KPI 显示为「**12.4** GB」形态：数字用 `--t-num`，单位小一号且是灰色。
- 全仓库无「显示出 `<span>` 源码」的位置。
- 数字在轮询更新时不左右抖动（`tabular-nums` 生效）。

## U5 · 结论备案：不做的清单与理由

**级别**：结论备案，无工作量　**目的**：避免这些东西日后被当作「提升科技感」重新提出来

以下一律**不做**：

| 不做的东西 | 理由 |
|---|---|
| 卡片渐变边框、发光 KPI 数字 | 装饰性视觉与数据无关，加上去只会让界面显得像模板，而不是像仪表 |
| 背景网格 / 粒子 / 扫描线 | 同上，且会持续占用 GPU |
| 侧栏毛玻璃 | 降低文字对比度，换不来任何信息 |
| 把 `--accent` 改成霓虹青蓝 | 现有强调色刻意选在语义色相之外（`tokens.css` 的注释），改成青蓝会与 `--info` 撞色，状态判读会出错 |
| 骨架屏改成扫描线动画 | 现有骨架屏刻意做成「形状同真实内容、无闪烁动画」（`UI-REDESIGN §6.5`），改回动画是倒退 |
| 引入前端框架 / 打包器 | 25 个 ES module + 按路由懒加载 + HTTP/2，在局域网上已经够用，改造成本换不回什么 |
| 引入图表库画 sparkline | 一条 polyline 用不着几十 KB 和一套自己的主题系统 |
| 传输层压缩（上传链路） | 千兆约 110MB/s，源盘顺序读通常 100–200MB/s，瓶颈本就不在网络；压缩只会把 CPU 变成新瓶颈。只有链路明显慢于磁盘（跨 VPN / 广域）时才值得重议 |
| 进度条做速率插值动画 | 那是在界面上编造没有采样到的数据 |

**判据**：一处视觉改动如果不能回答「它让人更快看清哪个事实」，就不做。「科技感」在运维工具里的来源只有三条——**运动来自数据、密度来自真信息、精度来自排版**——不在这三条里的都是装饰。

# 批次 S · 服务管理窗口

> 对象是 `src/server/BackupMonitor.Server.Setup/SetupForm.cs`。这是整个产品里视觉投入最少的一处：14 个默认样式的 WinForms 按钮塞进一个 `FlowLayoutPanel` 自动换行，服务状态是跟在按钮队尾的一个 Label。

## S1 · 装完之后窗口仍是「安装向导」

**级别**：P1　**工作量**：1 人日

### 现象

已经装好的机器每次打开这个程序，上半屏永远是「安装 BackupMonitor Server」大标题 + 两个密码输入框 + 一个「修复/升级」按钮，而实际要用的 14 个维护按钮挤在下面。

### 证据

`SetupForm.cs:38` 起：窗口标题写死 `"BackupMonitor Server 安装"`；`SetupForm.cs:67` 的大标题 Label 与 `SetupForm.cs:82`、`:83` 的两个密码字段无条件加进 `root`；维护区（`_maintenancePanel`）只是被 `Enabled = ServerInstaller.IsInstalled()` 控制可用性（`SetupForm.cs:180`），布局上仍在最后一行。

### 方案

按 `ServerInstaller.IsInstalled()` 分成两个完全不同的窗口形态：

| | 未安装 | 已安装 |
|---|---|---|
| 窗口标题 | `BackupMonitor Server 安装` | `BackupMonitor 服务端 · 服务管理` |
| 主内容 | 现有安装向导（标题 + 两个密码框 + 进度条 + 安装按钮） | 服务状态条（S2）+ 四组操作（S3）+ 日志区（S4） |
| 密码相关 | 主表单上 | 收进「重置管理员密码」弹窗 |

代码上把构造函数拆成 `BuildInstallLayout()` 与 `BuildConsoleLayout()` 两个方法，构造时二选一。安装成功后不留在安装态——直接切换到控制台态（把 `Controls` 清空重建），让人立刻看到服务状态。

### 边界与风险

- 「修复/升级」在已安装态下仍然需要，放进 S3 的「服务控制」组，文案改成「修复 / 升级安装」。
- `IsInstalled()` 的判定要在窗口打开时取一次即可，不要每次刷新都查。

### 验收标准

- 未安装的机器：窗口与现在完全一致。
- 已安装的机器：打开即是服务管理台，看不到密码输入框。
- 全新安装成功后不需要重开程序，窗口自动切到服务管理台。

## S2 · 服务状态排在 14 个按钮之后，且是静态文本

**级别**：P1　**工作量**：0.75 人日

### 现象

`SetupForm.cs:161` 的注释写着「服务状态摆在按钮之后：先知道现在是什么状态，才知道该按哪个按钮」——但 `FlowLayoutPanel` 是从左到右、自动换行的**流式**布局，把 `_serviceStatus` 添加在 14 个按钮之后，实际渲染位置就是**最后**。注释的意图和布局的效果正好相反。

而且它是静态的：只在 `RefreshServiceStatus()` 被显式调用时更新（构造时一次，各操作完成后一次）。

### 证据

`SetupForm.cs:160-164`；状态文本格式见 `SetupForm.cs:396`：

```csharp
_serviceStatus.Text = $"服务状态：Server {server} · PostgreSQL {postgres}";
```

### 方案

**1. 移到顶部，做成状态条而不是一行文字**

窗口顶部一条固定高度（约 64px）的 `TableLayoutPanel`，两列，每列一块服务：

```
● BackupMonitor.Server        运行中    端口 5443 · PID 4128
● BackupMonitor.PostgreSQL    运行中    PID 3204
```

- 左侧一个 10px 的圆点，自绘（`Paint` 事件里 `FillEllipse`）：运行=`#0f7a4a`、停止=`#7f8f99`、异常/未安装=`#b3261e`。三种颜色直接取自 `tokens.css` 的 `--ok-fg` / `--ink-400` / `--err-fg`，与 Web 端保持同一套。
- 服务名用正文字体，状态词用 `FontStyle.Bold`，端口/PID 用等宽（S5）。

**2. 加 2 秒轮询**

```csharp
// 服务状态必须是活的。这一条不是为了好看：
// 停止/启动/重启这三个按钮该不该点，唯一的依据就是当前状态；
// 而按下之后服务要几秒才真的起来，静态文本会让人以为没反应、于是再点一次。
_statusTimer = new System.Windows.Forms.Timer { Interval = 2000 };
_statusTimer.Tick += (_, _) => RefreshServiceStatus();
_statusTimer.Start();
```

`RefreshServiceStatus()` 目前是同步查 `ServiceController`，在 UI 线程上跑。2 秒一次、两个服务，开销可以接受；但**必须**保证异常路径不弹窗（现有代码已经是 try/catch 写进文本，保持）。窗口 `FormClosed` 时 `Stop()` + `Dispose()`。

### 验收标准

- 从服务管理器手动停掉 Server 服务 → 窗口内的圆点在 2 秒内变灰、状态词变「已停止」。
- 点「启动服务」后，状态在服务真正起来时自动变绿，不需要手动刷新。
- 服务查询抛异常时窗口不弹框、不卡死，状态区显示「读取失败」。

## S3 · 14 个同权重默认按钮平铺

**级别**：P1　**工作量**：1 人日

### 现象

`SetupForm.cs:126-138` 定义的 14 个按钮全部是默认样式、`AutoSize = true`，塞进同一个 `FlowLayoutPanel`（`SetupForm.cs:140-159`）。后果：

1. 「启动服务」和「卸载」长得一模一样、还挨着排。
2. 分组关系（服务控制 / 访问诊断 / 密钥配置 / 危险操作）在视觉上完全不存在。
3. 换行位置随窗口宽度漂移，同一台机器缩放窗口后按钮的相对位置会变。

### 方案

**1. 按四组分区**，每组一个带标题的区块。分隔用「1px 线 + 上方 11px 灰色小标题」，**不用 `GroupBox`**（那种凹边框是 Win2000 时代的观感）：

| 组 | 按钮 |
|---|---|
| 服务控制 | 启动服务 · 停止服务 · 重启服务 · 修复/升级安装 |
| 访问与诊断 | 打开管理网页 · 运行诊断 · 查看服务端指纹 |
| 密钥与配置 | 导出密钥包 · 导入密钥包 · 导出配置备份 · 导入配置备份 · 重新签发服务端证书 · 修复文件权限 |
| 危险操作 | 重置管理员密码 · 卸载 |

「危险操作」单独一组、放最下、用 `ForeColor = --err-fg` 的**文字**色（不是红色填充按钮——填充红太吵，会把注意力从状态条上抢走），且两个都必须二次确认。

**2. 只留一个主按钮**，按上下文变：

```csharp
// 主按钮跟着状态走：服务停着时人要做的是把它起来，
// 服务跑着时人来这个窗口多半是为了开管理网页。
// 14 个同权重按钮是「没设计」最直接的观感来源 —— 它让每一次使用都要重新读一遍全部标签。
var primary = serverRunning ? _openWeb : _startServices;
```

主按钮：`FlatStyle.Flat` + 背景 `#5b4fc7`（`--accent`）+ 白字 + 加粗。其余全部：`FlatStyle.Flat` + 白底 + `FlatAppearance.BorderColor = #ccd5da`（`--ink-200`）+ `BorderSize = 1`。不需要自绘。

**3. 固定按钮宽度**

同一组内按钮等宽（取该组最宽者），用 `TableLayoutPanel` 而不是 `FlowLayoutPanel`，消除换行漂移。

### 边界与风险

- **DPI**。`AutoScaleMode.Dpi` 已经设了（`SetupForm.cs:40`），但 `FlowLayoutPanel` + `AutoSize` 在 150% 缩放下换行会很难看。换成 `TableLayoutPanel` 后必须在 100% / 125% / 150% 三档各测一遍，尤其是 Server 2012 R2 的控制台。
- `MinimumSize` 现在是 680×500（`SetupForm.cs:42`），四组分区后要重算，确保最窄时不出现横向滚动条。

### 验收标准

- 100% / 125% / 150% 三档 DPI 下，四组分区都完整可见，无横向滚动条、无按钮被截断。
- 服务停止时主按钮是「启动服务」，运行时是「打开管理网页」。
- 「卸载」与「重置管理员密码」都需要二次确认才执行。

## S4 · 状态行是覆盖式的

**级别**：P2　**工作量**：0.5 人日

### 现象

`_status` 是一个单行 Label（`SetupForm.cs:85-93`），每次操作把它整个覆盖：「服务已发出重启命令。」被下一条「配置备份包已导出」冲掉，之前发生过什么完全不可考。

运维界面里「刚才发生了什么」必须留痕——尤其是导入密钥包、重新签发证书这类做完就不可逆的操作。

### 方案

窗口底部换成一个只读的多行区域（`TextBox` with `ReadOnly = true, Multiline = true, ScrollBars = Vertical`，或 `ListBox`），按时间戳追加：

```
14:32:07  服务已发出重启命令。
14:32:19  服务状态：Server 运行中 · PostgreSQL 运行中
14:35:02  配置备份包已导出（含服务端密钥与整库转储）；该文件包含敏感密钥，请仅保存到受控位置。
```

- 最多保留 200 条，超出丢最旧的。
- 提供一个「复制全部」按钮——出问题时管理员需要把这段发给支持。
- **不写盘**：这里出现过的内容包含路径等信息，且服务端本身已有 `logs/` 目录承担持久化。这个区域只服务于「本次会话里我做了什么」。

### 验收标准

- 连续执行 5 个操作，5 条结果都在，按时间倒序或正序均可但要一致。
- 「复制全部」能把内容放进剪贴板。
- 窗口关闭后内容不落盘。

## S5 · 指纹、端口、版本号用比例字体

**级别**：P2　**工作量**：0.25 人日

### 现象

`SetupForm.cs:689` 把指纹拼成一行普通文本：

```csharp
_status.Text = "服务端 TLS 指纹：" + normalized;
```

一串 64 位十六进制、比例字体、不分组——人要拿它和部署记录逐字核对，这个呈现方式基本保证会看错。

### 方案

- 全窗口凡是「机器产生的标识符」一律等宽：`new Font("Cascadia Mono", 9)`，取不到时回退 `Consolas`，再回退 `Courier New`。范围包括：TLS 指纹、端口号、PID、版本号、安装/数据目录路径。
- 指纹**按 4 位分组**显示：`A1B2 C3D4 E5F6 ...`，并提供「复制」按钮（复制时给的是不带空格的原值）。
- 状态条与日志区里的时间戳同样用等宽，好让多行时间纵向对齐。

Web 端已经有对应的 `--font-mono` 定义（`tokens.css`），字体族保持一致即可，不必也不可能共享代码。

### 验收标准

- 指纹按 4 位分组显示，「复制」拿到的是不带空格的规范值。
- 目标机器上等宽字体回退链至少有一档可用（Server 2012 R2 上 `Cascadia Mono` 通常不存在，必须落到 `Consolas`）。

# 附：本方案与既有约定的关系

- **不推翻**存储层的任何一条既有优化（1MB 缓冲、单次 `FlushFileBuffers`、分块并发、增量 CTE、硬链接入库）。
- **不推翻** `UI-REDESIGN` 的视觉判断，尤其是 §7.5「无装饰渐变」与 §6.5「骨架屏无闪烁动画」。
- **不改变**完整性判定的权威基准（`expected_sha256`）与限速的唯一口径（`BandwidthLimitKbps`）。
- **不新增**任何管控流程。T7 把并发度提到服务端是为了让性能参数可运维，不是为了增加一道审批。
