# 代码缺陷复审 2026-08-21

本轮聚焦**代码缺陷**（正确性与安全性），不含功能完整性与 UI 评估。
验证方式：`dotnet build`（0 警告 0 错误）+ 全量测试 114/114 通过
（本地 PostgreSQL 16 回退，`BACKUPMONITOR_TEST_LOCAL_POSTGRES=1`）。

## 一、本轮修复

### P0-1 强制改密仅在浏览器侧生效

`must_change_password` 此前只随登录响应交给前端，由 localStorage 决定是否跳转改密页，
服务端不做任何校验——带初始口令登录拿到的就是全权限访问令牌，curl 直连或清掉
localStorage 键均可绕过。

- `JwtTokenService`：`users.must_change_password` 为 true 时写入同名 claim。
- 新增 `PasswordChangeRequiredMiddleware`，注册在 `UseAuthentication` 之后、
  `UseAuthorization` 之前——该位置同时覆盖 MVC 控制器与 minimal API（如 `/health/db`），
  不是只挂 MVC 过滤器。未改密时仅放行 login/refresh/logout/me/change-password，
  其余一律 403 `PASSWORD_CHANGE_REQUIRED`。
- Agent 走客户端证书方案，主体不含此 claim，不受影响。
- 前端改为以服务端为准：`/auth/me` 的 `mustChangePassword` 是权威值，
  localStorage 降为首屏兜底；`api.js` 收到该错误码自行回到改密页。

覆盖：`PasswordChangeGateTests`（业务端点全拒 / 改密流程放行 / 已改密用户不受影响）。

**已知边界**：claim 是签发时快照。管理员将在线用户重新标记为「需改密」，
需待其下次 refresh 才生效（refresh 会重读库），最长一个访问令牌生命周期。

### P0-2 Turnkey 形态 mTLS 握手直接失败

`ClientCertificateValidation` 留空时 Kestrel 默认「SslPolicyErrors 非 None 即拒绝」。
本系统 CA 由服务端自签、只存放于 ProgramData、从不进操作系统信任存储，
Agent 证书必然报 `RemoteCertificateChainErrors`，结果是握手阶段连接即被重置，
连 401 都返回不了。

`Program.cs` 显式放行链校验，把身份判定交还 `ClientCertificateAuthenticationHandler`
的指纹查表（校验指纹归属、证书状态、有效期、客户端状态；私钥持有由 TLS 握手本身证明）。
链校验在此信任模型下本就不提供任何东西，真正的信任源是 `client_certificates` 表。

**无自动化测试**——验证需真实 TLS 握手，须起服务端 + Agent 手工过一遍。

### P0-3 保留策略物理删除缺仓库根围栏

`repository_path` 是数据库列，迁移出错、手工改库、仓库重配都可能使其指向任意目录，
而该处执行递归删除，原先仅有「至少两级目录」的弱守卫。

- `PathSafety.IsUnderBase`：与 `ResolveUnderBase` 共用同一套包含判定。
- `RetentionCleanupWorker` 删除前过围栏。根目录取自
  `IUploadStorage.GetRepositoryRootAsync()`，刻意复用写入端的同一解析，
  避免「能写的地方」与「允许删的地方」两套逻辑漂移。
- 越界走既有失败路径：**拒绝删除 + 告警 + 留在回收站**，不标记已删。
  仓库路径迁移过的历史备份集因此变为删不掉并持续告警——这是有意的，
  数据销毁的正确失败方向是拒绝并上报，由运维显式处理。

覆盖：`PathSafetyTests` 补 `IsUnderBase` 边界用例；`RetentionCleanupWorkerTests`
新增用例四——同一轮内围栏外目录必须留存且不写成功审计、围栏内照常删除，
后者用于证明拒绝来自围栏而非该轮未执行。

### P1 提交后收尾动作可摧毁已成功的备份

`UploadCommitWorker` 中 `CleanupSessionAsync` 与 `alerting.RecoverAsync`
位于事务提交**之后**，却仍在同一个 try 内，而对应 catch 会回滚事务并
删除正式目录。任一收尾步骤抛异常（如暂存文件被杀软占用），
就会走进删除已提交备份的分支。

当前之所以没出事，只因「对已提交事务调 `RollbackAsync` 会先抛异常」
这一实现细节恰好挡在删除之前——换个 EF/Npgsql 版本即可能真的删下去。

修复：提交后置 `committed = true`，收尾动作各自兜住异常仅记录日志；
catch 增加 `if (committed) throw;` 闸门作为纵深防御。

**无自动化测试**——构造该路径需注入 `IUploadStorage` 故障替身，
改动本身已使该分支结构上不可达。

## 二、本轮已排查且未发现问题的面

| 面 | 结论 |
| --- | --- |
| `async void` / `.Result` / `.Wait()` | 无（仅 `Program.cs` 迁移命令入口一处同步等待，合理） |
| 空 catch 吞异常 | 无 |
| SQL 注入 | 全部参数化（`FromSqlRaw`/`ExecuteSqlRaw` 占位符、`NpgsqlParameter`） |
| `DateTime.Now` 误用 | 无，全部 `UtcNow`；调度锁 `expires_at` 取数据库时钟 |
| 前端 XSS | `esc()` 覆盖一致；`tableHtml` 默认单元格、`openModal`/`openDrawer`/`formModal` 标题与选项、`status()` 均转义；`toast` 用 `textContent`；自定义 `render` 回调逐个核对无遗漏 |
| 上传会话越权 | `LoadOwnedSessionAsync`/`LoadOwnedFileAsync` 全链路校验 `ClientId` 归属 |
| 登录暴力破解 | 有锁定（`max_login_attempts`/`lockout_duration_seconds`）；用户不存在时走等成本 bcrypt，无用户名枚举时延泄露 |
| 恢复下载鉴权 | 令牌 32 字节随机、落库存哈希、带有效期；`path` 参数须精确匹配已入库文件记录 |
| 路径穿越（下载/归档） | `PathSafety.ResolveUnderBase` 兜底；ZIP 条目名二次校验 |
| 通知投递 | 重试有上限（`notification_max_attempts`），非无限重投 |
