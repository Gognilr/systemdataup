## 第六批：备份的可用性与核对口径

前五批解决的是「出事了有没有人知道」。这一批解决的是另一个问题：
**入库前的哈希核对证明了「仓库里的字节 = 客户端当时的字节」，
但没有任何一处证明「这个文件能用」。**

### ~~R14 — 入库时按文件类型做结构快检~~（A4）—— 2026-09-10 决定不做

原方案：在 `UploadCommitWorker` 整份算哈希那一步顺带检查 `.bak` 文件头 / 压缩包完整性 /
0 字节与尾部截断，抓「哈希对得上但文件根本打不开」的坏备份。

**不做的理由**：`.bak` 的结构判定要靠现场真实样本才敢写，而 R16 的历史基线大小告警
已经覆盖了同一类信号里最有价值的那部分——「备份跑了但是空的 / 只剩十分之一」。
剩下的收益不足以支撑这份实现和误报风险。

**残留风险**（决定如此，记录备查）：一份哈希完整但内容损坏的备份，
系统仍然会绿灯保存并长期守护，直到真要恢复那天才发现打不开。

## 第八批：客户端升级下发（R20）

### [x] R20 — 升级下发只暂存不生效（2026-09-11 新增，A 级）

**现象**：管理页面「客户端 → 升级」能选机器、填版本 / URL / SHA-256 并下发，
Agent 也确实执行了——但只执行了前半截。

`AgentWorker.StageUpgradeAsync`（src/agent/BackupMonitor.Agent/AgentWorker.cs:2317）做的事：
校验 URL 必须在本机的服务端上 → 下载 → 校验 SHA-256 → 解压到数据目录下的
`updates/<版本>/` → 写 `pending-update.json` → **回报 `UPGRADE_STAGED` 成功，
文案是「升级包已安全解压，将在受控重启时切换」**。

**然后没有然后了。** 全仓库 grep：`pending-update.json` 只有这一处写入，
**零个读取方**。Agent 的 Program.cs、install-agent.ps1、AgentInstaller、托盘——
没有任何一处应用这个暂存包，`updates/<版本>/` 只会越堆越多。

**为什么是 A 级**：界面显示下发成功、指令回报成功、实际运行的程序一个字节没变。
管理员据此认为全网已升级，真相要到出问题那天才暴露——与 A1、A4 同一族：
**平时完全看不出来，需要用的那天才发现没用。**

#### 第一步：止损（十分钟，即使后面的没做完也必须先做）

- [x] 把回报文案改成实话：「升级包已下载并校验，**需要人工到这台机器上完成安装**」，
      结果码从 `UPGRADE_STAGED` 换成能看出「没装上」的值。
      不能留着一句假成功。

#### 第二步：做成真正能用的

绕不过去的限制：**Windows 服务不能替换自己正在运行的程序文件**——
进程活着时它的 exe 和已加载的 dll 都被锁住。而 Agent 是自包含发布，一个包 502 个文件。
所以必须有一个住在被替换范围**之外**的第三方来做这次交换。

- [x] 新建 `BackupMonitor.Agent.Updater`：独立小工程，装在安装目录的同级子目录，
      **不在升级包的覆盖范围内**，否则它自己也会被锁
- [x] Agent 侧加「空闲判定」——这就是那句注释里的**受控**：
      没有扫描 / 预检在跑、没有上传会话在传、不在备份计划的执行窗口内。
      不空闲就推迟到下一个空闲点，不要一刀切下去让传了一半的备份作废
- [x] updater 流程：停服务 → 确认真的停了 → **备份当前目录** → 覆盖新文件 →
      启动服务 → 等心跳恢复并确认新版本号 → 删除备份
- [x] **回滚是命门**：任一步失败立刻回滚旧目录并重新启动服务。
      升级失败 = Agent 起不来 = 这台机器再也收不到任何指令，**包括修复指令**——
      它连不上，你就没法远程救它，只能上门。回滚路径要简单到不可能出错
- [x] 托盘一起换：它是登录用户会话里的另一个进程，跟服务不是一回事
- [x] **分批下发（金丝雀）**：先 1 台，等它心跳恢复且版本号变了，再放 5 台，再铺开。
      一个坏包同时推给 29 台就是 29 次上门。界面上要能看到每一批的结果
- [x] 新 Agent 起来后主动上报「升级完成 + 新版本号」，服务端据此判成功，
      而不是拿「指令执行完了」当成功
- [x] 下发表单自动填充：服务端已经通过 `AgentVersionService` 读
      `wwwroot/downloads/agent-version.txt` 知道随附版本（R11 用的就是它）；
      再让 build-turnkey.ps1 顺手写一份 zip 的 SHA-256，
      表单里的版本 / URL / 哈希三项就不必人工敲——**手抄 64 位哈希本身就是个故障源**

**验收**：在管理页面选 1 台客户端下发升级，无需上门，该机器在数分钟内自动完成切换、
心跳恢复、上报的版本号变成新版本；人为投一个坏包，该机器能回滚并恢复心跳，不掉线。

**不要做**：不要为了省事让 Agent 自己 kill 自己再靠 SCM 拉起——
SCM 拉起的还是旧文件，而且这条路上没有任何回滚余地。

#### 实现记录（2026-09-11）

- 新工程 `src/agent/BackupMonitor.Agent.Updater`（单文件自包含），装到
  `%ProgramFiles%\BackupMonitor\Updater`，与安装目录同级；升级时改名备份 → 铺新文件 →
  起服务 → 等 `state.json` 的心跳时刻刷新，任一步失败只做「删新目录 / 改回旧目录 / 起服务」三步回滚
- 换文件时**保留本机原有的 appsettings.json**：包里那一份是模板，盖掉等于把这台机器变成失联

  踩过的坑：保留 appsettings.json 意味着里面的 `AgentVersion` 升级后仍是旧值，

1. **升级执行器自身不随升级更新**——它在升级包的覆盖范围之外，这正是它能工作的原因。

2. 托盘的重启是尽力而为（`CreateProcessAsUser` 进当前控制台会话）。

## 第七批：2026-09-11 二次发现

三项都不是新功能，是上一批做完之后暴露出来的：托盘（R6）把「数据库通不通」搬上了台面，
而那一探从来没成功过；升级（R20）把前端改了一轮，而浏览器手里还留着上一版的模块。

### [x] R21 — 托盘与管理台的数据库自检（假警报 + 管理台盲区）

**现象**：两个 Windows 服务都是「运行中」，托盘却常亮橙灯「服务在跑但数据库不通」。

**成因**：托盘探的是 `/health/db`，而那个端点带 `perm:system.manage`（BATCH4 明确要求，
它会回显数据库版本与表计数，不匿名开放）。托盘手里没有令牌，拿回来的永远是 401，
而判据是「非 2xx 即数据库不通」——**这个警报在每一台健康的机器上都为真**。
报警一旦永远为真，它就不再是报警。

**改法**：

- 新增 `GET /health/db/local`：匿名，但**只认回环对端**
  （`LanNetworkPolicy.IsLoopback`，含 IPv4-mapped IPv6 归一化；
  `UseForwardedHeaders` 已按 `KnownProxies` 还原过真实客户端 IP，nginx 形态下外部请求装不成本机）。
  响应只有档次词与一句原因，**不回显**版本 / 表计数 / 缺失分区名——那些仍然只有带令牌的 `/health/db` 给
- 托盘与管理台按四档处置：正常 / 分区不齐（橙，说明重启无效）/ 不通（红）/
  **问不出来**（404、401 都归这一档，只说「没自检」，不冒充故障）
- 服务管理台状态条补第三行「备份收得进来吗」：上面那两个绿点回答的是
  「Windows 服务在不在跑」，而库不通时它们照样是绿的——**只有那两行的状态条会骗人**
- 「运行诊断」报告补一行「数据库自检」

### [x] R22 — 升级之后页面「点不开」

**现象**：左边导航点「客户端升级」，什么都不发生。没有报错、没有空白页，上一页还在屏幕上。

**成因两条，叠在一起**：

1. `wwwroot` 走默认的 `UseStaticFiles()`，只发 ETag/Last-Modified，**不发 Cache-Control**。
   浏览器按启发式规则自定新鲜期（常见是「自上次修改起时长的 10%」），
   于是升级之后，一个浏览器手里可能是**新的 app.js 配旧的某个 `views/*.js`**。
   旧模块 import 一个已经改名的导出 → 模块链接失败 → 动态 import 直接 reject
2. `route()` 里没有 try。上面那个 reject 静静地掉在地上，
   于是故障的表现就是「什么都不发生」——最难报修的一类：
   人只能说「点不开」，而控制台里那行错误谁都没看

**改法**：静态文件一律 `Cache-Control: no-cache`（可以存，用之前问一次；没变就是 304，
局域网里这点开销可以忽略）；`route()` 外面兜一层，把原因连同「按 Ctrl+F5 / 重做一次修复安装」
当场画在内容区里，并且**连外壳一起画**——否则错误卡片会把左边导航一起吃掉，人连换一页都做不到。

### [x] R23 — 到处显示版本号

报修的第一句话永远是「你那边是哪个版本」，而此前这台机器上没有一个地方能回答。

- 管理网页：侧栏底部由写死的 `Server API v1` 改为实际版本，取自登录前就匿名可见的
  `/api/v1/public/server-identity`（登录页显示指纹用的是同一个接口）
- 服务端托盘 / 客户端托盘：标题行带版本。取的都是**被管的那个程序**的版本
  （`BackupMonitor.Api.dll` / `BackupMonitor.Agent.exe`），不是托盘自己的——
  托盘在升级时不重启，报自己的版本会报错一个
- 服务管理台状态条：`服务端 vX · 管理台 vY` 分开写，不一致本身就是信息
- 两个安装器的标题行：装之前就该看得见自己拿的是哪一版

## 第八批：2026-09-11 现场反馈

### [x] R24 — 通知按渠道筛选

**现象**：启用邮件渠道 = 20 多类告警每一条都发。

**为什么要治**：「客户端 CPU 吃紧」「客户端版本落后」这类最容易变成没人看的背景噪音，
而它们一旦被习惯性忽略，「备份复查未通过」也会跟着被忽略——
**报警的可信度是整体的，摊薄了就都没了。**

**改法**：每个渠道各有一套 `filter`（最低等级 + 排除类别），群里可以收全量、邮箱只收要紧的。

- 默认 `warning`（Critical + Warning）。老配置里没有这个字段，**升级之后自动就是这个默认**，
  不需要迁移：两条 Notice 级（客户端登记成功、预检结果可疑）从此不进邮箱
- 筛的是**投递**不是**告警**：被挡下的告警照样建、照样计数、照样出现在管理网页和客户端托盘上。
  这是这套筛选敢于默认挡掉 Notice 的前提
- 等级名写错（直接改库、旧版本写进来的）退回默认，不放行一切也不挡掉一切
- 类别清单集中到 `AlertCategoryCatalog`（27 项）。此前它以字符串字面量散落在十几个服务里，
  没有一处能回答「一共有哪些」——前端那份 `L.alert_category` 就漏了 12 项，
  漏掉的在告警列表里直接显示成英文标识。这次一并补齐
- 13 项测试

### [x] R25 — 告警阈值搬上界面

`client_cpu_alert_percent`(85) / `client_memory_alert_percent`(90) /
`client_disk_free_alert_percent`(10) / `alert_renotify_hours`(24) 四个键**一直是可配的、代码也一直在读**，
但界面上没有任何入口：一台常年 90% CPU 的 ERP 服务器要把阈值调到 95%，
唯一的办法是连进数据库改 JSON，而知道该改哪个键的人只有写代码的。
于是实际发生的是没人调，告警每天照报，报到没人看。

界面上与 R24 并排放，并写明分工：**阈值决定告警什么时候产生，筛选决定产生之后发不发。**
两者不能互相替代——调高阈值会让它在告警页上也一并消失。

### [x] R26 — 升级安装的两个现场问题

**一、`The process cannot access the file ...\Accessibility.dll`**

托盘是 WinForms 程序、按松散文件发布在安装目录里，一运行就锁着 `Accessibility.dll` 那一批。
`StopTray()` 的注释写着「升级安装前必须先停」，而那一行实际被放在**解压完之后**——
停服务只解决了 `BackupMonitor.Api.dll` 那一半，另一半在托盘手里。
现在 `StopTray()` 与停服务并排，都在往安装目录写第一个文件之前。

顺带两处加固：解压单个文件撞占用时退避重试 5 次（杀软实时扫描会秒级占住刚落地的大文件，
这类占用不该让整个升级中断在解压到一半）；最终仍失败时，报错里**列出到底是谁占着**——
原来那句英文只说了哪个文件，唯独没说是谁占着，而那是唯一能让人动手的信息。

**二、装完弹出两个管理网页**

`ServerInstaller` 和 `SetupForm` 各开了一次，地址还不一样（主机名 / 127.0.0.1），
看上去像是装了两遍。开页面归调用方，安装器这一层不再有「弹出界面」这种副作用。

## 第九批：2026-09-11 现场日志带出来的

一台客户端的日志（恒源_OA服务器，08:01–15:16）一次性暴露了三件事，每一件都是
「系统知道，但没有一处界面说得出来」。

### [x] R26 补充 — 升级失败后服务停着不起来

见上一批。现场实证：升级安装撞占用报错之后，服务端服务停在那里，
全网客户端的日志里是一串 `SocketException (10060)`，而没有任何人会把
「连接尝试失败」和「刚才那次安装报错了」联系起来。

### [x] 托盘的错误洗不掉

心跳成功时只更新 `LastHeartbeatAtUtc`，**没有清 `LastError`**，
而托盘的绿灯判据恰恰是「服务在跑 + 心跳成功 + 无 LastError」三条并列。
于是服务端重启一次，客户端托盘就永久橙灯——只有「配置同步」「证书续签」
这两条偶发路径会清它。**一个不会消失的错误等于一个假的错误。**

### [x] 升级包地址：主机名 vs IP

Agent 日志里它连的是 `https://systemdatabase:5080`（局域网发现给的主机名），
而管理员从 `https://172.16.11.130:5080` 打开管理页面，下发表单便按 IP 拼出升级包地址。
Agent 只比 `host:port` 字符串，直接回 `UPGRADE_PACKAGE_URL_FORBIDDEN`。
两个地址指向同一台机器，没人会怀疑这里差了一个写法。

改：表单地址改用服务端**对外公告**的那个（`LanMode:AdvertisedUrl`，也就是客户端连过来用的），
并在输入框下写明这条约束和对应的错误码。

### [x] 升级指令失败，界面还在傻等

Agent 回报失败之后，原因写进了指令记录，而「客户端升级」页面那一行仍是
「已下发，等版本号」、结果列一横杠，一直等到 30 分钟超时才判失败——
而超时给出的说法（「版本号仍是 1.2.0」）与真正的原因毫无关系。
更糟的是 `upgrade_agent` 这类指令在整个管理界面上**没有任何入口能看到**。

改：指令一失败就把对应那台判失败并把结果码原文搬过去。
`UPGRADE_DOWNLOADED_NOT_INSTALLED` 虽然回报「成功」同样判失败——
它的意思正是「下载校验都过了，但程序一个字节没换」。

### [x] R27 — 客户端配置卡住，服务端毫不知情

**现场**：`2026-09-11 08:01:18 → 14:42:08`，**2336 条** `CONFIG_SIGNATURE_INVALID`，
每 10 秒一次，持续 6.5 小时。这台机器整整一个上午拿不到任何配置下发。

**为什么没人发现**：这是**纯客户端侧**的失败——Agent 自己把服务端的响应拒了
（它存的服务端签名公钥与服务端当前的对不上），498 这个码是它自己造的。
服务端只看到它一直在线、心跳从没断过，客户端列表里是绿的。
任务的增删改在这台机器上不生效、新加的任务永远下不去，而界面上一切正常。
**一个不生效的配置比一个报错的配置危险得多**，因为没有人会去找它。

**改法**：判据不需要客户端配合——心跳里本来就带着它当前持有的配置版本号。

- 新增 `clients.config_stale_since`（V042）：落后于要求版本的**起点**，追上就置空。
  存起点而不是布尔，因为短暂落后是正常的（改完配置到下一次心跳之间，每一台都会落后）
- 超过 `agent_config_stale_minutes`（默认 30）报 Critical，
  正文直接写明两个版本号、卡了多久，以及最常见的成因和处置
  （日志里是一串 CONFIG_SIGNATURE_INVALID → 在那台机器上重跑客户端安装器）
- 4 项测试
