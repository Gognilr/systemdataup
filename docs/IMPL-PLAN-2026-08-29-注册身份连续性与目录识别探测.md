# 实施方案 · 注册身份连续性 与 目录识别探测（2026-08-29）

本文档覆盖三组问题，来源是 2026-08-29 的一次设计质疑与一批使用反馈：

- **批次 A（注册与身份）**：起点是一个提问——「客户端安装时核对指纹有什么用，反正谁都能装客户端，也不需要服务端授权确认」。结论是指纹这一步不能删，但质疑指向了一个真实缺口：**重注册没有身份连续性证明**。
- **批次 B（目录识别探测）**：现有识别器能认的结构已经不少，但有两条会造成**静默错误答案**（轮转目录被当成多个业务单元；快照采样有偏而所有判据都是比例），以及六条覆盖面上的欠缺。
- **批次 D（手动「立即备份」）**：按钮可重复点击、等待时间过长、多点几次就并发压垮服务端读写。三条串在同一条链路上，一起改。

每条标注证据位置、根因、方案、验收标准和工作量。

## 范围与前提

已经定死、**不要再动摇**的边界：

- 本系统是**备份工具**，不是合规管控系统。任何一条改动都要先回答「它是否服务于『数据会不会丢』」；答不上来的不做。批次 A 只保留能回答这个问题的那一条，其余关于「谁有权安装」的管控一律不加。
- 客户端系统支持底线是 **Windows Server 2012 R2**。
- **系统未进生产**。语义变更直接改，不做存量兼容层、不考虑升级顺序。
- 识别器的既定原则不变：**宁可认不出来交给人选，也不要认错**。本方案新增的每一条判定分支都必须能返回「不成立」并落回原有路径。

# 批次 A：注册与身份

<a id="a0"></a>
## A0 · 结论备案：指纹核对与「服务端授权确认」分别在回答什么

**级别**：结论备案，无工作量　**目的**：避免这一步日后被当成冗余删掉

这两件事在代码里本来就是分开的，混在一起看才会觉得指纹是多余的。

### 指纹回答的是「我在跟谁说话」，不是「谁有权注册」

关键在时序。[`AgentInstaller.cs:134`](src/agent/BackupMonitor.Agent.Setup/AgentInstaller.cs:134) 把带外核对挡在下载之前：

```
progress.Report(new InstallProgress("等待核对服务端证书指纹…", 8));
await VerifyServerFingerprintAsync(...);
```

这之后的每一个字节都来自这条连接，**包括 `BackupMonitor.Agent.zip` 本身**，装完就是一个 LocalSystem 服务。而选服务端地址那一步走的是 [`LanDiscoveryClient`](src/src/BackupMonitor.Shared/Discovery/LanDiscoveryClient.cs) 的**无认证明文 UDP** 广播，任何人都能应答。

所以这一步本质是**代码来源校验**，只是长得像 TLS 校验。去掉它，「谁先应答谁就是服务端」，装进去的是谁的 Agent 没人知道。

它还有第二个用途：[`AgentWorker.cs:520`](src/agent/BackupMonitor.Agent/AgentWorker.cs:520) —— 没有固定指纹时 Agent **拒绝一切自动地址重发现**。指纹是运行期地址切换的唯一锚点。

同一批校验里还有两条同源的，一并备案，理由相同：

- [`AgentInstaller.cs:92`](src/agent/BackupMonitor.Agent.Setup/AgentInstaller.cs:92)：引导响应体里的指纹必须与本次连接实际出示的证书一致——否则等于把客户端配置成固定一张它从未验证过的证书。
- [`AgentInstaller.cs:144`](src/agent/BackupMonitor.Agent.Setup/AgentInstaller.cs:144)：UDP 发现应答自报的实例 ID 必须与这条已核对指纹的 HTTPS 连接自报的一致。

### 「服务端授权确认」是存在的，只是按部署模式分开

见 [`AgentRegistrationService.SubmitAsync`](src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs:67)：

| 模式 | 前置条件 | 落库状态 | 是否签发证书 |
|---|---|---|---|
| Secure | 必须带有效注册令牌（有效期 / `MaxUses` / 可吊销） | `PendingApproval`（[:183](src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs:183)） | **否**（[:164](src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs:164)） |
| LanSimple | 免令牌，但要求**私有网段来源** **且** 登记窗口未关闭 | `Online` | 是 |

Secure 模式下管理员不点头，客户端拿不到证书，什么也做不了——这就是「服务端授权确认」。

所以「任何人都能装客户端」的准确表述是：**LanSimple 模式、登记窗口开着、请求来自私有网段**，三条同时成立。这是为交钥匙部署明确换来的，不是遗漏。

### 为什么不给 LanSimple 再加一道人工审批

按「数据会不会丢」衡量，混进来一台客户端拿到的是一个**没有任务的身份**：服务端不会主动给它下发任何东西；上传必须挂在候选备份集上，而候选备份集来自任务（[`UploadSessionService.cs:112`](src/src/BackupMonitor.Infrastructure/Services/UploadSessionService.cs:112)）。危害面是客户端名单里多一行。

真正会让人丢数据的从来不是「多一台」，是「少一台没人发现」或「一台被伪装成正常」。后者就是 A1。

<a id="a1"></a>
## A1 · 重注册没有身份连续性证明

**级别**：P1　**工作量**：1.5 人日

### 现象

一台已被服务端判定为 `Offline` 的客户端，可以被另一台机器用同一个 `machineId` 静默顶替，并**继承管理员设过的显示名和分组**。界面上那一行仍然叫「财务服务器」，仍然在正常心跳。

### 证据

- [`AgentRegistrationService.cs:147`](src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs:147)：顶替的唯一判据是 `existing.Status == ClientStatus.Offline`。
- [`AgentRegistrationService.cs:322`](src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs:322) `SupersedeOfflineClientAsync`：旧身份让位。
- [`AgentRegistrationService.cs:173-175`](src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs:173)：`DisplayName` 与 `ClientGroupId` 从被顶掉的旧身份继承。
- [`AgentStateStore.cs:408-429`](src/agent/BackupMonitor.Agent/AgentStateStore.cs:408)：`machineId = SHA256(MachineGuid | MachineName | OSVersion)`。
- 新注册用的是一把**全新生成的密钥对**（[`AgentStateStore.cs:400`](src/agent/BackupMonitor.Agent/AgentStateStore.cs:400) 附近），服务端不校验它与旧身份 `PublicKey` 的任何关系。

### 根因

`Offline` 这一条让位规则本身是**对的**，且必须保留——它堵的是一个死锁：客户端重装后 `state.json` 没了，新装的 Agent 只能重新提交注册，而服务端旧记录还在，于是永远 409，Agent 卡在注册这一步、心跳循环根本不会启动。这段推理已经写在 [`AgentRegistrationService.cs:138-146`](src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs:138) 的注释里，不要推翻。

缺的不是这条规则，是**它没有区分两种来源完全不同的重注册**：

1. **同一台机器重装** —— 旧私钥随 `state.json` 一起没了，签不出任何东西。这是正常情况，必须放行。
2. **另一台机器冒用 `machineId`** —— 同样签不出东西。

现在这两种走同一条路径，都直接 `Online` + 继承名字分组。`machineId` 不是秘密：它由目标机器的 `MachineGuid`、机器名、OS 版本推出，任何在那台机器上待过的人都拿得到。

### 方案

把两态改成**三态**。核心是「能证明连续性就静默继承，不能证明就交给人确认」，而不是「不能证明就拒绝」——后者会把上面那个死锁装回来。

**1. Agent 侧：能签就签**

`SubmitRegistrationRequest` 增加两个可选字段：

```csharp
/// <summary>用旧身份私钥对 machineId 的签名（Base64）。本地没有旧身份时为 null。</summary>
public string? ContinuityProof { get; set; }

/// <summary>签名对应的旧公钥（Base64 SPKI），供服务端比对。</summary>
public string? PreviousPublicKey { get; set; }
```

Agent 在提交注册前，若 `state.json` 里还留着可用的旧密钥（`AgentStateStore` 已有 `ProtectedPrivateKey`），就用它对 `machineId` 签一次；没有就都留空。

注意 [`AgentStateStore.cs:237`](src/agent/BackupMonitor.Agent/AgentStateStore.cs:237) 那条「保留 MachineId 是这条路径能走通的关键」的既有逻辑：**修复重装**场景下 `state.json` 是保留的，所以修复安装能签出来，走静默继承；**卸载重装**默认删除 `state.json`，签不出来，走人工确认。这个分界正好合理。

**2. 服务端侧：三态判定**

在 [`AgentRegistrationService.cs:147`](src/src/BackupMonitor.Infrastructure/Services/AgentRegistrationService.cs:147) 那段 `existing.Status != ClientStatus.Offline` 判断之后、`SupersedeOfflineClientAsync` 之前插入：

| 情况 | 结果 |
|---|---|
| 无旧身份（`existing is null`） | 按现有逻辑走（LanSimple → `Online`，Secure → `PendingApproval`） |
| 有旧身份、`ContinuityProof` 用 `existing.PublicKey` 验签通过 | 顶替 + 继承名字分组 + 按模式给状态（**行为与今天一致**） |
| 有旧身份、无证明或验签失败 | 顶替 + 继承名字分组，但状态**强制 `PendingApproval`**，且不签发证书 |

第三态还要写清 `SupersedeReason`，让管理员在审批界面看到「该机器曾以另一把密钥注册过，本次无法证明是同一台机器」——不说清楚，审批就退化成盲点头（与 `StructureInference` 头部那条 Evidence 原则同源）。

**3. 审计**

第三态必须留一条独立的审计记录（`agent.registration.identity_unproven`），而不是复用现有的成功记录。这是唯一能事后回答「那台机器是什么时候被换掉的」的地方。

### 为什么这条值得做，而 A0 里的其他管控不值得

它回答的是「一台机器掉线了会不会被伪装成正常」——这正是备份监控唯一要防的那类静默。而「多一台无任务的客户端」不影响任何数据是否会丢。

### 验收标准

- 单测（`AgentRegistrationTurnkeyTests`）新增三例：
  - 带正确签名重注册 → `Online`（LanSimple）/ `PendingApproval`（Secure），名字分组继承，与改动前行为一致；
  - 不带签名重注册（模拟卸载重装）→ `PendingApproval`，**不签发证书**，名字分组仍然继承；
  - 带错误签名（用另一把密钥签）→ 与不带签名同样处理，且写出 `agent.registration.identity_unproven` 审计。
- 回归：旧版 Agent（不带这两个字段）重注册仍然能走通，落 `PendingApproval` 而不是被拒。
- 原有的 409 死锁修复不得回归：活跃 / 疑似离线的旧身份仍然一律 409。

### 影响面

`RegistrationDtos`、`AgentRegistrationService`、`AgentStateStore`、Agent 注册提交路径、审批界面的一处文案。不改证书体系、不改 mTLS、不改心跳。

# 批次 B：目录识别探测

<a id="b1"></a>
## B1 · 轮转式备份目录被判成 N 个业务单元

**级别**：P0　**工作量**：1 人日

### 现象

`周一\ 周二\ … 周日\`、`Day1\ … Day7\`、`A\ B\ C\` 这类**固定槽位轮转覆盖**的备份目录（中小机房的备份脚本极常见），向导会判成「N 个业务单元，每个子目录自成一份备份」，置信度 70。

### 证据

[`StructureInference.cs:201-219`](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:201) 情形三。走到这里的完整路径（以 7 个星期目录为例）：

1. `LooksLikeYear("周一")` → false，`yearRatio = 0`，跳过情形零；
2. `LooksLikeDate("周一")` → 数字位数 0 < 6 → false，`dateRatio = 0`，跳过情形一；
3. `ResolveUnits` 用 `date_leaf` 下探：每个槽位下面没有子目录 → 各自成为深度 1 的单元；`IsDateLayer([])` → false，`unitDateRatio = 0`，跳过情形二；
4. 情形三：7 个目录里都直接有文件，`unitFileRatio = 1.0 ≥ 0.6` → `subdirectory_units` + `businessUnitDepth: 1`。

### 根因

轮转的语义是**覆盖**：7 个槽位是同一份备份的 7 个历史副本，任一时刻只有一个是「当前的那份备份」。把它们登记成 7 个并列的业务单元，会带来三个后果：

1. **单元数与 `external_key` 全错**。`周一`…`周日` 成了业务单元名，而真实业务单元只有一个。
2. **存储与带宽 ×7**。7 个副本各自成为独立的候选备份集并各自上传，而它们本来是同一份东西的历史版本。
3. **槽位级故障没有任何判据**。这一条最要命，且要说准确：
   - **备份完全停跑**仍然会被发现——所有槽位都不再刷新，任务层面没有新候选，`MissedBackupWorker` 会判「到点没有备份」。
   - 但**周期性偏科失败**（例如每周三那次一直失败，其余六天正常）完全看不见：`MissedBackupWorker` 是**按任务**判的（[`MissedBackupWorker.cs:116`](src/src/BackupMonitor.Infrastructure/Services/MissedBackupWorker.cs:116)），只要 7 个槽位里有任何一个是新的就不会告警；而 `周三` 这个「单元」自己的预检永远是 `passed`——文件在、必需文件齐、早已过稳定窗口。于是「每周三的备份一直没成功」这件事，系统里没有任何一处会说出来。

### 方案

**不新增识别器类型。** 轮转的结构语义与现有的 `latest_directory` 完全一致——「源目录下若干子目录，每次只认最新的那个」——而 Agent 侧的 `latest_directory` 恰好是按「目录内最新文件的 mtime」选目录，不是按名字排序（[`BackupScanner.cs:259-271`](src/agent/BackupMonitor.Agent/BackupScanner.cs:259)），对 `周一`…`周日` 这种名字无序的槽位天然正确。

所以这是一条**纯推断端**的改动：Agent 一行不用改，配置 schema 不用动，`RecognizerRules.KnownKeys` 不用加键。

**1. 新增判定分支 `DetectRotatingSlots`**，插在情形二之后、情形三之前（比情形三更具体，先判不会抢走原有分支；不成立返回 null 原样落回，evidence 自己攒、成了才交出去——与 `InferNumericLayers` 同一套写法）。

两道判据必须**同时**成立：

- **名字判据**：子目录名整体落在一个固定小词表里。判的是「整组名字属于同一个词表且互不重复」，不是「某个名字像星期几」——单个名字撞上没有意义。

  **词表就这四类，不要再扩**：

  | 类别 | 取值 |
  |---|---|
  | 星期中文 | `周一…周日`（含 `周天`）、`星期一…星期日`（含 `星期天`） |
  | 星期英文 | `Mon…Sun`、`Monday…Sunday`（大小写不敏感） |
  | `DayN` | `Day1…Day7`、`Day01…Day07`、`D1…D7` |
  | 纯序号 | `1…7` / `01…07`，且**个数 ≥ 3、最大值 ≤ 31** |

  前三类词表封闭、语义唯一，名字本身就能自证。纯序号那一类靠额外两个约束收窄：不加最大值上限的话，`1…18` 这种账套编号会撞进来（时间判据也能挡，但在名字这一层先收一道更稳）。

  **明确不收 `A B C`、`奇/偶`、`一 二 三`**：`A/B/C` 与真实业务分组（车间 A/B/C、区域 A/B）无法区分，误判代价高于收益。真遇到了，走 B1 已经给的逃生门——人手动选 `latest_directory` 模板即可，一次配置的事。
- **时间判据**：各槽位「最新文件 mtime」明显**错开**，而不是聚集。这是区分轮转与真实业务单元的**主判据**：N 个账套是同一批跑的，最新时间聚集在同一天；N 个轮转槽位的最新时间大致等间隔铺开 N 个周期。

  具体取法：算各槽位最新 mtime 的两两间隔中位数 `m`，要求 `max - min ≥ (N-1) × m × 0.5`。任一槽位取不到 mtime 就整体不成立。

  只用名字判据是不够的：一个恰好按星期分的**业务**目录会被错认。宁可认不出来交给人选。

**2. 产出**

```json
{ "recognizerType": "latest_directory", "recognizerConfig": { } }
```

必需文件沿用 `InferRequiredFiles(槽位列表)`——各槽位内容同构，这一步本来就适用。

**3. 摘要与 Evidence 必须把「为什么不是 7 个单元」说出来**

摘要（人要能判断对错，所以要说人话）：

> `D:\备份\` 下的 7 个目录（周一、周二、周三 … 共 7 个）是同一份备份的轮换副本，不是 7 个不同的业务：它们的最新文件时间依次错开约 1 天，说明每天覆盖其中一个。每次只认最新的那个（当前是 周四）。

Evidence 至少三条：槽位名命中的词表、各槽位最新时间的实际分布、以及「如果这其实是 7 个不同的业务，请改选『子目录单元』模板」这一句逃生门提示——自适应判定没有逃生门就是死局。

置信度：两道判据都过且时间错开得干净给 78；名字命中但时间分布勉强过线给 62（低于 70，会连带把 `NeedsDeeperScan` 打开）。

### 验收标准

- `RecognizerWizardTests` 新增：
  - 7 个星期目录、mtime 依次相差 1 天 → `latest_directory`，摘要含「轮换副本」，`Units` 预演只有 1 个；
  - 7 个账套目录（`账套001…账套007`）、mtime 全在同一小时内 → 仍走情形三 `subdirectory_units`，**行为不变**（防回归）；
  - 7 个星期目录但 mtime 全部聚集 → 判定不成立，落回情形三；
  - `Day1…Day7`、`Mon…Sun`、`01…07` 三种词表各一例。
- 预演（`SnapshotRecognizer.Preview`）在轮转结构上只产出 1 个单元，且 `SourceRoot` 指向 mtime 最新的那个槽位。

### 影响面

`StructureInference` 新增一个私有分支和一份词表常量。不改 Agent、不改配置 schema、不改 `RecognizerRules`。

## B2 · 快照按字典序深度优先截断，而所有结构判据都是比例

**级别**：P0　**工作量**：1.5 人日

### 现象

目录条目稍多的备份盘，向导给出的结论会**偏**——不是「说自己没看全」（那是有的），而是在自己标了「没看全」之后，仍然用一个有偏样本算出比例并据此下结论、扣 20 分了事。

### 证据

- [`DirectoryBrowser.Enumerate:121-176`](src/agent/BackupMonitor.Agent/DirectoryBrowser.cs:121)：深度优先——对每个子目录立即递归到底，再处理下一个兄弟；目录与文件都按 `StringComparer.OrdinalIgnoreCase` 排序。
- [`DirectoryBrowser.cs:32`](src/agent/BackupMonitor.Agent/DirectoryBrowser.cs:32) + [`RecognizerWizardService.cs:94`](src/src/BackupMonitor.Infrastructure/Services/RecognizerWizardService.cs:94)：**全局** 3000 条预算，先到先得。
- 判据全是比例：`DateLayerThreshold = 0.6`（[:25](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:25)）、`PairedFileThreshold = 0.6`（[:46](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:46)）、`RequiredThreshold = 0.9`（[:22](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:22)），以及 `unitDateRatio`、`unitFileRatio`。

### 根因

18 个账套 × 7 天 × 20 个文件 = 2520 条，已经贴着 3000。一旦触顶，被丢掉的**永远是字典序靠后的那一批**，而不是随机的一批。

这两件事单独看都合理，凑在一起就不成立了：**用字典序截断的样本去算比例**。`HasGaps` 只能表达「不完整」，表达不了「有偏」——`Build` 里那句「以上结论只覆盖看得见的部分」在这里是不够诚实的，因为「看得见的部分」不是这个目录的代表性样本。

举一个会真错的例子：账套目录 `ZT001…ZT018`，其中 `ZT001` 下面挂了个历史归档子目录，条目数吃掉大半预算。剩下的账套只抓到前几个，`unitDateRatio` 用 3–4 个样本算出来，任何一个不规整的都能把比例压到 0.6 以下——本来看得懂的结构变成「没能看懂」。反过来也一样：靠前的几个恰好规整，就以 1.0 的比例给出 92 分的高置信度。

### 方案

**1. 枚举改为逐层广度优先 + 每目录配额**

`DirectoryBrowser.Enumerate` 从递归 DFS 改为按层推进的 BFS：

```
第 1 层全部枚举 → 第 2 层全部枚举 → … 直到 maxDepth 或预算耗尽
```

这样保证**每一层都看得见**，而 `StructureInference` 的每一条判据恰恰都是按层算的（第一层是不是日期层、单元层的比例、叶子层的必需文件）。深度优先则会出现「第 1 层只看见 3 个，第 4 层的细节倒是抓全了」这种对推断毫无用处的分配。

同一层内再加**每目录配额**：单个目录最多贡献 `remaining / 该层目录数` 条，防止一个胖目录吃掉整层。

**2. 文件抽样，但回传真实计数**

叶子目录里的文件只抓前 `N`（建议 40）个，同时在 `BrowseEntryDto` 上补两个字段：

```csharp
/// <summary>该目录下的文件总数（含未返回的部分）。</summary>
public int? FileCount { get; set; }

/// <summary>该目录下文件的总字节数（含未返回的部分）。</summary>
public long? TotalFileBytes { get; set; }
```

推断端需要的是**每个叶子的文件名模式分布与个数**，不是每个文件的名字。`InferRequiredFiles` 的第二档判据「各单元里的个数是否一致」（[`StructureInference.cs:750`](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:750) 附近的 `CountMin/CountMax`）现在只能数抓回来的那些；有了 `FileCount` 才能在抽样情况下仍然判得准。

抽样要取**该目录内 mtime 最新的 N 个**而不是字典序前 N 个——识别关心的是最近一份备份长什么样。

**3. 有偏与不完整分开表达**

`SnapshotNode` 增加 `Sampled`（这一层做过抽样）与现有的 `Truncated` / `DepthLimited` 区分开。`Build` 的置信度调整相应分成两档：

- `DepthLimited`（层数不够）：维持现状扣 20，且 `NeedsDeeperScan` 逻辑不变；
- `Sampled`（做过抽样但每层都有代表性样本）：**不扣分**，但 Evidence 要写明「每个目录只看了最新的 40 个文件，共 N 个」。

抽样后的样本是有代表性的，再按「不完整」扣分等于惩罚一个已经修好的问题。

**4. 预算可以适度提高**

`RecognizerWizardService.cs:94` 的 3000 是 D-06 从 20000 收下来的，理由是快照原样进 `commands.result_payload`、一条约 250 字节。做完抽样后同样的 3000 条能覆盖大得多的结构，**这一条先不动**；等 B7 落地、真实数据出来再评估。

### 验收标准

- 构造一个「第一个子目录含 2500 个文件 + 后续 17 个账套各 20 个文件」的快照，改动前后对比：
  - 改动前：`units` 只解析出个位数，`unitDateRatio` 用残缺样本算；
  - 改动后：18 个账套全部出现在 `units` 里，`ZT001` 标 `Sampled`，`FileCount = 2500`。
- `InferRequiredFiles` 在抽样目录上给出的 `CountPerUnitMin/Max` 与不抽样时一致（用 `FileCount` 而非样本条数）。
- `DirectoryBrowser` 的现有边界不得放宽：仍然只返回元数据、仍然有条目/深度/耗时三重上限、拒绝访问仍然如实标记。
- 现有 `RecognizerWizardTests` 全绿（未触顶的小快照行为完全不变）。

### 影响面

`DirectoryBrowser`、`BrowseDtos`、`SnapshotTree`、`StructureInference.Build` 的置信度分档。Agent 与服务端要同批发布（`BrowseEntryDto` 加字段，旧 Agent 不填 → 服务端按 null 走现有路径，兼容）。

## B3 · 向导不给尺寸基线，既有的 `size_abnormal` 判据形同虚设

**级别**：P1　**工作量**：0.5 人日

### 现象

「备份文件突然变成 0 字节」是备份故障里最经典的一种，系统里判据齐全，但现场基本不会生效——因为要人凭空想一个字节数填进去。

### 证据

判据**是存在的**，这一点先说清楚，免得重复造：

- [`AgentPrecheckService.cs:335-345`](src/src/BackupMonitor.Infrastructure/Services/AgentPrecheckService.cs:335) `ValidateSizeThresholds`：比 `MinTotalBytes` / `MaxTotalBytes` / `MinFileCount`，不过就落 `PrecheckStatus.SizeAbnormal`；
- 告警链路完整：[`AgentPrecheckService.cs:247-280`](src/src/BackupMonitor.Infrastructure/Services/AgentPrecheckService.cs:247) 有 raise / recover；
- 界面文案齐全：`ui.js:28`、`tasks.js:555`。

缺的只有一环：**向导不给建议值**。`RecognizerProposalDto`（[`RecognizerWizardDtos.cs`](src/src/BackupMonitor.Shared/Models/Admin/RecognizerWizardDtos.cs)）里没有这三个字段，向导落地成任务时它们是空的，而空值在 `ValidateSizeThresholds` 里等于不检查（`is > 0` 才比）。

推断阶段其实**已经算出了数据**：`RequiredFileCandidateDto.TypicalSizeBytes` 在四处都填了（[:526](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:526)、[:644](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:644)、[:734](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:734)、[:758](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:758)），只是拿去显示，没落盘。

### 方案

**1. `RecognizerProposalDto` 增加三个建议值**

```csharp
/// <summary>建议的备份总大小下限。取观察到的最小一份的一半，向下取整到 MB。</summary>
public long? SuggestedMinTotalBytes { get; set; }

/// <summary>建议的文件数下限。取推荐必需文件的条数。</summary>
public int? SuggestedMinFileCount { get; set; }

/// <summary>上面两个数是怎么来的，一句人话。界面要显示出来。</summary>
public string? SizeBaselineNote { get; set; }
```

**只给下限，不给上限。** 备份变大通常是业务正常增长，给上限会制造周期性假警报；备份变小才是故障信号。这与「不对文件个数变化做自动判定」是同一条取舍原则。

**2. 取值口径**

- `SuggestedMinTotalBytes` = 各叶子/各组的总字节数里的**最小值 × 0.5**，向下取整到 MB，并且不低于 1 MB。取一半是留出业务波动的余量——这个数要的是「掉了一个数量级」的检出力，不是精确基线。
- 单元/组数 < 3 时**不给**建议值（样本太少，给了就是瞎猜），`SizeBaselineNote` 写明原因。
- **离散度闸门：`最大值 / 最小值 > 20` 时同样不给建议值。** 这一条必须有，因为 `MinTotalBytes` 是**任务级**的单一阈值，而 `ValidateSizeThresholds` 拿它去比**每一个业务单元**的 `TotalBytes`（[`AgentPrecheckService.cs:337`](src/src/BackupMonitor.Infrastructure/Services/AgentPrecheckService.cs:337)）。18 个账套里最小的 5 MB、最大的 1.5 GB 时，任何一个统一下限要么对大账套毫无检出力，要么对小账套天天假警报。此时 `SizeBaselineNote` 直白说明：

  > 这 18 个业务单元的大小相差 300 倍（最小 5 MB，最大 1.5 GB），一个统一的下限对它们没有意义。这一项留空，需要的话请对单个任务单独设置。

  宁可不给，也不要给一个假装有用的数——与本方案「宁可认不出来交给人选」是同一条原则。
- `SuggestedMinFileCount` = `AddRequired` 实际写进 `requiredFiles` 的条数。

**3. 界面**

向导确认页把这两个数显示成**可改的输入框**，默认填入，旁边一句 `SizeBaselineNote`：

> 观察到的 18 份备份里最小的一份是 1.4 GB，建议下限设为 700 MB。低于这个值会判「备份大小不对」并告警。

不能默默带过去——这是个会产生告警的阈值，人必须看见并能改。

### 验收标准

- 单测：18 个单元、最小一份 1.4 GB → `SuggestedMinTotalBytes` 为 700 MB 附近且向下取整到 MB；
- 单元数 = 2 → 两个建议值都是 null，`SizeBaselineNote` 说明「样本不足，未给建议」；
- 端到端：向导建出的任务，`min_total_bytes` 在库里非空；把源目录里最大的文件截成 0 字节后重跑预检，落 `size_abnormal` 并出告警。

### 影响面

`RecognizerWizardDtos`、`StructureInference.Build`、`recognizer-wizard.js` 确认页、向导落地成任务的那段映射。不改 `AgentPrecheckService`、不改库表。

## B4 · 日期 token 已提取，却不推备份周期与历史缺口

**级别**：P1　**工作量**：1 人日

### 现象

向导已经把日期目录名和文件名里的日期都解析出来了，但只用来分组和挑「最新的那个」。两个现成的结论没有产出：

1. **备份周期**（日备 / 周备 / 月备）——这个数正是任务需要的，现在要人另填；
2. **历史缺口**——「过去 30 天里有 3 天没有备份」，这是在配置阶段就能交付的、直接关于「数据会不会丢」的事实。

### 证据

- [`FileNamePattern.ExtractDateToken`](src/src/BackupMonitor.Shared/Recognition/FileNamePattern.cs)：已能从文件名取出 `2026_08_22` / `20260822`；
- `StructureInference` 情形一、情形二把日期目录名收集齐了，但只做了 `OrderByDescending(...).First()` 取最新；
- `DetectDatedFileSets` 已按日期分了组（`groups`），间隔一次也没算过。

### 方案

**1. 新增 `Shared.Recognition.DateSequence`**

放在 Shared 而不是 Infrastructure：与 `DateName` 下沉同一个理由——这套语义将来 Agent 侧也可能要用（例如判断「这次的日期目录是不是接着上一个」）。

```csharp
/// <summary>一组日期名的时间规律：周期，以及缺了哪几个。</summary>
public sealed record DateSequenceInfo(
    TimeSpan MedianInterval,
    string PeriodLabel,     // "每天" / "每周" / "每月" / "不规律"
    int ExpectedCount,
    IReadOnlyList<DateTime> MissingDates,
    DateTime Earliest,
    DateTime Latest);

public static DateSequenceInfo? Analyze(IEnumerable<string> dateNames);
```

- 解析：复用 `DateName` 的判定尺度，把名字解析成 `DateTime`（解析不出的整条跳过，不猜）；
- 周期：取相邻间隔的**中位数**（不是平均——一个大缺口会把平均值拉飞）。中位数落在 1 天 ±25% → `每天`；7 天 ±25% → `每周`；28–31 天 → `每月`；其余 → `不规律`，并且此时**不算缺口**（周期都说不准，缺口无从谈起）；
- 缺口：按中位间隔在 `[Earliest, Latest]` 上铺网格，找出没有对应日期的格子。只在样本 ≥ 5 且周期不是「不规律」时才产出。

**2. 接进 `RecognizerProposalDto`**

```csharp
public string? DetectedPeriod { get; set; }          // "每天"
public List<string> MissingBackupDates { get; set; } = [];
```

**3. 摘要与 Evidence**

情形一、情形二、`DetectDatedFileSets` 三处的摘要各追加一句：

> 这 21 个日期目录跨了 21 天，是每天一备。

有缺口时，Evidence 里单列一条，措辞要直白：

> 按每天一备推算，2026-08-13、2026-08-19、2026-08-24 这 3 天没有对应的备份目录。

**4. 明确不做的事**

- **不因为有缺口就降低置信度**。缺口是被识别对象的性质，不是识别质量的问题——把两者混在一起，会让「这个目录有历史缺备」表现成「向导看不懂这个目录」。
- **不在配置阶段发告警**。这里只陈述事实给人看。告警归 `MissedBackupWorker`。
- **不自动把 `DetectedPeriod` 写成备份计划**。计划牵涉调度时间窗，向导只能建议，由人在建计划时确认。

### 验收标准

- 单测：21 个连续日期目录 → `每天`，`MissingBackupDates` 为空；
- 抠掉其中 3 个 → 周期仍判 `每天`（中位数不受影响），缺口精确列出这 3 天；
- 只有 4 个日期 → `MissingBackupDates` 为空（样本不足不产出）；
- 间隔杂乱（1、5、2、9 天）→ `不规律`，不产出缺口；
- 置信度在有缺口与无缺口两种输入上**完全相同**（防回归）。

### 影响面

新增 `DateSequence`，`StructureInference` 三处摘要，`RecognizerProposalDto` 两个字段，向导确认页一处展示。

## B5 · 日期形态漏掉中文年月与周序号

**级别**：P1　**工作量**：0.5 人日

### 现象

`2026年08月\`、`08月25日\`、`2026W35\` 这类目录名认不出来，于是本可以走情形零/情形一的结构落到「没能看懂」（置信度 25）。中文年月在国产 ERP 和手写批处理里很常见。

### 证据

[`DateName.cs`](src/src/BackupMonitor.Shared/Recognition/DateName.cs)：

- `LooksLikeDate("2026年08月")`：抽出数字 `202608`，长度 6 → 走 6/7 位分支，按 `YYMMDD` 解析成年 `20`、月 `26`（>12）→ false；
- `LooksLikeYear("2026年")`：要求 `IsAllAsciiDigits` → false；
- `LooksLikeMonthOrDay("08月")`：同上 → false。

### 根因

`LooksLikeDate` 的判据是「抽掉非数字后能不能读成一个合理日期」，`2026年08月` 恰好落进 `YYMMDD` 的解析口径被误读。而 `LooksLikeYear` / `LooksLikeMonthOrDay` 要求整名全是 ASCII 数字——这个约束当初是**刻意**的（注释里写着「`2026年`、`08月` 一律认不出来，宁可交给人选」），现在要放开的正是它。

放开的前提是不能引入更糟的误判。`ZT001`、`账套001` 这类必须继续认不出来——它们没有年月日的中文量词，靠量词就能区分，不需要动 6 位数字下限。

### 方案

**1. 中文年月日：先剥量词，再走既有判据**

在 `DateName` 加一个私有归一化：把 `年` `月` `日` 分别替换成 `-` `-` 和空，再交给现有的 `LooksLikeDate` / `LooksLikeYear` / `LooksLikeMonthOrDay`。

- `2026年` → `2026-` → 去尾 → `2026` → `LooksLikeYear` 成立；
- `08月` → `08` → `LooksLikeMonthOrDay` 成立；
- `2026年08月` → `2026-08` → 数字 `202608`，仍是 6 位。**这一条要单独处理**：新增一个「年月」形态判定 `LooksLikeYearMonth`（4 位年 + 1–2 位月，年在 1990–2100、月在 1–12），供情形零的月份层使用；
- `2026年08月25日` → `2026-08-25` → `LooksLikeDate` 成立。

必须同时验证反例仍然不成立：`账套001`（无量词、3 位数字）、`第01车间`、`ZT001`。

**2. 周序号**

新增 `LooksLikeWeek`：匹配 `^(19|20)\d{2}[-_]?[Ww](\d{1,2})$` 且周数在 1–53，或独立的 `^[Ww](\d{1,2})$`。接进 `LooksLikeDate` 的调用点（作为「像日期」的一种），并在 B4 的 `DateSequence.Analyze` 里把它解析成该周的周一。

**3. 边界不放宽的部分**

- 全角数字（`０８`）继续不认——现有注释的理由成立（几乎一定不是备份程序建的）；
- `name.Count(char.IsLetter) > 8` 这条上限保留，但中文量词在剥离之后才计数，否则 `2026年08月25日` 会因为 3 个中文字符更接近上限。

### 验收标准

- `DateNameTests` 新增正例：`2026年`、`08月`、`2026年08月`、`2026年08月25日`、`8月25日`、`2026W35`、`W35`；
- 反例必须全部保持 false：`ZT001`、`账套001`、`第01车间`、`０８`、`2026年13月`、`2026W54`；

## B6 · 分卷归档用「个数一致」这把错尺子

**级别**：P2　**工作量**：0.75 人日

### 现象

`db.7z.001 / .002 / .003…`、`db.z01 / .z02 / db.zip` 这类分卷归档，缺任何一卷整份都无法恢复，但系统不会告警。

### 证据

[`StructureInference.cs:750-767`](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:750) 第二档判据：模式要被推荐为必需，必须 `CountMin == CountMax`（各单元里个数一致）。

这条判据本身是对的，且来源明确——U8 的 `UFFile` 附件库按年度分，各账套启用年度不同，个数波动是正常形态，拿它当判据只会制造假警报。

但对分卷归档，这把尺子用反了：分卷数**天然随数据量浮动**，于是 `db_*.7z` 永远 `CountMin != CountMax` → 永远不推荐 → 缺卷不进 `requiredFiles` → 不告警。

顺带一个相关的边界问题：`Extension()`（[`StructureInference.cs:973`](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:973) 附近）只取最后一个点，`backup.tar.gz` → `.gz`、`db.sql.gz` → `.gz`，而 `BaseName` 给出 `backup.tar`，成对检测与扩展名分组都会串。

### 方案

**1. 分卷形态识别**

在 `FileNamePattern` 加：

```csharp
/// <summary>分卷归档的一卷：主干名 + 卷号。不是分卷则返回 null。</summary>
public static (string Stem, int Index)? ParseVolume(string fileName);
```

覆盖三种主流形态：`.7z.001` / `.z01`（配 `.zip` 末卷）/ `.part1.rar`。

**2. 换一把尺子：连续性，而不是个数稳定性**

`InferRequiredFiles` 第二档在判定 `stable` 之前先问一句「这个模式是不是分卷」。是分卷时：

- **判据换成卷号从 1 连续到 max**，中间不缺号；
- `Recommended = 出现在 ≥90% 单元 && 各单元内部卷号连续`；
- `requiredFiles` 里写主干模式（`db_*.7z.*`），**不写死卷数**；
- `NotRecommendedReason` 在不连续时说清楚：「`ZT003` 缺第 2 卷（有 001、003、004）」。

**3. 扫描端的连续性检查**

`RecognizerRules` 增加一个键 `volumeContinuity`（布尔），加进 `KnownKeys`（[`RecognizerRules.cs:58`](src/src/BackupMonitor.Shared/Recognition/RecognizerRules.cs:58)）。为真时，`HasMissingRequired` 之外再做一次卷号连续性检查，缺号按 `required_file_missing` 处理并在 `FailureMessage` 里点名缺第几卷。

这一条**必须同时改两侧**：`RecognizerRules`（Shared，两侧共用判定）、`BackupScanner.cs:143` 与 `SnapshotRecognizer.cs:98` 两个调用点。共用实现，不各写一份。

**4. 双扩展名**

`Extension()` 与 `BaseName()` 对一份复合扩展名白名单（`.tar.gz` / `.tar.bz2` / `.tar.xz` / `.sql.gz`）整体识别。这个改动会影响成对检测与扩展名分组，**必须**跑一遍现有 `RecognizerWizardTests` 确认致远 OA 那组（`.zip` + `.properties`）行为不变——那是 R1 的教训所在。

### 验收标准

- 单测：`db.7z.001/.002/.003` 三卷齐全 → 推荐为必需；抠掉 `.002` → 不推荐，理由点名缺第 2 卷；
- 各单元卷数不同（3 卷 / 5 卷）但各自连续 → **仍然推荐**（这正是与个数稳定性判据的区别）；
- U8 `UFFile_001_2022.dat` 那组行为完全不变（不是分卷，仍走个数一致判据，不推荐但照常上传）；
- `backup.tar.gz` 的 `Extension()` 返回 `.tar.gz`、`BaseName()` 返回 `backup`；
- 致远 OA 结构（`.zip` + `.properties` 成对）的既有断言全绿。

### 影响面

`FileNamePattern`、`RecognizerRules`（新增一个键）、`StructureInference` 第二档、`BackupScanner` 与 `SnapshotRecognizer` 两个判定点。Agent 与服务端同批发布。

## B7 · 没有主动探测入口

**级别**：P2　**工作量**：2 人日

### 现象

「这台机器上还有没有别的备份没被监控起来」——这个问题现在无法回答。向导的起点是盘符列表（[`DirectoryBrowser.BrowseDrives:66`](src/agent/BackupMonitor.Agent/DirectoryBrowser.cs:66)），之后只能人工一层层点进去找。

### 根因

不是缺陷，是能力缺失。现有的 `browse_path` 是**定向**的：给一个路径，返回那个路径下的树。没有「给一台机器，返回像备份目录的地方」这种形态。

### 方案

新增一个指令类型 `probe_backup_dirs`，与 `browse_path` 并列。

**1. 三条边界与 `browse_path` 完全一致，不得放宽**

- 只返回元数据，且比 `browse_path` 更严：**只返回候选目录本身的统计特征，不返回任何文件名**；
- 条目数 / 深度 / 耗时三重硬上限，触顶如实标记；
- 拒绝访问要说出来，不能表现成「这里没有备份」。

**2. 候选评分**

**深度不是靠一个固定值控制的，靠「预算 + 命中即止」**。默认深度 4，外加两条早停：

- **命中即止**：某个目录的分数过线、被收进候选后，**不再下探它的子树**。备份目录里面再套备份目录的情况极少，而它的子树恰恰是日期目录——条目数最多的那一层。少了这一条，深度 4 的枚举量会集中消耗在已经不需要再看的地方。
- **时间闸**：单个盘符 10 秒、全机 30 秒。超时就把**已经算出来的候选原样返回**并标记「未扫完」，而不是整个失败。

这样取 4 的实际枚举量小于无脑深度 3，同时能看到「盘符 → 应用目录 → 备份目录 → 日期目录」这条最常见的四层路径。深度本身不是成本，条目数才是，而备份盘上的条目数集中在最深的一两层。

从盘符根往下扫，对每个目录算一个分数，只回传 Top 20：

| 信号 | 权重 | 取法 |
|---|---|---|
| 目录名关键词 | 高 | `备份` `backup` `bak` `dump` `自动备份` `db_backup` 等 |
| 备份类扩展名密度 | 高 | 直接子文件里 `.bak/.trn/.dmp/.dbf/.sql/.gz/.zip/.7z/.dat` 的占比 |
| 下层是日期层 | 高 | 复用 `DateName.IsDateLayer` |
| 近期活跃 | 中 | 最新文件 mtime 在 7 天内 |
| 体积集中 | 中 | 该目录（含子树）占所在盘已用空间的比例 |
| 系统/程序目录 | **否决** | `Windows`、`Program Files`、`ProgramData`、`$Recycle.Bin`、`System Volume Information`、Agent 自己的数据目录 |

回传字段：路径、分数、命中的信号（人要看得懂为什么它被列出来）、文件数、总字节、最新 mtime、是否已被现有任务覆盖。

**最后一项在服务端算**：拿候选路径与该客户端已有任务的 `SourcePath` 比对，标成「已监控 / 未监控」。这才是这个功能真正的产出——**未监控的那几行**。

**3. 界面**

「探测备份目录」按钮放在客户端详情页和向导第一步。结果是一张按分数排序的表，每行一个「用这个目录建任务」按钮，点了直接带着路径进现有的推断流程（B1–B6 的成果全部复用）。

**4. 审计**

与 `client.browse_path` 同等留痕（`client.probe_backup_dirs`）。理由与 [`RecognizerWizardService.cs:103`](src/src/BackupMonitor.Infrastructure/Services/RecognizerWizardService.cs:103) 那条注释一致：这是一个「从管理界面枚举客户端文件系统」的能力，留痕是它可被接受的前提。

### 验收标准

- 在一台造好的测试机上（`D:\自动备份\`、`E:\数据库备份\`、`C:\Windows\` 各若干文件）跑一次探测：两个真备份目录进 Top 5，`C:\Windows` 及子目录一个都不出现；
- 返回体积必须显著小于同深度的 `browse_path` 快照（只有候选目录的统计，没有文件明细）；
- 触顶（条目/耗时）时如实标记，且已经算出的候选照常返回，不是整个失败；
- 拒绝访问的目录在结果里可见，标成「没有读取权限」而不是被静默跳过；
- 已被任务覆盖的目录正确标记。

### 影响面

新增指令类型（Agent 侧探测实现 + 服务端下发/取结果 + 一个新界面）。不改识别推断，不改任何既有指令。

## B8 · 应用先验不反哺判据；junction 未识别

**级别**：P2　**工作量**：0.5 人日

### B8.1 `GuessApplication` 只用来填名字

[`StructureInference.cs:898`](src/src/BackupMonitor.Infrastructure/Recognition/StructureInference.cs:898) 已经能从文件特征认出用友 U8 / SQL Server / Oracle / MySQL，但结果只写进 `SuggestedApplicationName`——填个名字而已，不参与任何判据。

**方案**：认出应用后，用该应用的已知形态**提升置信度并补必需文件**，但只在通用判据已经成立时叠加，不能靠先验单独下结论（否则一个恰好有 `.bak` 的目录会被强行套上 SQL Server 的结构假设）：

- 认出 **用友 U8** 且已判为 `subdirectory_units`：置信度 +8；`UFDATA.BAK` 若出现在 ≥90% 单元里而未被推荐，补进候选并说明理由。`UFFile_*.dat` 维持现状——个数随启用年度不同，不作判据（这一条已经是对的，不要改）。
- 认出 **SQL Server** 且同时存在 `.bak` 与 `.trn`：Evidence 补一句「有完整备份（.bak）和日志备份（.trn）两类」，提示人确认任务是否应该只认 `.bak`。
- 置信度加成**上限 +8**，且不得把一个低于 70 的结论顶到 70 以上——那会把 `NeedsDeeperScan` 关掉，等于用猜测取消了本该做的补抓。

### B8.2 junction / 符号链接未识别

[`DirectoryBrowser.BuildDirectoryEntry:178`](src/agent/BackupMonitor.Agent/DirectoryBrowser.cs:178) 读了 `Attributes` 但只用来判 `IsHidden`，没有检查 `FileAttributes.ReparsePoint`。备份盘上做 junction 指向另一个卷很常见，后果是同一批文件被重复计入统计、白白吃掉 B2 的条目预算。

因为有 `maxDepth` 兜底，不会无限递归，所以这是效率与统计准确性问题，不是崩溃问题。

**方案**：`BrowseEntryDto` 增加 `IsReparsePoint`；枚举时**不下探** reparse point，但照常列出该条目并标记。界面显示成「链接目录（未展开）」——不能静默跳过，那会让「这里有东西」表现成「这里是空的」。

### 验收标准

- U8 结构：置信度提升不超过 8 且不跨越 70 这条线；`UFFile_*.dat` 仍不被推荐为必需（防回归）；
- 造一个 junction 指向另一个目录：出现在结果里、标 `IsReparsePoint`、`Children` 为空、不消耗子树的条目预算。

### 影响面

`StructureInference.Build` 一处加成、`DirectoryBrowser`、`BrowseDtos`、前端一个图标。

# 批次 D：手动「立即备份」的可用性与并发

这一批与批次 B 无关，来源是使用中反馈的三件事：按钮可以重复点、等待时间长、点十个就十个一起传。三条串在同一条链路上（点击 → 预检指令 → 扫描 → 候选 → 上传指令 → 上传会话），因此放在一起改。

<a id="d1"></a>
## D1 · 「立即备份」可重复点击，服务端也不去重

**级别**：P1　**工作量**：0.5 人日

### 现象

点「立即备份」后弹出等待窗口，扫描要跑几分钟，这期间按钮仍然可用。点空白处把窗口关掉（很容易误触），列表里的按钮立刻又能点——于是同一个任务被下发了两条、三条预检指令。

### 证据

三处叠加，缺一条都不至于这么容易重复：

- [`app.js:218-220`](src/src/BackupMonitor.Api/wwwroot/js/app.js:218)：`case 'act'` 直接 `Promise.resolve(App.act(...))`，**不禁用按钮、不记在途状态**。所有 `data-ui-action="act"` 的按钮都是这样。
- [`tasks.js:490`](src/src/BackupMonitor.Api/wwwroot/js/views/tasks.js:490)：`openModal` 没传 `persistent`，而 [`ui.js:466`](src/src/BackupMonitor.Api/wwwroot/js/ui.js:466) 对非 persistent 的窗口是**点遮罩即关**。等待几分钟的窗口恰恰是最容易误触遮罩的那种。
- [`BackupTaskService.cs:518`](src/src/BackupMonitor.Infrastructure/Services/BackupTaskService.cs:518)：

  ```csharp
  idempotencyKey: $"manual-precheck:{task.Id}:{DateTimeOffset.UtcNow.ToUnixTimeSeconds()}"
  ```

  幂等键里带**当前秒**，只能挡住同一秒内的重复提交。3 秒后再点就是一条全新指令。

对照组就在同一个文件里：`TestRecognitionAsync`（[`BackupTaskService.cs:588`](src/src/BackupMonitor.Infrastructure/Services/BackupTaskService.cs:588) 附近）用的是稳定键 `test-recognition:{taskId}`，上一条还在跑就原样还回去并带 `already_running`。那段注释写得很清楚：「原先每点一次就多一条，全都排在那条没跑完的后面，越点越慢」——立即备份现在正处在被修好之前的那个状态。

### 方案

**1. 前端：`act` 分发加在途去重（全局修复）**

在 `app.js` 的 `case 'act'` 里按 `view + action + id` 记一个在途集合：

- 已在途 → 直接忽略这次点击，不发请求；
- 否则置位、给按钮加 `disabled` 与 `aria-busy="true"`，Promise settle（成功或失败都算）后复位。

这是分发层的改动，所有走 `act` 的按钮一起受益，不是给立即备份单独打补丁。

**2. 后端：幂等键改成稳定值**

```csharp
idempotencyKey: $"manual-precheck:{task.Id}"
```

语义与识别测试对齐，直接复用 `TestRecognitionAsync` 已经验证过的那套写法：

- 上一条处于 `pending` / `running` → 原样返回它，响应带 `status: "already_running"`；
- 上一条已终结（`succeeded` / `failed` / `cancelled` / `expired`）→ 复位重下。

**必须允许终结后重下**。只认「这个键存在就拒绝」会让任务在第一次备份之后永远点不动。

**3. 前端如实说明**

拿到 `already_running` 时文案写「这个任务已经有一次备份在进行，正在等它的结果…」，并接着轮询那条已有指令——而不是装作新发起了一次。人误以为自己刚点的没生效，就会去点第三次。

**4. 等待窗口改成 `persistent`**

扫描要跑几分钟，误触遮罩关掉的代价是「以为没发起，再点一次」。关闭仍有两条明路（「关闭」按钮、Esc），与 `ui.js:463` 那条既有理由完全一致。

### 验收标准

- 连续快速点击「立即备份」10 次：只产生 1 条预检指令（`commands` 表按任务过滤计数）；
- 第一条跑完之后再点：能正常发起第二次；
- 点遮罩不再关闭等待窗口，「关闭」按钮与 Esc 仍然可用；
- 回归：其他 `act` 按钮（暂停/恢复/删除等）在途期间禁用，完成后恢复，不出现按钮卡在禁用态。

### 影响面

`app.js` 分发层、`BackupTaskService.DispatchPrecheckAsync` 一行、`tasks.js` 两处文案与 `persistent`。不改指令模型。

<a id="d2"></a>
## D2 · 一次「立即备份」要把整份备份重读一遍算 SHA-256

**级别**：**P0**　**工作量**：1.5 人日

### 现象

点「立即备份」到「传输中」里出现这一条，中间要等很久——即使这份备份和上一次**完全相同**（最常见的情况：今天已经备过了，人只是想确认一下）。

### 证据

- [`BackupScanner.cs:134-135`](src/agent/BackupMonitor.Agent/BackupScanner.cs:134)：对每个文件**无条件**算两个哈希

  ```csharp
  Sha256    = testOnly ? null : await ComputeSha256Async(file.FullName, ct),
  QuickHash = testOnly ? null : await ComputeQuickHashAsync(file.FullName, ct),
  ```

- [`BackupScanner.cs:426`](src/agent/BackupMonitor.Agent/BackupScanner.cs:426) `ComputeSha256Async`：**整个文件读一遍**；
- [`BackupScanner.cs:433`](src/agent/BackupMonitor.Agent/BackupScanner.cs:433) `ComputeQuickHashAsync`：只读**头尾各 64 KB**；
- [`BackupScanner.cs:161`](src/agent/BackupMonitor.Agent/BackupScanner.cs:161)：`candidateKey = {taskId}:{unit}:{manifestHash}`，而 `manifestHash` 由全量 SHA-256 拼出；
- [`AgentPrecheckService.cs:118`](src/src/BackupMonitor.Infrastructure/Services/AgentPrecheckService.cs:118)：**服务端**才按 `CandidateKey` 发现「这份和上次是同一个」。

链条因此是：Agent 把 1.5 GB 整读一遍算完 SHA-256 → 上报 → 服务端一比 `CandidateKey`，发现和上次一样。**判断「是不是同一份」所需的信息，在读第一个字节之前就已经够了**（路径 + 大小 + mtime + 头尾采样），全量哈希是为了别的用途（manifest 完整性）才算的。

次要一项：[`AgentOptions.cs:19`](src/agent/BackupMonitor.Agent/AgentOptions.cs:19) `CommandPollIntervalSeconds = 10`。预检指令要等一轮才被领走，预检结果回来、服务端发出上传指令后**又要再等一轮**。这两个 10 秒不是主要矛盾，但在「点完到出现在传输中」这段里是白等的。

### 方案

**1. 两段式扫描：先便宜的，再贵的**

把现在的一次遍历拆成两段：

- **第一段**：只算 `QuickHash`（头尾 128 KB/文件），拼出 `QuickFingerprint`；
- 与该任务/该业务单元**最近一次候选的 `QuickFingerprint`** 比对：
  - 一致 → 直接回报 `no_new_backup`，**不做任何全量读取**；
  - 不一致 → 进第二段，按现在的逻辑算全量 SHA-256、拼 manifest、出 `CandidateKey`。

「上一次的值」由服务端在下发任务配置时带下来（`AgentConfigService` 的任务配置里加一个字段，`CandidateBackupSet.QuickFingerprint` 服务端已经存着）。**不让 Agent 自己另存一份**——两处状态迟早漂移，而漂移的表现是「明明有新备份却说没有」，那是这个系统最不能出的错。

效果：已经备过的任务，「立即备份」从「整份重读」变成「每个文件读 128 KB」；真有新备份时的耗时与今天完全一样（该读的还是要读）。

**2. 跑完一条指令后立即再拉一次，而不是等满 10 秒**

只在刚完成一条指令时多拉一次待办队列，空闲时的轮询频率不变——不增加常态负载，却把 `预检 → 上传` 之间那一跳的等待去掉。

**3. 逃生门：强制完整校验**

指令 payload 支持 `forceFullHash`，界面在「立即备份」旁给一个不显眼的「强制完整校验」勾选。定期做一次完整校验是有意义的，但它应该是人明确要求的动作，不是默认每次都做。

### 风险与取舍（要写进代码注释）

`QuickHash` 是头尾各 64 KB 的采样，**文件中段被改而大小和 mtime 都没变**时它认不出来。接受这个风险的理由：

- 它只用来决定「要不要重算全量哈希」，真正入库 manifest 的仍然是全量 SHA-256；
- `mtime` 与 `size` 一起参与比对，要绕过它得同时保持这两者不变并只改中段——正常的备份程序不会产生这种文件；
- 真要防篡改，`forceFullHash` 是明路。

**不接受的做法**：把 `QuickFingerprint` 直接当成 `CandidateKey`。那会让两份不同的备份撞成同一个候选——`BackupScanner.cs:145` 那条注释已经把这个坑写清楚了，不要走回去。

### 验收标准

- 同一个任务连续两次「立即备份」，第二次：Agent 侧读盘字节数从「备份总大小」降到「文件数 × 128 KB」量级（用 Agent 日志里的耗时与 `no_new_backup` 结论确认），结果仍是 `no_new_backup`；
- 源目录里放进一份新备份后再点：走完整路径，`CandidateKey` 与上次不同，行为与改动前一致；
- 只改动某个文件的中段（保持 size 与 mtime 不变）：判 `no_new_backup`（**这是已知且接受的边界**，写进测试用例以示刻意）；勾选「强制完整校验」后能正确认出变化；
- `预检 → 上传` 之间的等待从「最多 10 秒」降到接近 0；
- 试扫（`testOnly`）路径行为完全不变。

### 影响面

`BackupScanner`（两段式）、`AgentConfigService` 与任务配置 DTO（下发上次指纹）、`AgentWorker` 指令轮询、指令 payload 加 `forceFullHash`、`tasks.js` 一个勾选框。

## D3 · 手动备份不走执行队列，没有任何并发上限

**级别**：**P0**　**工作量**：1.5 人日

### 现象

在任务列表里连点十个任务的「立即备份」，十个会同时开始传，服务端暂存盘的读写扛不住。

### 证据

系统里**有**两套并发闸，手动立即备份两套都不走：

| 场景 | 闸门 | 位置 |
|---|---|---|
| 计划执行 | `ExecutionRun.MaxConcurrent`（默认 1） | [`ExecutionConfigurations.cs:23`](src/src/BackupMonitor.Infrastructure/Data/Configurations/ExecutionConfigurations.cs:23)，由 `SequentialExecutionWorker` 推进 |
| 批量操作 | `MaxConcurrentClients`（默认 2） | [`BatchOperationService.cs:204`](src/src/BackupMonitor.Infrastructure/Services/BatchOperationService.cs:204) |
| **手动立即备份** | **无** | [`DispatchPrecheckAsync:504`](src/src/BackupMonitor.Infrastructure/Services/BackupTaskService.cs:504) 与 [`DispatchUploadAsync:524`](src/src/BackupMonitor.Infrastructure/Services/BackupTaskService.cs:524) 直接 `CreateCommandAsync` |

唯一与上传并发有关的检查是**按客户端**的：

```csharp
// UploadSessionService.cs:150-155
var maxConcurrent = await _settings.GetIntAsync("max_concurrent_uploads", 2, ct);
var activeSessions = await _db.UploadSessions
    .CountAsync(s => s.ClientId == clientId && ActiveStatuses.Contains(s.Status), ct);
```

`s.ClientId == clientId` —— 它管的是「一台客户端最多同时传几个」，管不了「服务端同时被几台客户端传」。十个任务在十台不同客户端上，这个检查一次都不会触发。

**并且这个闸不能简单改成全局**：Agent 对 `UPLOAD_SESSION_CONFLICT` 没有退避重试，409 会让这条上传指令直接判失败。在建会话这一步限流，等于**把限流变成失败**。

### 方案

**1. 闸放在下发侧，不放在建会话侧**

理由如上。服务端决定「什么时候把上传指令发出去」，Agent 拿到指令就一定能建会话。这正是 `SequentialExecutionWorker` 对计划和批量已经在做的事。

**2. 手动「立即备份」接进 `ExecutionRun`**

- **单个任务点一次**：仍然走直接下发，保持即时反馈（重复点击由 D1 挡住）；
- **多选批量「立即备份」**：建一次 `ExecutionRun`（新增 `Kind = Manual`），并发度取系统设置，而不是发 N 条独立指令。

**3. 新增全局上限，覆盖所有来源**

系统设置 `max_concurrent_uploads_total`（默认 **4**），由 `SequentialExecutionWorker` 在放行下一项之前统一检查：全局活动上传会话数已达上限就不放行，等下一轮。

这一条的价值在于它**不只管手动点击**——计划执行、批量操作、自动模式下预检通过后的自动上传，全部受同一个上限约束。只堵手动这一条路，换个入口照样能把盘打满。

**4. `UploadSessionService` 里那条按客户端的检查保留不动**

它是兜底，不是队列。两者职责不同，不要合并。

**5. 界面要能看见排队**

「传输中」页面显示「N 个正在传 / M 个排队中（全局上限 X）」。不显示的话，限流的表现就是「点了没反应」——那比不限流更糟。

### 验收标准

- 10 台不同客户端的任务同时点「立即备份」：任一时刻全局活动上传会话数 ≤ `max_concurrent_uploads_total`，其余处于排队，**最终全部完成且无一失败**；
- 计划执行与手动备份同时进行时，全局上限对两者一并生效（不是各算各的）；
- 把上限设为 1：行为退化成串行，不出现死锁、不出现饿死；
- 上传因为客户端离线等原因终结后，名额能被释放（构造一个僵尸会话，确认 `LifecycleExpiryWorker` 回收后名额恢复）；
- 界面能看到排队数量。

### 影响面

`ExecutionQueueService`（新增 Manual kind）、`SequentialExecutionWorker`（全局闸）、`BackupTaskService` 批量入口、系统设置一项、「传输中」页面。不改上传协议、不改 `UploadSessionService` 的既有检查。

## 取舍与风险，以及明确不做的事

### 风险

- **B1 的轮转判定会误判**：一个恰好按星期分的**业务**目录（例如按值班班次分的），如果各班次的备份时间又恰好错开，会被认成轮转。缓解手段沿用既有那三条：双判据（名字 + 时间分布）同时成立才认、置信度分档、Evidence 把观察到的现象原样列出并给出逃生门提示。**自适应判定没有逃生门就是死局**。
- **B2 改变枚举顺序**，快照的 `Entries` 排列会变。前端如果有任何地方依赖「深度优先的自然嵌套顺序」需要一并确认。
- **B3 的建议下限会产生告警**。取最小一份的一半是刻意保守的；即便如此，第一批任务上线后要观察是否有假警报，必要时把系数从 0.5 调到 0.3。因为默认值可改且界面明示，风险可控。
- **B6 改 `Extension()` 的边界**会波及成对检测与扩展名分组，这正是 R1 那条最危险缺陷的所在区域。这一条的回归测试必须先写、后改。
- **D2 的 QuickFingerprint 门槛会漏掉「中段被改、size 与 mtime 都不变」的文件**。已在 D2 里论证过为什么接受，并要求写成一条刻意的测试用例。真正的兜底是 `forceFullHash`。
- **D3 的全局闸会让备份从「一起跑」变成「排队跑」**，总完成时间变长。这是刻意的取舍：服务端暂存盘被打满时所有上传一起变慢甚至超时，比排队更糟。上限默认 4 是个起点，上线后按暂存盘的实际吞吐调。
- **D3 若把闸放错位置就会把限流变成失败**。Agent 对 `UPLOAD_SESSION_CONFLICT` 没有退避重试，因此闸只能放在下发侧。这条不是优化建议，是必须遵守的约束。

### 明确不做

- **不给 LanSimple 模式加人工审批**（A0 已论证）。混进来一台无任务的客户端不影响「数据会不会丢」。
- **不因为无法证明身份连续性就拒绝注册**（A1）。那会把「重装后永远 409」的死锁装回来。三态里第三态是 `PendingApproval`，不是拒绝。
- **不对「文件个数变化」做自动判定或告警**（沿用 2026-08-28 的既定结论）。U8 附件库个数随账套启用年度天然不同，个数变化不代表丢数据。B6 换的是**分卷**这一种形态下的尺子，不是推翻这条原则。
- **不给尺寸判据加上限建议**（B3）。备份变大通常是业务增长，给上限会制造周期性假警报。
- **不因为历史缺口降低识别置信度、也不在配置阶段发告警**（B4）。缺口是被识别对象的性质，不是识别质量的问题。
- **不靠应用先验单独下结论**（B8.1）。先验只在通用判据已经成立时叠加，且加成有上限、不得跨越 70 这条线。
- **不在探测接口里返回文件名**（B7）。`browse_path` 的三条边界对新指令同样成立，且更严。
- **不调大快照条目上限**（B2 第 4 点）。先用抽样把同样的预算用得更值，等 B7 带回真实数据再评估。
- **不把全局并发闸放进 `UploadSessionService`**（D3）。在建会话这一步 409，等于把限流变成备份失败。
- **不动 `UploadSessionService` 里那条按客户端的检查**（D3）。它是兜底，与队列职责不同，合并只会让两件事都说不清。
- **不给上传队列做优先级抢占**（D3）。先把「有没有闸」解决掉；抢占是另一个量级的复杂度，现在加会让排队行为变得无法预测。
- **不把 `QuickFingerprint` 当成 `CandidateKey`**（D2）。那会让两份不同的备份撞成同一个候选，`BackupScanner.cs:145` 的注释已经写过这个坑。
- **不靠调小 `CommandPollIntervalSeconds` 来缩短等待**（D2）。10 秒不是主要矛盾，调小它是拿全天候的轮询负载换一次交互的观感。

## 确认记录与待确认项

### 已确认（2026-08-29）

- **指纹核对不删**，理由见 A0：它是代码来源校验，且是运行期地址重发现的唯一锚点。
- **一处修正**：讨论中曾说「识别规则里没有任何尺寸判据」，不准确。判据存在（`ValidateSizeThresholds` + `BackupTask.MinTotalBytes/MaxTotalBytes/MinFileCount` + 完整告警链路），缺的是向导不给建议值。B3 按修正后的口径写。
- **B1 不新增识别器类型**：`latest_directory` 在 Agent 侧按「目录内最新文件的 mtime」选目录，对轮转槽位天然正确，因此这是纯推断端改动。

- **原先三个待确认项已定案**，取值与理由见下。三条的共同原则是同一条：**判据宁可窄而可信，也不要宽而含糊**；边界情况一律交给人，而不是让系统猜。

  1. **B1 轮转词表**：只收四类（星期中文 / 星期英文 / `DayN` / 纯序号，后者附加「个数 ≥ 3 且最大值 ≤ 31」）。`A B C`、`奇/偶`、`一 二 三` **不收**——与真实业务分组无法区分，误判代价高于收益，走逃生门手动选模板即可。详见 B1 方案第 1 点。
  2. **B3 下限口径**：系数维持 `最小值 × 0.5`（下限 1 MB），但**新增离散度闸门**：`最大值 / 最小值 > 20` 时不给建议值。理由是 `MinTotalBytes` 是任务级单值而判定是按业务单元做的，账套大小相差百倍时任何统一阈值都必然在一头出错。详见 B3 方案第 2 点。
  3. **B7 探测深度**：默认 4，但真正控制成本的是**命中即止 + 时间闸**（单盘 10 秒 / 全机 30 秒），而不是深度数字本身。深度不是成本，条目数才是。详见 B7 方案第 2 点。

### 待确认

- **D3 全局上传并发上限的默认值**：暂定 4。这个数取决于服务端暂存盘的实际吞吐（机械盘 / SSD / 阵列差别很大），需要一次实测：并发 2 / 4 / 8 时的总完成时间与磁盘队列深度，取拐点前的那一档。
- **D2 是否需要定期强制完整校验**：`forceFullHash` 已给了手动入口。是否要再加一条「每月第一次备份走完整校验」的自动策略？倾向于**不加**——它会让某一天的备份莫名其妙变慢且无人知道原因；但如果现场对「静默位腐」有实际担忧，可以再议。
