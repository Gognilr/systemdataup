## 2. 总体技术约束

### 2.1 数据库原则

- 使用关系型数据库保存元数据；
- 原始备份文件不存入数据库；
- 文件清单和哈希存数据库，同时保存 `manifest.json`；
- 全部主键使用 UUID；
- 业务时间和系统时间分开；
- 所有敏感操作必须审计；
- 状态字段使用受控枚举；
- 大体量监控数据限制保留周期；
- 删除正式业务数据优先采用软删除；
- 审计日志原则上只追加、不修改。

### 2.2 API 原则

- 全部接口使用 HTTPS；
- 客户端接口与管理接口逻辑隔离；
- 客户端必须使用独立身份；
- 管理接口使用用户会话或 JWT；
- 写接口支持幂等；
- 批量接口必须返回逐项结果；
- 长任务采用异步状态查询；
- 上传采用会话和分块协议；
- 服务端生成正式存储路径；
- API 不提供任意操作系统命令执行。

### 2.3 命名规范

数据库表名使用小写蛇形：

```text
backup_tasks
backup_sets
upload_sessions
```

字段名使用小写蛇形：

```text
created_at
client_id
total_bytes
```

API 使用复数名词：

```text
/api/v1/clients
/api/v1/backup-tasks
/api/v1/upload-sessions
```

## 3. 逻辑数据模型

核心关系：

```text
users ── user_roles ── roles ── role_permissions ── permissions

client_groups ── clients ── backup_tasks ── business_units
                         └─ client_heartbeats
                         └─ client_disks
                         └─ monitored_service_definitions
                         └─ commands

backup_tasks ── candidate_backup_sets ── candidate_files
             └─ backup_sets ── backup_files
             └─ upload_sessions ── upload_files ── upload_chunks
             └─ alerts

backup_sets ── restore_requests
backup_sets ── retention_locks

backup_plans ── backup_plan_items ── backup_tasks
backup_plans ─┐
upload_batches ┴─ execution_runs ── execution_run_items ── commands / upload_sessions

all major entities ── audit_logs
```

备份计划与批量上传都落到同一条队列上（`execution_runs`）：
前者解决「跨客户端按顺序执行」，后者解决「多台客户端同时传时的并发闸」，
两件事需要的机制是同一个，因此只做一套。

#### 5.6.1 `browse_path` 指令契约

下发参数（`commands.payload`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `path` | string? | 要浏览的绝对路径；留空表示列出本机固定磁盘，作为浏览起点 |
| `maxDepth` | int | 向下抓取的层数，默认 3，Agent 侧上限 6 |
| `maxEntries` | int | 整棵子树最多返回的条目数，默认 3000，Agent 侧上限 20000 |

执行结果（`commands.result_payload`，小驼峰）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `root` | string | 本次快照的根路径；磁盘列表模式为空串 |
| `isDriveList` | bool | true 表示 `entries` 是磁盘列表 |
| `entries` | array | 目录树；目录节点的 `children` 按同一份限额填充 |
| `totalEntries` | int | 实际返回的条目总数（含各层） |
| `truncated` | bool | 是否因条目数或耗时触顶而截断 |
| `maxDepth` | int | 本次实际使用的抓取深度 |
| `capturedAt` | datetime | 采集时刻；规则预演按这个时刻回放稳定观察窗口 |
| `elapsedMs` | long | 枚举耗时 |
| `deniedPaths` | string[] | 枚举时被拒绝访问的目录 |

`entries[]` 节点：`name` / `relativePath`（相对 `root`，`/` 分隔）/ `isDirectory` /
`sizeBytes` / `lastModifiedAt` / `childCount` / `truncated` / `depthLimited` /
`accessDenied` / `isHidden` / `children`。

约束：

1. **只返回元数据。** 文件内容在任何情况下都不通过这条通道传输。
2. **三重限额。** 条目数、深度、耗时任一触顶即停止并置 `truncated`，
   由界面如实转达"结论只覆盖看得见的部分"。
3. **拒绝访问要说出来。** 无权限目录进 `deniedPaths` 与节点的 `accessDenied`，
   不能表现成"这个目录是空的"。
4. **可收紧范围。** Agent 侧 `Agent:BrowseRoots` 为白名单，留空表示全部固定磁盘。
5. **留痕。** 服务端每次下发都写审计 `client.browse_path`（谁、哪台机器、哪个路径）。
6. **权限。** 管理端接口一律要求 `tasks.manage`——能建任务的人本就能让该客户端扫任意路径，
   而只有 `tasks.read` 的人不该能枚举别人机器上的文件名。

配套管理端接口：

- `POST /api/v1/admin/clients/{clientId}/browse` → 下发指令，返回 `commandId`
- `GET  /api/v1/admin/clients/browse/{commandId}` → 轮询结果，成功时带 `snapshot`
- `POST /api/v1/admin/recognizer/infer` → 在快照上推断识别规则，附带预演结果
- `POST /api/v1/admin/recognizer/preview` → 拿一条具体规则在快照上预演

#### 5.6.2 `list_services` 指令契约

下发参数：`includeStopped`（bool，默认 true——要监控的服务此刻恰好停着，
正是最需要把它加进来的时候）。

执行结果：`{ capturedAt, services: [{ serviceName, displayName, status, startType }] }`。
`status` 取 running / stopped / paused / start_pending / stop_pending / …；
`startType` 取 boot / system / auto / manual / disabled，读不到时为 null。
服务端在返回给界面前额外填 `alreadyMonitored`。

只读：这条指令不对任何服务做启停，只列清单。

#### 5.6.3 客户端配置版本 `clients.config_revision`

Agent 靠心跳里的 `requiredConfigVersion` 判断要不要重新拉配置。该版本号自 V016 起为

```
requiredConfigVersion = max(该客户端所有任务的 config_version, clients.config_revision)
```

在此之前只取任务版本，而监控服务定义虽然随配置一起下发，改动它却不会让任何任务的
版本号变化——新增的监控服务永远到不了客户端，且没有任何报错；客户端一个备份任务都
没有时更彻底：版本恒为 0。

监控服务的增删改必须把 `config_revision` 抬到**当前生效版本之上**（即
`max(config_revision, 任务版本最大值) + 1`），只比自己上一次大是不够的。

`GetRequiredVersionAsync` 与 `GetConfigAsync` 必须用同一个算法：后者算小了，
Agent 存下的版本会永远低于心跳要求的版本，于是每次心跳都触发一次全量配置拉取。

配套管理端接口（权限：读用 `clients.read`，写用 `clients.manage`）：

- `GET    /api/v1/admin/clients/{id}/monitored-services`
- `POST   /api/v1/admin/clients/{id}/monitored-services`
- `PUT    /api/v1/admin/clients/{id}/monitored-services/{definitionId}`
- `DELETE /api/v1/admin/clients/{id}/monitored-services/{definitionId}`
- `POST   /api/v1/admin/clients/{id}/monitored-services/discover` → 下发 `list_services`
- `GET    /api/v1/admin/clients/{id}/monitored-services/discover/{commandId}` → 轮询结果

写操作会顺带下发一条 `sync_config`：不发也能生效（下一次心跳会发现版本变了），
但那要等最多一个心跳周期（默认 60 秒）；发了就是一个指令轮询周期（10 秒）。
客户端不在线时这条指令过期作废，不影响正确性。

### 6.26 保留策略表 `retention_policies`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | 策略 ID |
| name | varchar(128) | 名称 |

| keep_monthly_count | int | 月版本 |
| keep_yearly_count | int | 年版本 |
| minimum_retention_days | int DEFAULT 0 | 最短天数。不满该天数一律不回收，**会覆盖「保留最近 N 份」**；默认 0 表示只按份数/周期规则算 |
| recycle_bin_days | int DEFAULT 7 | 回收区天数：删掉的先放回收站，到期才物理删除 |
| config | json/jsonb | 扩展规则 |
| created_at | timestamptz | 创建 |

装机时预置三份策略，任务表单直接选，不必自己建：

| ID | 名称 | 规则 |
|---|---|---|
| `d0000002-…-0003` | 只留最近 3 份 | keep_last=3，最短 0 天，回收站 7 天 |
| `d0000002-…-0007` | 只留最近 7 份 | keep_last=7，最短 0 天，回收站 7 天（**新建任务的默认策略**） |
| `d0000002-…-0012` | 日备留 7 天 + 月末留 12 个月 | keep_last=7 + keep_monthly=12 |

`system_settings.default_retention_policy_id` 指定新建任务默认绑定哪一份；
创建任务时未指定 `retention_policy_id` 即绑定它（见 §16.1）。
不绑定策略的任务**永远不会被清理**——这是「仓库无限增长」的唯一成因，
因此默认值不能是留空。当前的默认策略禁止被删除（409）。

保留清理的回收熔断（`retention_recycle_breaker_percent`，默认 50%）对
「该任务从未被清理过」的第一轮做一次性豁免：第一次给一个已攒了几十份的任务
配上策略必然是大比例回收，被熔断整体挡住的结果仍然是「一份不删」。
豁免只发生一次——本轮回收之后就有 recycle_bin 记录，下一轮再出现大比例回收就是真的异常。

### 6.33 备份计划表 `backup_plans`

把多个备份任务编成一组，到点按顺序驱动。

调度原本完全在客户端：Agent 按各任务自己的 cron 触发扫描。这样做**跨客户端的顺序执行
是不可能的**——A 机器无从知道 B 机器传完没有。因此服务端需要自己的调度器。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | 计划 ID |
| name | varchar(128) UNIQUE | 名称 |
| enabled | boolean DEFAULT true | 是否启用 |
| schedule_kind | plan_schedule_kind DEFAULT 'daily' | daily / weekly |
| run_at | time DEFAULT '02:00' | 执行时刻（计划时区里的本地时刻） |
| days_of_week | varchar(32) NULL | weekly 时生效：ISO 周几 1~7，逗号分隔，如 `1,3,5` |
| timezone | varchar(64) DEFAULT 'Asia/Shanghai' | 计划时区 |
| max_concurrent | int DEFAULT 1 | 1 = 严格一个接一个；N = 最多 N 个同时跑。约束 1~50 |
| item_timeout_minutes | int DEFAULT 240 | 单项超时。约束 5~10080 |
| last_run_at | timestamptz NULL | 上一次已处理的应执行时刻 |
| created_by | UUID NULL FK | 创建人 |
| created_at / updated_at | timestamptz | |

### 6.34 备份计划成员表 `backup_plan_items`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | |
| plan_id | UUID FK ON DELETE CASCADE | 所属计划 |
| task_id | UUID FK ON DELETE CASCADE | 备份任务 |
| sort_order | int | 执行顺序 |
| created_at | timestamptz | |

唯一索引 `uq_backup_plan_items_task (task_id)`：**一个任务只能属于一个计划**。
否则「由计划 X 驱动」这句话没法说，两个计划同时驱动同一个任务也让顺序执行失去意义。

任务一旦进了计划，服务端下发配置时会把它的 `scan_schedule` 置空（§11.2）——
两者都留着的话，同一个任务一天会跑两次：一次 Agent 按 cron 触发，一次计划驱动。
进出计划都会递增该任务的 `config_version`，Agent 下一次心跳即感知。

### 6.35 顺序执行表 `execution_runs`

一次顺序执行。备份计划到点产生一次，一次批量上传也产生一次——两者共用同一个队列
与同一个执行器，`max_concurrent` 就是那道并发闸。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | |
| kind | execution_run_kind | backup_plan / upload_batch |
| plan_id | UUID NULL FK ON DELETE SET NULL | 计划触发时非空 |
| upload_batch_id | UUID NULL FK ON DELETE CASCADE | 批量上传时非空 |
| name | varchar(255) | |
| status | batch_status DEFAULT 'pending' | pending/running/completed/partial/failed/cancelled |
| max_concurrent | int DEFAULT 1 | 队列并发度，约束 1~50 |
| item_timeout_minutes | int DEFAULT 240 | 单项超时 |
| trigger_source | varchar(32) DEFAULT 'schedule' | schedule（到点）/ manual（人点了立即执行） |
| total_items / succeeded_items / failed_items | int | 计数 |
| triggered_by | UUID NULL FK | 触发人 |
| scheduled_for | timestamptz NULL | 计划的这一次「应执行时刻」 |
| created_at / started_at / finished_at | timestamptz | |

唯一索引 `uq_execution_runs_plan_scheduled (plan_id, scheduled_for) WHERE 两者非空`：
同一个应执行时刻只允许产生一次 run，兜住重复触发与多实例竞态。

### 6.36 顺序执行单项表 `execution_run_items`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | |
| run_id | UUID FK ON DELETE CASCADE | 所属执行 |
| sort_order | int | 放行顺序 |
| client_id | UUID FK | 客户端 |
| task_id | UUID FK ON DELETE CASCADE | 任务 |
| candidate_backup_set_id | UUID NULL FK ON DELETE SET NULL | 批量上传时的候选；计划驱动时为空 |
| command_type | command_type | `precheck_task`（计划驱动任务）或 `upload_candidate`（批量上传候选） |
| status | execution_item_status DEFAULT 'pending' | 见 §5.13 |
| command_id | UUID NULL FK ON DELETE SET NULL | 放行时下发的指令 |
| upload_session_id | UUID NULL FK ON DELETE SET NULL | 判定终结时定位到的上传会话 |
| started_at / finished_at | timestamptz NULL | |
| message | varchar(1000) NULL | 终结原因（跳过原因、失败信息、「没有需要上传的新备份」） |

**终结判定**（决定何时放行下一项）：

1. 超时优先——`now - started_at ≥ item_timeout_minutes` 即判 `timeout`，发告警，继续下一项。
   一台关机的客户端不能让整晚的计划全部不执行；
2. 指令 failed / cancelled / expired / rejected → `failed`；
3. 指令 succeeded 后找上传会话（批量上传按候选定位，计划驱动按「本项开跑之后该任务新建的会话」定位）：
   committed → `succeeded`；failed / cancelled / expired → `failed`；
4. 指令成功但过了宽限期（`execution_queue_no_upload_grace_minutes`，默认 10 分钟）
   仍然没有会话 → `succeeded`，`message = 没有需要上传的新备份`。

### 10.1 提交注册

```json
  "publicKey": "..."
}
```

响应：

```json
{
  "registrationId": "...",
  "status": "pending_approval",
  "pollAfterSeconds": 30
}
```

#### 免令牌登记窗口

局域网部署允许新机器**不带令牌**注册，但只在窗口开着时。窗口只管这一件很窄的事：

| 情形 | 是否受窗口影响 |
|---|---|
| 新机器、不带令牌、来自私有网络 | **是**：窗口关着返回 401 `ENROLLMENT_WINDOW_CLOSED` |
| 带注册令牌注册 | 否，走令牌校验 |
| 已注册客户端的日常通信 | 否，走 mTLS 客户端证书 |

也就是说，**窗口关着不会让任何已有客户端断掉**。这一点必须写在界面上：
不写的话，管理员看到「窗口已关闭」会以为客户端要掉线。

窗口的到期时间有两个来源，界面要能区分，否则功能看起来像失效：

- **安装默认**：服务端首次启动 + 24 小时（`LanMode:EnrollmentOpenUntil` 可覆盖）。
  这是个没人开过的窗口，界面应标注它来自安装默认值；
- **手动开放**：`POST /api/v1/admin/deployment-status/enrollment-window`
  从当前时刻起延长固定时长（服务端常量，当前 30 分钟），写入
  `system_settings.lan_enrollment_open_until`。

部署状态接口返回 `enrollmentOpenUntilUtc` / `enrollmentWindowOpen` /
`enrollmentExtendMinutes` / `enrollmentWindowIsInstallDefault` 四个字段，
界面据此分别显示「当前窗口什么时候关」和「再开 N 分钟」这两件不同的事——
把延长时长写死在界面上，就会出现「按钮写 30 分钟、窗口显示 24 小时」这种对不上的组合。

### 14.8 中断会话

```http
POST /api/v1/agent/upload-sessions/{sessionId}/interrupt
```

```json
{
  "errorCode": "UPLOAD_ERROR",
  "errorMessage": "连接被重置"
}
```

「这次传挂了，但等下还要接着传」。会话停在 `retry_wait`：状态仍然可写、暂存仍然在，
同一候选的下一条上传指令凭幂等键拿回这个会话（§14.1 返回 `resumed`），
从缺哪块传哪块继续。

没有这个接口时，Agent 的异常收尾只能调 cancel，于是「断网能续传（会话还活着），
出错不能续传」——6GB 传到 90% 出一次错就全部重来。

已终结的会话（committed / cancelled / expired）与被管理端暂停的会话（paused）
调用此接口无副作用，直接返回成功。

## 17b. 备份计划与顺序执行接口

### 17b.1 计划增删改查

```http
GET    /api/v1/admin/backup-plans
GET    /api/v1/admin/backup-plans/{planId}
POST   /api/v1/admin/backup-plans
PUT    /api/v1/admin/backup-plans/{planId}
DELETE /api/v1/admin/backup-plans/{planId}
```

请求：

```json
{
  "name": "夜间全量备份",
  "enabled": true,
  "scheduleKind": "daily",
  "runAt": "02:00",
  "daysOfWeek": [],
  "timezone": "Asia/Shanghai",
  "maxConcurrent": 1,
  "itemTimeoutMinutes": 240,
  "taskIds": ["...", "...", "..."]
}
```

`taskIds` **按执行顺序排列**，整体替换成员（逐条 diff 只会把顺序改乱）。

约束：

- `scheduleKind = weekly` 时 `daysOfWeek` 至少一项（ISO 1~7）；
- 同一任务不能在计划里出现两次；
- 任务已属于别的计划 → 409，响应列出「任务名 → 计划名」；
- 计划正在执行时不能删除 → 409。

响应在计划字段之外带 `nextRunAt`（下一次应执行时刻，停用时为空）与
`activeRun`（正在执行的那一次，没有则为空）。

### 17b.2 立即执行一次

```http
POST /api/v1/admin/backup-plans/{planId}/trigger
```

不影响下一次到点执行。计划已经在执行、或里面一个任务都没有 → 409。

### 17b.3 执行记录

```http
GET  /api/v1/admin/backup-plans/{planId}/runs      # 该计划的历次执行（分页）
GET  /api/v1/admin/execution-runs                  # 全部执行记录（分页）
GET  /api/v1/admin/execution-runs/{runId}          # 详情，含每一项的状态
POST /api/v1/admin/execution-runs/{runId}/cancel   # 取消
```

取消的语义：**还没开跑的项一律置 `cancelled`，已经在跑的项让它自己跑完**。
中途掐断上传只会留下半份数据，而队列的作用是「不再放行新的」。

### 17b.4 传输干预（暂停 / 恢复 / 取消）

```http
POST /api/v1/admin/upload-sessions/{sessionId}/pause
POST /api/v1/admin/upload-sessions/{sessionId}/resume
POST /api/v1/admin/upload-sessions/{sessionId}/cancel
```

- **暂停**：会话置 `paused`。该状态不在可写状态集合里，客户端再写分块一律
  409 `UPLOAD_SESSION_CONFLICT`；暂存与已传的块都留着。
  暂停中的会话仍然占着并发额度与暂存空间，因此仍然参与会话超时判定（§25）——
  有人点了暂停之后忘掉时，超时线是唯一的兜底。
- **恢复**：放回可写状态（传过东西的回 `uploading`，一块都没传的回 `created`），
  并重新下发一条上传指令（幂等键 `resume:{sessionId}`）。客户端凭幂等键拿回同一个会话，
  从断点继续——与断网续传走同一条路。
- **取消**：已入库的会话不能取消。


- 备份集已锁定（`locked`）；
- 存在生效中的保留锁（`retention_locks.active` 且未过期）；
- 存在进行中的恢复请求（verifying / downloading，或已签发令牌的 ready）。

守卫与 §18.8 相同；目录删除受 §23.4 的三道路径守卫约束

```http

```

### 19.3 下载

```http
GET /api/v1/downloads/{downloadToken}
```

要求：

- 令牌短期有效；
- 令牌只绑定一个恢复请求；
- 支持 Range；
- 记录下载 IP 和字节；
- 下载前完成完整性校验。

两种下发方式，能力不同，界面必须说清楚：

| 方式 | 请求 | Content-Length | 断点续传 |
|---|---|---|---|
| 整包 ZIP | 不带 `path` | 无（边打包边写出） | **不支持**，响应 `Accept-Ranges: none` |
| 单文件 | `?path=相对路径` | 有 | 支持，响应 `Accept-Ranges: bytes`，Range 命中返回 206 + `Content-Range` |

`Accept-Ranges` 两个头都必须写出：浏览器与下载工具据此判断能不能续。
不写的话，工具会自己发一个 Range 请求，被 ZIP 路径当成普通请求全量重发，
表现成「续传了但进度回到 0」——比直接说不支持更难排查。

因此**大备份集（默认阈值：≥ 2GB 或 ≥ 50 个文件）应引导走单文件下载**：
管理端签发令牌后列出逐文件清单，每个文件一个可续传的链接，
并提供「复制全部链接」以便交给下载工具批量下。ZIP 留给小集合。

`?path=` 只接受清单内的相对路径，大小写不敏感精确匹配，命中不到返回 404；
路径解析同样受 §23.4 的基目录约束。

## 24. 上传状态一致性

服务端必须保证：

1. 数据库会话状态和临时文件一致；
2. 入库操作具备事务性；
3. 数据库写入失败时不得暴露半成品正式目录；
4. 正式目录成功创建后写入备份集记录；
5. 服务重启后扫描未完成会话；
6. 孤立临时目录进入隔离清理；
7. 同一候选只能生成一个有效正式版本。

建议入库流程：

```text
校验完成
  → 创建仓库临时提交目录
  → 暂存文件进入提交目录（同卷 NTFS 建硬链接，否则复制）
  → 写入 manifest
  → 刷新文件缓存
  → 原子重命名为正式目录
  → 数据库事务写 backup_sets 与 backup_files
  → 标记 upload_session=committed
```

若文件系统和数据库无法形成真正分布式事务，必须通过可恢复状态机保证最终一致。

**入库为什么用硬链接而不是移动**：整份复制的代价是「6GB 读 + 6GB 写」，
而硬链接是一次元数据操作，瞬间完成。它优于 `File.Move` 的关键在于
**暂存文件仍然在**（链接计数为 2）：入库是个多步过程，中间任何一步失败都要能重试，
Move 走过之后暂存已经没了，重试无从谈起。

共享同一份数据是安全的：暂存文件在提交之后只会被删除、不会被改写
（分块写入发生在提交之前），删掉暂存那个名字只是把链接计数减一。

跨卷、非 NTFS、非 Windows、权限不足时一律回退到复制路径，行为与从前一致；
硬链接是优化路径，它自己不能成为入库失败的原因。

- 客户端离线判定；
- 指令过期；
- 上传会话超时（阈值 `upload_session_timeout_seconds`，默认 21600 秒 = 6 小时。
  它不是「一次上传最多能传多久」，而是「多久没有任何动静才认定它废了」；
  paused 的会话同样参与判定）；
- 临时文件清理；
- 顺序执行器（`worker:execution_queue`，默认 15 秒一轮）：
  到点的备份计划产生一次执行 → 判定在跑的项是否终结 → 按 `max_concurrent` 放行下一项。
  服务端停机超过 `execution_queue_catchup_hours`（默认 12 小时）的那次计划不再补跑；
- 保留策略计算；
- 回收区物理删除；
- 仓库一致性检查；
- 数据库备份；
- 告警通知；
- 证书到期检查；
- 监控数据汇总；
- 审计归档。

所有定时任务应支持：

- 单实例锁；
- 幂等；
- 执行日志；
- 失败重试；
- 手动触发。

第一版单服务端部署时可使用数据库锁或进程内锁。

## 26. 数据迁移与版本管理

数据库使用迁移工具管理版本。

要求：

- 每次发布包含数据库迁移脚本；
- 迁移前自动检查版本；
- 迁移前备份数据库；
- 不允许手工修改生产表；
- 破坏性迁移必须提供回滚或恢复方案；
- API 版本与数据库版本可查询。

迁移脚本置于 `database/V***__*.sql`，由 `MigrationRunner` 按文件名顺序执行并记录 checksum，
已应用脚本的内容变更会被拒绝。本文档涉及的近期迁移：

| 版本 | 内容 |
|---|---|
| V027 | 保留策略默认值（最短 0 天 / 回收站 7 天）、三份预置策略、`default_retention_policy_id`，并把既有未绑定任务绑上默认策略 |
| V028 | 备份计划与顺序执行队列四张表 + 三个域；删除 `upload_batches.max_concurrent_per_client` |
| V029 | `upload_session_timeout_seconds` 3600 → 21600 |

## 27. 日志与追踪

所有接口生成 `requestId`。

日志应包含：

- 时间；
- 请求 ID；
- 用户或客户端 ID；
- API；
- 状态码；
- 耗时；
- 错误码；
- 目标资源；
- 上传会话 ID；
- 指令 ID。

不得记录：

- 明文密码；
- 注册令牌；
- 私钥；
- 完整访问令牌；
- 敏感文件内容。

## 28. 性能指标

建议目标：

- 100 个客户端心跳无压力；
- 每分钟至少处理 500 次心跳；
- 同时 2 至 5 个大文件上传；
- 列表查询 95% 小于 2 秒；
- 心跳接口 95% 小于 500ms；
- 创建上传会话小于 2 秒；
- 断点恢复查询小于 3 秒；
- 支持单文件 1TB；
- 支持单会话 100,000 个文件。

大量文件清单提交应支持分页或压缩传输，避免单个 JSON 过大。

## 29. 数据库备份

服务端数据库必须定期备份。

建议：

- 每日全备；
- 重要变更前手动备份；
- 数据库备份复制到正式仓库之外；
- 定期恢复验证；
- 数据库备份本身纳入离线副本。

需要备份：

- 数据库；
- 服务端配置；
- 证书和密钥；
- 任务模板；
- 通知配置；
- 正式仓库。

## 31. 数据库验收要求

- 所有主外键正确；
- 关键唯一约束有效；
- 重复指令不会重复执行；
- 同一候选不会重复正式入库；
- 客户端注销后不能继续上传；
- 并发修改任务产生版本冲突；
- 审计日志不可普通修改；
- 分块上传断点可恢复；
- 入库失败不会留下可见半成品；
- 删除备份前检查锁和保留策略；
- 备份元数据与仓库文件可一致性校验。

---

## 32. 接口验收要求

- 所有接口仅 HTTPS；
- 无证书客户端不能调用 Agent API；
- 无权限用户不能访问管理资源；
- 分页、筛选、排序正常；
- 幂等键生效；
- 指令签名和有效期生效；
- 目录穿越被拒绝；
- 超大请求被限制；
- 上传块哈希错误被拒绝；
- 文件哈希错误不能入库；
- Range 下载正常；
- 接口错误返回统一错误码；
- 全链路 requestId 可追踪；
- 关键写操作生成审计日志。

---

## 33. 总结

数据库和接口设计围绕以下核心原则展开：

- 元数据关系化，原始文件文件化；
- 客户端主动连接，服务端不反向控制主机；
- 每台客户端独立身份；
- 指令白名单、签名、防重放；
- 预检、上传、校验、入库分别建模；
- 分块上传支持断点续传；
- 服务端不信任客户端哈希，必须重新校验；
- 正式仓库路径由服务端生成；
- 客户端不能覆盖或删除历史版本；
- 备份文件脱离系统仍然可使用；
- 数据库、文件系统和审计记录能够相互核对。
